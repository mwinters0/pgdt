# P12.5 — `int2vector`: the fixture column

What 12.6 inherits. The fixture table's own reasoning is filed by subject:
[`architecture.md`](architecture.md), "Fixtures" — why it sits with the scalar
families rather than the array ones, and what each of its five rows is for.
This doc holds only what the next slice needs and what is not recoverable from
the tree.

## The declared name is bare, and that is what the arm keys on

`v_vec int2vector` at all six majors — no `pg_catalog.` prefix, even though
`pg_dump` empties `search_path`. `pg_catalog` is on the path implicitly, so
`format_type` qualifies nothing in it, and a `pg_catalog` type with no standard
SQL spelling falls back to a bare `typname`. That is I8's claim, and its proof
sentence used to read as though *standardness* were what kept a name bare; the
committed column is now the evidence for the other reading, which is the one
12.6's `builtin_scalar` arm depends on — the arm matches `"int2vector"`, not a
qualified spelling.

Today the column resolves `ColumnResolution::Unknown` — `pgdq info --verbose`
prints `v_vec: unknown type — no mapping for this build` — so this slice adds
no new resolution outcome and
`every_resolution_outcome_is_produced_by_a_real_fixture_column` is unmoved.

## Row 2 is the one that decides the codec

`int2vectorout` writes elements space-separated with no quoting, no escaping
and no possible NULL element, so the four non-NULL values are the whole
grammar. An **empty** vector is legal (`int2vectorin` breaks out of its loop at
`n = 0`) and `int2vectorout` writes it as the empty string, so the file holds
an empty *field* for it and `\N` for the NULL beside it. An empty list and a
NULL are therefore still distinguishable, which is what lets 12.6 decode `''`
to a zero-length `List<Int16>` rather than folding it into NULL. Rows 3 and 4
are the `SHRT_MIN`/`SHRT_MAX` bounds `int2vectorin` range-checks against, and a
single element.

## The oracle case is 12.6's, and the reconciliation will demand it

`oracle_register.py` reads **one arm per declared base name in
`builtin_scalar`**, so the moment 12.6 adds an `"int2vector"` arm the
register-to-oracle reconciliation fails until a case in
`scripts/comparison_oracle.py` names the type. That is not a defect in the
seam — it is the same both-ways check that made `interval` cheap — but it is
work 12.6 owns and the spec's D11 row does not name.

It is cheap: the oracle is a separate pass over the same containers, so
`uv run generate_fixtures.py --skip-dumps --skip-floor` re-takes it across six
majors without touching the `.sql` tree, which is where a dump regeneration's
`\restrict` and OID noise would otherwise bury the change. **Do not fold the
case into a dump regeneration.**

The case was deliberately not added here. Landing it a slice early would put
`int2vector` into `predicate.rs`'s exactly-asserted set of columns the register
refuses an ordering operator on, and 12.6 would take it straight back out — two
edits of one tested assertion, bought for nothing, since a comparison oracle is
generated by a PostgreSQL server and cannot be tainted by the arm it checks.

## What the server actually answers for `int2vector`, which 12.6 must match

Taken by hand against `postgres:16.15-trixie`, and the reason the case above is
not a formality:

- **No operator names `int2vector` on either side.** `pg_operator` has zero
  rows for it, and `pg_cast` has none either. The comparison resolves through
  **`anyarray` polymorphism**: `typlen = -1` with `typelem = smallint` makes
  `get_element_type` answer, so `array_lt`/`array_eq` (operators 1072 and 1070,
  declared over `anyarray`) are what a server runs.
- **So the order is element-wise, not bytewise**, and the two disagree on the
  first pair anyone would try: `'2'::int2vector < '10'::int2vector` is **true**
  on the server and false read as text. A `ComparisonPlan` that fell back to
  text would return wrong rows, and the oracle case is what would catch it.
- **The lower bound is 0, not 1.** `int2vectorin` sets `lbound1 = 0`, so
  `'1 2 3'::int2vector::int2[]` has dims `[0:2]`. Nothing in `int2vectorout`
  writes that — the text is bare space-separated digits with no `[lb:ub]=`
  decoration — so it costs the codec nothing, but it is why routing the type
  through the ordinary array literal path would be wrong rather than merely
  redundant.
- `oidvector` shares every one of those properties. It stays in the opaque
  tail (`arrow.opaque` over `binary` at every major) and this phase does not
  reach it.

## What the regeneration moved

`uv run generate_fixtures.py --schema types --skip-oracle --skip-floor`, **43 s**
for six majors. Scoped to the one schema on purpose: nothing else reads
`fixture_schema_types.sql`, and regenerating the other four schemas would have
added a `\restrict` token to every one of their files for no reason.

The oracle and floor passes were skipped for the same reason and their three
reconciliations run by hand afterwards — `oracle_differences.py`,
`oracle_register.py`, `floor_mapping.py`, all clean, with
`fixtures/oracle-differences.tsv` byte-unchanged. `floor_mapping.py` still
reports `int2vector` as `waiting, 12.6`, which is correct: this slice maps
nothing.

Eighteen files moved, and the diff is exactly what
[`architecture.md`](architecture.md), "Fixtures" predicts. `default` and
`data-only` at all six majors carry the new table, its `COPY` block and its
primary-key constraint, plus a fresh `\restrict`/`\unrestrict` token pair and
nothing else — checked by filtering the diff rather than by reading it.
`binary-upgrade` carries those plus OID drift on the relations that follow the
new one, which two more catalog rows necessarily produce.
