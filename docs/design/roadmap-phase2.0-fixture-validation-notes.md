# Phase 2.0 notes — types fixture and mapping-table validation

No library code. Generates `fixtures/<version>/types/*.sql` and checks the
mapping table in `roadmap-phase2-typed-columns.md` ("Type mapping") against
what `pg_dump` actually emits, per that doc's "Fixtures" section.

## What landed

- `scripts/fixture_schema_types.sql` — one table per mappable type family plus
  the boundary values from the phase doc's "Boundary values worth building in"
  table: `numeric` at the 38/39-digit `Decimal128`/`Decimal256` boundary and
  with `NaN` through both a typed and an untyped column; `real`/`double
  precision` `NaN`/`±Infinity`/`-0.0`/subnormal; `date`/`timestamp`/`timestamptz`
  `infinity`/`-infinity`, BC, year 0001, year 9999, a year past 9999, and a
  timestamp at PostgreSQL's actual maximum (`294276-12-31 23:59:59.999999`);
  `time`/`timetz` at `24:00:00` and microsecond precision; `bytea` empty/NULL/high
  bytes/embedded-backslash-byte; `uuid` all-zeros and mixed-case input; an enum
  with a space/comma/quote in a label; a domain over a domain with `NOT NULL`;
  plus `json`/`jsonb`/`inet`/`cidr`/`macaddr`/`macaddr8` (mapped rows not
  otherwise exercised) and array/composite/range tables kept here rather than
  in `edge_cases` because the boundary values (`{}` vs `{NULL}` vs NULL array,
  nested quoting) are Phase 4's, not Phase 1's, and the schema is already set
  up for them.
- `fixtures/<version>/types/{default,data-only,binary-upgrade}.sql` for
  v13/16/18, generated by the now-schema-aware `generate_fixtures.py`. Byte-
  identical `COPY` payloads across all three versions except the two version
  header lines and one v18-only `SET transaction_timeout = 0;` — confirms the
  mapping table isn't chasing a moving target.
- `fixtures/<version>/edge_cases/` gained a `binary-upgrade` flag set (the
  design doc calls for this explicitly: the dropped-column dummy-type shape
  had zero coverage before) and two new tables, `dropped_column` and
  `generated_column`, exercising I5 (`COPY`'s column list as a strict subset
  of `CREATE TABLE`'s) directly rather than by inference from source reading.
- Existing `fixtures/<version>/*.sql` moved to `fixtures/<version>/edge_cases/`
  per the doc's nesting convention; `generate_fixtures.py` now loops over
  `(schema, flag_set)` with each schema owning its own flag list. Test fixture
  path helpers in `tests/{scan,batch,stream}.rs` updated to match; row/block
  count assertions in `tests/scan.rs` updated for the two new edge-case tables
  (140 → 144 rows, 4 → 6 blocks in the `data-only` fixture).

## What the fixture confirmed

Every mapping-table row was checked against real output; nothing in the table
itself was wrong. Two things the table didn't spell out, now added directly to
`roadmap-phase2-typed-columns.md`:

- `NaN` is reachable through **any** `numeric` column, typed or not —
  PostgreSQL's precision/scale check doesn't apply to it. The "Failure and
  diagnostics" `FieldDecode` path already covers "a non-finite in a decimal";
  the mapping table's `numeric(p,s)` row now says so explicitly instead of
  only the untyped row implying it.
- `infinity`/`-infinity` are reachable for `date`, not just `timestamp` — the
  Failure-and-diagnostics text said "timestamp"; it now says "`date` or
  timestamp". Neither `Date32` nor `Timestamp` has a sentinel for these, so
  they hit `FieldDecode` by construction. This was already the design's
  intent (the boundary-values table asked for `infinity`/`-infinity` on all
  three temporal types), just not cross-referenced from the failure section.

Neither is a new decision — both apply a rule the spec had already made
("a value that doesn't parse as its mapped type is a hard error") to cases
the table happened not to spell out. Flagging here rather than silently:
if this read is wrong, the fix is in `roadmap-phase2-typed-columns.md`'s
"Failure and diagnostics", not here.

## Evidence worth carrying forward, not acted on this slice

- **`--binary-upgrade` interleaves OID-preservation noise between a TOC
  comment and the statement it announces**, for every object type, not just
  the enum-label case I6 already documents (`SELECT
  pg_catalog.binary_upgrade_set_next_pg_type_oid(...)`-style calls, one to
  three of them, between `-- Name: ...` and the `CREATE`). Slice 2.2's
  preamble parser ("TOC comment segments, then a strict grammar parses the
  statement") needs to tolerate this under `--binary-upgrade` rather than
  expect the statement immediately after the comment. Recorded on I6 in
  `postgres-invariants.md`.
- **Array dimensionality isn't in the catalog.** `v_multidim integer[][]` in
  the fixture's `CREATE TABLE` comes back out of `pg_dump` as plain
  `integer[]`, identical to a genuinely one-dimensional column — PostgreSQL
  arrays carry no fixed dimensionality in the type system. Phase 4's array
  decoder will need to infer nesting from the literal's own brace structure
  (`{{1,2},{3,4}}`), not from the declared type. Not acted on now since
  Phase 2 leaves arrays as `Utf8View`; worth an invariant entry when Phase 4
  becomes current.
- `jsonb` reformats whitespace on storage (`{"a":1,...}` in, `{"a": 1, ...}`
  out) while `json` preserves the source text verbatim. Doesn't affect the
  mapping (both stay `Utf8View`) or the round-trip test design (it round-trips
  against what the dump emits, not against the original `INSERT`).

## Fixture generation

`cd scripts && uv run generate_fixtures.py` regenerates both schemas across
v13/16/18 in one run (~2 min, three throwaway 512MB containers). `--schema
types` or `--schema edge_cases` narrows to one; `--version N` narrows to one
PostgreSQL major, same as before.
