# pg_dump Option Compatibility Matrix

Tracks `pg_dump` options/output variants against this library's support
status. Exists so compatibility scope stays explicit rather than implicit —
raised during MVP design review. Populated/kept current by the fixture
tooling described in `docs/design/architecture.md` ("Fixtures")
— `scripts/generate_fixtures.py`, run against containers for the routine
version set (latest minor of every major, 13 through 18 as of this writing —
see that doc's "Version policy" for the current pins). Rows evidenced this
way say so; rows not yet exercised by that tooling are asserted from manual
inspection of the `koji` sample dump or from `pg_dump` documentation instead
— that distinction is called out per row.

Status values: **Tested** (fixture or real-dump evidence), **Untested**
(plausibly relevant, no evidence yet), **Planned (Phase N)** (in scope, not
built, roadmap phase named), **Unsupported** (explicitly out of scope), **N/A**
(flag doesn't apply to plain format at all).

**A status here is coverage, not a deficiency.** `Unsupported (by design)` is
a scope decision with nothing to fix and `Untested (deliberately)` an absence
of evidence, so neither earns a `KD<k>` in the deficiency register
([`../status/STATUS.md`](../status/STATUS.md)). A row whose behaviour **is** a
register entry names the identifier inline — `--disable-triggers` names `KD1` —
so the absence of one means there is no entry, not that naming it was
forgotten.

| Option / variant | Status | Notes |
|---|---|---|
| `--format=plain` (default) | Tested | Confirmed against the koji sample (784GB, `pg_dump 16.14`). This is the library's only target format. |
| `--format=custom` | Planned (P8) | Container layer over the same COPY TEXT payload: `PGDMP` header + TOC gives the entries, each entry's data block is separately compressed. Needs streaming decompression; no new row parser. |
| `--format=directory` | Planned (P8) | `toc.dat` plus one compressed file per entry. Same container layer as custom, different entry addressing. |
| `--format=tar` | Planned (P8) | Tar member index plus `toc.dat`; members are uncompressed, so this is the cheapest of the three to add. |
| `--inserts` | Tested (fixture) | Confirmed against all 6 routine versions: produces `INSERT INTO` statements, zero real `COPY` blocks (the fixture's dollar-quoted decoy lines that merely *look* like a `COPY` header still appear, as intended — see the dollar-quote row below). The map groups a whole table's run into one `Data(InsertRun)` span (location + row count, no row parser); reading the rows themselves is P8 Track A — this row's "Tested" only ever meant *fixture data existing*, not row-level support. **Scanning one costs ~4.9× the per-byte CPU of scanning a `COPY` block warm, nothing on this SATA SSD cold, and most of the scan on NVMe** — 1.03× that device's floor against a `COPY` scan's 1.00×, and 2.62× against 1.06× on a 970 EVO Plus (`measurements.md`, "Scan throughput by input shape"). Unlike the large-object region an `INSERT` run has no scanner-level skip, because its boundaries rest on no line-anchored invariant: every statement's bytes have to be crossed quote-aware to find where it ends. That much is a property of the two algorithms; the rest of the residual is the deficiency register's `KD9`, and it does reach a faster device (`architecture.md`, "Bulk regions: one span kind, three payloads"). It read mid-teens until P7's slice 7.5. This row's status is coverage, not that deficiency. |
| `--column-inserts` | Tested (fixture) | Same as above; fixture confirms the variant output shape (and that a leading column list doesn't confuse the map's `INSERT INTO` target parsing). P8 Track A for actual row support. |
| `--rows-per-insert=N` | Untested (deliberately) | Only relevant once `--inserts` support exists (P8 Track A); a fixture no code will read for several phases is cost without coverage. |
| `--load-via-partition-root`, and the partitioned shapes that force it | Observed, no fixture yet | Every leaf partition's `TABLE DATA` entry writes a `COPY` header naming the **root** table, so one header name owns several blocks in one dump, the TOC entry's `Name:` (the partition) disagrees with the header's name (the root), and a `-- load via partition root <root>` marker line sits between them. Not opt-in: `pg_dump` forces the mode for a table hash-partitioned on an enum column, so a **flagless** dump produces this. The several blocks are **not** adjacent — entries sort by the partition's own name, so an unrelated table sorts between them. The marker survives `--no-comments`, `--data-only` and `--inserts`. Observed against pg_dump 16.15 — see I2 in [`postgres-invariants.md`](postgres-invariants.md) for the reproduction. No fixture schema exercises partitioning at all today; the shape matters to any code that stops scanning at the first matching block, or that joins a TOC entry to the `COPY` header beneath it. |
| `--data-only` | Tested (fixture) | Confirmed against all 6 routine versions: `COPY` blocks present with minimal preceding DDL, as expected. |
| `--disable-triggers` | Observed, degrades | Requires `--data-only` or `--section=data` (I31); alone it emits nothing. `pg_dump` writes `ALTER TABLE … DISABLE TRIGGER ALL;` — and a `SET SESSION AUTHORIZATION DEFAULT;` ahead of the first entry — *between* each `-- Data for Name:` block and the data it heads, breaking the adjacency both `map::Builder::on_copy_start` and the `INSERT`-run arm need. Result, measured against 16.15 on a two-table database: **no data span in the file carries a TOC entry**, `COPY` (2/24 TOC coverage) and `--inserts` (2/24) alike, the two attributed spans being the comment blocks themselves. Not a correctness hazard — tiling stays byte-exact, the table name comes from the `COPY` header or the `INSERT INTO` line, the object census still reads `TABLE DATA: 2`, and roles still come off the entry's `Owner:`. What is lost is the TOC-coverage diagnostic and `Span::toc` on data spans. No fixture: accepted rather than fixed, because a fix needs three coordinated changes to `governing_toc`'s inheritance rule — deficiency `KD1`, `architecture.md` ("TOC enrichment"). |
| `--schema-only` | Tested (fixture) | Confirmed: zero `COPY` blocks in the output across all 6 versions — the degenerate case parses to "no tables found," not an error. |
| `--no-owner`, `--no-privileges` | Tested (fixture) | Confirmed no structural effect on `COPY` blocks across all 6 versions. |
| `--no-comments`, `--no-security-labels` | Tested (fixture) | Added (`fixtures/<version>/edge_cases/no-comments.sql`) specifically to check I3's claim that TOC header comments survive `--no-comments` — until this landed, that claim rested on `pg_dump` source reading alone. Confirmed: the `-- Name: ...` TOC header count is identical between `default.sql` and `no-comments.sql` for every version. Neither fixture schema contains a `COMMENT ON` statement, so the flag's actual suppression target isn't separately exercised — only the segmenter-relevant half is. |
| `--clean` / `--if-exists` | Tested (fixture) | Confirmed: adds `DROP ... IF EXISTS` before `CREATE`s, no structural surprise, across all 6 versions. |
| `--schema=X` (schema filtering) | Untested (deliberately) | The koji sample happens to contain two schemas (`lock_monitor`, `public`) with `COPY` blocks in each, so multi-schema dumps are informally covered — but the filtering *flag* itself hasn't been exercised. Left that way: it only removes objects, a shape the matrix already covers in kind. |
| Multiple databases (`pg_dumpall`, concatenated dumps) | Tested (fixture) | The fixture tree has `fixtures/{13,16,18}/edge_cases/create.sql` (the only flag combination that emits a `\connect`) and tests that concatenate two renamed copies of it into a real `\connect`-delimited multi-database file (`docs/design/architecture.md` ("Fixtures")). Confirmed against real `pg_dump` output: the preamble search re-arms at each `\connect` (I1), both databases' DDL and version headers (I9) are recovered correctly, and I2 holds (one qualified table name owns a `COPY` block per database). It also has the genuine `pg_dumpall` fixture (`fixtures/<version>/edge_cases/dumpall.sql`, all 6 versions, real `pg_dumpall --no-role-passwords`) the hand-concatenated stand-in couldn't produce: `pg_dumpall` passes `--create` for ordinary databases but not for `postgres`/`template1`, writing those `\connect` lines itself, which flips those segments' version headers to *after* their `\connect` — confirmed present on 13.23 and 18.6, both shapes in the same file (I9). A query never silently spans databases (`docs/design/architecture.md`, "One target per query"): `CopyBlock` now carries the database it belongs to, `resolve.rs::database_for_name` selects by that attributed name rather than guessing from DDL content, and a query matching blocks in more than one database — or, bare-name, more than one schema in one database — is `Error::AmbiguousTable { name, candidates }`, with `--database`/`QueryOptions::database` as the way out. Every database is typed without a prior `pgdq parse`: the mapping pass restates `DumpMetadata` at each `\connect`ed database's first `COPY` block (I1's recurring boundary), which it necessarily passes before banking any of that database's blocks, so a cold query and one run after `parse` answer alike and an interrupted `parse` comes back typed for every segment it finished. The two answers to "this block's database has no DDL behind it" — `Error::MetadataNotScanned` for a stream, `ColumnResolution::MetadataNotScanned` for a listing — stay for metadata some other scan built (`docs/design/architecture.md`, "Joining a header against the metadata"). |
| `CREATE EXTENSION` / dump-level metadata | Tested (fixture + koji) | Source server version, `pg_dump` version, and the extension list (name + schema) are scanned from the preamble, cached in `DumpMetadata`, and shown by `pgdq info`. Extension *versions* are not recoverable from a regular dump — `dumpExtension()` omits them by design so the restore target picks its own default. Guaranteed to precede all `COPY` blocks (`addBoundaryDependencies()` makes `DO_EXTENSION` pre-data), so the search can terminate at the first block. The extension-count/schema grammar itself has no fixture coverage (none of the fixture schemas define an extension, and koji has zero), so it's unit-tested against hand-written statement text only. Evidence: `docs/status/history/2026-08-22.md`; `docs/design/architecture.md` ("The preamble grammar and `DumpMetadata`"). |
| `CREATE TYPE` / `CREATE DOMAIN` (user-defined types) | Tested (fixture + koji) | Captured by the same preamble scan as extensions (`DO_TYPE`/`DO_SHELL_TYPE` are pre-data, so the same early exit applies). Six emission shapes: enums and domains are fully parsed (including transitively through a domain-over-domain, and both the plain and `--binary-upgrade` split-across-`ALTER TYPE ADD VALUE` enum-label shapes — confirmed identical across all 6 routine `pg_dump` versions); composites parse their field list, all-or-nothing — a body with any unparseable fragment yields no field list at all, since `record_out` is positional and has no name-join to recover a dropped field with (I23). Ranges and C-level base/shell types gained real fixture evidence in slice 2.3.2 (`fixtures/<version>/types/default.sql`'s `public.myrange`/`public.mybase`/`public.shellonly`, all 6 versions): `mybase` emits twice (`SHELL TYPE` then `TYPE`), `shellonly` once (`TYPE`), and `myrange`'s body is multi-line with a multi-word subtype (`double precision`) — the shape the range grammar had never seen for real before this (I10, I11), all resolving correctly via `pgtype.rs::resolve_declared_type` — `myrange` to the five-field range struct over `Float64`, `mybase`/`shellonly` to `OpaqueBaseType`, and `mybase[]` to `OpaqueElementType`. Multirange types (PG14+) are also recognized as of slice 2.3.3 (`docs/design/architecture.md` ("Type resolution")): the six built-ins resolve bare, like the built-in ranges, to a `List` of the range struct over their hardcoded subtype, and a user range's auto-created companion — emitted nowhere in the dump at all, surviving only as the `multirange_type_name` parameter inside its range's DDL (I10) — resolves the same way via `TypeKind::Range::multirange_type_name`, taking its bound type from the range that names it, confirmed present on 14 through 18 and absent (parameter doesn't exist as grammar) on 13. Extension-owned types are *not* emitted this way — `checkExtensionMembership()` suppresses them — so this list and the extension list are disjoint and both are needed. Evidence: `docs/status/history/2026-08-22.md`; `docs/design/architecture.md` ("The preamble grammar and `DumpMetadata`", "Type resolution", "Fixture tree", "Type resolution"). |
| `CREATE COLLATION` (user-defined collations) | Partially tested (fixture) | Parsed by the same preamble scan as types, into `DatabaseMetadata::collations` as a name plus whether the statement said `deterministic = false` (I42). **Both determinism halves have fixture evidence at all six routine versions** — `fixtures/<13-18>/types/default.sql` carries `CREATE COLLATION public.c_collation (provider = libc, locale = 'C');` and `CREATE COLLATION public.nd_collation (provider = icu, deterministic = false, locale = 'und');`, read back as `deterministic: true` and `false` by `tests/preamble.rs`, with `t_collate.v_nd` a column of the second. The ICU exclusion is scoped rather than reversed: a plain dump's `CREATE COLLATION` carries no `collversion` (I42) and the column earns no oracle case, so the drift the exclusion avoids stays out of every flag set but `binary-upgrade`, which alone appends `version = '<collversion>'` — guarded by `tests/preamble.rs`'s `the_icu_collversion_reaches_binary_upgrade_alone_and_agrees_across_majors`, which requires the six majors to agree on the value without naming it. Also untested: the `CREATE COLLATION x FROM y` copy form, which `pg_dump` never writes — it emits the full option list for every collation it dumps — and which this parse reads as deterministic whatever the source collation was. |
| `--binary-upgrade` | Tested (fixture) | The only mode that records extension versions, via `binary_upgrade_create_empty_extension(name, schema, relocatable, version, ...)` instead of `CREATE EXTENSION`. Also emits `CREATE TYPE ... AS ENUM ()` with an **empty** body, adding labels afterwards via oid-preserving calls, and re-creates dropped columns as `INTEGER /* dummy */` (I5) — confirmed against all 6 routine versions in both the `edge_cases` and `types` fixture schemas; `COPY` block structure unaffected. Also interleaves `SELECT pg_catalog.binary_upgrade_set_next_*_oid(...)` calls between every object's TOC comment and its real statement — a detail the preamble parser tolerates. Evidence: `docs/design/architecture.md` ("Type resolution"). |
| `--extension=PATTERN` / `--exclude-extension=PATTERN` | Untested | Filters which extensions appear in the preamble (`--exclude-extension` is PG 17+). No structural effect on `COPY` blocks; relevant only in that a filtered dump's extension list is incomplete by construction. |
| Large objects (BLOBs) | Contents unsupported (by design); ranges tested | Plain-format dumps carry large-object data as ordinary single-line SQL — `SELECT pg_catalog.lo_open('<oid>', …);`, a run of `SELECT pg_catalog.lowrite(0, '\x…');`, then `lo_close` — always after every `COPY` block and before post-data DDL, wrapped in `BEGIN;`/`COMMIT;` (I12). **Not a correctness hazard:** a bytea hex literal cannot contain a line break, so no `COPY` header or `\.` terminator can hide inside the region. Decoding the contents stays permanently out of scope — opaque bytes belonging to no table. The byte *range* is one `Data(LargeObjects)` span of the full file map, since a hole is what that map exists to forbid. This is also the one inter-`COPY` gap that is not schema-sized — hex encoding roughly doubles the objects' on-disk size — so the scanner recognizes the region (a bare `BEGIN;`/`COMMIT;` pair) and skips it unread rather than walking it statement by statement. Tested (fixture) (`scripts/fixture_schema_objects.sql`, `fixtures/<version>/objects/default.sql`, all 6 routine versions): the archive-entry shape itself changed at v17 — v13-16 puts every large object's data in one shared `BLOBS` entry (one `BEGIN;`/`COMMIT;` for the whole database's large objects), v17-18 gives each object its own `BLOB METADATA`/`BLOBS` entry pair, merged back into one span each by `crate::map::Builder::on_large_object_start` — verified against both shapes, all 6 versions, `tests/map.rs::the_large_object_region_is_one_data_span_on_every_routine_version`. Per-object subdivision stays deferred either way (no reader needs it yet). Throughput on a synthetic 3GB region: ~1.9GB/s (`docs/status/history/2026-08-24.md`) — an order of magnitude above the 243MB/s `COPY`-decode baseline, confirming the region is skipped rather than walked. Still no koji coverage: koji has no large objects. See I12 for the full breakdown. |
| `\restrict` / `\unrestrict` / `\connect` (psql meta-commands) | Tested | Confirmed present in the koji sample (`pg_dump 16.14`) bracketing the DB-create preamble and the main content section. Also confirmed present in **all 6** routine fixture versions (`13.23` through `18.6`) from the 2025 search_path-safety patch. Narrows (doesn't yet pin down exactly) the version threshold: present by `13.23`, so introduced somewhere between `13.0` and `13.23` in that patch series (and the equivalent point release in each other series). |
| Non-UTF8 `client_encoding` | Unsupported (errors) | koji sample is UTF8 only. Field decoding validates UTF-8 and returns `Error::InvalidUtf8` otherwise, so a non-UTF8 dump fails loudly rather than silently corrupting. Block *structure* (`COPY`/`\.` boundaries) is still found correctly, since it is located at the byte level. |
| `COPY` header variants | Tested (fixture) | The scanner accepts `COPY <table> [(<cols>)] FROM stdin;` — schema-qualified or bare, quoted or unquoted identifiers, with or without a column list. Anything else on a `COPY` line (notably `TO stdout;` and any trailing `WITH (...)`) is deliberately not recognised and is skipped as ordinary SQL rather than guessed at. |
| `COPY ... FROM stdin;` at line start inside a dollar-quoted body | Tested (fixture) | `pgdump_query::copy::scan_dollar_quotes` tracks `$tag$ ... $tag$` state across the whole scan, so a line inside one is never checked as structure regardless of what it looks like. `fixture_schema_edge_cases.sql`'s `public.sample_fn` (untagged `$$`, body contains a byte-for-byte valid `COPY` header) and `public.tagged_fn` (body forces `pg_dump` to pick a tagged `$_$` delimiter, with an untagged `$$` pair inside it) exercise both shapes through real `pg_dump` output on all 6 routine versions. Evidence: `docs/design/architecture.md`. |
| Dump-level compression (`-Z`/`--compress`) for plain format | Planned (P15) | **Plain format compresses too**, and `pg_dump`'s own documentation is explicit about it: "For plain text output, setting a nonzero compression level causes the entire output file to be compressed, as though it had been fed through gzip, lz4, or zstd" (`doc/src/sgml/ref/pg_dump.sgml`, the `--compress` entry, 18.6). gzip long predates the method selector; lz4 and zstd arrive with PG 16. So a `pg_dump -Fp -Z9` file is ordinary plain-format output this build cannot read — a compatibility gap, not a scope decision. P15 owns those codecs; the mechanism they arrive through is P13's decompressing byte source. Untested at every level until then: no fixture flag set produces a compressed dump. **Provenance:** this row read `N/A for plain` until 2026-09-02 — a documentation-asserted status, never a fixture, and contradicted by the paragraph quoted above. |
| Dump-level compression for custom/directory | Planned (P8) | Different problem, same codecs: an archive compresses **per entry**, internally, so the decompression sits inside the container layer rather than beneath it. gzip throughout, plus lz4/zstd from PG 16 on. |
| External compression of the `.sql` file (e.g. `.xz`, `.gz`) | Planned (P13 for `.xz`, P15 for `.gz`/`.zst`) | Not produced by `pg_dump` — a file somebody compressed afterwards — but the same input either way, and in scope: `pgdq --source foo.dump.xz`. Today input is assumed already-decompressed plain SQL text and decompressing is a caller-side step. The koji sample's own `.xz` is the worked case, and it is not the shape this was assumed to be: 31,150 self-contained streams, so it is randomly accessible at ~24 MiB granularity without an index of ours ([`roadmap-P13-compressed-input-inbox.md`](roadmap-P13-compressed-input-inbox.md)). |
| CSV-format `COPY` blocks | Planned (post-1.0, alternate formats); not a `pg_dump` shape | **Closed — this was never a compatibility question.** `pg_dump` has no CSV mode: `dumpTableData()` branches only on `dump_inserts`, emitting either the fixed format string `"COPY %s %s FROM stdin;\n"` (no options clause, nowhere for `WITH (FORMAT csv)` to appear) or `INSERT INTO`; its server-side read is a bare `COPY ... TO stdout;`; and `grep -rni csv src/bin/pg_dump/` matches nothing in any version (I13). The `--format` flag names the *archive container* (plain/custom/directory/tar), not the `COPY` data format — the likely source of the confusion. **Provenance:** entered as an aside in `docs/design/historical/initial.md`'s "Configurable option (future)" list, bundled with `--inserts`/`--column-inserts`, and inherited by this matrix without evidence. P8 Track A therefore covers `--inserts`/`--column-inserts` only. **Not a non-goal:** `psql` writes `COPY ... WITH (FORMAT csv)` and that is valid PostgreSQL, so it is inside the input contract (`roadmap.md`, "The input contract is valid PostgreSQL") and planned post-1.0 under alternate formats, with its own fixtures — see that doc's Future section. What it costs is a second field decoder, not a new scanner. |
| COPY TEXT wire format stability across PG 13-18 | Tested | Confirmed byte-identical escaping across all 6 routine versions (`13.23` through `18.6`): the `public.escapes` fixture table holds one row per codepoint (`chr(n)` for 1-127 plus a 2-/3-/4-byte UTF-8 spread), and the decoder round-trips every row back to the original character on every version. All six escape only `\b \t \n \v \f \r \\` and emit the remaining control bytes raw. |
| TOC `Type:` kinds needing a C-level handler or an unavailable provider | Untested (deliberately) | Seven of the ~63 TOC kinds have no fixture: `SECURITY LABEL` (needs a security-label provider such as sepgsql registered via `shared_preload_libraries`, absent from a stock `postgres:*-trixie` image) and `ACCESS METHOD`, `OPERATOR`, `OPERATOR CLASS`, `OPERATOR FAMILY`, `TRANSFORM`, `TEXT SEARCH PARSER`, `TEXT SEARCH TEMPLATE` (each needs a C-level handler function, so a real one arrives only via an extension). Pulling an extension into `scripts/fixture_schema_objects.sql` to exercise a label the schema needs for nothing else is out of proportion to what it buys. Safe to leave: TOC coverage is reported per file by design, so an unexercised kind degrades to "unrecognized" in the map, never a crash or a hole. Revisit if the sysadmin-inventory use case turns out to need one specifically. Also uncovered, for other reasons: `DATABASE`/`DATABASE PROPERTIES`/`ENCODING`/`SEARCHPATH`/`STDSTRINGS` (dump-level metadata, already exercised via `edge_cases/create.sql` and the `dumpall` fixture, and not DDL objects the inventory is about). `STATISTICS DATA` is now covered — see the `--statistics` row below. Everything else is covered — see `docs/design/architecture.md`. |
| `--statistics` (PG18+) | Tested (fixture, v18 only) | `fixtures/18/objects/stats.sql`, via `generate_fixtures.py`'s version-conditional `objects/stats` flag set (routine versions 13-17 don't have the flag at all). Produces one `STATISTICS DATA` TOC entry per relation, headed `-- Statistics for Name: <table>; Type: STATISTICS DATA; Schema: <schema>; Owner: -` (`TOC_PREFIX_STATS`, always an empty owner — `dumpRelationStats` sets none) followed by `pg_catalog.pg_restore_relation_stats(...)`/`pg_restore_attribute_stats(...)` calls. The real flag name is `--statistics`; `--with-statistics`, used in this project's own earlier notes, does not exist in any version (`pg_dump.c`'s long-option table has no such string). Recognized: `map::parse_toc_header_line` reads all three of `_printTocEntry()`'s prefixes, so each entry is one attributed span carrying a `STATISTICS DATA` TOC kind (see I18 in `postgres-invariants.md`). |
| `--statistics-only` (PG18+) | Untested (deliberately) | Produces the same `STATISTICS DATA` entries the `--statistics` row covers, with the `COPY` blocks omitted — so it exercises no parsing path `fixtures/18/objects/stats.sql` does not already reach. What it would add is a *reporting* shape, a dump `pgdq info` finds zero tables in, and that is already covered by every `schema-only` fixture, which has no `COPY` blocks either. A flag set for it would cost a sixth `objects` variant and pin nothing new. Revisit if `--statistics-only` ever gains an entry kind or a header spelling `--statistics` does not emit. |
| `objects` fixture schema under flag sets beyond `{default, verbose}` | Partially tested | The `objects` schema runs `default` and `--verbose` on every routine version, plus `--statistics` on v18 only (see the row above) — not the full flag matrix `edge_cases` runs (`data-only`, `schema-only`, `binary-upgrade`, `inserts`, …). `--verbose` is the one flag that changes what this schema exists to exercise — it widens the TOC comment block past three lines with `-- TOC entry`/`-- Dependencies:` lines. The other flags vary *which* objects appear, not the TOC shapes this schema was built for, and `edge_cases` already exercises each of them. Adding a flag set here is fixture generation, not a code change, if a later slice's tiling or enrichment test wants one. |
| v18-only `CREATE TABLE` column shapes: `CONSTRAINT <name> NOT NULL`, `NO INHERIT`, virtual `GENERATED ALWAYS AS (expr)` | Untested | Three shapes v18's `dumpTableSchema` can write between a column's type and its `COLLATE` clause that no earlier major can (I37). Named in the invariant from v18.6's source; **not exercised by any fixture**, so the preamble grammar's handling of them rests on source reading alone — which is what this row exists to say, since `fixtures/18/types/*.sql` otherwise looks like full v18 coverage. `COLLATE` is found regardless: `extract_collation` scans the whole fragment at paren depth zero rather than expecting a particular window, and `CONSTRAINT`/`NOT NULL`/`GENERATED` are all already type-parse stop words. **The blocker is schema-level version conditioning**: `generate_fixtures.py` conditions dump *flag sets* on version (that is how `fixtures/18/objects/stats.sql` exists) but runs one schema `.sql` against every major, so an 18-only DDL shape fails on 13-17. Adding that capability is a fixture-family change and wants its own slice; nothing depends on it today. |
| A range type declaring a `canonical` function | Untested | `dumpRangeType` writes `,\n    canonical = <function>` for any range whose `pg_range.rngcanonical` is set, after `multirange_type_name` and before `subtype_diff` (I10) — read out of the v13.23 and v18.6 sources and confirmed against one 16.15 probe dump. **No fixture carries one**, so the grammar's handling of the parameter and the refusal it triggers rest on a hand-written dump in `pgdump_query/tests/ordering.rs` rather than on `pg_dump` output. **The blocker is that a canonical function cannot be written in SQL**: it must be declared against the shell type, and `CREATE FUNCTION` refuses one there (`ERROR: SQL function cannot accept shell type`), so the fixture schema would need a `LANGUAGE internal` function naming a built-in symbol — I11's base-type recipe applied to a range, plus a subtype whose successor a built-in symbol happens to compute. Nothing depends on it today: the parameter's *presence* is all the register reads, and the answer either way is a refusal. |
| Producers other than `pg_dump` (hand-written or hand-edited SQL, `pg_dump`-compatible tools) | Untested | **In contract, with no evidence.** pgdq reads plain SQL a PostgreSQL server would accept, whoever wrote it (`roadmap.md`, "The input contract is valid PostgreSQL"), and the preamble parser is a general SQL parser rather than a `pg_dump`-shaped one — arbitrary whitespace, quoted identifiers, trailing constraints, block comments. No producer other than `pg_dump` has a fixture generator, so nothing here is exercised. The one place this class is known to differ is the declared-type grammar: five of PostgreSQL's six array-declaration spellings never appear in `pg_dump` output and are pinned by unit test against I28 rather than by fixture (`roadmap.md`, "Where a fixture is impossible"). This row changes status when a specific producer is identified and gains a generator in `scripts/`. |
