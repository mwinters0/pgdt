# pg_dump Option Compatibility Matrix

Tracks `pg_dump` options/output variants against this library's support
status. Exists so compatibility scope stays explicit rather than implicit —
raised during MVP design review. Populated/kept current by the fixture
tooling described in `docs/design/roadmap-phase1-mvp.md` (Testing & fixtures)
— `scripts/generate_fixtures.py`, run against containers for the routine
version set (latest minor of every major, 13 through 18 as of this writing —
see that doc's "Version policy" for the current pins). Rows evidenced this
way say so; rows not yet exercised by that tooling are asserted from manual
inspection of the `koji` sample dump or from `pg_dump` documentation instead
— that distinction is called out per row.

Status values: **Tested** (fixture or real-dump evidence), **Untested**
(plausibly relevant, no evidence yet), **Planned (Phase N)** (in scope, not
built, roadmap phase named), **Unsupported** (explicitly out of scope), **N/A**
(flag doesn't apply to plain format at all).

| Option / variant | Status | Notes |
|---|---|---|
| `--format=plain` (default) | Tested | Confirmed against the koji sample (784GB, `pg_dump 16.14`). This is the library's only target format. |
| `--format=custom` | Planned (Phase 8) | Container layer over the same COPY TEXT payload: `PGDMP` header + TOC gives the entries, each entry's data block is separately compressed. Needs streaming decompression; no new row parser. |
| `--format=directory` | Planned (Phase 8) | `toc.dat` plus one compressed file per entry. Same container layer as custom, different entry addressing. |
| `--format=tar` | Planned (Phase 8) | Tar member index plus `toc.dat`; members are uncompressed, so this is the cheapest of the three to add. |
| `--inserts` | Tested (fixture) | Confirmed against all 6 routine versions: produces `INSERT INTO` statements, zero real `COPY` blocks (the fixture's dollar-quoted decoy lines that merely *look* like a `COPY` header still appear, as intended — see the dollar-quote row below). Parser support for this shape is Phase 8 Track A — this row tracks the *fixture data existing*, not library support. |
| `--column-inserts` | Tested (fixture) | Same as above; fixture confirms the variant output shape. Phase 8 Track A for actual support. |
| `--rows-per-insert=N` | Untested (deliberately) | Only relevant once `--inserts` support exists (Phase 8 Track A); a fixture no code will read for several phases is cost without coverage. |
| `--data-only` | Tested (fixture) | Confirmed against all 6 routine versions: `COPY` blocks present with minimal preceding DDL, as expected. |
| `--schema-only` | Tested (fixture) | Confirmed: zero `COPY` blocks in the output across all 6 versions — the degenerate case parses to "no tables found," not an error. |
| `--no-owner`, `--no-privileges` | Tested (fixture) | Confirmed no structural effect on `COPY` blocks across all 6 versions. `--no-comments`/`--no-security-labels` get their own fixture flag set in slice 2.3.2 — not because they are expected to differ, but because I3's claim that TOC header comments survive `--no-comments` is what the whole preamble segmenter rests on, and it is currently proven by `pg_dump` source reading alone. |
| `--clean` / `--if-exists` | Tested (fixture) | Confirmed: adds `DROP ... IF EXISTS` before `CREATE`s, no structural surprise, across all 6 versions. |
| `--schema=X` (schema filtering) | Untested (deliberately) | The koji sample happens to contain two schemas (`lock_monitor`, `public`) with `COPY` blocks in each, so multi-schema dumps are informally covered — but the filtering *flag* itself hasn't been exercised. Left that way: it only removes objects, a shape the matrix already covers in kind. |
| Multiple databases (`pg_dumpall`, concatenated dumps) | Tested (fixture, structural only) | Phase 2.3.1 added `fixtures/{13,16,18}/edge_cases/create.sql` (the only flag combination that emits a `\connect`) and tests that concatenate two renamed copies of it into a real `\connect`-delimited multi-database file (`docs/design/roadmap-phase2.3.1-multidb-fixtures-notes.md`). Confirmed against real `pg_dump` output: the preamble search re-arms at each `\connect` (I1), both databases' DDL and version headers (I9) are recovered correctly, and I2 holds (one qualified table name owns a `COPY` block per database). **A genuine `pg_dumpall` fixture is added in slice 2.3.2** — the hand-concatenated stand-in cannot produce every real shape: `pg_dumpall` passes `--create` for ordinary databases but not for `postgres`/`template1`, writing those `\connect` lines itself, which flips a segment's version headers to *after* its `\connect` (I9). Meanwhile the design intent that a query never spans databases — matching blocks in more than one is an error naming the candidates, not a silent union — is **not implemented yet, but decided and scheduled as slice 2.3.3** (`docs/design/roadmap-phase2-typed-columns.md`, "One target per query"), generalized to cover bare-name cross-*schema* ambiguity within a single database as well. Today: `resolve.rs::database_for` resolves a table's type against the first database whose DDL mentions it (unchanged simplification, now proven end-to-end rather than only against hand-written input — see `docs/design/roadmap-phase2.3-type-resolution-notes.md`, "Decisions worth a second look"), and `stream::table_stream` matches `COPY` blocks by name alone, so a table genuinely defined in two databases returns both databases' rows unioned, in file order (`querying_a_table_name_shared_by_two_databases_silently_unions_both` in `pgdump_query/tests/stream.rs` locks in and documents this current behavior). |
| `CREATE EXTENSION` / dump-level metadata | Tested (fixture + koji) | Source server version, `pg_dump` version, and the extension list (name + schema) are scanned from the preamble, cached in `DumpMetadata`, and shown by `pgdq info`. Extension *versions* are not recoverable from a regular dump — `dumpExtension()` omits them by design so the restore target picks its own default. Guaranteed to precede all `COPY` blocks (`addBoundaryDependencies()` makes `DO_EXTENSION` pre-data), so the search can terminate at the first block. The extension-count/schema grammar itself has no fixture coverage (none of the fixture schemas define an extension, and koji has zero), so it's unit-tested against hand-written statement text only. Evidence: `docs/status/history/2026-08-22.md`; `docs/design/roadmap-phase2.2-preamble-notes.md`. |
| `CREATE TYPE` / `CREATE DOMAIN` (user-defined types) | Tested (fixture + koji) | Captured by the same preamble scan as extensions (`DO_TYPE`/`DO_SHELL_TYPE` are pre-data, so the same early exit applies). Six emission shapes: enums and domains are fully parsed (including transitively through a domain-over-domain, and both the plain and `--binary-upgrade` split-across-`ALTER TYPE ADD VALUE` enum-label shapes — confirmed identical across all 6 routine `pg_dump` versions); composites parse their field list (decoding COPY TEXT's record literal is Phase 4); ranges and C-level base/shell types are recognized but have zero fixture or koji evidence (koji's own range column is a built-in type) — unit-tested against hand-written statement text only. All three *are* reachable from pure SQL, no compiled extension needed (I11), and slice 2.3.2 adds them to `fixture_schema_types.sql`; the range grammar is the one that most needs it, having never seen `pg_dump`'s real multi-line, multi-word-subtype output. Multirange types (PG14+) are a separate shape: the six built-ins appear bare like the built-in ranges, and a user range's auto-created companion is emitted nowhere in the dump at all, surviving only as the `multirange_type_name` parameter inside its range's DDL (I10). Extension-owned types are *not* emitted this way — `checkExtensionMembership()` suppresses them — so this list and the extension list are disjoint and both are needed. Evidence: `docs/status/history/2026-08-22.md`; `docs/design/roadmap-phase2.2-preamble-notes.md`. |
| `--binary-upgrade` | Tested (fixture) | The only mode that records extension versions, via `binary_upgrade_create_empty_extension(name, schema, relocatable, version, ...)` instead of `CREATE EXTENSION`. Also emits `CREATE TYPE ... AS ENUM ()` with an **empty** body, adding labels afterwards via oid-preserving calls, and re-creates dropped columns as `INTEGER /* dummy */` (I5) — confirmed against all 6 routine versions in both the `edge_cases` and `types` fixture schemas; `COPY` block structure unaffected. Also interleaves `SELECT pg_catalog.binary_upgrade_set_next_*_oid(...)` calls between every object's TOC comment and its real statement — a detail the Phase 2.2 preamble parser needs to tolerate. Evidence: `docs/design/roadmap-phase2.0-fixture-validation-notes.md`. |
| `--extension=PATTERN` / `--exclude-extension=PATTERN` | Untested | Filters which extensions appear in the preamble (`--exclude-extension` is PG 17+). No structural effect on `COPY` blocks; relevant only in that a filtered dump's extension list is incomplete by construction. |
| Large objects (BLOBs) | Contents unsupported (by design); ranges planned (Phase 3) | Plain-format dumps carry large-object data as ordinary single-line SQL — one `SELECT pg_catalog.lo_open(pg_catalog.lo_create('<oid>'), …);`, a run of `SELECT pg_catalog.lowrite(0, '\x…');`, then `lo_close` per object — all inside one contiguous `BLOBS` region that sits after every `COPY` block and before post-data DDL, wrapped in `BEGIN;`/`COMMIT;` (I12). **Not a correctness hazard:** a bytea hex literal cannot contain a line break, so no `COPY` header or `\.` terminator can hide inside the region, and the scanner steps over it as ordinary outside-block lines. Decoding the contents stays permanently out of scope — opaque bytes belonging to no table. The byte *range* becomes one span of Phase 3's full file map, since a hole is what that map exists to forbid; per-object subdivision is deferred (the OID appears only in each `lo_create` opener). This is also the one inter-`COPY` gap that is not schema-sized — hex encoding roughly doubles the objects' on-disk size — so Phase 3's cheap tier must skip the region by TOC header rather than walk it. No fixture or koji coverage: koji has no large objects. |
| `\restrict` / `\unrestrict` / `\connect` (psql meta-commands) | Tested | Confirmed present in the koji sample (`pg_dump 16.14`) bracketing the DB-create preamble and the main content section. Also confirmed present in **all 6** routine fixture versions (`13.23` through `18.6`) from the 2025 search_path-safety patch. Narrows (doesn't yet pin down exactly) the version threshold: present by `13.23`, so introduced somewhere between `13.0` and `13.23` in that patch series (and the equivalent point release in each other series). |
| Non-UTF8 `client_encoding` | Unsupported (errors) | koji sample is UTF8 only. Field decoding validates UTF-8 and returns `Error::InvalidUtf8` otherwise, so a non-UTF8 dump fails loudly rather than silently corrupting. Block *structure* (`COPY`/`\.` boundaries) is still found correctly, since it is located at the byte level. |
| `COPY` header variants | Tested (fixture) | The scanner accepts `COPY <table> [(<cols>)] FROM stdin;` — schema-qualified or bare, quoted or unquoted identifiers, with or without a column list. Anything else on a `COPY` line (notably `TO stdout;` and any trailing `WITH (...)`) is deliberately not recognised and is skipped as ordinary SQL rather than guessed at. |
| `COPY ... FROM stdin;` at line start inside a dollar-quoted body | Tested (fixture) | Closed in Phase 2.1: `pgdump_query::copy::scan_dollar_quotes` tracks `$tag$ ... $tag$` state across the whole scan, so a line inside one is never checked as structure regardless of what it looks like. `fixture_schema_edge_cases.sql`'s `public.sample_fn` (untagged `$$`, body contains a byte-for-byte valid `COPY` header) and `public.tagged_fn` (body forces `pg_dump` to pick a tagged `$_$` delimiter, with an untagged `$$` pair inside it) exercise both shapes through real `pg_dump` output on all 6 routine versions. Evidence: `docs/design/roadmap-phase2.1-dollar-quote-tracking-notes.md`. |
| Dump-level compression (`-Z`/`--compress`) | N/A for plain; Planned (Phase 8) elsewhere | Per `pg_dump` docs, compression only applies to custom/directory/tar archive formats, not plain SQL text output — so it is N/A for the only format Phase 1 reads. It becomes load-bearing with those formats: gzip throughout, plus lz4/zstd from PG 16 on. |
| External compression of the `.sql` file (e.g. `.xz`, `.gz`) | Unsupported (by design) | Input is assumed already-decompressed plain SQL text; decompression is a caller-side preprocessing step (see: the koji sample also exists as a separate `.xz`-compressed download, decompressed before use here). |
| CSV-format `COPY` blocks | Unsupported (not a `pg_dump` shape) | **Closed — this was never a compatibility question.** `pg_dump` has no CSV mode: `dumpTableData()` branches only on `dump_inserts`, emitting either the fixed format string `"COPY %s %s FROM stdin;\n"` (no options clause, nowhere for `WITH (FORMAT csv)` to appear) or `INSERT INTO`; its server-side read is a bare `COPY ... TO stdout;`; and `grep -rni csv src/bin/pg_dump/` matches nothing in any version (I13). The `--format` flag names the *archive container* (plain/custom/directory/tar), not the `COPY` data format — the likely source of the confusion. **Provenance:** entered as an aside in `docs/design/historical/initial.md`'s "Configurable option (future)" list, bundled with `--inserts`/`--column-inserts`, and inherited by this matrix without evidence. Reading CSV would mean accepting input `pg_dump` never emits — a new input source to argue on its own merits, not a `pg_dump` variant. Phase 8 Track A therefore covers `--inserts`/`--column-inserts` only. |
| COPY TEXT wire format stability across PG 13-18 | Tested | Confirmed byte-identical escaping across all 6 routine versions (`13.23` through `18.6`): the `public.escapes` fixture table holds one row per codepoint (`chr(n)` for 1-127 plus a 2-/3-/4-byte UTF-8 spread), and the decoder round-trips every row back to the original character on every version. All six escape only `\b \t \n \v \f \r \\` and emit the remaining control bytes raw. |
