# pg_dump Option Compatibility Matrix

Tracks `pg_dump` options/output variants against this library's support
status. Exists so compatibility scope stays explicit rather than implicit —
raised during MVP design review. Populated/kept current by the fixture
tooling described in `docs/design/roadmap-phase1-mvp.md` (Testing & fixtures)
— `scripts/generate_fixtures.py`, run against containers for the routine
version set (latest minor of every major, 13 through 18 as of this writing —
see that doc's "Version policy" for the current pins). Rows evidenced this
way say so; rows not yet exercised by that tooling are asserted from manual
inspection of the `koji` sample dump or from `pg_dump` documentation instead
— that distinction is called out per row.

Status values: **Tested** (fixture or real-dump evidence), **Untested**
(plausibly relevant, no evidence yet), **Planned (Phase N)** (in scope, not
built, roadmap phase named), **Unsupported** (explicitly out of scope), **N/A**
(flag doesn't apply to plain format at all).

| Option / variant | Status | Notes |
|---|---|---|
| `--format=plain` (default) | Tested | Confirmed against the koji sample (784GB, `pg_dump 16.14`). This is the library's only target format. |
| `--format=custom` | Planned (Phase 8) | Container layer over the same COPY TEXT payload: `PGDMP` header + TOC gives the entries, each entry's data block is separately compressed. Needs streaming decompression; no new row parser. |
| `--format=directory` | Planned (Phase 8) | `toc.dat` plus one compressed file per entry. Same container layer as custom, different entry addressing. |
| `--format=tar` | Planned (Phase 8) | Tar member index plus `toc.dat`; members are uncompressed, so this is the cheapest of the three to add. |
| `--inserts` | Tested (fixture) | Confirmed against all 6 routine versions: produces `INSERT INTO` statements, zero real `COPY` blocks (the fixture's dollar-quoted decoy lines that merely *look* like a `COPY` header still appear, as intended — see the dollar-quote row below). Parser support for this shape is Phase 8 Track A — this row tracks the *fixture data existing*, not library support. |
| `--column-inserts` | Tested (fixture) | Same as above; fixture confirms the variant output shape. Phase 8 Track A for actual support. |
| `--rows-per-insert=N` | Untested (deliberately) | Only relevant once `--inserts` support exists (Phase 8 Track A); a fixture no code will read for several phases is cost without coverage. |
| `--load-via-partition-root`, and the partitioned shapes that force it | Observed, no fixture yet | Every leaf partition's `TABLE DATA` entry writes a `COPY` header naming the **root** table, so one header name owns several blocks in one dump, the TOC entry's `Name:` (the partition) disagrees with the header's name (the root), and a `-- load via partition root <root>` marker line sits between them. Not opt-in: `pg_dump` forces the mode for a table hash-partitioned on an enum column, so a **flagless** dump produces this. The several blocks are **not** adjacent — entries sort by the partition's own name, so an unrelated table sorts between them. The marker survives `--no-comments`, `--data-only` and `--inserts`. Observed against pg_dump 16.15 — see I2 in [`postgres-invariants.md`](postgres-invariants.md) for the reproduction. No fixture schema exercises partitioning at all today; the shape matters to any code that stops scanning at the first matching block, or that joins a TOC entry to the `COPY` header beneath it. |
| `--data-only` | Tested (fixture) | Confirmed against all 6 routine versions: `COPY` blocks present with minimal preceding DDL, as expected. |
| `--schema-only` | Tested (fixture) | Confirmed: zero `COPY` blocks in the output across all 6 versions — the degenerate case parses to "no tables found," not an error. |
| `--no-owner`, `--no-privileges` | Tested (fixture) | Confirmed no structural effect on `COPY` blocks across all 6 versions. |
| `--no-comments`, `--no-security-labels` | Tested (fixture) | Added in slice 2.3.2 (`fixtures/<version>/edge_cases/no-comments.sql`) specifically to check I3's claim that TOC header comments survive `--no-comments` — until this landed, that claim rested on `pg_dump` source reading alone. Confirmed: the `-- Name: ...` TOC header count is identical between `default.sql` and `no-comments.sql` for every version. Neither fixture schema contains a `COMMENT ON` statement, so the flag's actual suppression target isn't separately exercised — only the segmenter-relevant half is. |
| `--clean` / `--if-exists` | Tested (fixture) | Confirmed: adds `DROP ... IF EXISTS` before `CREATE`s, no structural surprise, across all 6 versions. |
| `--schema=X` (schema filtering) | Untested (deliberately) | The koji sample happens to contain two schemas (`lock_monitor`, `public`) with `COPY` blocks in each, so multi-schema dumps are informally covered — but the filtering *flag* itself hasn't been exercised. Left that way: it only removes objects, a shape the matrix already covers in kind. |
| Multiple databases (`pg_dumpall`, concatenated dumps) | Tested (fixture) | Phase 2.3.1 added `fixtures/{13,16,18}/edge_cases/create.sql` (the only flag combination that emits a `\connect`) and tests that concatenate two renamed copies of it into a real `\connect`-delimited multi-database file (`docs/design/roadmap-phase2-typed-columns-notes.md` ("Fixture tree")). Confirmed against real `pg_dump` output: the preamble search re-arms at each `\connect` (I1), both databases' DDL and version headers (I9) are recovered correctly, and I2 holds (one qualified table name owns a `COPY` block per database). Slice 2.3.2 added the genuine `pg_dumpall` fixture (`fixtures/<version>/edge_cases/dumpall.sql`, all 6 versions, real `pg_dumpall --no-role-passwords`) the hand-concatenated stand-in couldn't produce: `pg_dumpall` passes `--create` for ordinary databases but not for `postgres`/`template1`, writing those `\connect` lines itself, which flips those segments' version headers to *after* their `\connect` — confirmed present on 13.23 and 18.6, both shapes in the same file (I9). Slice 2.3.3 implemented the design's stated intent that a query never silently spans databases (`docs/design/roadmap-phase2-typed-columns.md`, "One target per query", `docs/design/roadmap-phase2-typed-columns-notes.md` ("One target per query")): `CopyBlock` now carries the database it belongs to, `resolve.rs::database_for_name` selects by that attributed name rather than guessing from DDL content, and a query matching blocks in more than one database — or, bare-name, more than one schema in one database — is `Error::AmbiguousTable { name, candidates }`, with `--database`/`BatchOptions::database` as the way out. A query against a database an incremental scan hasn't read the DDL for is `Error::MetadataNotScanned`, remedied by `pgdq parse` or `--schema-mode strings`. |
| `CREATE EXTENSION` / dump-level metadata | Tested (fixture + koji) | Source server version, `pg_dump` version, and the extension list (name + schema) are scanned from the preamble, cached in `DumpMetadata`, and shown by `pgdq info`. Extension *versions* are not recoverable from a regular dump — `dumpExtension()` omits them by design so the restore target picks its own default. Guaranteed to precede all `COPY` blocks (`addBoundaryDependencies()` makes `DO_EXTENSION` pre-data), so the search can terminate at the first block. The extension-count/schema grammar itself has no fixture coverage (none of the fixture schemas define an extension, and koji has zero), so it's unit-tested against hand-written statement text only. Evidence: `docs/status/history/2026-08-22.md`; `docs/design/roadmap-phase2-typed-columns-notes.md` ("Preamble parsing"). |
| `CREATE TYPE` / `CREATE DOMAIN` (user-defined types) | Tested (fixture + koji) | Captured by the same preamble scan as extensions (`DO_TYPE`/`DO_SHELL_TYPE` are pre-data, so the same early exit applies). Six emission shapes: enums and domains are fully parsed (including transitively through a domain-over-domain, and both the plain and `--binary-upgrade` split-across-`ALTER TYPE ADD VALUE` enum-label shapes — confirmed identical across all 6 routine `pg_dump` versions); composites parse their field list (decoding COPY TEXT's record literal is Phase 4). Ranges and C-level base/shell types gained real fixture evidence in slice 2.3.2 (`fixtures/<version>/types/default.sql`'s `public.myrange`/`public.mybase`/`public.shellonly`, all 6 versions): `mybase` emits twice (`SHELL TYPE` then `TYPE`), `shellonly` once (`TYPE`), and `myrange`'s body is multi-line with a multi-word subtype (`double precision`) — the shape the range grammar had never seen for real before this (I10, I11), all `Mapped`/`Deferred` correctly via `pgtype.rs::resolve_declared_type`. Multirange types (PG14+) are also recognized as of slice 2.3.3 (`docs/design/roadmap-phase2-typed-columns-notes.md` ("Type resolution")): the six built-ins resolve `Deferred(Range)` bare, like the built-in ranges, and a user range's auto-created companion — emitted nowhere in the dump at all, surviving only as the `multirange_type_name` parameter inside its range's DDL (I10) — resolves the same way via `TypeKind::Range::multirange_type_name`, confirmed present on 14 through 18 and absent (parameter doesn't exist as grammar) on 13. Extension-owned types are *not* emitted this way — `checkExtensionMembership()` suppresses them — so this list and the extension list are disjoint and both are needed. Evidence: `docs/status/history/2026-08-22.md`; `docs/design/roadmap-phase2-typed-columns-notes.md` ("Preamble parsing", "Type resolution", "Fixture tree", "Evidence carried forward for later phases"). |
| `--binary-upgrade` | Tested (fixture) | The only mode that records extension versions, via `binary_upgrade_create_empty_extension(name, schema, relocatable, version, ...)` instead of `CREATE EXTENSION`. Also emits `CREATE TYPE ... AS ENUM ()` with an **empty** body, adding labels afterwards via oid-preserving calls, and re-creates dropped columns as `INTEGER /* dummy */` (I5) — confirmed against all 6 routine versions in both the `edge_cases` and `types` fixture schemas; `COPY` block structure unaffected. Also interleaves `SELECT pg_catalog.binary_upgrade_set_next_*_oid(...)` calls between every object's TOC comment and its real statement — a detail the Phase 2.2 preamble parser needs to tolerate. Evidence: `docs/design/roadmap-phase2-typed-columns-notes.md` ("Evidence carried forward for later phases"). |
| `--extension=PATTERN` / `--exclude-extension=PATTERN` | Untested | Filters which extensions appear in the preamble (`--exclude-extension` is PG 17+). No structural effect on `COPY` blocks; relevant only in that a filtered dump's extension list is incomplete by construction. |
| Large objects (BLOBs) | Contents unsupported (by design); ranges planned (Phase 3) | Plain-format dumps carry large-object data as ordinary single-line SQL — `SELECT pg_catalog.lo_open('<oid>', …);`, a run of `SELECT pg_catalog.lowrite(0, '\x…');`, then `lo_close` — always after every `COPY` block and before post-data DDL, wrapped in `BEGIN;`/`COMMIT;` (I12). **Not a correctness hazard:** a bytea hex literal cannot contain a line break, so no `COPY` header or `\.` terminator can hide inside the region, and the scanner steps over it as ordinary outside-block lines. Decoding the contents stays permanently out of scope — opaque bytes belonging to no table. The byte *range* becomes one span of Phase 3's full file map, since a hole is what that map exists to forbid. This is also the one inter-`COPY` gap that is not schema-sized — hex encoding roughly doubles the objects' on-disk size — so Phase 3's cheap tier must skip the region(s) by TOC header rather than walk them. Tested (fixture) as of slice 3.1 (`scripts/fixture_schema_objects.sql`, `fixtures/<version>/objects/default.sql`, all 6 routine versions): the archive-entry shape itself changed at v17 — v13-16 puts every large object's data in one shared `BLOBS` entry (one `BEGIN;`/`COMMIT;` for the whole database's large objects), v17-18 gives each object its own `BLOB METADATA`/`BLOBS` entry pair — so per-object subdivision (still deferred) would be cheap from the TOC header alone on v17+ but requires walking `lo_open` openers on v13-16. See I12 for the full breakdown. Still no koji coverage: koji has no large objects. |
| `\restrict` / `\unrestrict` / `\connect` (psql meta-commands) | Tested | Confirmed present in the koji sample (`pg_dump 16.14`) bracketing the DB-create preamble and the main content section. Also confirmed present in **all 6** routine fixture versions (`13.23` through `18.6`) from the 2025 search_path-safety patch. Narrows (doesn't yet pin down exactly) the version threshold: present by `13.23`, so introduced somewhere between `13.0` and `13.23` in that patch series (and the equivalent point release in each other series). |
| Non-UTF8 `client_encoding` | Unsupported (errors) | koji sample is UTF8 only. Field decoding validates UTF-8 and returns `Error::InvalidUtf8` otherwise, so a non-UTF8 dump fails loudly rather than silently corrupting. Block *structure* (`COPY`/`\.` boundaries) is still found correctly, since it is located at the byte level. |
| `COPY` header variants | Tested (fixture) | The scanner accepts `COPY <table> [(<cols>)] FROM stdin;` — schema-qualified or bare, quoted or unquoted identifiers, with or without a column list. Anything else on a `COPY` line (notably `TO stdout;` and any trailing `WITH (...)`) is deliberately not recognised and is skipped as ordinary SQL rather than guessed at. |
| `COPY ... FROM stdin;` at line start inside a dollar-quoted body | Tested (fixture) | Closed in Phase 2.1: `pgdump_query::copy::scan_dollar_quotes` tracks `$tag$ ... $tag$` state across the whole scan, so a line inside one is never checked as structure regardless of what it looks like. `fixture_schema_edge_cases.sql`'s `public.sample_fn` (untagged `$$`, body contains a byte-for-byte valid `COPY` header) and `public.tagged_fn` (body forces `pg_dump` to pick a tagged `$_$` delimiter, with an untagged `$$` pair inside it) exercise both shapes through real `pg_dump` output on all 6 routine versions. Evidence: `docs/design/roadmap-phase2-typed-columns-notes.md`. |
| Dump-level compression (`-Z`/`--compress`) | N/A for plain; Planned (Phase 8) elsewhere | Per `pg_dump` docs, compression only applies to custom/directory/tar archive formats, not plain SQL text output — so it is N/A for the only format Phase 1 reads. It becomes load-bearing with those formats: gzip throughout, plus lz4/zstd from PG 16 on. |
| External compression of the `.sql` file (e.g. `.xz`, `.gz`) | Unsupported (by design) | Input is assumed already-decompressed plain SQL text; decompression is a caller-side preprocessing step (see: the koji sample also exists as a separate `.xz`-compressed download, decompressed before use here). |
| CSV-format `COPY` blocks | Unsupported (not a `pg_dump` shape) | **Closed — this was never a compatibility question.** `pg_dump` has no CSV mode: `dumpTableData()` branches only on `dump_inserts`, emitting either the fixed format string `"COPY %s %s FROM stdin;\n"` (no options clause, nowhere for `WITH (FORMAT csv)` to appear) or `INSERT INTO`; its server-side read is a bare `COPY ... TO stdout;`; and `grep -rni csv src/bin/pg_dump/` matches nothing in any version (I13). The `--format` flag names the *archive container* (plain/custom/directory/tar), not the `COPY` data format — the likely source of the confusion. **Provenance:** entered as an aside in `docs/design/historical/initial.md`'s "Configurable option (future)" list, bundled with `--inserts`/`--column-inserts`, and inherited by this matrix without evidence. Reading CSV would mean accepting input `pg_dump` never emits — a new input source to argue on its own merits, not a `pg_dump` variant. Phase 8 Track A therefore covers `--inserts`/`--column-inserts` only. |
| COPY TEXT wire format stability across PG 13-18 | Tested | Confirmed byte-identical escaping across all 6 routine versions (`13.23` through `18.6`): the `public.escapes` fixture table holds one row per codepoint (`chr(n)` for 1-127 plus a 2-/3-/4-byte UTF-8 spread), and the decoder round-trips every row back to the original character on every version. All six escape only `\b \t \n \v \f \r \\` and emit the remaining control bytes raw. |
| TOC `Type:` kinds needing a C-level handler or an unavailable provider | Untested (deliberately) | Seven of the ~63 TOC kinds have no fixture: `SECURITY LABEL` (needs a security-label provider such as sepgsql registered via `shared_preload_libraries`, absent from a stock `postgres:*-alpine` image) and `ACCESS METHOD`, `OPERATOR`, `OPERATOR CLASS`, `OPERATOR FAMILY`, `TRANSFORM`, `TEXT SEARCH PARSER`, `TEXT SEARCH TEMPLATE` (each needs a C-level handler function, so a real one arrives only via an extension). Pulling an extension into `scripts/fixture_schema_objects.sql` to exercise a label the schema needs for nothing else is out of proportion to what it buys. Safe to leave: TOC coverage is reported per file by design, so an unexercised kind degrades to "unrecognized" in the map, never a crash or a hole. Revisit if the sysadmin-inventory use case turns out to need one specifically. Also uncovered, for other reasons: `DATABASE`/`DATABASE PROPERTIES`/`ENCODING`/`SEARCHPATH`/`STDSTRINGS` (dump-level metadata, already exercised via `edge_cases/create.sql` and the `dumpall` fixture, and not DDL objects the inventory is about) and `STATISTICS DATA` (`--with-statistics`, PG18+, outside the routine matrix). Everything else is covered — see `docs/design/roadmap-phase3.1-objects-fixture-notes.md`. |
| `objects` fixture schema under flag sets beyond `{default, verbose}` | Untested (deliberately) | The `objects` schema runs only `default` and `--verbose`, not the full flag matrix `edge_cases` runs (`data-only`, `schema-only`, `binary-upgrade`, `inserts`, …). `--verbose` is the one flag that changes what this schema exists to exercise — it widens the TOC comment block past three lines with `-- TOC entry`/`-- Dependencies:` lines. The other flags vary *which* objects appear, not the TOC shapes this schema was built for, and `edge_cases` already exercises each of them. Adding a flag set here is fixture generation, not a code change, if a later slice's tiling or enrichment test wants one. |
