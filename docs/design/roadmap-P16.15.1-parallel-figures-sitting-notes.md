# P16.15.1 — the sitting

`16.15` changed `stream::plan_partitions`' divisor and left the figure
re-take as `16.15.1`, needing a commit to name. The row that admitted it named
the wrong figure — `parallel-peak-rss`, not `parallel-scan-throughput` — which
`f7176a4`'s review corrected before this sitting ran (`STATUS.md`'s `16.15.1`
row, "The figure `16.15`'s admitting row named is not the one that moved").

## The run

`cd scripts && uv run measure.py --figure parallel-scan-throughput`, detached
(`runs/parallel-scan-throughput-20260908-1837/`), against `20fd77c`. 140
`pgdq` invocations (4 legs × 7 `--jobs` values × 5 reps), 1485 s wall clock,
none discarded, none retried. Output: `runs/measure-20260908T183715/tables.md`,
folded into `measurements.md` verbatim (with the sub-stream annotation below
added) under its existing heading, its marker now declaring `20fd77c` where it
declared `e29939c`.

**This is the second launch.** The first (`runs/measure-20260908T182750/`) was
discarded and marked `CONTAMINATED.md`: the round that started it also ran
`cargo test --workspace` for its own verification, inside the measurement
window — a `cargo` job across 24 cores moves the numbers a sweep is taking.
Nothing about the anchoring decision or the acknowledgement below was in
question, only the sitting itself, so the re-launch changed nothing but the
timestamp and the resulting commit it names.

## The other half: `parallel-peak-rss` needed no sitting

`a30cc43`'s only executable hunk is inside `stream::plan_partitions` and
`table_stream_partitions`; `parallel-peak-rss`'s command shape is `pgdq parse`
(`parse-rss-jobs-N`), which reaches `worker_count` through
`leader::scan_region` and never calls the changed function. That is
reachability, the one mechanical oracle that settles an executable diff, so it
is discharged by an `ACKNOWLEDGED` entry naming `a30cc43` in
`scripts/acknowledged.py` rather than a second sitting, and `e29939c`'s table
stands unmoved — still green, per `--stale`.

## What the table now says that `e29939c`'s did not

**The rows above four workers on both typed-`query` legs now state the
sub-stream count `PARALLEL_BUDGET` actually planned**, computed arithmetically
rather than read off a shipped constant — `plan_partitions`' divisor is
`partition_bytes + max_source_span`, and `worker_count` floors `budget /
divisor`:

- `.xz`: `24 MiB` block + `1 MiB` chunk buffer = `25 MiB`; `+ 64 MiB` span =
  `89 MiB` divisor; `floor(1 GiB / 89 MiB) = 11`.
- Plain: `8 MiB` (`POOL_MAX_BYTES`, the pool's unhinted default — the query
  path's `LocalFileSource` is asked for its partitioning advice before the
  mapping pass's `hint_read_size` ever lands on it, so `BufferPool::slot_bytes`
  answers its own default rather than `ScanOptions::chunk_size`) `+ 64 MiB`
  span = `72 MiB` divisor; `floor(1 GiB / 72 MiB) = 14`.

Both numbers were checked against the STATUS row's own claim ("about eleven …
and fourteen") by tracing `plan_partitions`, `worker_count`,
`LocalFileSource::partitions` and `XzSource::partition_advice` in
`pgdump_query/src/stream.rs` and `pgdump_query/src/io.rs`, not re-derived
independently — they agree exactly, which is the check.

`scripts/measure.py` gained a `QUERY_SUBSTREAM_CAP` constant (beside
`PARALLEL_BUDGET`) and `run_parallel_scan_throughput` now appends
`· N sub-streams` to a typed-`query` cell on any row above four, where `N =
min(jobs, cap)`. This is a **formatting change, not a measurement change** —
it does not declare `scripts/measure.py` as one of the figure's own `depends`,
so it does not itself make the figure stale (`--stale` confirms
`parallel-scan-throughput` is not red after it), and it needed no re-run: the
wall-clock cells are unchanged from `tables.md`, only the trailing annotation
is new. The hand-computed pair is checked against the source once, the same
discipline `PARALLEL_JOBS`' literal 4 for `POOL_DEPTH` already uses, rather
than mirrored as a second formula that would go stale silently if either
constant moved.

## The comparison is unchanged: anchored at four workers, no constant moved

`PARALLEL_BUDGET` stays 1 GiB, `PARALLEL_MEMORY` stays 3g, `PARALLEL_JOBS` is
unchanged — `f7176a4`'s review already settled this and nothing here revisits
it. 1 GiB affords four sub-streams on the worst leg with room to spare
(`4 × 89 MiB ≈ 356 MiB`), which is the count `POOL_DEPTH` itself delivers on a
plain source and the one `16.14` ran its parallel leg at.

## Fold-in mechanics

- **The session-stamp accounting sentence** (`measure.sitting_accounting`) was
  regenerated by `--check` and pasted verbatim into `measurements.md`'s
  "Session stamp" paragraph, replacing `parallel-scan-throughput`'s `e29939c`
  with `20fd77c`. `STATUS.md` carries a hand-kept paraphrase of the same fact
  in three places (the "What exists" opening, the staleness narrative around
  `16.15`'s split, and the "Figures" summary) — none machine-checked, all
  updated by hand in this change.
- **`parallel-scan-throughput` and `parallel-peak-rss` no longer share a
  sitting commit.** They never shared a `shares` edge — `--check` already held
  that a shared commit is not one — so this costs nothing; `measurements.md`'s
  "Session stamp" paragraph now says why in place of the sentence claiming
  they were taken together, which stopped being true the moment only one of
  them was re-taken.
- **`docs/design/roadmap-P16-parallel-scan.md`** is the figure's one
  `quoted_by` consumer and was re-read for anything repeating this table's
  numbers. Nothing does: its references to `parallel-scan-throughput` are
  structural ("the remaining probe", "taken by `scripts/measure.py`, on the
  HDD, the SATA SSD and the NVMe, compressed and plain") rather than numeric,
  so nothing there needed a fold-in edit.
- **`--check` passes clean** (exit 0) with the fold-in applied: 21 of 21
  markers reconciled, the accounting sentence matches, no sitting problem, no
  miscount.
- **The table is the harness's own output, not a hand-edit of it.** The
  sub-stream annotation is a renderer change made *after* the readings were
  taken, so it reached `measurements.md` by re-rendering the sitting
  (`uv run measure.py --render runs/measure-20260908T183715`, `M73`) rather
  than by editing the pasted table. The doc's section is byte-identical to
  what that render emits, minus the fold-in scaffolding line the harness
  addresses to the folder-in.

  This is not incidental: the first attempt *was* hand-applied, and put both
  `.xz` sub-stream counts in the `.xz`, `parse` column — every number correct,
  attached to a leg that plans no sub-streams at all, while the leg the spec
  row named carried none. The prose two paragraphs below it said "both
  typed-`query` legs" throughout, and the table disagreed.
