## `M115`: the tree is reflowed and `cargo fmt --check` is green

`cargo fmt --check` had been red since `2e8bd7b` ("Renames for clarity"), which
pushed import lists and expressions past the 100-column limit and was never
re-run through `cargo fmt`. `3feeaff`, the commit before it, is clean under the
same `rustfmt 1.9.0-stable`, so it was a rename pass and not a toolchain bump or
a disagreement with `rustfmt.toml`.

`M115` is that reflow: 25 diffs across eleven files — `gather.rs`, `lib.rs`,
`map.rs`, `stream.rs`, `main.rs` and six test files — every one of them import
ordering or expression wrapping. No comment prose moved, `wrap_comments` being
off, so the humanization commits' wording was never what `cargo fmt` would
rewrite. Checked rather than assumed: each touched file's multiset of
identifier tokens is unchanged across the reflow, which leaves layout and
punctuation as the only thing that moved.

It went out-of-band rather than into `P14.1` because it touches eleven files
that slice does not, and folding it in would have buried a small diff under
twenty-five unrelated reflows ([`../../process.md`](../../process.md), "Working
unattended"). It blocked `P14` because the gate every slice lands through cannot
pass while it stands: a session reading `cargo fmt --check` against a remembered
count of 25 is separating its own errors from a baseline's by arithmetic.
**That baseline is now gone — the check is clean, and any diff it reports is the
session's own.**

## `M116`: `pgdq info` takes `--strict-identity`, and the flag means one thing everywhere

Reviewed under STATUS's "Decisions worth another look", where 14.3 filed the
call that `info` should not carry the flag. The entry is closed, the answer went
the other way, and the flag landed: **it has one meaning on every command**, so
`pgdq info --strict-identity=time --source X` refuses a cache whose bound signal
has moved, exactly as `parse` and `query` do.

The slice's reasoning was that a refusing `info` would remove the one command
that can say why the others stopped. **That mistakes a refusal for a silence.**
`Error::StrictIdentityUnmet` names the cache, the term that bound and the clause
that failed, so the refusal *is* the explanation, and the flag being **opt-in**
leaves the advisory report one omission away. The alternative cost a
command-shaped exception to a flag the spec describes as one question asked of
every provider
([`../../design/roadmap-P14-remote-input.md`](../../design/roadmap-P14-remote-input.md),
"D5").

`info` reads the whole `CacheStatus` through `cache::load` rather than
`CacheMode::load`, where the refusal lives, so the comparison moved out to
`CacheMode::strict_identity_refusal` and both callers ask it — the library still
owning it, which is D5's own reason for putting the selection on `CacheMode`.

**Cache-only `info` is a usage error, not a refusal.** With no `--source` the
identity is *null* rather than absent, and D5's "absence is a failure" never
reached it: absence is a source that exists and cannot answer, while asking for
a guarantee about a source nobody named is malformed. clap's
`requires = "source"` answers it before anything is opened.

The review also surfaced that the refusal explained itself without saying what
it *saw*, which was live for `parse` and `query` too and so took its own row —
`M117`, below.

## The oracle stays bespoke, and the gap it leaves is a stall and a conformance test

Reviewed under STATUS's "Decisions worth another look", where 14.4 filed the
call that the oracle was written against `std` where
[`../../design/roadmap-P14-remote-input.md`](../../design/roadmap-P14-remote-input.md),

**D6 now carries the whole argument** — the two knobs nothing that ships can

Two things the review settled that D6's text does not carry. **Containers were
not a gap in the record but a refusal in it**: D6 already read "no container, no
`mise` tool", and here they also want root (`CLAUDE.local.md`'s `sudo nerdctl`)

[`../../design/roadmap.md`](../../design/roadmap.md), "A test may assume the
tools `mise` pins" is satisfiable for a binary and not for a daemon. And **no
rule was written**: nothing here generalizes to writing a server over depending
on one.

**What a later session picks up**: the stalled origin, a missing knob rather
than a missing server, lands in **14.5** with D9's deadlines and D16's
cancellation race asserted against it; and **`M118`**, the opt-in, env-gated
conformance test against a real static origin that answers whether the oracle
encodes our own misreading of HTTP — the shape `CLAUDE.local.md` already sets
for the koji replica, and not a blocker for `P14`.

## `M112`: the batch span's floor is the chunk the caller announced

`MIN_SOURCE_SPAN` is struck. `plan_partitions` takes the replay's own
`ScanOptions::chunk_size_bytes` as the floor its derived span stops at
([`../../design/decisions.md`](../../design/decisions.md), "D84"), so the span
floors at the unit the source actually retains at any `--chunk-size` rather
than at the shipped `SCAN_CHUNK_DEFAULT_SIZE_BYTES`. D84's argument — one read
chunk — is unchanged; only the constant realizing it moved, which is why this
was a ledger row and not a spec amendment.

Pinned by `partitioned_replay::the_span_floors_at_the_announced_chunk_not_the_shipped_one`,
which asserts both floors on one shape: at a 64 KiB announced chunk, eight jobs
against a budget of exactly eight partition-units leave no room for a span at
all, so the floor is the whole answer — seven sub-streams at the announced floor
where the shipped one seats two and declines the other five in a
`ParallelismBudgetLimited` note, for bytes no batch pins.

**No figure moves.** Every `parallel-*` leg states no `--chunk-size`, so its
floor is the shipped default either way (`scripts/measure.py`,
`QUERY_SUBSTREAM_CAP`); `measure.py`'s comment now says which unit it is
reasoning about.

## A day's file is open to its own sessions, and the cap is 200

Reviewed under STATUS's "Decisions worth another look", where `M112` filed the
call that it had condensed an earlier section of this file to land under the
cap. The maintainer settled both halves: **a day's file may be condensed by the
sessions writing it**, and **the cap is 200 lines**, raised from 120.

The rule was never in conflict, only imprecise. "An entry carries yesterday's
truth and is not maintained **afterwards**" was already the wording; what the
repoint procedure and the keystone are forbidden is editing a **closed** day.
[`README.md`](README.md), "An entry carries yesterday's truth" now says so
outright — condensing today is writing it, rewriting yesterday is falsifying it
— which makes `M112`'s call correct rather than merely tolerated, and makes it
the expected way several sessions' worth of a day fits one file.

**The number had five copies and no handle** — twice in
[`../../process.md`](../../process.md), once in the `process` skill, twice in
`scripts/repoint.py`'s prose — so raising it anywhere but everywhere would have
left a trap. It is now stated once, in `README.md`, asserted by
`repoint.py`'s `HISTORY_LINES`, and cited without a number everywhere else.

## `M113`: the statistics allowance's two lines are pinned, and the decline test is off one

`statistics_allowance`'s floor is not `margin_allowance`'s, and neither of its
lines had a test. Both are pinned now, in `pgdump_query/src/io.rs` by
`statistics_are_starved_below_their_own_line_and_unfloored_above_the_crossover`:
the **zero line**, `MEMORY_UNPOOLED_BOUND × 100 / (100 − MEMORY_MARGIN_PERCENT)`,
at and below which the margin ceiling is zero whatever the budget; and the
**cap/ceiling swap** at `5 × (MEMORY_RESERVE − MEMORY_UNPOOLED_BOUND)`, below
which `ceiling − cap` survives every per-worker charge and above which a source
whose step divides the ceiling leaves the statistics nothing
([`../../design/decisions.md`](../../design/decisions.md), "D85"). Nothing else
would have noticed one of those three constants moving past another.

The decline test in `pgdump_query-cli/tests/statistics.rs` stated `--memory
335544320`, the zero line exactly — where `(a / 100) * 80` truncates to 16 bytes
under the bound, so the run it asserts on turned on the rounding direction of an
integer division it does not otherwise care about. It states `314572800` now,
20 MiB inside the band, and cites the unit test for where the line falls.

The rustdoc said the ceiling is zero *below* the line. It is zero *at* it too,
which the new test asserts first, and the comment now says so.

## `M114`: the narrowing note's remedy, and the origin clause follows the budget

Two corrections to text about what a memory knob buys, split out of `M112`.

**`BatchSpanNarrowed`'s remedy named the one lever the source it fires on does
not have.** The note is raised only where the span is charged, which is a
chunk-retaining source, and a plain one recommends no per-reader cost — so
`Parallelism::fit`'s zero-cost arm holds its budget at `DEFAULT_MEMORY_BUDGET`
for every allowance past the reserve plus that constant, and "raise the memory
budget" was inert wherever a user would read it (`KD32`). It now names the
sub-stream count first — the other term `derived_source_span` divides, and the
one a caller always states — and says a larger allowance is not a larger budget
on such a source ([`../../design/decisions.md`](../../design/decisions.md),
"D83").

**The origin clause follows the budget a note quotes, not its severity.**
`announce_plan_notes` appended it in the `warning:` arm, which held only while
every budget-quoting note was one; `BatchSpanNarrowed` is a `note:` and quotes
a budget, so it lost the half saying where that number came from — on a plain
source the only thing that says the carved budget is not the allowance typed.
`PlanNote::budget_bytes` is what the CLI now asks, pinned by
`stream::tests::a_note_quoting_a_budget_is_the_one_that_reports_it` against
each note's own sentence rather than a second list of kinds.

**`M119` is admitted, not landed.** `ParallelismBudgetLimited`'s own "raise the
memory budget to get more" is inert on a plain source for the same reason, and
was left outside a row that names one note.

## `M117`: the strict-identity refusal names the times it compared

`Error::StrictIdentityUnmet`'s clause was one of two `&'static str`s, so the
refusal said what failed and never what it saw. `WeakIdentity` now carries the
evidence out of the comparison that produced it — `Differs { cached, live }`
and `Absent { cached, live }`, as `SystemTime`s converted at
`SourceIdentity::weak_against` from L1's on-disk `(seconds, nanoseconds)` — and
`unmet` builds the sentence from them. The rendering is epoch seconds and
nanoseconds because nothing the library links carries a calendar, and
`date -d @<seconds>` reads it back.

`Absent` stopped overstating with it: reached when *either* side is silent, its
one clause said "neither it nor the source carries a modification time" in all
three cases, and it now names the silent side and the time the other one kept.

Pinned at both levels — `identity::strict_time_refuses_a_moved_mtime_and_a_missing_one`
asserts both epoch stamps against the file's own mtimes and covers the one-sided
silence, and the CLI's `info_refuses_a_moved_signal_under_strict_time_and_reports_without_it`
asserts the clause reaches stderr.
