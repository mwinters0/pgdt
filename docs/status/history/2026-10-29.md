## D121's reopening, reviewed: the chunk priced at the default count

`gzip-first-pass` at `9aa23e5a` read the 4 MiB chunk leg beating the shipped
chunk on GNU gzip's file at four jobs and level on the other three, which
meets D121's `Reopens` ([`../../design/measurements.md`](../../design/measurements.md),
"What a parallel gzip first pass buys"). Reviewed with the maintainer:

- **The shipped chunk is not changed on this reading.** One file of four, at
  a count that is not the default, from two builds whose layouts differ and
  with nothing attributing what moved it, is short of what a default rests
  on.
- **The leg was priced at a count nothing ships.** The spec prices the chunk
  "at one worker count" without naming it; the harness reads it at four, and the default is the physical
  count (D2), settled by the same figure.
- **The leg moves to the physical count**, one leg in place of the four-job
  one: it exists to price a constant that ships, and the four-job reading has
  no consumer once the default is physical.
- **Across the three sittings the four-job column moved toward the 4 MiB
  chunk** (`c4069143`, `eb3f9c7b`, `9aa23e5a`, in the commits' tables), and it
  was the 4 MiB build's rows that moved, the shipped chunk's four-job rows
  holding still. D125 and D126 landed between them; nothing attributes it.
- **A 4 MiB chunk enters a task's charge twice**, as the chunk and as its feed
  (`Chunking::task_bytes`, `pgdt_gzip_seek`'s `speculate::most_held`): 6 MiB
  a task more, by arithmetic, which the figure, affording every count its
  memory, never shows.
- **What switches it is a bar on the set of files**, each read by 15.7.1's
  bar: the 4 MiB chunk ships if it beats the shipped one on at least two of
  the three level-6 writers' files and is beaten on none, the level-1 file's
  included. One writer's gain does not move a default every task pays for,
  and a bar on all three is held up by a writer level for reasons that are
  not the chunk's. It is D121's `Reopens` now; the old one, any re-take on
  which a longer chunk beats, is what one file at one count tripped.
- **It is slice 15.20, before 15.7.2**, not an out-of-band row: it may change
  what P15 ships, so the admission rule keeps it out of the ledger, and the
  phase's record is written over the chunk it ends on. The spec's pricing
  clause now names the default count ("Slice order").
- **A switch inverts the leg** to cut the shipped 1 MiB rather than retiring
  it: D121's `Reopens` is a re-take, and a re-take that cannot read the
  length the entry rejects can never meet it.

## `M254`: the release build's clock pinned

- **Every step `release.py` runs in the image builds under `SOURCE_DATE_EPOCH=CLOCK`**, set by `ready_inside`
  whatever the step was handed. `CLOCK` is CI's v0.2.0 build time, the one value under which a build of that commit
  can reproduce CI's binary. **The clock is a line of the target directory's key** too: an object compiled before it
  kept its own `__DATE__`, cargo never rebuilding `libmimalloc-sys` for the variable, so every existing target
  directory — the release state's, the check's, each figure leg's — is cleared once, at its next step.
- **Accepted**: v0.2.0 built clean, and over state an earlier commit's build left, by this tree's `release.py` both
  give CI's x86-64 `pgdt` byte for byte (`runs/m254-clock/findings.md`).
- **`attach` refuses** CI's x86-64 archive unless it is the rehearsal's, and a rehearsal's x86-64 archive missing or
  archived at another commit's time, before anything is uploaded; D109 and `/release`'s step 5 say so.
