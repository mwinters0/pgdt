# 2026-09-01

## The acknowledgement register accounts for commits, and a path needs all of them

`excused_paths` has always required that **every** commit touching a declared
path be excused before the path counts as clean — the conservative direction,
and its own docstring says so. The consequence nobody had drawn: one unexamined
commit makes every earlier entry on that path **inert**, and an inert entry
appeared in no output at all. `--stale` built its "Acknowledged" block out of
the paths that came out clean, so an entry whose path was re-reddened by a later
commit was indistinguishable, from the outside, from an entry that had never
been written.

That is what happened. `a6e713f`'s entry was filed by `7cc2429` and covered the
four `parse`-shaped figures. `c614c4b` (11.4) then changed one line of
`stream.rs` — `project` cloning a comparison plan rather than copying it —
which made `a6e713f`'s excuse inert. 11.4 reasoned that `stream.rs` "has been a
changed declared path since `a6e713f`, so the stale set is the same eleven, for
the same reasons": true about the set, wrong about the register, which tracks
commits and not colours. A later session read `--stale`, saw four red figures
and no entry named, read 11.3's notes — which still said the entry had been
deferred, months of prose after it was written — and filed a decision entry
asking whether `a6e713f`'s acknowledgement should be written. It already was.

Three fixes, and the middle one is the one that pays:

- **`c614c4b` is acknowledged** for the same four figures. Its diff is a strict
  subset of `a6e713f`'s over the same paths, and the reachability argument
  transfers unchanged: `pgdq parse` enters `map_file`, which reaches neither
  `resolve_block` nor `project`, whose only non-test call sites are inside
  `table_stream`. The four are green; seven of thirteen figures remain stale.
- **`--stale` names an inert entry** under the figure it failed to clear, with
  the commits actually holding the path red (`measure.inert_excuses`). The
  register's own rule is now visible in the output someone is already reading,
  rather than only in a docstring they have to think to open. It immediately
  surfaced two more: `eca96be` is inert on `batch.rs` for `nested-end-to-end`
  and `cross-file-floor`, and `682819d` is inert on `preamble.rs` for
  `preamble-prepass` — both correct, both previously silent.
- **`acknowledged.py`'s docstring states the rule**, where the person writing
  an entry reads, with its two consequences: writing an entry does not mean the
  figure goes green, and a slice landing on an already-red declared path still
  owes an entry or a stated reason not to write one.

`M29` is the standing example of the second kind. It touched `batch.rs` with a
real `ColumnBuilder::UInt32` variant and its match arms, on the decode path, and
gets **no** entry: those figures were red anyway, but "red anyway" is not
evidence that a reading did not move, and writing an inert entry to tidy the
ledger is the over-broad-acknowledgement failure 11.3 named. What it earned
instead is a sentence in `STATUS.md` saying so, because silence is what makes
the next session re-derive this.

Ledger row: `M30`.

## A deficiency entry is struck when its last part closes, not at a phase wrap

The register had no closure rule. `process.md`'s five rules covered allocation,
stance, property-versus-deficiency, locality and reconciliation — every one
about an entry's birth and upkeep — and nine entries had been allocated since
the register was created without one ever being struck, so nothing had tested
the gap. `KD7` is what reached it: the P11 spec binds *"`KD7` is retired by this
phase, not narrowed"*, and its rows close on a schedule that ends at **11.6**,
with 11.7–11.10 still ahead. Waiting for the wrap would leave `STATUS.md`
asserting a divergence the code no longer has, for four slices, in the file
whose whole contract is the present tense.

So: **struck by the change that closes its last part**, mirroring allocation on
discovery rather than at a boundary. Partial closure rewrites the entry to what
is still true rather than annotating what was fixed — already the de facto
practice, since 11.4 rewrote `KD7` from five rows to four. A part that closes
*by statement* into a property migrates beside its mechanism instead of being
deleted, which is two of `KD7`'s rows. The strike is one atomic change, and
`deficiencies.py` already fails if index line, detail paragraph or code marker
is left behind.

**A watermark survives the strike.** `KD1`–`KD9` are allocated and none is
struck yet; the line exists because commit messages already cite these
identifiers — `c614c4b` says "the `KD7` source marker moves to
`ComparisonPlan::AS_TEXT`" — and after a strike `KD7` would otherwise resolve to
nothing, leaving a reader unable to tell "struck" from "typo". Same argument as
the out-of-band ledger's watermark, and `deficiencies.py` is purely relational,
so a numbering gap passes.

## A slice that anticipates closing an entry, and that entry, name each other

The forward reference alone rots: a slice list is rewritten as a phase is
grilled and re-sliced, and an entry naming a slice number quietly starts
pointing at work that no longer exists. Naming both directions makes the pair
self-checking — landing a slice is also the moment its entry is re-read, and a
split is obliged to re-target rather than leaving the pointer aimed at a number
whose meaning changed. It also answers at spec time the question a `(b)` stance
raises and cannot itself answer: *which* piece of the owning phase discharges
this.

`KD7` names 11.5 and 11.6; those slices name `KD7`. **The pointer breaking on a
split is the feature.** Wording it as a condition instead — "struck when
`char(n)` closes" — was rejected: it removes the cross-reference, so nothing
points from the entry into the slice list and landing a slice stops being a
register check. A condition that silently stays true is how the register drifts;
a slice number that goes wrong loudly is what forces the re-target. 11.6 is a
likely split — it has already absorbed 11.11's deferred `char(n)` trim, and P11
has earned four third-level slices — so this will be exercised.

`KD5`, `KD6` and `KD9` name phases that are sketched, not sliced, so they have
no slice to name yet. The obligation lands when those phases are sliced, which
is why it went in the `process` skill rather than only in `process.md`: the
skill is the trigger that fires at that moment.

## The pairing is reconciled, not owed

`deficiencies.py` carries a fourth relation, and it is the one whose *failure*
is the point. The other three catch an index that has drifted from its detail;
this one catches a slice list that has been rewritten out from under an entry —
which nothing else notices, because the entry still reads well and the slice
that took over the closure says nothing. So a re-slice now fails the check:
a renumbered slice leaves the entry naming an id the checklist does not list,
and a split that moves the closure leaves the named slice's line no longer
naming the entry.

Two boundaries decide where the obligation exists, and both are **read from
`STATUS.md` rather than configured**, so nothing has to be turned on:

- **A phase with no `## P<N> progress` checklist has not been sliced**, so an
  entry owned by it names no slice and is not asked to. `KD5`, `KD6` and `KD9`
  are that case today. Writing the slice list is what arms the check for them,
  which is the moment the obligation lands anyway.
- **A ticked line is a record, not a promise.** A landed slice's line still says
  which entry it closed, and by then the entry has been rewritten to what is
  still true or struck outright — so holding a ticked line to the pairing would
  force one of the two to lie. The slice-to-entry **back-pointer** reads unticked
  lines only; what a ticked line's `KD<k>` is instead held to is the section
  below. This is not hypothetical: 11.5's line will say it closed `KD7`'s
  text-held row long after `KD7` stops naming 11.5, and `KD7` will be gone
  entirely while 11.5 and 11.6 still name it.

A slice reference is hunted **scoped to the owning phase's own number** — `11.6`
for a `P11` entry, never a bare "looks like `<n>.<m>`" — because an entry's
prose carries figures, section numbers and doc names, and `roadmap-P11.3-…` is a
document rather than a claim about the slice list.

Ledger row: `M31`.

## A checklist line cites, an entry claims

The two halves of the slice pairing are held to different standards, because a
checklist line and an index entry are different kinds of artifact.

**A ticked line's `KD<k>` is a citation, and citations resolve against the
watermark.** A landed slice's line is a record of what happened — the same kind
of artifact as the commit message the register's "a spent number stays
resolvable" promise was written for — so it may name a struck entry, and may not
name a number nobody ever allocated. `M31` framed the exemption as a binary,
hold the line or exempt it, which missed that third option; full strictness was
rejected twice over, since it costs the record of which slice closed what and
would demand stripping exactly the citation the watermark exists to keep
resolvable.

**Resolution keys off the allocated range, not a list of struck names**, and
that is what lets a struck entry disappear at a keystone. Naming one is
provenance — it answers *when*, `git log` answers *when* — so it takes the
keystone's provenance disposition and is deleted, leaving the range behind
exactly as the out-of-band ledger leaves its high-water mark; a check reading a
named struck-list would break at the first keystone. Reading only the mark
tolerates both forms by construction: a number at or below it that the index
does not carry *is* struck, which is also what keeps "struck" tellable from
"typo" with nothing written down per entry. The mark is carried by an
`<!-- deficiency-watermark: … -->` marker rather than by the sentence stating
it, which is rewritten at every strike and again at that keystone — the
fragility `measurements.md` set its figure markers against. Deriving it as
`max(indexed)` was rejected: it breaks exactly when the highest-numbered entry
is struck, which is when it is needed. Allocating above the mark without moving
it fails, so a new entry bumps it. The named struck entries stay unparsed; a
contradiction between them and the index is visible in the sentence a reader is
already in.

**An entry naming a ticked slice is stale by construction**, and fails. The
exemption is one-directional: partial closure *rewrites the entry* in the change
that ticks the box, so "names a ticked slice" is never a valid resting state —
either that slice closed its part and the entry should no longer name it, or it
did not and the entry is aimed at the wrong slice. Making it an error is what
enforces the partial-closure rewrite mechanically, and that rule is the one most
likely to be skipped: striking an entry is a visible ceremony, rewriting one
because a single row closed is quiet. The two directions therefore pull opposite
ways on purpose — the entry is present-tense and may name only live slices; the
checklist line is a record and may cite spent numbers.

**A `(b)` entry's owner is read from the roadmap's phase index**, which carries
a `Complete` state set at the wrap, in the change that deletes the phase's
`STATUS.md` checklist. Without it a surviving entry owned by a wrapped phase
reverts to `M31`'s "no checklist means not sliced yet" and goes quiet at the
moment its pointer becomes most wrong — still naming a slice number that now
exists nowhere — and the distinction between *not yet sliced* and *sliced, run
and finished* is not in `STATUS.md` at all. An entry owned by a phase that is
`Complete`, `Struck`, or absent from the index therefore fails, and **the
failure says the entry drops to `(c)` unless a phase actually absorbs it**:
`(b)` means a named destination and a finished phase is not one, while inventing
an owner to preserve the stance manufactures intent nobody holds, which is the
failure the unowned rule was written against. Inferring completion from the
missing checklist plus a non-`Sketched` state was rejected — a phase that is
specified and not yet sliced carries neither, so the inference fires on a phase
that has not started. Keeping a completed phase's checklist in `STATUS.md`
until the keystone was the alternative to all of the phase-index work and needs
no parsing at all; it was rejected because a keystone lands once or twice in a
project's life while phases complete routinely, so the ticked boxes accumulate,
putting chronology back into the document the keystone exists to take it out of.

**The phase-index read is pinned at both ends, so no transition can half
happen.** A wrap sets `Complete` and deletes the checklist; a slicing sets
`Current` and writes one. The rule is that a phase carrying a `## P<N> progress`
checklist is `Current` and a `Current` phase carries one — which makes a wrap
that deleted the checklist and forgot the cell visible as `Current` with nothing
under it, and a slicing that wrote the checklist and forgot the cell visible as
`Specified` with a checklist under it.

`M32` landed only the `Complete` half of that and wrote the other half down as
an edge it could not close, costing the closure as a new `Sliced` state and
rejecting it as an index edit at slicing time with nothing else pulling a
session to that table. Reviewing the entry it raised turned up the fact that
undoes the rejection: **`Current` was already in the vocabulary, meaning exactly
"sliced and in flight", and used by no row** — it appeared only in
`process.md`'s prose list and `roadmap.md`'s state sentence. So the
`Specified`/`Sliced` split was the same rule under a new word, and the closure
costs one cell that the wrap's mirror image already pays. `P11`, sliced and in
flight, was carrying `Specified; open` and now carries `Current`.

`deficiencies.py` holds that pairing in both directions, over the phase index
and the checklist parsers it already had: a checklist under a row the index
calls anything but `Current` fails, and so does a `Current` row with no
checklist, each naming the phase and the half that is missing. A checklist
under a phase the index does not list at all fails the same way, since a phase
carrying one is `Current` and an unlisted phase is nothing.

**Two calls in `M32`'s phase-index read were reviewed and affirmed unchanged**,
with the reasoning now in `deficiencies.py`'s docstring beside the mechanism.
An unrecognised state word stays an error rather than a guess in either
direction — reading it as *still running* fails open on the silence `Complete`
was added to end, and reading it as *finished* keeps that property but invents a
claim about a phase somebody deliberately marked something else. And an
unreadable cell still fails the whole run rather than only the `(b)` entries
that resolve against it: consulting the index lazily would surface a malformed
row only when something happened to point at it, going quiet exactly when the
register is healthiest, which is the failure `--stale`'s inert-entry rule was
written against. The accepted cost is that a roadmap edit touching no deficiency
can fail the register check.

Ledger rows: `M32`, and `M33` for the pairing.

## `pg_dump` pins `IntervalStyle`, and I4 said the opposite

`pg_dump.c` runs `ExecuteSqlStatement(AH, "SET INTERVALSTYLE = POSTGRES")` on
its source connection, immediately after `SET DATESTYLE = ISO` and under the
comment *"Likewise, avoid using sql_standard intervalstyle"* — at v13 through
v18, guarded at v13 alone by a `remoteVersion >= 80400` every supported server
exceeds. I4 claimed the setting was never made and concluded that "an
`interval` value's text is in the server's default style and is **not**
determined by the file"; the committed fixtures already contradicted it, since
all six majors write `1 year 2 mons 3 days 04:05:06` for a value inserted as
`1 year 2 months 3 days 04:05:06`, which is the `postgres` style.

Two decisions rested on the false half. **11.5's `interval` comparison needed
it and could not have shipped without it**: a value that might be
`1 day 02:03:04` or `P1DT2H3M4S` with nothing in the file to say which cannot
be parsed at all. I4 is amended and I40 states the grammar.

**The `interval` type *mapping*'s stated rationale is also gone.** The mapping
table's cell read "`IntervalStyle` is never recorded (I4) — the file does not
determine the value", and that was the whole argument for `Utf8View`. Arrow's
`Interval(MonthDayNano)` carries PostgreSQL's months, days and microseconds as
three independent fields, so the mapping is open rather than blocked. 11.5 did
not take it — a mapping change moves the schema every consumer sees and every
snapshot asserts, which is not the review a comparison slice should carry — and
the table now says so plainly. Filed under STATUS's "Decisions worth another
look".

## `jsonb`'s register row cannot close the way P11's spec promised

The phase doc's closure table put `jsonb` with `interval` and the network types
as "closed by code, one comparison per type". `compareJsonbContainers` is
structural and would be, except for its leaves: `compareJsonbScalarValue`
passes `DEFAULT_COLLATION_OID` to `varstr_cmp` for every `jbvString`, and
object *keys* arrive at that same call. The database's collation is the one
thing a plain dump does not record (I32), so a structurally correct `jsonb`
comparison still diverges wherever a string decides it — the text row's residue,
one level down.

The spec's closure table is amended to say so, and `jsonb` becomes **11.5.1**
rather than riding in on 11.5: it is a recursive container walk with a JSON
parser behind its literal side, which is a different review from "`inet`
compares by family then bits". `KD7` is retargeted at 11.5.1 and 11.6.

## `M34`: the comparison oracle asks a column, not a cast

`comparison_oracle.py`'s `pgdq_cmp` builds a temp table declared
`(a <typ>, b <typ>)` per case, inserts the two literals through the same `text`
coercion as before, and asks `a <op> b`. A case that names a collation declares
it on the columns, which is where a dump writes one (I37); a case that names
none gets the column's `attcollation`, which is the declared type's own
default — what a bare column in a dump has.

**A cast cannot answer the question a bare case poses.** The shape it replaces
is `EXECUTE format('SELECT ($1::%s%s) %s ($2::%s%s)', …) USING lhs, rhs` with
`lhs`/`rhs` of type `text`, and a cast derives its collation from its *input*,
so `$1::name` is compared under the parameter's `default` rather than under
`name`'s own `C` type default (`pg_type.dat`, `typcollation => 'C'`). Both
spellings on one PostgreSQL 16.15 session (the koji replica, `datcollate`
`en_US.UTF-8`), same database, same statement block, beside a bare `name`
column and that column's collation: `f | t | t | "C"`.

```
via-text-param|f      -- pg_temp.c('name','A','a','<'), the cast shape
via-literal|t         -- 'A'::name < 'a'::name
```

Only `name` was reached among the cases, and the bound was the case table's
rather than the defect's: every other collatable case states a collation
explicitly and an explicit `COLLATE` overrides the derived one. That is also
why it survived 11.2.1's reconciliation and 11.11.1's relabelling — both were
about which arm a case joins to, not about what the server was asked. It was
found by running the register against every committed cell — 2454 ordered pairs
over all types and all six majors — as a throwaway Rust test during 11.5, which
is the check nothing in the tree performs; two families mismatched, `jsonb`
(the open row, above) and `name`.

**The cost is an oracle pass, not a fixture rebuild.** `--skip-dumps` writes
`fixtures/<major>/oracle/{comparisons,literals,meta}.tsv` and nothing else —
eighteen files, no dump touched — against the six pinned images, in 57 s for
all six majors.

**Four families of cell moved. Three share a mechanism and split into two
populations, which is the distinction that decides whether anything is owed.**
`interval`'s infinities are `values`, so their move is on ordinary value rows:
on 13–16 the literal is genuinely refused, `literals.tsv` has always said so,
and the old `u` was the planner answering in the server's place. That half is a
defect the column form fixed, and the differ seeing the 16→17 transition is the
evidence. `json`'s `{a:1}`, `xml`'s `<a>` and `empty_enum`'s `x` are `inputs`,
paired against `values[0]` by `comparison_cases()`: those rows are now a
mechanical function of `literals.tsv` — 111 of 1792 rows on 16 — and they are
kept deliberately, because that redundancy is the only place two separately
generated halves of the oracle are forced to agree. The reason is in
`comparison_cases()`'s docstring, where someone shrinking the file will meet
it. Nothing was lost with them: `E42883` still records "this type has no
comparison operator" on all sixteen valid `json` rows and all nine valid `xml`
ones.

`name`'s two
ordered pairs over `A` and `a` answer bytewise. The other three follow from the
pair being built before it is compared, so a literal the server refuses answers
all six cells with its own rejection instead of with whatever the comparison
happened to do: `interval`'s infinities against SQL NULL read `E22007` on 13–16
rather than `u`, `public.empty_enum`'s `x` against SQL NULL reads `E22P02`, and
`json`'s `{a:1}` and `xml`'s `<a>` read their own `E22P02`/`E2200N` rather than
the missing operator's `E42883`. Fifty-two rows, and what replaces them is a
property `test_comparison_oracle.py` asserts against `literals.tsv`: a refused
literal answers every cell of every comparison it appears in, the left side
winning where both are refused. Downstream that is 24 additive cells added to
`fixtures/oracle-differences.tsv` at 16→17 — the `interval` infinity-against-NULL
pairs a planner fold used to hide — for 533 differences, still every one
additive.

**The two `u`s had unrelated causes, and both read as answers.**
`eval_const_expressions` replaces a strict comparison holding a constant NULL
argument with a NULL constant *without* evaluating the other argument; whether
that argument had already raised depends on its input function's volatility.
`numeric`'s is immutable and folded, raising at plan time; the datetime
family's and `enum_in`'s are stable, so they did not fold and the bad literal
was never reached. `json` and `xml` are the second cause: with no `<` for the
type the statement fails at analysis time, ahead of its own malformed literal.

**`public.text_c` joins the cases** — the domain declared `AS text COLLATE
"C"`, and the one type in the oracle's schema whose collation comes from
neither an explicit clause nor `default`, which makes it the case that would
have caught the cast. It parses as a `Domain` and lands on the existing
`user/Domain` arm beside `base_domain`, `derived_domain` and `box_domain`: 37
arms, 54 cases, both directions green, no register change.

*Rejected: inlining the literals.* `format('SELECT (%L::%s) …')` derives no
collation either, since an unknown literal has none to give, and it is a much
smaller diff. It swaps every case from a cast-from-`text` to the type's input
function, so any cell may move — and the property worth having here is that the
diff is confined and checkable, not that it is small.

*Rejected: emitting the type's `typcollation` as an explicit `COLLATE`.*
Cheapest of the three, and it reads the catalog rather than our claim, so it is
not simply the relabelling already rejected. It still asserts that a column
inherits `typcollation` instead of observing that it does, and that step is the
one under scrutiny.

Ledger row: `M34`.

## `M35`: the register is asserted against the oracle's answers, cell for cell

The comparison oracle exists so that "the register agrees with PostgreSQL" is
verifiable rather than asserted, and until now nothing committed verified it.
`oracle_register.py` reconciles register *arms* against oracle *cases* in both
directions; `oracle_differences.py` reconciles majors against each other. Both
are about which rows exist. Nothing compared an answer to an answer, and `M34`
was the second defect that gap let through — both were found by a throwaway
Rust test run during 11.5, which walked the register over every committed cell
and reported two mismatching families: `name`, which `M34` fixed, and `jsonb`,
which 11.5.1 fixed.

That walk is now `the_register_answers_every_committed_oracle_cell`, a unit
test in `predicate.rs`, and what it is and what it skips is filed in
`architecture.md`, "The register against the oracle's answers". Three calls in
it are worth having written down:

**Both sides are put in the type's own `*_out` form.** Using the case's *input*
spelling instead would have reported the filter grammar's deliberate
strictness — a literal is accepted only as the type's own output spelling — as
an ordering disagreement, over `integer`'s ` 42 `, `oid`'s `-1` and every other
non-canonical input the oracle deliberately carries.

**The exception set is enumerated by pair, not by divergence class.** The
smaller rule — permit any disagreement on a column that announces an
`OrderingDivergence` — is churn-free and was rejected because it lets a `jsonb`
structural regression hide behind an announcement that is only ever about the
string leaves. What is kept from it is the second half: a disagreeing column
must still announce, so an exception cannot be claimed for a column the
register says it is confident about.

**The test lives in `src/`, not `tests/`.** `resolve_term` and `compare_keys`
are `pub(crate)`; exporting them so the test could sit beside the other
fixture-driven suites would widen the public surface for a test's convenience.

Landing it took the `jsonb` cases with it, for the reason below.

## `interval` keeps its `Utf8View`, for a reason the file can state

11.5 corrected I4 and left the type-mapping row's rationale gone: `pg_dump`
pins `INTERVALSTYLE = POSTGRES`, so "the file does not determine the value" was
never true. The row's replacement reason is the value space, not the format.

`Interval(MonthDayNano)` matches PostgreSQL's `Interval` field for field —
months, days, and a time part — and fails to hold two values a dump can carry.
v17's `infinity`/`-infinity` set every field extremal (`timestamp.h`'s
`INTERVAL_NOBEGIN`/`INTERVAL_NOEND`) and have no Arrow encoding at all. And the
time part is microseconds where Arrow's is nanoseconds in the same `int64`, so
the representable span is a thousandth: verified on 16.15, `interval
'2562047:00:00'` is 9.2233692e18 ns and fits, `'2562048:00:00'` overflows, and
`interval '100000000 hours'` is legal, unnormalized and thirty-nine times over.

**The ADBC driver takes the mapping and pays with an error.**
`PostgresCopyIntervalFieldReader` guards the multiply against
`kMaxSafeMicrosToNanos` and returns `EINVAL`, failing the batch rather than the
value; an infinite interval's time field is `INT64_MAX`, so it errors there too
— by a message about nanosecond overflow, since the driver has no infinity case
and predates v17.

*Rejected: mapping it and making both a `FieldDecode`, as `numeric(p,s)` does
for `NaN`.* It behaves better than ADBC — one value lost, not a batch — and was
the strongest argument for taking the mapping. What separates the two rows is
the typmod: it is a promise about the range, which is what makes `Decimal128`'s
residue rare by construction. `interval` has no typmod, nothing bounds how often
the fallback fires, and that is precisely why bare `numeric` is `Utf8View` one
row above.

**What settles it per column is a census, and it is filed at P10.** Whether a
given column holds either value is answerable from its values, and a pass that
already reads every value to summarize it computes the answer for nothing. The
objection — that it makes the Arrow type data-dependent — is one this project
has already accepted for the array-shape census, where `List<T>` against
`List<List<T>>` is no smaller a difference. So the mechanism and the objection
share a precedent, and the reason not to build it here is cost rather than
principle: a scan taken for this alone buys one type.

I40 gains the ceiling that carries this — the hour field is unbounded above
literally, nothing normalizes hours into days, and the true bound is the
struct's `int64` microseconds.

## `M35` absorbs the `jsonb` container cases, and an oracle diff was never expensive

11.5.1 closed the `jsonb` register row against 972 existing oracle cells and
left six load-bearing facts — the boolean and string kinds, an object's pair
count deciding before its keys, storage order differing from alphabetical, and
the raw-scalar anomaly behind `'1'::jsonb > '[]'::jsonb` — backed only by the
container probe in I41's **Observed** paragraph. The call not to add oracle
cases rested on a cost that does not exist.

**Adding an oracle case touches no `.sql` file.**
`generate_fixtures.py --skip-dumps` regenerates `fixtures/<13–18>/oracle/` and
nothing else: 18 TSVs plus `oracle-differences.tsv`, in 62 seconds over six
containers. `architecture.md`'s "Fixtures" says so outright — `--skip-dumps` is
the ordinary way to re-take the oracle *because* a dump regeneration is not
byte-reproducible, so touching the `.sql` tree to change an answer table would
bury the change in noise. The "cannot share a review with a library change"
rule that the call invoked is about the `.sql` tree, and `M34` shared an oracle

**The value is not the cross-major differ.** Upstream froze the raw-scalar
anomaly with a comment in v18, and the 220 new rows per major moved no cell
across any adjacent pair — the differences file is unchanged at 533. What the
cases are worth is that `M35` executes them: an oracle cell was Python-side
evidence, and is now an assertion against `predicate.rs`.

So the cases folded into `M35` rather than earning their own number, and
`jsonb` went from 6 values to 16, chosen one per branch of
`compareJsonbContainers` rather than as a sample. Two traps were worth naming
and both are now in the case table's own comment: `false < true` needs both
booleans, not just `true`; and "count decides before members" needs the
one-pair object's key to sort *after* the two-pair object's
(`{"zzz": 1}` against `{"y": 3, "zz": 4}`), or the count and the key comparison
point the same way and the case proves nothing. The grid is all-pairs, so each
value added is quadratic: 16 values put `jsonb` at 266 of `comparisons.tsv`'s
2020 rows.

**The general fact behind this is filed beside the reconciliation.**
`oracle_register.py` joins arms to cases by *existence*, so an arm whose cases
exercise one branch of a multi-branch comparison passes exactly as one whose
cases exercise all of them — `jsonb`'s arm counted as covered by cases reaching
four of six kinds and no container structure. That is a property of the join
rather than a defect: a branch-coverage check over a `match` in another language
is not something it can become. It is written into `architecture.md`, "The
register-to-oracle reconciliation", because the preamble's "an arm added with no
case is a claim nothing checks" reads stronger than the check is, and that
sentence is what let 36 cells look sufficient.
