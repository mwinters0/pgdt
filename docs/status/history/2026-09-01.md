# 2026-09-01

## The acknowledgement register accounts for commits, and a path needs all of them

`excused_paths` has always required that **every** commit touching a declared
path be excused before the path counts as clean — the conservative direction,
and its own docstring says so. The consequence nobody had drawn: one unexamined
commit makes every earlier entry on that path **inert**, and an inert entry
appeared in no output at all. `--stale` built its "Acknowledged" block out of
the paths that came out clean, so an entry whose path was re-reddened by a later
commit was indistinguishable, from the outside, from an entry that had never
been written.

That is what happened. `a6e713f`'s entry was filed by `7cc2429` and covered the
four `parse`-shaped figures. `c614c4b` (11.4) then changed one line of
`stream.rs` — `project` cloning a comparison plan rather than copying it —
which made `a6e713f`'s excuse inert. 11.4 reasoned that `stream.rs` "has been a
changed declared path since `a6e713f`, so the stale set is the same eleven, for
the same reasons": true about the set, wrong about the register, which tracks
commits and not colours. A later session read `--stale`, saw four red figures
and no entry named, read 11.3's notes — which still said the entry had been
deferred, months of prose after it was written — and filed a decision entry
asking whether `a6e713f`'s acknowledgement should be written. It already was.

Three fixes, and the middle one is the one that pays:

- **`c614c4b` is acknowledged** for the same four figures. Its diff is a strict
  subset of `a6e713f`'s over the same paths, and the reachability argument
  transfers unchanged: `pgdq parse` enters `map_file`, which reaches neither
  `resolve_block` nor `project`, whose only non-test call sites are inside
  `table_stream`. The four are green; seven of thirteen figures remain stale.
- **`--stale` names an inert entry** under the figure it failed to clear, with
  the commits actually holding the path red (`measure.inert_excuses`). The
  register's own rule is now visible in the output someone is already reading,
  rather than only in a docstring they have to think to open. It immediately
  surfaced two more: `eca96be` is inert on `batch.rs` for `nested-end-to-end`
  and `cross-file-floor`, and `682819d` is inert on `preamble.rs` for
  `preamble-prepass` — both correct, both previously silent.
- **`acknowledged.py`'s docstring states the rule**, where the person writing
  an entry reads, with its two consequences: writing an entry does not mean the
  figure goes green, and a slice landing on an already-red declared path still
  owes an entry or a stated reason not to write one.

`M29` is the standing example of the second kind. It touched `batch.rs` with a
real `ColumnBuilder::UInt32` variant and its match arms, on the decode path, and
gets **no** entry: those figures were red anyway, but "red anyway" is not
evidence that a reading did not move, and writing an inert entry to tidy the
ledger is the over-broad-acknowledgement failure 11.3 named. What it earned
instead is a sentence in `STATUS.md` saying so, because silence is what makes
the next session re-derive this.

Ledger row: `M30`.

## A deficiency entry is struck when its last part closes, not at a phase wrap

The register had no closure rule. `process.md`'s five rules covered allocation,
stance, property-versus-deficiency, locality and reconciliation — every one
about an entry's birth and upkeep — and nine entries had been allocated since
the register was created without one ever being struck, so nothing had tested
the gap. `KD7` is what reached it: the P11 spec binds *"`KD7` is retired by this
phase, not narrowed"*, and its rows close on a schedule that ends at **11.6**,
with 11.7–11.10 still ahead. Waiting for the wrap would leave `STATUS.md`
asserting a divergence the code no longer has, for four slices, in the file
whose whole contract is the present tense.

So: **struck by the change that closes its last part**, mirroring allocation on
discovery rather than at a boundary. Partial closure rewrites the entry to what
is still true rather than annotating what was fixed — already the de facto
practice, since 11.4 rewrote `KD7` from five rows to four. A part that closes
*by statement* into a property migrates beside its mechanism instead of being
deleted, which is two of `KD7`'s rows. The strike is one atomic change, and
`deficiencies.py` already fails if index line, detail paragraph or code marker
is left behind.

**A watermark survives the strike.** `KD1`–`KD9` are allocated and none is
struck yet; the line exists because commit messages already cite these
identifiers — `c614c4b` says "the `KD7` source marker moves to
`ComparisonPlan::AS_TEXT`" — and after a strike `KD7` would otherwise resolve to
nothing, leaving a reader unable to tell "struck" from "typo". Same argument as
the out-of-band ledger's watermark, and `deficiencies.py` is purely relational,
so a numbering gap passes.

## A slice that anticipates closing an entry, and that entry, name each other

The forward reference alone rots: a slice list is rewritten as a phase is
grilled and re-sliced, and an entry naming a slice number quietly starts
pointing at work that no longer exists. Naming both directions makes the pair
self-checking — landing a slice is also the moment its entry is re-read, and a
split is obliged to re-target rather than leaving the pointer aimed at a number
whose meaning changed. It also answers at spec time the question a `(b)` stance
raises and cannot itself answer: *which* piece of the owning phase discharges
this.

`KD7` names 11.5 and 11.6; those slices name `KD7`. **The pointer breaking on a
split is the feature.** Wording it as a condition instead — "struck when
`char(n)` closes" — was rejected: it removes the cross-reference, so nothing
points from the entry into the slice list and landing a slice stops being a
register check. A condition that silently stays true is how the register drifts;
a slice number that goes wrong loudly is what forces the re-target. 11.6 is a
likely split — it has already absorbed 11.11's deferred `char(n)` trim, and P11
has earned four third-level slices — so this will be exercised.

`KD5`, `KD6` and `KD9` name phases that are sketched, not sliced, so they have
no slice to name yet. The obligation lands when those phases are sliced, which
is why it went in the `process` skill rather than only in `process.md`: the
skill is the trigger that fires at that moment.

## The pairing is reconciled, not owed

`deficiencies.py` carries a fourth relation, and it is the one whose *failure*
is the point. The other three catch an index that has drifted from its detail;
this one catches a slice list that has been rewritten out from under an entry —
which nothing else notices, because the entry still reads well and the slice
that took over the closure says nothing. So a re-slice now fails the check:
a renumbered slice leaves the entry naming an id the checklist does not list,
and a split that moves the closure leaves the named slice's line no longer
naming the entry.

Two boundaries decide where the obligation exists, and both are **read from
`STATUS.md` rather than configured**, so nothing has to be turned on:

- **A phase with no `## P<N> progress` checklist has not been sliced**, so an
  entry owned by it names no slice and is not asked to. `KD5`, `KD6` and `KD9`
  are that case today. Writing the slice list is what arms the check for them,
  which is the moment the obligation lands anyway.
- **A ticked line is a record, not a promise.** A landed slice's line still says
  which entry it closed, and by then the entry has been rewritten to what is
  still true or struck outright — so holding a ticked line to the pairing would
  force one of the two to lie. The slice-to-entry direction reads unticked
  lines only. This is not hypothetical: 11.5's line will say it closed `KD7`'s
  text-held row long after `KD7` stops naming 11.5, and `KD7` will be gone
  entirely while 11.5 and 11.6 still name it.

A slice reference is hunted **scoped to the owning phase's own number** — `11.6`
for a `P11` entry, never a bare "looks like `<n>.<m>`" — because an entry's
prose carries figures, section numbers and doc names, and `roadmap-P11.3-…` is a
document rather than a claim about the slice list.

Ledger row: `M31`.
