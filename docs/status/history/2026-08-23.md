## Phase 2.4: PostgreSQL's float formatting, tracked down from a live mismatch to its source

The mapping table's I4 (`extra_float_digits = 3` guarantees an exact
round-trip) says nothing about *when* PostgreSQL's `float4out`/`float8out`
switch from fixed-point to scientific notation, and Rust's own `Display`
never makes that switch at all (it always prints full fixed-point, however
many digits that takes) — exactly the failure mode "Testing the mapping's
correctness" in `roadmap-phase2-typed-columns.md` calls out for the
round-trip test to catch.

Querying a spread of values against a live `postgres:16-alpine`
(`1e14` vs `1e15`, `1e5` vs `1e6`, `123456789012345` vs `1234567890123456`,
`1.5e-4` vs `1.5e-5`) showed the switch tracks the exponent against a fixed
threshold (6 for `real`, 15 for `double precision`) rather than the
shortest-round-trip digit count — `1234567890123456` (16 digits, exponent
15) goes scientific while `123456789012345` (15 digits, exponent 14) stays
fixed. Reading `src/common/f2s.c`/`d2s.c` (PostgreSQL's Ryu-derived shortest-decimal
formatter) confirmed it outright: `exp >= -4 && exp < 6` / `< 15`, literal
constants, checked in before any digit-count logic runs. Recorded as
`postgres-invariants.md` I14, which is what `decode::render_f32`/`render_f64`
now implement — Rust's own `{:e}` formatting supplies the same shortest
digits (checked digit-for-digit against every value queried here), so only
the fixed-vs-scientific placement decision needed reimplementing.

`decode.rs`'s `float_formatting_matches_postgresql_exactly` test pins the
exact cases captured live.

## Phase 2.4: PostgreSQL's own maximum timestamp overflows this build's Arrow mapping

PostgreSQL's documented maximum timestamp, `294276-12-31 23:59:59.999999`, is
defined relative to *its* internal epoch (2000-01-01). Arrow's
`Timestamp(Microsecond)` stores `i64` microseconds since the Unix epoch
(1970-01-01) — 30 years earlier — so the identical 64-bit budget is used up
about 30 years sooner when counted from 1970 than from 2000. Direct
computation (`i64::MAX` microseconds, converted back to a calendar date) puts
the true representable ceiling at `294247-01-10`, not PostgreSQL's own
maximum.

This means PostgreSQL's own maximum timestamp value is a **real, expected**
`Error::FieldDecode` under this mapping — not a bug, and not something a
different decode algorithm could fix, since it's a genuine capacity
mismatch between the two epochs sharing one 64-bit width. Every other
boundary value in `fixture_schema_types.sql`'s `t_timestamp` table
(`0001-01-01`, `9999-12-31`, the `0044-01-01 BC` era case, six-digit
fractional seconds) round-trips fine; only this one specific value, right at
PostgreSQL's own ceiling, doesn't. Pinned as
`postgresqls_own_max_timestamp_overflows_the_unix_epoch_i64_range` in
`decode.rs` so a future reader sees it as a documented property of the
mapping rather than rediscovering it as a test failure.

No action taken beyond documenting it — `Timestamp(Microsecond)` since the
Unix epoch is standard Arrow, not a choice this project made freely, and the
30-year gap is a few-nanosecond fraction of the representable range's total
span either way.

## Phase 3 grilling: measurements of the non-`COPY` content Phase 3 has to map

The koji sample's full-scan log (`runs/koji-scan.log`, 74 blocks, 784,019,857,152
bytes) fixes the sizes Phase 3's cost argument turns on. Gaps computed from the
logged `header offset`/`end offset` pairs:

| Region | Bytes |
|---|---|
| Preamble (file start → first `COPY` header) | 63,333 |
| 73 inter-block gaps | 6,440 total; min 78, max 102, mean 88 |
| Tail (last `COPY` block → EOF) | 87,855 |
| **All non-`COPY` bytes** | **157,628 — 0.00002% of the file** |

An inter-block gap in a dump with no large objects is just a TOC comment plus
blank lines. The whole DDL surface of a 784GB dump fits in 154KB, so running a
line-oriented grammar over every gap is unmeasurable against the scan itself.
Large objects (I12) and `--inserts` output are the two shapes that break this;
koji has neither.

koji's post-data TOC types: 191 `FK CONSTRAINT`, 112 `CONSTRAINT`, 59 `INDEX`,
34 `ACL`, 30 `SEQUENCE SET` (data-section entries that sort after all table
data, so they land in the tail). Its pre-data: 75 `TABLE`, 30 each of
`SEQUENCE`/`SEQUENCE OWNED BY`/`DEFAULT`, 8 `FUNCTION`, 2 `SCHEMA`, 1 `TYPE`,
1 `DATABASE`.

## The TOC `Type:` vocabulary is closed and enumerable from source

`pg_dump`'s TOC header comment (I3) carries `Name`, `Type`, `Schema`, and
`Owner` for every object it emits, and the `Type` field's value set is finite:
57 string literals assigned to `ArchiveEntry.description` across
`src/bin/pg_dump/*.c`, plus seven computed values — `reltypename` ∈ {`TABLE`,
`VIEW`, `MATERIALIZED VIEW`, `FOREIGN TABLE`}, `keyword` ∈ {`FUNCTION`,
`PROCEDURE`, `CHECK CONSTRAINT`, `CONSTRAINT`} — for a universe of ~63 kinds.

Re-derive with:

```sh
grep -rhoP '\.description = "\K[^"]+' src/bin/pg_dump/*.c | sort -u
grep -n 'reltypename = \|keyword = ' src/bin/pg_dump/pg_dump.c
```

Verified against v18.6.

## koji's role and privilege references, as the role-discovery use case sees them

`Owner:` appears on every TOC header: 590 `koji`, 14 `postgres`. Statement-level:
105 `OWNER TO koji`, 12 `OWNER TO postgres`, 30 `GRANT SELECT ... TO backup`,
1 `GRANT ALL ... TO koji`, 12 `GRANT SELECT ... TO PUBLIC`.

So restoring koji needs exactly three roles — `koji`, `postgres`, `backup` — and
`backup` is reachable *only* through post-data `GRANT` statements, which is the
concrete case for scanning past the first `COPY` block. `PUBLIC` is a pseudo-role
and must not be reported as one.

## The TOC comment has an optional `Tablespace:` field, and a variable-height body

`_printTocEntry()` (`pg_backup_archiver.c`) appends `; Tablespace: <name>` to
the `-- Name: …` line whenever the entry has a non-empty tablespace and
`--no-tablespaces` was not given. It is the per-object record of tablespace
placement; the statement side carries it as `SET default_tablespace = …;`
emitted by `_selectTablespace()` ahead of the definition. Phase 3's tablespace
cross-reference reads both.

Under `pg_dump --verbose` the comment block also gains `-- TOC entry <id>
(class <oid> OID <oid>)` and, when the entry has dependencies, `--
Dependencies: <ids>` — so the block is three lines at minimum but not a fixed
height, and a parser must read to the closing `--` rather than assume an
offset.

## The file prologue and epilogue are archiver framing, not TOC entries

Neither is announced by a `-- Name:` header, so a TOC-driven reader sees them
as unattributed. Prologue, in order: the `--\n-- PostgreSQL database dump\n--`
banner, `\restrict <token>`, the two version-header comment lines (I9), then
the `SET`/`SELECT pg_catalog.set_config` block — 11 statements at v18.6,
written by `_doSetFixedOutputState()` directly rather than as archive entries.
Epilogue: the `-- PostgreSQL database dump complete` banner and `\unrestrict
<token>`. The `ENCODING`, `STDSTRINGS` and `SEARCHPATH` TOC descriptions exist
in the vocabulary but never surface as headers in plain output for this reason.

## Object layout between TOC entries is regular

`--\n-- Name: …\n--\n\n`, then the definition, then a blank line, then any
`ALTER … OWNER TO` for the same entry, then a blank line before the next
entry's opening `--`. Definitions within one entry are separated by two blank
lines. This regularity is a convenience for a span-boundary rule, not a
guarantee to depend on — nothing in `pg_dump` promises the blank-line counts.

## The Phase 2 statement accumulator is not yet safe for arbitrary statements

`preamble.rs`'s `statement_complete` tracks paren depth and single-quoted
strings (including `''` doubling) and requires a trailing `;`. Two shapes
defeat it:

- **`--` line comments inside a statement.** An apostrophe in comment prose
  (`-- it's here`) opens a string that never closes, so the statement never
  completes and every following line is absorbed into it.
- **Double-quoted identifiers containing an apostrophe** (`CREATE TABLE
  public."it's" (…)`) — same failure.

Neither is reachable today: the accumulator only ever starts on one of five
`CREATE`/`ALTER TYPE` trigger keywords, and `pg_dump` emits none of those
shapes for them. Phase 3 absorbs arbitrary statements, which makes both
reachable, so the accumulator needs `--`-comment and double-quote handling
before it is reused. `E'…'` escape strings are not a concern: `pg_dump` sets
`standard_conforming_strings = on`, so `''` is the only in-string escape.

## Dollar-quoted lines never reach `Event::Line`

`scan.rs`'s outside-block arm calls `scan_dollar_quotes` and `continue`s
whenever the line is inside, entering, or leaving a dollar-quoted string — so
no `Event::Line` is emitted for it. `preamble.rs` therefore never sees a
`CREATE FUNCTION` body, which is why it needs no defence against one.

Phase 3 inherits this: a span covering a `CREATE FUNCTION` gets its body bytes
attributed automatically (spans are greedy and run to the next span's start),
but the span's *text* cannot be accumulated from `Event::Line` alone. It must
either be sliced from the file by offset or the scanner must surface
dollar-quoted lines to the map.

## `INSERT` statements span multiple physical lines; `COPY` and `BLOBS` regions cannot

`pg_dump --inserts` writes values as single-quoted SQL literals, and a literal
carrying a newline puts the rest of the statement on the next physical line.
`fixtures/18/edge_cases/inserts.sql` has it directly — `public.escapes` row 10
(`chr(10)`) emits:

```
INSERT INTO public.escapes VALUES (10, '
');
```

so a continuation line begins with `');`, not `INSERT INTO`. A line-anchored
`INSERT INTO ` prefix check therefore cannot find where an `INSERT` run ends;
that needs string-aware scanning (tracking `'` with `''` doubling — `pg_dump`
sets `standard_conforming_strings = on`, so no backslash escapes).

The other two bulk regions do not have this problem, and both have an invariant
behind them:

| Region | End marker | Why it is line-anchored-safe |
|---|---|---|
| `COPY` block | `\.` alone on a line | I7 — `LF 5C 2E` cannot occur at the start of a data line |
| `BLOBS` | `COMMIT;` | I12 — payload is a bytea hex literal, which cannot contain a line break |
| `INSERT` run | next TOC header | **no such invariant** — a value can contain a newline followed by anything |

`--inserts` output also emits a `TABLE DATA` TOC header for a table with **zero**
rows (`public.empty_table`), so a data span with no data lines at all is a shape
the map must handle.

## Phase 3 slice 3.1 landed: the `objects` fixture schema

`scripts/fixture_schema_objects.sql` (new) plus real `pg_dump` output for all
6 routine versions (`fixtures/<version>/objects/{default,verbose}.sql`)
covers every TOC `Type:` kind neither `edge_cases` nor `types` produces,
except six deliberately skipped ones needing an extension or unavailable
provider — see that file's header and `roadmap-phase3-object-inventory.md`'s
updated "Current fixture coverage" note for the full list either way. Two
large objects, built with `lo_from_bytea` since no `pg_dump` flag produces
one, give I12's fast-path skip its first real evidence (previously
source-reading only). `generate_fixtures.py` gained the `objects` schema
entry (`{default, verbose}` flag set — `--verbose` is what widens the TOC
comment block past three lines) and a `drop_fixture_db` fix: the fixture's
subscription and role both outlive a plain `dropdb` otherwise (a
subscription blocks dropping its own database; a role is cluster-global and
would leak into whatever schema runs next in the same container).

**A version-gated feature needed a fallback inside the fixture itself.**
`FOR TABLES IN SCHEMA` (the `PUBLICATION TABLES IN SCHEMA` TOC shape) is
PG15+; since this schema loads against every routine version back to 13, a
straight `CREATE PUBLICATION ... FOR TABLES IN SCHEMA` fails outright on
13/14. Fixed with psql's `\gset`/`\if` reading `server_version_num` and
falling back to a second `FOR TABLE` publication below 15 — confirmed both
branches fire correctly across all 6 versions (`PUBLICATION TABLE` on 13/14,
`PUBLICATION TABLES IN SCHEMA` on 15+). No other version gate was needed:
every other object kind in the schema (`serial`, extended statistics,
declarative partitioning, row-level security, materialized views, event
triggers, `postgres_fdw`) has been available since PG10 or earlier, safely
inside the routine matrix's PG13 floor.

**`SEQUENCE OWNED BY` needed `serial`, not `GENERATED ALWAYS AS IDENTITY`.**
`pg_dump.c`'s `dumpSequence` special-cases `is_identity_sequence` and folds
an identity column's ownership into the identity clause itself rather than
emitting a separate `SEQUENCE OWNED BY` entry — confirmed by diffing real
output between the two column-definition styles. A `serial` column's
sequence gets the separate entry, since `serial` is sugar for a plain
`CREATE SEQUENCE` + `nextval()` default + explicit `OWNED BY`, none of which
carries the identity special-case.

**`DEFAULT` needed a view column, not an ordinary table column.**
`dumpAttrDef`'s `separate` flag — which is what makes pg_dump emit a
default as its own `ALTER TABLE ... SET DEFAULT` entry instead of folding it
into `CREATE TABLE` — is only ever set for a suppressed column (the
`--binary-upgrade` dropped-column shape `edge_cases` already covers) or a
view column (views can never carry an inline default). Confirmed by reading
`pg_dump.c` directly after an ordinary table default didn't produce a
separate TOC entry on the first attempt.

## I12 revised: the large-object archive-entry shape changed at v17, and the routine matrix spans both

Slice 3.1's large-object fixture is real evidence where I12 previously had
only source reading. It confirms the source-derived claims (line-oriented,
no `COPY`/`\.` ambiguity possible, `BEGIN;`/`COMMIT;`-wrapped) but shows the
prior "one `BLOBS` archive entry for all of it" claim held only through v16:

- **v13-16:** one `BLOB` entry per object (ownership/comment/ACL), but every
  object's data shares **one** `BLOBS` entry with **one** shared
  `BEGIN;`/`COMMIT;` wrapping every object's `lo_open`/`lowrite*`/`lo_close`
  run back to back.
- **v17-18:** `pg_dump.c` renamed the definition entry to `BLOB METADATA`
  and — per its own comment, "Create a BLOBS data item for the group, too"
  — started splitting large objects into groups, each with its own `BLOBS`
  entry and its own `BEGIN;`/`COMMIT;`. A two-object fixture can't establish
  the group-size threshold, only that "always exactly one entry" stopped
  being true.

This matters for Phase 3's "one `Data` span per bulk region" design: on
v17+, finding where the large-object *region* ends (as opposed to one
entry) means walking past every consecutive `BLOB METADATA`/`BLOBS` TOC
header rather than stopping at the first `COMMIT;` — recorded as a decision
note in `roadmap-phase3-object-inventory.md`'s "Bulk regions" section for
slice 3.2 to pick up. Per-object OID recovery is now free from the TOC
header alone on v17+ (previously required walking every `lo_open` opener,
still true on v13-16) — not acted on, since the phase's design treats the
whole region as one span regardless.

Full detail, including the source line numbers and the version-split table:
`docs/design/postgres-invariants.md` I12.
