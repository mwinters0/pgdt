# 2026-09-17

## Repoint findings for the maintainer

The repoint at `3b61c04..HEAD` read nine module groups blind. These are the
findings it could not correct in scope — the decision register, the invariants
register and `roadmap.md`'s standing rules are beyond a phase
([`../../process.md`](../../process.md), "Working unattended"). Everything else
it found is corrected in the repoint commit.

**`decisions.md`, "D27" — the heading claims no `unsafe` on a hot path, and
there is one.** The record: *"D27 UTF-8 is validated once per chunk, and no hot
path uses `unsafe`"*. The code, `pgdump_query/src/batch.rs:1070`:
`unsafe { builder.append_view_unchecked(block, local_offset, len) }`. It is the
library's only `unsafe` (`grep -rn unsafe pgdump_query/src` returns one hit) and
it sits on the per-field zero-copy append. The entry's body — *"Four `unsafe`
attempts lost to the safe shape"* — is about the validation path in `copy.rs` /
`scan.rs`, where it holds; the heading is what overreaches.

**`decisions.md`, "D83" — the plain-source budget claim holds only upward.**
The record: *"a source recommending nothing is left on `DEFAULT_MEMORY_BUDGET`
whatever is stated"*. The code, `pgdump_query/src/io.rs:853`:
`return (jobs, DEFAULT_MEMORY_BUDGET.min(cap));`. Below an allowance of
`MEMORY_RESERVE + DEFAULT_MEMORY_BUDGET` the budget falls *below* the constant,
and at or under the reserve it is zero — `io.rs`'s own test asserts `Some(0)`
under a 128 MiB limit. `discover_for`'s rustdoc already has the precise form
("taken no higher, and may fall below"). `STATUS.md`'s `KD32` line carries the
same wording and was left alone so the two move together.

**`decisions.md`, "D82" — "never while a piece lives" is not what `finish`
does.** The record: *"D82 A block merges pairwise, exactly, between its minimum
and its maximum, never while a piece lives"*. The code,
`pgdump_query/src/gather.rs:363`: `let cap = if finishing { self.cap } else
{ self.merging_cap() };` — and `fit_density` (`gather.rs:392`) consults no piece
state at all. The alive-piece check binds mid-scan only; at the block's end it
merges whatever is outstanding, a piece alive there being past joining.
`fit_cap`'s own doc states the exception. The two source comments that restated
it are corrected.

**`decisions.md`, "D55" — the widening list is short by two families.** The
record: *"hex digits of either case, and integers … are wider"*. The code,
`pgdump_query/src/predicate.rs:294` and `pgdump_query/src/decode.rs:862`: both
`numeric` kinds share one grammar whose only requirement is a digit somewhere,
so `.5`, `1.`, `007` and `-0` are accepted spellings `numeric_out` never writes
(`-0` deliberately, `predicate.rs:303`). And `decode.rs:742` strips every hyphen
before counting nibbles, so a `uuid` literal's hyphen placement is free. The
`accepted_form` comment is corrected to match the code; the entry is not.

**`decisions.md`, "D76" — one clause reads two ways and is false under one.**
The record: *"bounds stay valid and only row order is lost (`Unsorted`), as for
a decoded-kind value past the cap"*. The code,
`pgdump_query/src/gather.rs:1336`: a keyed kind past `DICTIONARY_ENTRY_MAX_BYTES` calls
`lose_value`, and a `lost` group stores no bounds (`gather.rs:1468`). Only the
row-order half carries across to that case. If "as for…" attaches to the
row-order clause alone the sentence is fine; it does not read that way.

**`postgres-invariants.md` — three lines name a type that does not exist.**
Lines 381, 389 and 391 cite `PreambleBuilder`, `PreambleBuilder::feed_line` and
`PreambleBuilder::pending_headers`. Nothing of that name is in the tree.
`preamble.rs` has no line-driven builder: the staging described is
`dump_metadata_from_spans`' `SpanBody::VersionHeader` arm,
`pgdump_query/src/preamble.rs:1207-1223`, and `DumpMetadata` is a derived view
over spans. The two test docs that named it are corrected.

**`postgres-invariants.md:564` — a consequence the code rules out.** The
record: *"One name can own two `TypeDef` entries, so `resolve_user_type`'s
first-match lookup returns the `Shell` entry for a completed base type"*. The
code, `pgdump_query/src/preamble.rs:687-693`: `record_type` finds the name and
replaces that entry's `kind` in place, or pushes a new one — a name never owns
two. `pgdump_query/tests/preamble.rs:250` asserts one entry per type over every
fixture. The underlying I11 claim (two *statements* under one name) stands; the
consequence drawn from it does not.

**`roadmap.md`, "Four workers is the optimization baseline" — a standing rule
quotes two measured numbers.** The record, line 122: *"a compressed parse scales
to **5.60×** at twenty-four against 1.76× at four"*. Both match
`measurements.md`'s `parallel-scan-throughput` cells exactly today, so nothing
is wrong; what the rule has is a second copy of a number that is stated once
elsewhere, in a document with no check against it, and that figure is currently
stale.

**`scripts/citations.py` resolves document+section citations and nothing else.**
A bare relative link to a deleted file passes it clean: the P20 wrap deleted the
nine per-slice notes docs and left `out-of-band.md`'s `M113` pointing at one, and
a green `citations.py` said nothing. Repaired in `94220cc`. Every other dangling
relative link in the tree is inside a dated entry, which is exempt.
