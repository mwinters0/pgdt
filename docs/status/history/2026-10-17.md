## DataFusion's cross-order answer is DataFusion's own

The maintainer reviewed 36.4.4's split of DataFusion's cross-order answers
and chose to answer them in `datafusion-pgdump`, by DataFusion's own
`comparison_coercion` and cast, a cast it refuses answering `None`. 36.4.5
moves there (spec, "A key for every value"). The codec reproduces no
arrow-cast, and D74 stands.

Facts found in DataFusion 55.1.0
(`datafusion/expr-common/src/type_coercion/binary.rs`), which decided it:
- **A comparison's cast refuses rather than nulls.** The physical
  `CastExpr` uses `safe: false` (`physical-expr/src/expressions/cast.rs`).
  A text that does not parse as the number it is compared with errors the
  query. DataFusion's semantics emits a bare `numeric`, `timetz`, `inet`,
  `macaddr`, `jsonb` and an enum as text, so most text-against-number pairs
  error in DataFusion.
- **Few pairs are cast-free.** `temporal_coercion` takes a `Date32` against
  any `Timestamp` to `Timestamp(Nanosecond, None)` on both sides, which
  overflows outside 1677–2262 and drops a `timestamptz`'s zone through
  arrow-cast. A widened decimal's precision is capped, so a rescale can
  overflow. Only integer widths, and an integer against a float (an `as`),
  are exact without arrow-cast. Reimplementing the rest in the codec would
  copy arrow-cast's edges and need a re-check at every upgrade.
- **DataFusion relates more pairs than 36.4.4 listed**: a `Date32` against
  any integer, as days; a text against a `bytea`, and a `uuid`'s
  `FixedSizeBinary(16)` against a `bytea`, as bytes (`binary_coercion`); a
  `Date32` against a time, through nanosecond timestamps. `KD119` now lists
  them.
- **Nothing in the workspace asks.** Pushdown refuses a column wrapped in a
  cast (`datafusion-pgdump/src/filter/pushdown.rs`, `translate`), which is
  where DataFusion's analyzer puts every cross-type coercion. The answer is
  an embedder's alone.

Rejected: arrow-cast linked into the codec, which builds no array and links
no arrow-cast (D74); the cast-free pairs reimplemented there; 36.4.5 struck
with `KD119` left unowned; and narrowing DataFusion's semantics to Arrow's
`cmp` kernels, which relate one type only. The last contradicts "each
semantics answers as its own engine does" (2026-10-16, "36.4.1's calls
reviewed: the order's identity moves to `ValueKey`"). PostgreSQL's answers
already count its casts, as `int4` to `oid` and `numeric` to `float8`.

Its shape, settled in the same review (spec, "A key for every value"):
- **A key read in DataFusion's semantics carries its column's emitted
  `DataType`.** Its order does not determine it: `ScalarOrder::Decimal`
  keeps only the scale, a `numeric(p,s)` is `Decimal128` to 38 digits and
  `Decimal256` past (`pgtype.rs`), and an enum ordered as `Text` is emitted
  as a `Dictionary`. `ComparisonPlan` carries no Arrow type. D40's "key/
  reads no Arrow type" gains, when 36.4.5 lands, that the type is carried
  for DataFusion's coercion and never read to order. Rejected: the caller
  passing each key's type, which nothing checks (`KD115`'s shape); a second
  key type holding a `ScalarValue`.
- **One function answers every pair**, so an embedder asks in one place.
- **DataFusion is the oracle**, as the server is D70's: the one thing not
  true by construction is the value rebuilt from a key.

## A nested key names its types at every level

The maintainer affirmed 36.4.4's call that a nested key's order names each
leaf's type (D56, its `Rejected` line), and admitted `M224` to close
`KD120` whole: the converse holes are the same principle one level up.

Facts probed on the koji replica (PostgreSQL 16.15, rolled back):
- `text[] < varchar[]`, `int4[] < int8[]` and `bpchar[] < text[]` resolve
  no operator; `varchar(3)[] < varchar(5)[]`,
  `timestamp(3) with time zone[] < timestamptz[]` and
  `numeric(5,1)[] < numeric[]` compare — a typmod never decides, a leaf's
  type always does.
- Two composite-typed columns, `(integer, text)` against
  `(integer, varchar)`, raise `record_cmp`'s "cannot compare dissimilar
  column types"; two composite types of identical column types compare. So
  a composite's own type decides below the top level only, where it is a
  column or element type.
- An anonymous `row(1, 'a'::text) < row(1, 'b'::varchar)` answers `t`: the
  parser splits a row constructor column by column and `record_cmp` never
  runs. No key is a row constructor — a filter literal is read in its
  column's type — so nothing follows from it.

`M224` landed, closing `KD120` (D56, I92):
- **A nested order names each node where the server tells two apart**: a
  range's and a multirange's type at every level, a composite's below the
  top, and at an element or a field the domain it is declared as, an
  array's and `int2vector`'s included, as `record_cmp` refuses a domain
  over `integer[]` against `integer[]`. Every `NestedCompare` node carries
  `declared`, set at a position by `compare/walk.rs`'s `at_position`.
- **Leaves of one type relate as scalars do**, through `relate::postgres`
  inside `array_cmp`'s and `record_cmp`'s walk (`relate::related`), so
  `numeric[]` at two scales compares; a range relates to its own order
  alone.
- **`CompareKind::Text` carries `varying`**, a `ScalarOrder` of its own in
  PostgreSQL's semantics only. Folding it in `datafusion_order` instead was
  refused: `bounds_kinds` would have kept a second bounds set for every
  `character varying` column.
- The filter's `compare_nested`, `CompareKind`'s size and the golden order
  digest are unchanged; no cache format bump.

## 36.4.5's call reviewed: a key's resolution names its semantics

The maintainer affirmed 36.4.5's two calls: `ValueKey::of` and
`ValueKey::literal` take `(&ResolvedSchema, column)`, filed in D56's
`Rejected` line, and `EmittedValue` is the codec's API, filed in D106's.

The review found a third input the resolution carries and the key does not
check: the semantics. `resolve_columns` does not depend on it, but
`read_as_text` does (D100), and `ResolvedSchema` does not record it, so a
`ValueKey` asked for in the other semantics answers wrongly or `None`
(`KD121`). The spec now has 36.9's column record carry the semantics a
widening was applied under, and a key asked for in the other semantics
answer `None` (spec, "Values passed back together"). Rejected: the
constructors taking the semantics from the record, since a schema never
widened, gathering's included, has none to give; and the declared plan kept
in both semantics with one accessor deriving DataFusion's text order, which
is D100's own refusal.

## Boxing `Event::CopyStart` admitted as `M225`

The maintainer affirmed 36.5's acceptance and admitted the box as its own
change, not as recovering 36.5: it shortens every event's move in every
read loop, the parent's as much as the tree's.

Facts found in review, at `ee7850d3`:
- **`CopyStart` alone sets `Event`'s size**: a `CopyHeader` of three owned
  fields and two offsets, against `Row`'s slice and two offsets, the next
  largest. Shrinking `CopyHeader`'s fields without boxing stays above
  `Row`.
- **The allocation it adds is one beside several per block already**:
  `parse_copy_header` allocates the table, the schema, the column list and
  each name, and `next_event` the qualified name `Endings::Refused` holds
  (`pgdt-dump/src/scan.rs`).
- **The probe's figures** are `runs/attr-36.5-20261017-callgrind/probe/probe.txt`:
  a no-LTO build, the box alone removing most of the tree's rise and the
  cold continuation nearly all the rest.

What `M225` is held to:
- **`Event::CopyStart(Box<CopyStart>)`, the box on the variant.** Rejected:
  `CopyStart` holding a `Box<CopyHeader>`, which puts the indirection in a
  public field rather than on the enum whose size is the problem; and the
  cold continuation, whose saving rests on inlining attributes (2026-10-16,
  "36.4's rework recovers the data-level rise; the summary reads by kind").
- **A compile-time assertion beside `Event`** that it is no larger than
  `Row` and its tag, so a variant regrowing it fails to build.
- **Its own `measure.py --count-pair HEAD~1`**, its reading written here
  before it runs: a fall on the metadata-level `parse`, no row resolving
  as a rise. The probe was not the shipped profile. A rise drops the box,
  and the reading is filed.

## `M225` lands, every row a fall

`Event::CopyStart(Box<CopyStart>)`, with the compile-time assertion beside
`Event` in `crates/pgdt-dump/src/scan.rs`. `Builder::on_copy_start` still
takes a `CopyStart`, its three callers in `pgdt-mapping` unboxing it once
a block.

Its `--count-pair` against `8e4f0f4d`
(`runs/count-pair-M225-20261017/log`, the table at its end) resolves a
fall on all five rows, the metadata-level `parse` the largest, and no
rise: the reading above holds, and `M225`'s Date is filled in. The no-LTO
re-probe 36.5's notes named was not run; the pair is the shipped profile.

## 36.6 splits: the open lands, the scan entry points taking it is 36.6.1

`CacheMode::open` landed, with `pgdt info` and `PgDump::open` opening
through it ([notes](../../design/roadmap-P36.6-open-notes.md)). The row as
specified also had the cache decoded once for `pgdt parse` and `pgdt query`.
That needs `map_file`, `preamble_only` and the query entry points to take
the open instead of loading the cache themselves: a rework of every test
that calls them, and it was not bundled with the protocol. It is now
36.6.1. Narrowing `scan`'s options, which moves the cancellation
announcement D26 relies on, is now 36.6.2. Until 36.6.1 lands, `claim`
stays in the API for `pgdt`'s `open_for_scan`. Whether 36.6.1's query half
should instead fold into 36.8 is under STATUS's "Decisions worth another
look".
