P5's grilling. The scope was settled first, splitting statistics out as P10;
the design tree was then worked and the spec written,
[`roadmap-P5-pushdown.md`](../../design/roadmap-P5-pushdown.md). Facts found

produced are in that spec and in
[`roadmap.md`](../../design/roadmap.md)'s P10 and P11 sections.

## The sketch's premise for predicate pushdown is already banked

P5's roadmap sketch promised to "evaluate predicates *during* the scan/parse,
so non-matching rows never get fully unescaped/materialized — as opposed to
today's post-parse filtering". **The second half is not what the code does.**

`stream.rs`'s replay loop evaluates the predicate against the raw row and calls
`RowBatcher::push_row` only if it passes. `Predicate::matches` walks
`split_fields` to the predicate's column index and calls `decode_field` on that
one field. So a rejected row already costs: the scanner's `memchr` for the row
terminator, a field walk as far as one column, and one field's unescape. It
never reaches a `ColumnBuilder`, never unescapes another field, and never
touches the `Utf8View` chunk machinery.

`architecture.md`'s "Predicates" section says "a row is fully parsed, then
dropped" — accurate about the *scanner* having produced the row, and read by the
roadmap sketch as though it meant materialization.

What remains of the idea is therefore small and worth naming exactly: the
scanner must find every row's terminator whatever the predicate says, so the
only per-row work a smarter arrangement can remove is the partial field walk.
The wins that are actually unclaimed sit elsewhere — projection, which is
unbuilt, and block/row-group skipping, which is P10.

## Pushdown cannot touch the mapping pass, which is where a cold query's time is

A query is two passes (`architecture.md`, "Query: mapping and streaming are
separate passes"). The mapping pass walks from `scanned_through` to the target,
censusing every row it sees, and nothing about a predicate or a projection
changes a byte of it. Replay then re-reads only
`[block.header_offset, block.end_offset)`.

So every performance claim P5 can make is a claim about the **replay** pass,
which is the whole cost only when the map is already cached. On a cold koji
query the map pass reads hundreds of gigabytes and the replay reads one block;
pushdown's share of that wall clock is the block, not the file.

## Statistics are a phase, not a companion

Per-row-group column statistics were sketched as P5's companion. They are now
**P10**, scheduled after P7 (`../../design/roadmap.md`, both sections). Three
arguments, and only the third is about scheduling:

- The two halves fail `process.md`'s "size a slice by its review" test at the
  phase level. Projection and predicate expressiveness are a self-contained
  query-API change whose worst bug is a wrong row count on a filter. Statistics
  span all four layers and their worst bug is **silently dropped data** — a
  pruned row group that did contain matches, with no error to notice. Bundling
  them forces one review confidence across both.
- `layering.md` already names statistics "the sharpest test of these rules",
  and pre-answers two of its questions (rule 5 for persistence, rule 6 for
  compute). Nothing in the projection/predicate half needs either.
- **The addressing scheme belongs to P7.** Statistics attach to row groups, the
  row group is the sparse row index's checkpoint interval, and
  `CopyBlock::sparse_index` is a reserved `None` that P7 fills. Running
  statistics before P7 means inventing a second addressing scheme for P7 to
  reconcile with the one it wanted.

The number is 10 because it was allocated when the split happened, not because
it runs last; the roadmap's index table is the schedule and it sits between P7
and P8.

**One consequence for P7's own section.** Its scheduling paragraph led with
"P5's pushdown changes which bytes get touched at all, so optimizing the
pre-pushdown parser would partly optimize code that pushdown deletes". That
reason is withdrawn — pushdown deletes no parser code, per the finding above.
P7's position is unchanged, because the `object_store` reason was always the
load-bearing one.

## Typed nested comparison and full boolean structure are P11, not P5

P5's inbox carried one entry: nested columns get typed Arrow representations
but keep an untyped, text-shaped predicate, and making such a predicate mean
what PostgreSQL means needs the input-side grammar plus range canonicalization.
Draining it split the entry in two. The half that says a **string comparison is
right for every value a dump contains** — because dumps hold canonical output
form — folded into P5 as the justification for leaving nested columns alone.
The half that specifies what typed nested comparison would have to do moved to
[`roadmap-P11-typed-predicates-inbox.md`](../../design/roadmap-P11-typed-predicates-inbox.md).

**NULL is what made the split, not code volume.** A NULL field today matches
neither `Eq` nor `Ne`: unknown is collapsed to false at each term. That collapse
is sound under `AND` and unsound under `NOT`, since SQL's `NOT UNKNOWN` is
`UNKNOWN` rather than `TRUE`. So `OR`/`NOT` is not two more operators bolted
onto a conjunction — it obliges a real three-valued evaluator and re-opens the
semantics of every operator that already exists. And the inbox's measured
probes show nested equality does **not** follow that logic anyway:
`array[1,null] = array[1,null]` and `row(1,null) = row(1,null)` are both true,
because `array_eq` and `record_eq` are NULL-aware rather than
NULL-propagating. One 3VL evaluator applied uniformly would get both wrong.

Grouping the two into one phase follows the same argument that made statistics
P10: the worst bug in P5 is a wrong column list, the worst bug in P11 is a
silently wrong row *set*, and bundling forces one review confidence across
both. It is scheduled after P6 because DataFusion hands a `TableProvider` an
`Expr` tree and asks per filter whether pushdown is exact, inexact or
unsupported — designing a boolean expression language before seeing that shape
is inventing a second one to reconcile.

## What the code already does, against what the sketch's remaining half assumed

Three facts the spec rests on, so they are not re-derived from the source:

- **`BatchOptions` has five fields and none is a projection**, and
  `batch::RowBatcher::push_row` walks every field of every row, calling
  `push_field` — `decode_field` plus a builder append — for each. Projection's
  saving is unclaimed and real.
- **`ResolvedSchema` is four positional, parallel vectors** — `schema`,
  `columns`, `notes`, `plans` — and `RecordBatch::try_new` checks the built
  arrays against `schema` exactly. That is why a projection cuts all four
  together and why `resolved_schema()` reports the projected schema rather than
  the full table's: the alternative desynchronizes the one invariant the Arrow
  layer is already checking.
- **A predicate column is resolved by name, once per block**
  (`stream::resolve_predicate_index`), against that block's own schema, erroring
  `UnknownPredicateColumn`. A projection is addressed the same way for the same
  reason — a `COPY` header is the only column list a block supplies, so an
  index at this layer would mean something different depending on which block
  matched. DataFusion's `Option<Vec<usize>>` is translated to names by P6,
  against the schema pgdq advertised it.

## An aggressive filter pins read chunks in proportion to `1/selectivity`

Found while deciding what P5 owes on the chunk-pinning obligation P7 named.
The hazard is **live in the shipped system**, not something pushdown
introduces, so it is recorded as a known gap now rather than with the fix.

`stream.rs`'s replay loop evicts the `chunks` deque at the scanner position, so
the deque is bounded. That is not what holds the memory. `SourceChunk::block_for`
passes `StringViewBuilder::append_block` a `buffer.clone()` — an `Arc` — so the
**in-flight batch** keeps every chunk it took a view into alive until the batch
flushes, whatever the deque does. Both flush triggers count *selected* rows or
*selected* field bytes; neither bounds the source extent a batch spans. With
the default 1 MiB `chunk_size` and 8192-row batches, a 1%-selective filter
holds roughly 80 MiB and a 0.01%-selective one roughly 8 GiB.

P7's sketch answered this with compaction below a selectivity threshold. That
is withdrawn in favour of a **third flush trigger on the source byte span**:
compaction is the same fix applied after the fact, still admitting an unbounded
peak before the threshold trips, and it copies precisely the data the zero-copy
path exists not to copy. A span cap bounds memory against a number a caller can
set, and is testable at fixture scale with a small chunk size where a
selectivity threshold is not.

## `push_row` is the only field-count check there is

`batch.rs`'s two `Error::ColumnCountMismatch` raise sites are the only ones in
the workspace. The mapping pass *does* walk every field of every row — the
array-shape census requires it — but it never errors on a count; it produces a
per-column vector and nothing compares its length to anything.

That is why a projection narrows what is **decoded** and not what is
**walked**. Stopping the walk at the last needed column buys the `memchr` half
of the per-row cost, which was never shown to cost anything, and pays for it by
converting a malformed row into a silently wrong answer — against the standing
rule that the input contract is valid PostgreSQL rather than `pg_dump`'s
output, where a hand-edited file with a stray tab is the case that check is for.

## The measurement apparatus is shaped around projection's absence, so P5 supersedes it

Both the generator and the doc say so outright — `generate_perf_data.py`'s
`COMPOSITE_COLUMNS` comment and `measurements.md`'s nested section each state
that "`pgdq query` has no column projection, so there is no within-file way to
ask". Three figures are built on that gap:

- **`nested-end-to-end`** attributes cost by generating three separate 3.00 GiB
  files holding different column sets and subtracting across them.
- **`cross-file-floor`** exists only to measure that subtraction's own noise
  floor, ~0.5 µs/row.
- **`composite-isolated`** — built under `M23`, never taken — works around it
  with two files declaring one column two ways over byte-identical rows.

Column projection makes all three within-file. P5's figure is therefore one
file at five widths (0 columns, 1 scalar, 16 scalars, 16 + composite, all 19)
on the existing `--arrays --composite` input, and every attribution the
cross-file apparatus makes becomes a subtraction between two adjacent rows of
it — same file, same rows, so neither the cross-file floor nor the census's
file-dependent untyped baseline enters.

Two consequences. **The generator needs no change**, so `P5.1` loses the
staleness-acknowledgement ritual it was sliced to pay and becomes registration
only. And **`M25` no longer publishes `composite-isolated`**: writing its
section and marker only to delete both a few slices later is the outcome the
doc's own "a figure whose apparatus is gone should be deleted" rule exists to
avoid. `M25` keeps what genuinely needs a quiet machine — two sweeps, the
re-stamp, and `session-drift` — and the composite column's cost stays a bound
until `P5.7`, as it has been all along.

## Typed ordering is registered, not refused — and text is the reason the register exists

P5's ordering operators apply to any column that resolved `Mapped` with a
`Scalar` plan, which includes `text`. PostgreSQL orders text **by collation**,
and a plain dump records none: `dumpDatabase` is the only emitter of
`LC_COLLATE`/`LOCALE`/`ICU_LOCALE` and `pg_dump.c`'s `main` calls it only
`if (dopt.outputCreateDB)` — verified identical in the v13.23, v14.24, v15.19,
v16.15, v17.11, v18.6 and master worktrees. Filed as **I32**.

Refusing text was weighed and not taken. The decision instead is to compare
bytewise and **maintain a register of every Arrow type an ordering operator can
land on**, saying whether our comparison agrees with the server and what would
close the gap if it does not — because closing these is expected to proceed
type by type, and a register is what makes that possible without re-deriving
each one. It is in the spec now and moves to `architecture.md`'s "Predicates"
when `P5.6` lands.

What the register found, each checked against upstream v16.15 rather than
assumed:

- **`uuid` and `bytea` agree exactly.** `uuid_internal_cmp` is `memcmp` over 16
  bytes; `byteacmp` is `memcmp` then length. Both are what Rust's `Ord` gives.
- **Floats agree only under PostgreSQL's NaN rule, and they are the only rows
  that reach one.** `float8_gt(a, b)` is `!isnan(b) && (isnan(a) || a > b)`, so
  NaN is greater than every value including infinity and `NaN = NaN` is true,
  where Rust's `partial_cmp` returns `None`; we implement PostgreSQL's. Only
  `real`/`double precision` decode `NaN` to a float — a `NaN` in a
  `numeric(p,s)` column is already a hard `Error::FieldDecode`, since
  `Decimal128` cannot hold one, so it never reaches a comparison.
- **Enum ordering diverges and is cheaply fixable.** PostgreSQL orders an enum
  by declaration order; comparing label text orders it alphabetically. The
  dump carries the declaration order verbatim in `CREATE TYPE … AS ENUM (…)`,
  so closing this is additive.
- **Bare `numeric` is the sharp edge.** `map_numeric` returns `Utf8View` when
  there is no typmod, and that column is still `Mapped` — so an unconstrained
  `numeric` orders lexicographically, and `"9" < "10"` is false. It is exactly
  the case `predicate.rs`'s original comment refused ordering over, now
  reachable through a column that looks numeric.

## The divergence warning has no channel, so it stays in the CLI

Announcing a divergent ordering comparison needs a per-column signal that is
conditional on a predicate. That is L4, and both existing channels are lower:
`DumpIndex.diagnostics` is L1 and file-level, `ResolvedSchema.notes` is L2 and
per-column. Writing into either inverts the layering, and adding a third
channel now would hand P6's sink — already recorded in its inbox as the
designated unification point — one more thing to reconcile before it has
decided what it reconciles.

So P5 warns in the **CLI only**, once, on stderr, after the schema resolves,
and files the embedded case into P6's inbox. An embedder gets nothing until
then, which is exactly where they already stand for the undetectable
ambiguous-table gap filed in the same place.

The same reasoning retargets `layering.md`'s P5 paragraph. Its rule — L1
defines the callback, L4 supplies it, `predicate.rs` stays L4 — is intact, but
its premise ("evaluating predicates during the scan") describes something P5
does not do, so it now states the shape any future move of that evaluation must
take rather than attributing it to a phase.
