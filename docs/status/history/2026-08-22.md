## `COPY` header recognition: strict grammar, and the dollar-quoted-body gap

`mvp.md`'s "Parser robustness requirements" calls for line-anchored `^COPY `
detection because row *data* can contain a `COPY ... TO stdout;` substring
mid-line. Building the scanner surfaced a second, sharper case that
line-anchoring alone does not cover: a `COPY` line at **column 0 inside a
dollar-quoted function body**. `pg_dump` emits function bodies verbatim
between `$$` markers, so the body's own line breaks are real line breaks in
the dump, and a body containing `COPY ... FROM stdin;` at the start of a line
is indistinguishable from a real block header by position alone.

The failure mode is bad: a false `CopyStart` puts the scanner into
data-consuming mode, and it then swallows every following line — including
genuine `COPY` headers — until it happens to hit a line that is exactly `\.`.
One false positive can therefore hide an arbitrary amount of real structure,
rather than producing one bad row.

Two mitigations were considered:

1. **Track dollar-quoting** in the scanner, so text inside `$tag$ ... $tag$`
   is never treated as structure. Correct, but it means carrying quote state
   across the whole file and getting `$tag$` matching right, for a case not
   yet observed in any real dump.
2. **Match the full header grammar**, not just the `COPY ` prefix.

Option 2 was taken. `parse_copy_header` requires the entire line to be
`COPY <table> [(<cols>)] FROM stdin;` with nothing trailing; anything else is
skipped as ordinary SQL. This is cheap and it rules out the near-misses that
actually occur in practice — `COPY ... TO stdout;` and any `WITH (...)`
suffix — both of which are now covered by
`pgdump_query/tests/data/edge_cases.sql`. It does **not** rule out the exact
`FROM stdin;` shape inside a function body; that residual gap is recorded in
`docs/design/pg-dump-compatibility.md`, and option 1 is what closing it
would take.

The same strictness has a deliberate second consequence: a `COPY` variant the
grammar does not cover is invisible rather than misparsed. Silently finding
no block is a recoverable, inspectable outcome; misreading SQL as data is
not.

## Scanner shape: the caller owns the buffer

`CopyScanner` is a synchronous state machine that never owns or copies the
bytes it scans — the caller holds a buffer, passes it as a slice, and the
scanner reports how much it consumed (`take_consumed`). The alternative,
having the scanner own an internal carry buffer, forces events to borrow from
`self` and makes the `&mut self` borrow in `next_event` conflict with the
returned event's lifetime.

The chosen shape keeps events zero-copy with no self-referential borrows, and
it means the async driver (`scan()`) is a thin loop rather than a second
parser. When the pull-mode `Stream` in `mvp.md` gets built, it can reuse the
same state machine instead of reimplementing the line splitting.

The consequence a future session should know about: because the scanner
cannot emit a row until it holds that row's whole line, the caller's buffer
is the only thing bounding memory. That is why `ScanOptions::max_line_bytes`
exists and why exceeding it is a hard error rather than an ever-growing
buffer.
