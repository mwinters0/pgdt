## Dump-level metadata: what `pg_dump` emits, and why an early exit is safe

From `pg_dump` source at `/mnt/wd12t/upstream/postgres/`, checked in
`release-v13.0`, `release-v16.0` and `release-v18.6` — unchanged across all
three.

**`CREATE EXTENSION` and `CREATE TYPE` always precede every `COPY` block, by
dependency graph rather than convention.** `addBoundaryDependencies()` in
`pg_dump.c` classifies `DO_EXTENSION`, `DO_TYPE` and `DO_SHELL_TYPE` as pre-data
objects: the pre-data boundary object depends on each of them, and every
`DO_TABLE_DATA` depends on that boundary, so the topological sort has no freedom
to interleave them. The `dbObjectTypePriorities` enum in `pg_dump_sort.c` agrees
(`PRIO_EXTENSION` 5, `PRIO_TYPE` 6, `PRIO_PRE_DATA_BOUNDARY` 25,
`PRIO_TABLE_DATA` 26) but is only a tiebreak within the sort — the dependency is
the real guarantee. A preamble scan may therefore stop at the first `COPY`
header with no correctness fallback.

The invariant holds **per database, not per file**: `pg_dumpall` concatenates one
`pg_dump --create` output per database, so a later database's preamble follows an
earlier one's data. Hence re-arming the search at `\connect`.

**Extension versions are not in a regular dump.** `dumpExtension()` emits
`CREATE EXTENSION IF NOT EXISTS <name> WITH SCHEMA <schema>;` and nothing more,
with an explicit comment that it is "intentionally not specifying a version, so
that the destination installation's default version is used." The version
appears only under `--binary-upgrade`, as the 4th argument to
`binary_upgrade_create_empty_extension(name, schema, relocatable, version,
extconfig, extcondition, ARRAY[...])`.

The two header lines `-- Dumped from database version` and `-- Dumped by pg_dump
version` come from `RestoreArchive()` in `pg_backup_archiver.c` and are not gated
on `--no-comments`. The same two strings live in the custom/directory/tar archive
header, so this part of the metadata carries to Phase 8 unchanged.

## `CREATE TYPE`: six emitted forms, four of them informative

`pg_dump` has six type-emission paths (`dumpEnumType`, `dumpDomain`,
`dumpCompositeType`, `dumpRangeType`, `dumpBaseType`, and `dumpShellType` /
`dumpUndefinedType`). Only two produce something a type mapping can do nothing
with:

- **Enums** (`CREATE TYPE x AS ENUM ('a', 'b', …);`) are fully determined by the
  DDL. COPY TEXT emits the label as ordinary text and the complete label set is
  in the statement, so this maps to `Dictionary(Int32, Utf8)` with no guessing.
- **Domains** (`CREATE DOMAIN x AS <basetype> …`) reduce to their base type,
  named directly in the statement. Resolution must be transitive, since a domain
  over a domain is legal; a trailing `NOT NULL` is a free nullability refinement.
- **Composites** and **ranges** carry their field types / subtype, so an Arrow
  `Struct` or range representation is reachable later. What blocks them is
  decoding COPY TEXT's record literal `(a,b,"c,d")` and range syntax `[a,b)`,
  which have their own nested quoting. String-plus-warning is the interim answer;
  they are not permanently opaque.
- Only **C-level base types** (`CREATE TYPE x (INPUT = …, OUTPUT = …)`) and
  **shell/undefined types** (`CREATE TYPE x;`) are genuinely information-free.

So a diagnostic should carry the *kind* of unknown rather than one
"unrecognised type" message — the interim cases are worth distinguishing from
the permanent ones, if only to show what future work would buy.

**Extension types and user-defined types are disjoint sets in the dump.**
`checkExtensionMembership()` clears `DUMP_COMPONENT_DEFINITION` on every
extension member in a regular dump, so an extension's types are never emitted as
`CREATE TYPE`. PostGIS `geometry` is explained only by its `CREATE EXTENSION`
line; a hand-rolled type only by its `CREATE TYPE`; and koji shows the third
combination, a bare `CREATE TYPE` with no extension at all. Both lists are
needed, and either can legitimately be empty.

One trap: under `--binary-upgrade`, `dumpEnumType` emits the `AS ENUM ()` body
**empty** and adds labels afterwards through oid-preserving calls, so a
body-only label extractor yields an empty enum there rather than failing.

## Predicate filtering: NULL semantics and unknown-column handling

Two calls made implementing `roadmap-phase1-mvp.md`'s "Predicate filtering
(MVP)" that the spec didn't pin down:

**A NULL field matches neither `=` nor `!=`.** SQL's own three-valued logic
says `NULL = x` and `NULL != x` are both `UNKNOWN`, and a `WHERE` clause
treats `UNKNOWN` as "don't return this row" for `=` but as "do return it" for
a naive `!=` reading (`col != x` looks like it should include NULLs to a
caller thinking in `!==`-across-languages terms, even though real SQL
excludes them too via the same `UNKNOWN` collapse). Since this MVP has no
`IS [NOT] NULL` predicate to let a caller ask for NULLs explicitly, excluding
them from both operators is the reading least likely to surprise: it matches
real SQL's `!=` behavior exactly, and for `=` it's the only sane choice
regardless.

**Referencing a column not in the matching block's schema is a hard error**
(`Error::UnknownPredicateColumn`), not a silent zero-row or all-row result.
Column resolution happens per-block (not once for the whole query) because a
headerless block's schema is placeholder names (`column1`, `column2`, ...)
sized from its first row, which can genuinely vary block-to-block for the
same table name. A typo'd `--filter` column should fail loudly the same way
`ColumnCountMismatch` and the cache's write-failure path already do in this
codebase, rather than joining the cache's "missing/foreign is a quiet `Ok`"
convention — that convention exists specifically for cache staleness, which
is provably safe to fall back from; an unresolvable predicate column has no
safe fallback reading.

## `COPY` header recognition: strict grammar, and the dollar-quoted-body gap

`parse_copy_header` requires the entire line to be
`COPY <table> [(<cols>)] FROM stdin;` with nothing trailing; anything else is
skipped as ordinary SQL.

Line-anchoring alone is not enough, because a `COPY` line can appear at column 0
**inside a dollar-quoted function body** — `pg_dump` emits bodies verbatim
between `$$` markers, so the body's line breaks are real line breaks and such a
line is indistinguishable from a real header by position. The failure mode is
severe: a false `CopyStart` puts the scanner into data-consuming mode, where it
swallows every following line — genuine `COPY` headers included — until it hits a
line that is exactly `\.`. One false positive can hide an arbitrary amount of
real structure.

The full-grammar match rules out the near-misses that occur in practice
(`COPY ... TO stdout;` and any `WITH (...)` suffix, both covered by
`pgdump_query/tests/data/edge_cases.sql`). It does **not** rule out the exact
`FROM stdin;` shape inside a function body; closing that requires tracking
`$tag$ ... $tag$` quote state across the whole file, and the residual gap is
recorded in `docs/design/pg-dump-compatibility.md`.

The strictness has a deliberate second consequence: a `COPY` variant the grammar
does not cover is invisible rather than misparsed. Silently finding no block is
recoverable and inspectable; misreading SQL as data is not.

## Terminator search: `LF 5C 2E` is a safe needle

Enumerating newlines inside a `COPY` block is unnecessary. Because `pg_dump`
doubles backslashes, the byte sequence `LF 5C 2E` cannot occur at the start of a
data line, so a single `memmem` search for that 3-byte needle finds the block
terminator directly and safely.

The outside-block path should stay line-oriented — it is a few MB out of 784 GB,
and keeping it that way preserves the option of adding the dollar-quote tracking
described above.

## Scanner shape: the caller owns the buffer

`CopyScanner` is a synchronous state machine that never owns or copies the bytes
it scans — the caller holds a buffer, passes it as a slice, and the scanner
reports how much it consumed (`take_consumed`). The alternative, an
scanner-internal carry buffer, forces events to borrow from `self` and makes the
`&mut self` borrow in `next_event` conflict with the returned event's lifetime.

The chosen shape keeps events zero-copy with no self-referential borrows, and
makes the async driver (`scan()`) a thin loop rather than a second parser. The
pull-mode `Stream` in `roadmap-phase1-mvp.md` can reuse the same state machine
instead of reimplementing line splitting.

The consequence to know about: because the scanner cannot emit a row until it
holds that row's whole line, the caller's buffer is the only thing bounding
memory. That is why `ScanOptions::max_line_bytes` exists and why exceeding it is
a hard error rather than an ever-growing buffer.

## Archive formats: in scope, and additive

`--format=custom`/`directory`/`tar` are Phase 8, Track B. The criterion: tools
whose job ends at reading a dump are well served by `pgdumplib` and friends, but
an embeddable Arrow-native source behind a DataFusion `TableProvider` is a
different class of thing, and "query a table out of a custom-format archive" is
squarely what it is for.

Finishing the plain-format slice first is safe because the restructuring is
smaller than it looks. All four formats store table data as the **same COPY TEXT
payload**, so `copy.rs` is reused verbatim and there is no second row parser;
what differs is only how you find an entry and get its bytes. That is a container
layer, and it slots between two boundaries that are format-agnostic by design —
`ByteRangeSource` below and the batch/stream API above.

Genuinely new work deferred with it: per-entry streaming decompression (gzip,
plus lz4/zstd for PG 16+), and the fact that a raw file offset is not a resumable
position inside a compressed entry. The four Phase 1 choices that keep all of
this additive are recorded under "Decisions that keep later phases open" in
`roadmap-phase1-mvp.md`.

## Phase 2.1: dollar-quote tracking closes the Phase 1 known gap

`pgdump_query::copy::scan_dollar_quotes` now tracks `$tag$ ... $tag$` state
across the whole scan, so a line inside a dollar-quoted function body is
never checked as structure — closing the gap where a body line that happened
to both start at column 0 and match the full `COPY` header grammar would
have been read as a real block. Full write-up:
`docs/design/roadmap-phase2.1-dollar-quote-tracking-notes.md`.

`appendStringLiteralDQ()` in `src/fe_utils/string_utils.c` (source: all three
worktrees) picks `$$` for a function body unless the body itself contains
`$$`, in which case it appends `_`, `X`, `1`, … suffix characters until the
candidate no longer collides. Confirmed empirically on `postgres:16-alpine`:
a body with no `$$` inside dumps as `$$`; a body containing `$$` dumps as
`$_$`. This is the mechanism behind the "tagged delimiter with an inner
untagged pair" test case — the tag doesn't need to be chosen by hand, an
adversarial body forces `pg_dump` to pick one itself.

One trap worth remembering for future fixture-writing: an early draft put
descriptive prose containing literal `$func$`/`$$` substrings in a `--`
comment above the test functions. The scanner read those as real delimiter
tokens (correctly, per its own heuristic — it can't distinguish a comment
from code) and swallowed every block after them. Not a scanner bug; a
reminder to keep dollar-sign pairs out of a fixture file's own prose.

## Phase 2.2: the version header lines print once per `pg_dump` invocation, not once per database

Recorded as `postgres-invariants.md` I9, discovered while validating the new
preamble pass against a truncated slice of the real koji dump (not just the
fixture matrix, which has no `--create` output at all). `RestoreArchive()`
(`pg_backup_archiver.c`) writes `-- Dumped from database version` / `-- Dumped
by pg_dump version` exactly once, near the top of a plain-format file, ahead
of any `CREATE DATABASE`/`\connect` — there is exactly one `RestoreArchive()`
call per `pg_dump` invocation, so a `--create` dump switching into the
database it just created does **not** get a second copy. koji confirms this
directly: one pair, one `\connect koji`, nothing repeated.

`pg_dumpall` is the one shape that does end up with a pair per database, but
only because it isn't one `pg_dump` invocation at all — `pg_dumpall.c` shells
out to a fresh `pg_dump --create` child process per database
(`find_other_exec(..., "pg_dump", ...)`) and concatenates each child's
complete output. Each concatenated segment is its own full `RestoreArchive()`
call and gets its own pair.

This mattered because Phase 2.2's `PreambleBuilder` discards a `--create`
dump's pre-`\connect` segment (it's pure `CREATE DATABASE` noise, never a
real table or type — see `docs/design/roadmap-phase2.2-preamble-notes.md`).
The first implementation discarded the version headers along with it, which
is wrong for exactly the common case (a direct `pg_dump --create`, not
`pg_dumpall`): every such dump's version headers live *only* in that
discarded segment, so `pgdq info` would have shown no version at all for
koji or any file like it. Fixed by carrying `server_version`/`pg_dump_version`
forward onto the database the first `\connect` switches into; a later
`\connect` (real `pg_dumpall` output, untested — no fixture for it) needs no
carry-over, since that database's own segment holds its own pair from its own
`pg_dump` child.

Verification technique worth reusing: rather than running a full ~1-hour
`pgdq parse`/`info` scan of the 784 GB koji file (explicitly against
`CLAUDE.md`'s long-running-process rule for an unattended session), a `head
-n` truncation cut right after the first block's line-anchored `\.`
terminator (`lock_monitor.activity`, found by `grep -n -F '\.'`) produces a
small, valid, self-contained plain-format prefix that exercises the real
preamble bytes end to end in well under a second.

## Roadmap: "role discovery" generalizes into Phase 3, full DDL object inventory

Reasoning behind `docs/design/roadmap.md`'s Phase 3, "Full DDL object
inventory" — inserted between Phase 2 and the former Phase 3 (now Phase 4,
composite value decoding; every later phase shifted up by one to make room).
It replaces the narrower "role discovery" Future item that used to carry
this reasoning.

**I1's short-circuit was never buying meaningful CPU, only correctness
scope.** `PreambleBuilder::feed_line` skips keyword matching once
`preamble_complete` is set, but the scan must already visit every byte of
every gap line-by-line to find the next `COPY` header — there's no way to
skip ahead without an index that doesn't exist yet. Preamble/gap line counts
run to a few thousand even for koji's 784 GB, so the skipped keyword checks
were never a real saving. That means the cheap keyword-dispatch tier can run
over every gap unconditionally, including the post-data tail (last `COPY`
block to EOF) that Phase 2.2 never looks at today, with no measurable cost —
closing the correctness gap outright rather than gating it behind a
gap-size heuristic.

**A byte-size threshold is real, but belongs one tier up.** Interior gaps
between two `COPY` blocks are small in ordinary `pg_dump` output (a
`setval` or a short comment); the post-data tail is the one gap that's
reliably large, because indexes/constraints/triggers/grants/ownership all
land there by `pg_dump`'s own dependency-sort ordering. So the threshold's
job isn't "decide whether to look" (the cheap tier always looks) — it's
"decide whether a leftover, unattributed span is worth a heavier
statement-shape classifier," and separately, a size worth surfacing to a
sysadmin.

**Running the heavier classifier as a deferred, index-driven pass rather
than inline** falls out of `CopyBlock` already storing `header_offset`/
`data_offset`/`terminator_offset`/`end_offset` (`index.rs:49-58`): a
post-scan stage can seek directly to each gap from a persisted index with no
rescan, and a caller who only wants rows never pays for it. `Extension`/
`TypeDef`/table entries in `DatabaseMetadata` carry no offset today, though
— only `CopyBlock` does — so a full file map needs those added before gaps
between individual DDL objects (not just between `CopyBlock`s) can be
computed.

**Coverage as an invariant, not a heuristic.** Once whitespace-run and
comment-run(n lines) join known/known-but-unhandled/unknown as span kinds,
every byte of the file is attributed to something, so "did the scan miss
anything" becomes a sum-of-spans-equals-file-size check rather than a
judgment call — and "this dump has zero comments" or "this dump has an
unusual amount of unrecognized content" become facts read off the map
rather than impressions. That second part matters for testing against
non-`pg_dump`-generated dumps: I1 itself is proven from `pg_dump`'s specific
dependency-sort behavior (`addBoundaryDependencies()`), not a SQL-level
truth, so a differently-built "postgres-compatible" dump has no obligation
to honor it.

## Module layering: four layers, enforced as modules, drawn where crates would go

The library is small (~3,100 lines of `src`) but its module graph is already
an acyclic layering, and the phases ahead each cut across it. Recording the
layer assignment as a standing constraint — `docs/design/layering.md` — is
what keeps that graph a DAG as it grows; the alternative, splitting into
separate crates now, buys the same property at a much higher ongoing cost and
would force API decisions two phases early.

**The split-into-crates motivation is real but is a Cargo feature, not a crate
boundary.** The want is that a caller interested only in dump metadata should
not carry Arrow. In Rust that cost is almost entirely `arrow`'s compile time,
and a feature flag delivers it with no version lockstep across crates and no
API churn. The layering is also *the same property*: if the Arrow-free module
set compiles without `arrow`, L1's independence is machine-checked. So the
feature flag and the layer boundary are one mechanism, and the crate split is
deferred with nothing lost.

**Two boundaries an intuitive split gets wrong**, and the reason the layer
table has four rows rather than three:

- *"Parse row data into Arrow types" is not one self-contained concern.* The
  zero-copy `Utf8View` path appends fields as views into the `arrow::Buffer`
  wrapping the chunk `io.rs` read (`stream.rs:337` converts `Bytes` →
  `Buffer`; `batch.rs` takes views via `append_block`). Array construction is
  therefore married to the reader's buffers and cannot be lifted into a
  standalone types layer. What *is* standalone is type *resolution* — declared
  type string → Arrow `DataType`, plus the decode/render-back functions over
  `&[u8]`. Hence L2 (pure, `arrow::datatypes` only) and L3 (arrays and
  buffers) as separate layers, with the rule that a decode function never
  takes a builder.

- *Predicate application does not stay above the reader.* Phase 5 pushdown
  moves evaluation into the scan loop, which would invert an L4 → L1
  dependency if written naively. It does not have to: L1 defines the callback
  and L4 implements it, the shape `ByteRangeSource` already uses.

**Phase 2 already decided the cache half of this.** "Store what the dump said,
never what we concluded" — `DumpMetadata` holding declared type strings rather
than resolved Arrow types — is exactly "the cache format is L1's, so it cannot
hold an L2 conclusion." Generalizing it to a rule costs nothing now and
pre-answers Phase 5's statistics, where `RowGroupStats` must likewise record
the declared PostgreSQL type a statistic was computed as rather than an Arrow
`DataType`.

Verified at the time of writing: no L1 module imports `arrow`, and no L1
module imports from a higher layer.
