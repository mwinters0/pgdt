# 2026-09-30

## 28.6 keys a timestamp past `i64`, settled with the maintainer

The one value no `predicate::order_key` orders is a `timestamp` or
`timestamptz` past `i64` microseconds from the Unix epoch (`t_extremes`' rows
2 and 13), keyed through `decode::decode_timestamp_micros`: a field there is
`Error::FieldDecode` to a filter, and its group's every-value view is
unbounded ("D97"). An `interval` past Arrow's nanoseconds keys in both orders
(`each_view_of_the_types_fixture_bounds_the_values_it_takes`).

- **28.6 owns the key**, its spec row amended to say so: the refuse mode's
  filter over a column it does not materialize compares the text in
  PostgreSQL's order (the spec's refuse-mode paragraph), the first slice
  needing that value keyed. Until then the view's absence costs nothing,
  every such group's filter refusing on the key. Keying it fills the view
  with no change to the gatherer, and flips that test's `v_ts` assertion.
- **The intended key is `i64` microseconds from PostgreSQL's epoch,
  2000-01-01**, PostgreSQL's own storage, so every value it admits fits by
  construction rather than by a chosen margin; 28.6 adds the
  `postgres-invariants.md` entry once it depends on that. Rejected: `i128`
  from the Unix epoch, a width chosen rather than inherited. The key leaves
  the decoder's epoch, as it already does for the infinities.
