# 2026-09-30

## 28.6 keys a timestamp past `i64`, settled with the maintainer

A `timestamp` or `timestamptz` past `i64` microseconds from the Unix epoch
(`t_extremes`' rows 2 and 13) was the one value no `predicate::order_key`
ordered, leaving its group's every-value view unbounded ("D97"). **28.6 owns
keying it**, its spec row amended to say so: the refuse mode's filter over a
column it does not materialize compares the text in PostgreSQL's order, the
first to need that value ordered. Keying it fills the view with no change to
the gatherer.

- **The key is `i64` microseconds from PostgreSQL's epoch, 2000-01-01**,
  PostgreSQL's own storage, so every value it admits fits by construction
  rather than by a chosen margin (I49; "D97" carries the rejected `i128`).

## `KD56` is a wrong answer under default settings; the shell turns its filter off

`KD56`, filed by 28.5 as the typed mode's harness failure, is DataFusion
55.1's and reaches ordinary data under the provider's defaults: with
statistics gathered and rows undropped, `MIN(x), MAX(x) … WHERE id > 0` over a
column NULL in a partition's first batch answers a `MIN` too high, and
`MIN(a), MAX(a), MIN(b), MAX(b)` answers `b`'s as NULL
(`datafusion-pgdump/tests/aggregate_bounds.rs`). Upstream fixed both cases on
`main` (`docs/status/upstream.md`, "UF1"), in no release yet.

- **The fix is taken only through a DataFusion release** and the pin bump;
  patching it into this workspace would fix our builds and no consumer's.
  Asking upstream to backport it to `branch-55` is the maintainer's to do.
- **`KD56` stays (c) unowned**, promoted by the release carrying the fix.
- **28.7's "the harness is green" excludes the configurations `KD56` meets**,
  its spec row amended: the failure is not particular to unrepresentable
  values, so it is not `KD8`'s to close.
- **`datafusion-cli-pgdump` starts with
  `enable_aggregate_dynamic_filter_pushdown` off** unless the environment
  states it; the library tells an embedder to do the same, a session being
  its caller's (M181).
- **Dependency defects we wait on now have a register**, `upstream.md`, with
  `scripts/upstream.py` resolving each entry to `upstream: UF<k>` markers; the
  `upstream-issue` skill holds its rules and `upgrade-deps` reads it at each
  upgrade. Its three entries are `KD56`'s, `chrono`'s calendar end under
  `arrow-cast`'s display (`RT21`) and `RESET` of a provider's settings.

## D98's calendar tier stays keyed on the semantics

Affirmed with the maintainer: `ComparisonSemantics::Arrow` is DataFusion's
comparison, so keying the calendar tier on it keys it on the front end, and a
field beside it would state one fact twice (D98's Rejected). The name hides
that, so the variant is renamed `DataFusion` (M182, blocking nothing); a
front end other than DataFusion takes semantics of its own, filed in P24's
inbox. The tier retires with `upstream.md`'s "UF2".

- **M182 renames what names the semantics**: the variant, "Arrow('s)
  semantics" in rustdoc and the register, the tests named for it, and the
  nested-column refusal's text (`predicate.rs`, `NESTED_IN_DATAFUSION`).
- **What names DataFusion semantics' mapping is renamed too (M183)**,
  settled with the maintainer: `arrow_order`, `arrow_divergence`,
  `arrow_position_divergences` and both `arrow_divergences` become
  `datafusion_*`, their contract being that semantics' order, `-0` made `0`
  and an enum compared by label being DataFusion's choices, not Arrow's
  kernels'; `BoundsSet::Arrow` and `arrow_bounds` become `DataFusion` and
  `datafusion_bounds`, their kind being `arrow_order`'s, which renames
  `pgdt info --json`'s key and leaves bincode's cache unchanged;
  `NestedArrowOrder` becomes `NestedOrder`, named for what differs as its
  neighbours are. Prose on `make_comparator` inside a nested column keeps
  "Arrow", being literally Arrow's. The P28 spec's "in Arrow's (the
  DataFusion translators)" is renamed with them, a term changed and no
  decision. Rejected: an "emitted order" name, no one order being the
  emitted value's. Prose calling the second bounds set "the Arrow set" or
  "Arrow's order" says DataFusion's with them, "D79" included;
  `ARROW_AGREEMENT` and `arrow_against` keep the name, holding the order to
  Arrow's kernels literally.

## The pruning check's error leg returns over `KD2`, settled with the maintainer

28.6 deleted the generated pruning check's error leg, its population (the
refuse mode's read-time refusals, the unkeyed timestamp) gone. `pg_dump` still
writes a value this library fails to decode at read time: a multi-dimensional
array in a composite field, left on the optimistic path by a census keyed by
column (`KD2`). So the leg can have a population inside the input contract,
not only one hand-built from text no type reads.

- **M184 restores the leg and its floor** (`errors_raised_pruned > 0`), a row
  of the types schema holding a 2-D array in a composite field at every major
  (`public.tagged`'s `tags`, `scripts/fixture_schema_types.sql`). The check
  already builds filter terms over columns its projection leaves out, so a
  term comparing that column raises wherever evaluation reaches the row. It
  is the first generated fixture for `KD2`, whose one test is hand-written
  (`tests/decode.rs`, `an_array_inside_a_composite_keeps_the_optimistic_path`,
  which says no fixture writes one). Blocks nothing in P28.
- **The population lives exactly as long as `KD2`.** When a path-keyed census
  closes it, the floor goes red. That is when a hand-built dump holding text
  no decoder reads, fed through `check_fixture`, becomes the population. It is
  outside the contract, so it is not chosen while a population inside the
  contract exists.
- **Until M184 lands, only the tree walk is tested.** D54's clause that a
  decode failure is never raised in a group statistics rule out, or past a
  sorted block's stop, has no test. The only test of where a failure is
  reached is `predicate.rs`, `a_decode_failure_surfaces_only_where_it_is_reached`.

## `pgdump_unrepresentable`'s guard becomes the embedder's to install, settled with the maintainer

`install_unrepresentable`, run by `register_dump` and
`register_table_factory`, rebuilds the caller's `SessionState` to wrap its
query planner ("D101"). DataFusion 55.1 has no in-place setter for either a
query planner or a physical optimizer rule, so installing either into a live
`SessionContext` is a rebuild, and **a rebuild drops the session's prepared
statements** (`SessionStateBuilder::build`, `prepared_plans:
HashMap::new()`, `session_state.rs:1639`; nothing public copies them). The
`Installed` mark lives in the config's extensions, which survive an
embedder's later `with_query_planner` rebuild while `Guarded` does not, so
the guard can be lost and a later registration will not restore it.

- **Refusing on evaluation is sound**: `invoke` always errs, and DataFusion
  skips it only where the answer does not depend on it (an `AND`'s
  short-circuit, an untaken `CASE` branch, an empty batch, `IS NULL` folded
  on the non-nullable return field). Refusing at planning makes the refusal
  independent of the data and early; it is not what makes an answer right.
- **Registration registers the function and leaves the session's planning
  alone**; the planning refusal is a guard the embedder installs, and
  `datafusion-cli-pgdump` does. The roadmap's "Standing rules" already hand
  an embedder a mechanism to take deliberately, and DataFusion extensions
  needing a planner (datafusion-federation, delta-rs) are set on the
  builder by their embedder. Rejected: the function too made opt-in, which
  withholds even the pushed use, always sound.
- **The guard is a physical optimizer rule, not a wrapped planner.** "D101"
  rejected a physical rule for having no expression walk; 55.1's
  `ExecutionPlan::apply_expressions` is a required method
  (`physical-plan/src/execution_plan.rs:349`), `PgDumpExec` reports only its
  dynamic filters (`exec.rs:238`), and a scalar subquery's plan is a child
  of `ScalarSubqueryExec` (`scalar_subquery.rs:162`). A rule joins a list
  rather than taking the one planner slot, and the function anywhere in the
  physical plan is DataFusion evaluating it, where the logical walk needs
  "RT22"'s claim that an `Exact` conjunct leaves every node above its scan.
- **The guard is offered on a `SessionStateBuilder` alone**, appending the
  rule and the function, so nothing rebuilds a session its embedder owns: one
  holding a live `SessionContext` rebuilds it with `new_from_existing`, the
  prepared statements lost in its own code. `datafusion-cli-pgdump` builds its
  state rather than calling `SessionContext::new_with_config_rt`. Rejected: a
  `SessionContext` form, the rebuild back with a doc comment on it.
- **An embedder without the guard learns of it from the refusal**: the error
  `invoke` raises says the guard moves it to planning, and `register_dump`'s
  and `register_table_factory`'s rustdoc name it. Rejected: a `Finding` at
  registration, nagging a choice that loses no answer.
- **28.11 lands it** (the P28 spec, "Slices", and its scope clause amended),
  before 28.9, which times nothing that reads the term.
