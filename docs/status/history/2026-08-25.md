## An `INSERT` run costs ~5× what a `COPY` block costs, per byte

Out-of-band item **M3** — the measurement slice 3.6 deferred — is done, and it
does not confirm what 3.6 assumed. Three 3.00 GiB synthetic dumps on the SSD,
`pgdq info --dqcache none` in a 512MB-limited container, run three times each
back to back in one session so page-cache state is comparable:

| Input | Wall (3 runs) | Rate |
|---|---|---|
| `COPY` block (`generate_perf_data.py`) | 3.27 / 3.24 / 2.55 s | ~1.0–1.26 GB/s |
| Large-object region (`generate_large_object_bench.py`) | 4.99 / 4.28 / 3.61 s | ~645–890 MB/s |
| `INSERT` run (`generate_insert_run_bench.py`, new) | 14.74 / 14.79 / 14.55 s | ~218–221 MB/s |

`cat`-to-`/dev/null` of the same files takes 3.67–3.85 s (~840–880 MB/s), so
**the `COPY` and large-object scans are at the I/O floor and the `INSERT` scan
is four times above it** — roughly 11 s of CPU per 3 GiB that the other two do
not spend. Max RSS is ~35–42 MB for all three; the fold-into-one-span half of
3.6's `INSERT` work does what it claimed, and memory is not the issue.

**So `Event::Line` decode plus the statement accumulator dominates an
`INSERT`-run scan**, which is the outcome 3.6's notes named as the one that
would earn `INSERT` runs a scanner-level fast path. Mapping an `--inserts`
file costs about what *decoding* a `COPY` file costs (Phase 1's 243 MB/s
baseline), not what *scanning* one costs — the "cheap tier" is not cheap for
this input. Concretely: a koji-scale 1 TB `--inserts` dump maps in ~75
minutes rather than the ~15 the `COPY` rate implies.

This changes a decision rather than confirming one, so per the roadmap's
out-of-band admission rule M3 stops being an out-of-band item at exactly this
point: the measurement was in scope, the response is not. Building the
scanner-level path needs grilling and a slice number, and the maintainer has
not seen this number yet — it is filed in `STATUS.md`'s "Decisions worth
another look" and as a Phase 7 inbox entry, and the residual cost is recorded
as a known gap. Nothing in Phase 3's own "Verification" section gates on it;
both measurements that *do* gate the phase were already done.

The new generator is `scripts/generate_insert_run_bench.py` (committed; its
output is not — regenerate with `--seed 42`). What it writes is one
`INSERT INTO public.bench_inserts VALUES (…);` per line under an ordinary
`TABLE DATA` TOC comment — 7,656,060 rows, with an apostrophe doubled the way
`pg_dump` writes one in ~15% of them, so the accumulator's quote tracker is
actually exercised.

All three inputs are left in place at
`/mnt/ssd/fedora/pgdump_query-bench/{copy_control,insert_run_bench,large_object_bench}.sql`;
the `COPY` one came from Phase 2's `generate_perf_data.py --size-mb 3072
--seed 42`.

## The keystone: the doc set is now filed by subject, not by phase

Phases 1-3 are complete and the system's shape is settled — every use case has
an implementation, and what remains is expansion or ergonomics, not structure.
That is the point at which the phase-by-phase record stops holding anything up.
`docs/process.md` gains the general rule as step 7 and "The keystone: striking
the centering"; this entry records why it was worth doing here.

**The measurement that motivated it.** The phase 1/2/3 specs and notes were
187KB of a 477KB doc set — 39%, or 42% counting the roadmap's phases 1-3
sketches. Rust carried 273 phase references across 26 files, of which a large
share was pure provenance: `cache.rs` had fourteen lines of "bumped to 2 in
Phase 3.2; to 3 in 3.2.1; to 4 in 3.2.1.2.1…" that `git log -p` already held.

**The correction to the obvious reasoning, which set the order of operations.**
Orientation cost is set by what `CLAUDE.md`'s read-triggers pull into context,
not by what exists on disk. `history/2026-08-22.md` is 26KB and costs nothing,
because no trigger names it. Meanwhile "read `roadmap-phase3-object-inventory.md`
before touching `DumpIndex`, the cache format, the preamble grammar, or
anything that adds a span kind" was 52KB plus 36KB of notes — ~22k tokens, paid
on most sessions. So the saving comes from **retargeting**, and deletion does a
different job: it removes the second authority, so nobody has to adjudicate
between the spec and the distillate. Deleting first would have saved nothing
and destroyed the source the distillate came from.

**What could not have been rediscovered.** The premise that the docs could be
deleted and re-derived from code holds for provenance, module maps, and the
span/enum vocabulary. It fails for **rejected alternatives**, which the code
cannot record by construction — and fails silently, because a session that
doesn't know an approach was tried will build it. The load-bearing examples now
carried in `architecture.md`: the start-floor-on-`Builder` attempt (it tiles,
but makes a multi-scan map differ from a single-pass one); close-time span-text
slicing (needs a retention watermark fed back into two scan drivers); TOC-driven
segmentation as the primary structure (fails on non-`pg_dump` input, and I3's
own caveat means the statement grammar must corroborate anyway); lazy type
resolution (makes the Arrow schema depend on scan progress); `spans` alongside
`blocks` (two owners for one byte offset); Arrow's own display formatting for
`pgdq query` (does not round-trip). Harvesting these was the first step, before
anything was deleted.

**What the distillate cost.** The record of *intent* is gone: "what did phase 3
commit to, and did it deliver?" is no longer answerable, and cannot be
reconstructed from a document describing the result. That question expires at
the keystone by construction, which is what makes it affordable.

**One number came out smaller than expected.** `architecture.md` is 64KB, not
the ~22KB projected. The three notes docs were 66KB and were already ~90%
subject-filed durable content wearing a phase title — the re-filing was mostly
a *move*, not a compression. The doc set went 477KB → 356KB (-25%), and the
read-triggered set for a `DumpIndex` change went 88KB across two docs to 64KB
in one, section-addressable via a contents table. The specs were the expendable
half; the notes never were.

## Out-of-band **M4**: `pgdq info --json`

Phase 3's "CLI surface" section has carried "the output shape is provisional,
pending real user trials" since it was written, and users have since asked
for the dump's structure in several different shapes for several different
scripts. Rather than picking one and growing a bouquet of flags this early,
`pgdq info` gained `--json`: it serializes `DumpIndex` (or, with
`--preamble-only`, `DumpMetadata`) straight through `serde`, with
diagnostics added back in (`DumpIndex::diagnostics` is `#[serde(skip)]` for
the cache's own reasons, which don't apply to a one-shot export). No new
field, method, or shape was designed for it — `Serialize` was already
derived on every type in the structure except the diagnostic channel
(`Severity`/`DiagnosticKind`/`Diagnostic` in `pgdump_query/src/diagnostic.rs`,
`TilingIssue` in `map.rs`), which now derives it too. `--json` is rejected
alongside `--verbose`/`--map`, since both only add formatting detail the raw
struct already carries.

This changes no decision the architecture doc records — the text output's
"provisional" status is untouched, and the JSON carries an explicit zero
compatibility promise of its own, so a later change to `DumpIndex` is free to
change the JSON along with it. That is what keeps it out-of-band rather than
a slice: `docs/design/architecture.md`, "CLI surface", and
`docs/manual/dump-inspection.md`, "Scripting against the output: `--json`",
both say so explicitly. Detail: `pgdump_query-cli/src/main.rs`'s
`IndexJson`/`MetadataJson`.

## Phase 4 is grilled and specified

`docs/design/roadmap-phase4-composite-decoding.md` holds the decisions and the
six-slice plan; `STATUS.md` carries the unchecked checklist. Recorded here is
only what changed the plan.

**The roadmap's premise for this phase was wrong in a way that changes the
work.** It grouped the families because each is "a value rendered by COPY TEXT
with its own nested quoting rules" and concluded that "writing that nested
decoder once unlocks all three". The second half does not follow from the
first: `array_out` backslash-escapes inside a quoted element while `record_out`
and `range_bound_escape` double, and the three force-quote on different
character sets. What is written once is a quoted-token scanner *parameterized*
by wrapper, separator, force-quote set and escape convention; the three
instantiations are the cheap part. A composite inside an array carries both
conventions at once. Recorded as I20.

**Array dimensionality is per-value and the DDL says nothing about it** (I21,
verified against a live server: one `int[]` column took `{1,2}`,
`{{1,2},{3,4}}` and `[0:2]={7,8,9}` in consecutive rows). This collides with
"one schema per stream, resolved up front". The maintainer's ruling: a full
scan of the data to learn shapes across every `COPY` block is an acceptable
price, which turns the baseline hard `FieldDecode` into a floor rather than the
answer.

**koji cannot size this phase, and that is itself the finding.** Its six array
columns are all `text[]`, all in `lock_monitor.transaction_locks`, which has 19
rows — and every one of the six is NULL in every row. There are no composite,
range or multirange columns at all. So the flagship dataset contains zero
non-scalar values, and it can neither measure the cost of a representation nor
argue for one. Phase 4 chose `List<T>` over the shape-general
`Struct{dims, lbounds, elements}` on that thin evidence plus Arrow-layout
arithmetic (+16 bytes per row, worst on short arrays: +80% for one element,
+400% for an empty one), and **the maintainer's ruling was to preserve the
struct as a selectable alternative rather than discard it** — a schema of
matrices or scientific data inverts the arithmetic, and those users should get
the struct, not a string. It is filed under the roadmap's "Future" section as a
knob, beside caller-supplied type mapping.

**Nested predicate semantics were measured on both sides rather than assumed,
and the answer was to change nothing.** PostgreSQL compares these as values
(`array_eq` is dimension- *and* lower-bound-sensitive but treats NULL elements
as equal; discrete ranges canonicalize on input, so `'[1,2]'::int4range` stores
and dumps as `[1,3)`), and DataFusion v55 is structurally the same — element-wise
list comparison, struct equality coerced by field name. Neither compares text.
But every value in a *dump* is already in canonical output form, and
`predicate.rs` compares the COPY-unescaped field before any nested decoding
happens, so leaving it untouched is byte-identical to today and agrees with
PostgreSQL except when a user types a non-canonical literal. Full semantics are
filed in the new `roadmap-phase5-inbox.md`, which is where the input-side
grammar and range canonicalization belong.

## The two unattended Phase 4 calls are reviewed and stand

Both `STATUS.md` entries are ratified as built. What the review added is on the
spec, not the code.

**`NestedPlan` beside the `DataType` stands, and its rejected list gains the
alternative it was missing.** The collision is real rather than theoretical —
`batch.rs`'s `array_of_ranges_and_multirange_share_a_type` asserts that
`int4range[]` and `int4multirange` produce *identical Arrow data* from
different literal text — and the `Field`-metadata rejection is correct on
arrow-rs's facts: `Field`'s `PartialEq` includes `metadata`, and
`DataType::List(FieldRef)`/`Struct(Fields)` embed the field, so metadata enters
every schema comparison.

The alternative neither the slice nor the entry considered is a **single tree
owning both** halves (`Scalar(DataType)`/`Array(Box<…>)`/… with a
`data_type()` accessor), which makes a type/plan disagreement unrepresentable
rather than a panic. It was weighed and declined: the drift window is two
sites, both inside this phase — resolution produces the pair, 4.5's census
rewrites it — so the cheaper defence is the rule that those are the *only* two,
which the spec now states. The single tree is the named fallback if the pairing
ever gains a third writer.

**`render_field` does not survive 4.4.** Today it is safe because nothing
resolves to a nested type; the moment 4.4 flips resolution it panics on one,
through an `unreachable!` whose message ("`resolve_columns` never resolves a
column to …") has by then become false. Deleting it and giving the name to
`render_field_with_plan` turns "did every caller switch?" into a compile error.

**The cache entry's one forward risk does not exist.** The worry was that 4.5's
census-completeness rule would need a fact `CacheMode::load` had discarded.
`table_stream` already computes `source.size()` before mapping (`stream.rs`),
and the CLI's live path already open-codes the same comparison
(`main.rs`), so the check is free at the point the census is consumed. 4.5
names it `DumpIndex::is_complete(size)` — three call sites is where the rule
earns a name; two would have been a rename. `architecture.md`'s claim that
`CacheStatus::Incomplete` *is* the reusable primitive was over-broad and now
distinguishes the cache-only caller (matches the variant) from the
live-source caller (compares against the size it stats anyway).

## The Phase 4 review's second round: three spec amendments

**A per-column reason is a note, never a file-level diagnostic.** The spec had
the census degradation and the opaque-element refusal becoming `DiagnosticKind`
variants. Every variant that channel actually holds is a property of the file —
`TilingBroken`, `CacheMtimeChanged`, `CacheOffline`, `TocCoverage` — and the
note-versus-diagnostic split is stated deliberately in `architecture.md`: one
`ColumnNote` per column always, with success the ordinary case. The reason the
spec gave for the choice is also false on inspection: `--json` exports
`DumpIndex`, which carries no `ResolvedSchema`, so a column-level fact is
invisible there whichever type holds it. They become `ColumnResolution`
variants instead, and `Deferred`/`DeferredKind` are deleted in the same move —
these four families are the only things that defer, so after the flip the
variant is an option no input can reach.

**The plan is a third parallel vector on `ResolvedSchema`.** `ColumnNote` is
the human-facing record and no display reads a plan; a payload on
`ColumnResolution::Mapped` would express the invariant best but breaks the
three sites comparing that enum by equality (`unmapped_count`,
`ColumnNote::severity`, the CLI's unmapped filter), to buy a coupling that
"one producer" already supplies.

**4.4 splits, and the split is planned rather than earned.** Its scope had
grown to one rework of `pgtype.rs`/`resolve.rs`/`batch.rs` *plus* the `info`
rendering and the manual rewrite — two review confidences in one diff, which
the process doc's sizing rule exists to prevent. The presentation half becomes
`4.4.1`. A third level is meant to be earned mid-slice, and planning one is
off-label; it beats the alternative, which is renumbering the census and the
measurement and invalidating every reference to them.

## The delimiter trap survives a domain, and 4.1's fixtures did not know

Phase 4's spec removed the `typdelim` trap by refusing to type an array whose
element is `box` or a `TypeKind::Base`. Two facts verified against upstream
(now I22) say that rule leaks:

`typecmds.c`'s domain-definition path copies `delimiter = baseType->typdelim`,
so `CREATE DOMAIN d AS box` gives `d` the delimiter `;`, and `CREATE DOMAIN`
has no clause that records it — the base type's *name* is the only trace in the
dump. Meanwhile `pgtype.rs` unwraps domains transitively and `box` is a
built-in, so `d` resolves to `Unknown`, not `OpaqueBaseType`: it is named
neither `box` nor `Base`, slips the refusal, and lands as `List<Utf8View>`
split on the wrong character. Wrong element boundaries, silently — the failure
mode the rule exists to prevent, reached through the path the rule did not
consider.

The refusal now tests the element type *after* domain unwrapping. A domain over
a user-defined base type was already safe, because unwrapping preserves
`OpaqueBaseType`; only the built-in `box` leaked, because it alone is
recognized by name.

**Two facts bound the fix and are why it can stay this small.** `box` is the
only entry in `pg_type.dat` with a non-default `typdelim`, identical v13.23
through master; and `record_out` writes `,` unconditionally with no reference
to any field type's delimiter. Arrays are the entire exposure — composites,
ranges and multiranges carry no equivalent.

*Rejected:* refusing every array whose element does not map. Same hole closed,
but it degrades `interval[]`, `money[]` and every unknown-element array to a
whole-column string, where `List<Utf8View>` recovers the element boundaries
correctly.

**This earns `4.1.1`.** The fixture value that would catch it does not exist,
and 4.4 is where the refusal is implemented — so the fixture has to land first,
and a fixture regeneration is its own review rather than a rider on the
resolution rework.

## Three more things the flip would have broken at row 1

**Six hardcoded range subtypes are half the table.** `map_builtin` recognizes
twelve bare names — the six built-in ranges and their six PG14+ multirange
companions — and answers `Deferred(DeferredKind::Range)` for all twelve,
because until now nothing needed them told apart. 4.4 has to *introduce* that
distinction, in the built-in table and again in `resolve_user_type`'s
`multirange_type_name` fallback (I10). Implementing the spec's paragraph
literally would have typed a `{[1,10),[2,3)}` column as a `Struct`.

**A composite's field list has to be all-or-nothing.** `parse_create_type` uses
`filter_map`, so an unparseable field fragment is silently dropped and the type
keeps a short list. `record_out` is positional with no field names, so there is
no recovery: a three-field type parsed as two makes the field-count refusal
fire on every row of valid data, and relaxing that check later would instead
decode field 3's text as field 2's type. The `CREATE TABLE` path keeps its
`filter_map` — there `resolve_columns` joins by *name*, which is exactly what
makes a dropped column degrade to a string instead of shifting everything after
it. The asymmetry is now stated so it does not get tidied away.

**A zero-field composite maps rather than being refused.** The `EmptyEnum`
precedent points the other way and does not transfer: a zero-label enum has no
value its dictionary can hold, while `()` is a real value that round-trips
exactly through a well-formed zero-field `StructArray`.

All three need fixture values that do not exist, which is what `4.1.1` is for.

## The census needed a second number, and it does not reach nested arrays

**A maximum dimension count cannot detect mixed dimensionality.** The census as
specified stored one per column, and the rule it feeds has three outcomes:
uniform 1-D, uniform 2-D, mixed. A column holding `{1,2}` and `{{1,2},{3,4}}`
records `max = 2`, and so does a column holding only 2-D values — so the mixed
column would have resolved to `List<List<T>>` and then failed the decoder's
dimensionality refusal on every 1-D row. That is the confidently-wrong schema
the census's own completeness rule exists to prevent, produced by the census
itself. It stores **min and max** now, uniform being `min == max`, with SQL
NULL and `{}` contributing to neither (I20: `{}` fits any depth).

**The census is keyed by column, so an array inside a composite is never
covered.** I21 is a fact about values, not positions: a `text[]` field of a
composite varies in shape exactly as freely as a top-level `text[]` column, and
the per-column census has nowhere to put it. So "census present → the error
becomes unreachable" holds only for top-level array columns; a nested array
stays on the optimistic path however much scanning has happened. Stated as a
limit rather than fixed — a per-*path* census is filed under the roadmap's
"Future", where it is purely additive: it only ever converts a hard error into
a resolved type.

**No multirange fixture is needed.** `fixture_schema_types.sql` already carries
`t_multirange` with a bare built-in and `myrange`'s companion, `{}` and NULL
rows included, behind an `\if :has_multirange` gate — the per-version
conditional mechanism the schema already uses. `4.1.1` is the domain-over-`box`
array and the zero-field composite only.

## The resolution flip landed, and it took the cache to v10 first

Phase 4.4 is in the tree (unreviewed, uncommitted): the four container
families resolve to real Arrow types and decode end to end, `Deferred` and
`DeferredKind` are gone, and `render_field` takes a `NestedPlan`. Detail is in
`docs/design/roadmap-phase4.4-resolution-flip-notes.md`; only what changed the
plan is here.

**4.5's cache bump is now v11, not v10.** The spec's all-or-nothing rule for a
composite's field list needs "no fields parsed" and "no fields declared" to
stay apart in the type definition (I23's "Relied on by" says so explicitly), so
`TypeKind::Composite::fields` became `Option<Vec<…>>` — a reshaped persisted
field, which the cache's own stated rule says to bump for. The decision the
spec records is untouched: the census still bumps the format, and the integer
was never the decision. The alternative considered and declined was dropping
the whole `TypeDef` for an unparseable body, which needs no bump but hides the
type from `pgdq info`'s census and makes the column's reason
indistinguishable from a type the dump never declared.

**`StructArray::new` panics on a zero-field struct.** It reads the row count
off the first child, and a zero-field composite (I23) has none —
`try_new_with_length` is the constructor that takes it explicitly. Together
with `decode_record("()")` reporting one NULL field, this is the second thing
about `CREATE TYPE x AS ()` that only shows up once a fixture holds the value.
Both are handled in `batch.rs`; neither was visible to 4.3, whose tests built
every nested shape by hand.

**I24 is new**: PostgreSQL refuses to create a type that contains itself
through composites, ranges, domains or array elements
(`CheckAttributeType`'s `containing_rowtypes`), which is what lets
`resolve_declared_type` recurse with no cycle guard and no depth limit — the
same licence the domain walk already took, now extended to three more routes
and written down.

**The koji scan is not re-run.** Nothing in this slice touches the map, the
scanner or the row counts, and koji holds no non-scalar values at all, but the
phase spec lists it under Verification: it is outstanding, not passed.
