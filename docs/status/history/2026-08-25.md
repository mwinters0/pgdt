## An `INSERT` run costs ~5× what a `COPY` block costs, per byte

Out-of-band item **M3** — the measurement slice 3.6 deferred — is done, and it
does not confirm what 3.6 assumed. Three 3.00 GiB synthetic dumps on the SSD,
`pgdq info --dqcache none` in a 512MB-limited container, run three times each
back to back in one session so page-cache state is comparable:

| Input | Wall (3 runs) | Rate |
|---|---|---|
| `COPY` block (`generate_perf_data.py`) | 3.27 / 3.24 / 2.55 s | ~1.0–1.26 GB/s |
| Large-object region (`generate_large_object_bench.py`) | 4.99 / 4.28 / 3.61 s | ~645–890 MB/s |
| `INSERT` run (`generate_insert_run_bench.py`, new) | 14.74 / 14.79 / 14.55 s | ~218–221 MB/s |

`cat`-to-`/dev/null` of the same files takes 3.67–3.85 s (~840–880 MB/s), so
**the `COPY` and large-object scans are at the I/O floor and the `INSERT` scan
is four times above it** — roughly 11 s of CPU per 3 GiB that the other two do
not spend. Max RSS is ~35–42 MB for all three; the fold-into-one-span half of
3.6's `INSERT` work does what it claimed, and memory is not the issue.

**So `Event::Line` decode plus the statement accumulator dominates an
`INSERT`-run scan**, which is the outcome 3.6's notes named as the one that
would earn `INSERT` runs a scanner-level fast path. Mapping an `--inserts`
file costs about what *decoding* a `COPY` file costs (Phase 1's 243 MB/s
baseline), not what *scanning* one costs — the "cheap tier" is not cheap for
this input. Concretely: a koji-scale 1 TB `--inserts` dump maps in ~75
minutes rather than the ~15 the `COPY` rate implies.

This changes a decision rather than confirming one, so per the roadmap's
out-of-band admission rule M3 stops being an out-of-band item at exactly this
point: the measurement was in scope, the response is not. Building the
scanner-level path needs grilling and a slice number, and the maintainer has
not seen this number yet — it is filed in `STATUS.md`'s "Decisions worth
another look" and as a Phase 7 inbox entry, and the residual cost is recorded
as a known gap. Nothing in Phase 3's own "Verification" section gates on it;
both measurements that *do* gate the phase were already done.

The new generator is `scripts/generate_insert_run_bench.py` (committed; its
output is not — regenerate with `--seed 42`). What it writes is one
`INSERT INTO public.bench_inserts VALUES (…);` per line under an ordinary
`TABLE DATA` TOC comment — 7,656,060 rows, with an apostrophe doubled the way
`pg_dump` writes one in ~15% of them, so the accumulator's quote tracker is
actually exercised.

All three inputs are left in place at
`/mnt/ssd/fedora/pgdump_query-bench/{copy_control,insert_run_bench,large_object_bench}.sql`;
the `COPY` one came from Phase 2's `generate_perf_data.py --size-mb 3072
--seed 42`.

## 3.6's ~1.9 GB/s large-object figure is a page-cache-warm number

Re-run cold in this session, the same 3 GB large-object bench measures
~5.7–6.4 s (~560 MB/s) rather than the ~1.6–1.7 s (~1.9 GB/s) recorded on
08-24, and warms back to ~3.6 s (~890 MB/s) — the `cat` floor for the same
file — on a third consecutive run. 1.9 GB/s is more than twice what this disk
delivers to `cat`, so that figure could only have been served from page cache;
the file had just been generated when it was taken.

It stands as a measurement of the *scan path* and 3.6's conclusion is
unaffected — the skip is still several times cheaper per byte than walking the
same bytes, and it is now the `INSERT`-run comparison above that shows what
"walking" actually costs. What changed is how the number should be read: as a
ratio against another figure taken in the same cache state, never as a disk
throughput. The consolidated notes doc records both the warm and cold figures
with the `cat` floor beside them, so the next reader does not have to
re-derive this.
