# 2026-09-10

## `xz-seek`'s interface is final: `P8` is landed and nothing else in it moves

**From `xz-seek`'s `8.4`, which is the slice that owed this message.** Their
`P8` — the range read fetches whole blocks and decodes from borrowed bytes — is
complete, and it is the last of their work that moves a number `19.14` divides
by. Earlier slices deliberately sent nothing: `8.1` through `8.3` each moved the
surface, and a consumer told mid-flight would have built against a figure that
changed again. Their `8.4` changes no surface at all, which is why it carries
the message.

**`Reader::decode_footprint()` is unchanged, in value and in composition.**
9,471,776 B on the koji shape under `liblzma`, 9,467,864 B under `xz4rust` —
the same numbers `7.4` published. `19.14` divides by exactly what it was going
to divide by.

One caveat is new and does not reach this consumer. The chunk term is now an
**upper bound** rather than an allocation that always happens: a source that can
lend the decoder a slice of itself — a memory map, a `bytes::Bytes` — is decoded
out of borrowed bytes and holds no input chunk at all, so `decode_footprint()`
over-charges such a caller by 1 MiB. `XzSource` opens a `std::fs::File`, which
declines to lend, so the number is exact here.

**Four things in their public surface moved, and one of them is a removal.**
The message that arrived named three; `StreamEntry`'s new field is the fourth
and the only one that breaks a build here.

- `StreamEntry` gained `first_block_dict_size: Option<u64>` — the per-stream
  dictionary `decode_footprint()` maxes over. It reshapes the persisted
  `SeekTable`, so it is what `M77`'s `FORMAT_VERSION` bump is for, and two
  synthetic table literals in `io.rs` construct `StreamEntry` field-by-field.

- `CompressedSource` gained a third method,
  `fn slice_at(&self, offset: u64, len: usize) -> Option<&[u8]>`, **provided**
  and defaulting to `None`. An existing implementor compiles unchanged. `None`
  means *ask `read_at`* and never means end of file, so implementing it can skip
  a copy and cannot introduce an error case.
- `RangePlan::input_chunk_bytes()` is **gone**. `Reader::input_chunk_bytes()` is
  in its place — the accessor moved to where the memory actually is, because no
  decoder on the range path owns an input buffer any more.
- `RangePlan::footprint()` lost its `workers × chunk` term, so it reports
  **less** and `admitted_workers` admits **more** inside the same budget. On the
  koji multistream shape the per-worker unit goes 34.3 → 33.3 MiB and 512 MiB
  admits 15 workers where it admitted 14; on the 128 MiB-block recompression the
  unit goes 143.4 → 142.4 MiB and 3 workers is 3 either way.

**Only the first reaches the library**, which calls `Reader::new`,
`Builder::open_with_table`, `SeekTable::from_source`, `block_task`/`decode_into`
and `decode_footprint`, and never `plan_range`, `footprint()` or `fits()`. The
`xz_decode` **example** does call `plan_range` and `footprint()` and clamps on
`plan.workers()` — it reaches past the library to the decoder's own bulk entry
point on purpose — so the smaller footprint admits more workers there at the
same budget. It never called the removed accessor, so nothing failed to compile.

**The message also found two doc comments here false in both directions**, and
the re-vendor it called for is `M77` below, which corrects them and carries the
reasoning: the dictionary went **into** their `RangePlan::footprint` at `7.5`
and the input chunk came **out** at `8.3`, so a sentence naming that plan as
excluding the dictionary and allowing 8 MiB a worker was wrong at each end.

**Their register moved by two entries, and one of them is worth knowing about
if this repository ever brings a resident source.** `KD11` — the plan charging a
compressed window at one worker that the read never allocated — is struck,
because the read now allocates it. `KD12` is new, stance *(a) deliberate
tradeoff*: a caller whose source already holds the compressed bytes still pays
one copy of every one of them, because the fetch stage builds a window out of a
source that could have lent the range. It is `workers + 2` compressed windows,
20.6 MB of 482.1 MiB at 14 workers on the multistream shape. A `File`-backed
reader is unaffected.

**And the pool's own overhead is now measured rather than bounded.** Their `F5`
prices per-block coordination at **3,107 instructions**, 0.0010% of what one
24 MiB block costs to decode — five orders of magnitude, where the same figure
read four before `P8` removed a copy from its numerator. If any partition-sizing
argument here treats scheduling cost as a reason to prefer larger units of work,
it is arguing from a term that does not exist at this scale.

## `M77`: the re-vendor, and the window route priced and refused

**`vendor/xz-seek` is at `87d55715`**, from `5b549d72` of 2026-09-06 — forty
commits, taking that crate's `P7` (the decode footprint), `P8` (borrowed input)
and `M25`. `19.14` is unblocked: `xz_seek::Reader::decode_footprint()` is
callable, 9,471,776 B on the koji shape, and the charge that slice assembles no
longer needs a constant standing in for the decoder's own retention.

**The whole compile cost was two fields.** `StreamEntry` gained
`first_block_dict_size: Option<u64>`, which two synthetic table literals in
`io.rs` construct field-by-field; nothing else in the tree moved. That was
established before the sync rather than after, by vendoring into a throwaway
worktree and running `cargo check --workspace --all-targets` there — so the
question "what does this break" was answered while the working tree was still
clean.

**`FORMAT_VERSION` is 17, and the bump is load-bearing rather than tidy.** The
new field is inside the persisted `SeekTable`, so the rule on the constant —
bump whenever a persisted field is added, removed or reshaped — applies
directly. What makes it more than bookkeeping is the order in `read_cache_file`:
the envelope is `bincode`-decoded *whole* before the version is looked at, and
`bincode` is not self-describing, so an old cache read by the new binary
mis-frames every byte after the first stream entry. That decode may fail — an
`Option` tag byte that is neither 0 nor 1 — or it may succeed and hand back a
plausible-looking table. `format_version` is `CacheFile`'s **first** field, so
it decodes correctly whatever happens after it, and the check is what turns the
second case into `UnsupportedVersion` rather than a silently wrong table. Both
outcomes start cold. The price is a cold re-scan of the koji dump, accepted
knowingly when that crate's `P7` was specified.

**No figure went from green to red.** Three declare `vendor/xz-seek/src/` —
`xz-decode-scaling`, `parallel-scan-throughput`, `parallel-peak-rss` — and all
three were already stale on paths this change did not touch, `xz-decode-scaling`
on `scripts/generate_xz_input.py` since `4f573b7`. So the re-vendor adds a
reason to figures already red and owes no acknowledgement.

### The window route is refused against a local file, and the number is why

`xz-seek` guarantees that a block decodes out of a `Window` cut to its own
`compressed_range()` without copying the compressed bytes — `fill` asks for the
*block's* remaining tail, so the window holds it whole and lends it. Taking that
route here would close that crate's `KD3` for this caller: a positioned block
read costs two source reads, the header's and the payload's, and against a
window both come out of memory.

**It is not a memory saving, which is the premise that had to be corrected.**
The window is the block's whole compressed extent where the input chunk it
replaces is capped at 1 MiB, so a caller that takes it holds *more*, by an
amount that scales with the block size — on the two koji files, +242 KiB a
worker at 24 MiB blocks and **+5,487 KiB** at 128 MiB, which is 134.8 MB at a
twenty-four-worker ceiling against budgets that start at 256 MiB.

So the trade is a second source read against that memory, and against a local
file the read being spared is a `pread` out of page cache. `XzSource` keeps
handing `decode_into` a `std::fs::File`, which declines to lend, and charges
`decode_footprint()` whole — exact for a declining source, since the chunk is
genuinely allocated. Over ranged GETs the same saving is one fewer round trip
per block and the trade plausibly reverses, which is `P14`'s to decide: it is
filed in that phase's inbox with the arithmetic, and `Reader::decoder_bytes()`
is the divisor if it ever takes the route.

**Two doc comments were false in both directions and are corrected here.**
`Partitioning::partition_bytes` and [`../../design/architecture.md`](../../design/architecture.md),
"Execution model and API surface" both said `xz_seek::RangePlan::footprint`
excludes the dictionary and names 8 MiB a worker as the allowance. The
dictionary went *into* that plan at the crate's `7.5` and the input chunk came
*out* at its `8.3`, so both halves had gone wrong; what replaces them is that
the decoder's own retention is one number, `Reader::decode_footprint()`, and
that it is a very good estimate rather than a sound ceiling — `memlimit`, compared
against each block's own declared dictionary before any backend object is built,
is what cannot understate.

### The copy takes `HEAD`, and another sync is owed

`87d55715` is that crate's `HEAD` at the moment of the sync and **not a version
this project chose to sit on**. Its sweep and keystone are in flight, so `HEAD`
moves again and `vendor/xz-seek` follows it — the standing policy that the copy
tracks upstream rather than waiting for a consumer that needs the newer work
([`../../design/architecture.md`](../../design/architecture.md), "The compressed
source"). A later session re-runs `scripts/vendor_xz_seek.py` and finishes at
`cargo check --workspace` and `cargo test --workspace`, not at the byte copy.

Two things about that next sync are knowable now. It should cost **nothing** in
this tree: a sweep re-takes figures and a keystone re-files documents, neither
of which is `src/`, so the sync is expected to be a byte copy plus a green test
run — and a compile break would mean the crate changed its surface inside a
keystone, which is worth noticing rather than absorbing. And it will **strike
that crate's phase docs**, so references from here into its tree are the thing
to re-check: the `P14` inbox entry above points at its `architecture.md`, which
is the keystone's distillate and survives, while its `KD3` and `KD10` survive as
register entries with numbers that are never reused. `M77`'s ledger row names
mechanisms rather than that crate's phase numbers for the same reason.
