# 2026-09-10

## `xz-seek`'s interface is final: `P8` is landed and nothing else in it moves

**From `xz-seek`'s `8.4`, which is the slice that owed this message.** Their
`P8` — the range read fetches whole blocks and decodes from borrowed bytes — is
complete, and it is the last of their work that moves a number `19.14` divides
by. Earlier slices deliberately sent nothing: `8.1` through `8.3` each moved the
surface, and a consumer told mid-flight would have built against a figure that
changed again. Their `8.4` changes no surface at all, which is why it carries
the message.

**`Reader::decode_footprint()` is unchanged, in value and in composition.**
9,471,776 B on the koji shape under `liblzma`, 9,467,864 B under `xz4rust` —
the same numbers `7.4` published. `19.14` divides by exactly what it was going
to divide by.

One caveat is new and does not reach this consumer. The chunk term is now an
**upper bound** rather than an allocation that always happens: a source that can
lend the decoder a slice of itself — a memory map, a `bytes::Bytes` — is decoded
out of borrowed bytes and holds no input chunk at all, so `decode_footprint()`
over-charges such a caller by 1 MiB. `XzSource` opens a `std::fs::File`, which
declines to lend, so the number is exact here.

**Four things in their public surface moved, and one of them is a removal.**
The message that arrived named three; `StreamEntry`'s new field is the fourth
and the only one that breaks a build here.

- `StreamEntry` gained `first_block_dict_size: Option<u64>` — the per-stream
  dictionary `decode_footprint()` maxes over. It reshapes the persisted
  `SeekTable`, so it is what `M77`'s `FORMAT_VERSION` bump is for, and two
  synthetic table literals in `io.rs` construct `StreamEntry` field-by-field.

- `CompressedSource` gained a third method,
  `fn slice_at(&self, offset: u64, len: usize) -> Option<&[u8]>`, **provided**
  and defaulting to `None`. An existing implementor compiles unchanged. `None`
  means *ask `read_at`* and never means end of file, so implementing it can skip
  a copy and cannot introduce an error case.
- `RangePlan::input_chunk_bytes()` is **gone**. `Reader::input_chunk_bytes()` is
  in its place — the accessor moved to where the memory actually is, because no
  decoder on the range path owns an input buffer any more.
- `RangePlan::footprint()` lost its `workers × chunk` term, so it reports
  **less** and `admitted_workers` admits **more** inside the same budget. On the
  koji multistream shape the per-worker unit goes 34.3 → 33.3 MiB and 512 MiB
  admits 15 workers where it admitted 14; on the 128 MiB-block recompression the
  unit goes 143.4 → 142.4 MiB and 3 workers is 3 either way.

**Only the first reaches the library**, which calls `Reader::new`,
`Builder::open_with_table`, `SeekTable::from_source`, `block_task`/`decode_into`
and `decode_footprint`, and never `plan_range`, `footprint()` or `fits()`. The
`xz_decode` **example** does call `plan_range` and `footprint()` and clamps on
`plan.workers()` — it reaches past the library to the decoder's own bulk entry
point on purpose — so the smaller footprint admits more workers there at the
same budget. It never called the removed accessor, so nothing failed to compile.

**The message also found two doc comments here false in both directions**, and
the re-vendor it called for is `M77` below, which corrects them and carries the
reasoning: the dictionary went **into** their `RangePlan::footprint` at `7.5`
and the input chunk came **out** at `8.3`, so a sentence naming that plan as
excluding the dictionary and allowing 8 MiB a worker was wrong at each end.

**Their register moved by two entries, and one of them is worth knowing about
if this repository ever brings a resident source.** `KD11` — the plan charging a
compressed window at one worker that the read never allocated — is struck,
because the read now allocates it. `KD12` is new, stance *(a) deliberate
tradeoff*: a caller whose source already holds the compressed bytes still pays
one copy of every one of them, because the fetch stage builds a window out of a
source that could have lent the range. It is `workers + 2` compressed windows,
20.6 MB of 482.1 MiB at 14 workers on the multistream shape. A `File`-backed
reader is unaffected.

**And the pool's own overhead is now measured rather than bounded.** Their `F5`
prices per-block coordination at **3,107 instructions**, 0.0010% of what one
24 MiB block costs to decode — five orders of magnitude, where the same figure
read four before `P8` removed a copy from its numerator. If any partition-sizing
argument here treats scheduling cost as a reason to prefer larger units of work,
it is arguing from a term that does not exist at this scale.

## `M77`: the re-vendor, and the window route priced and refused

**`vendor/xz-seek` is at `87d55715`**, from `5b549d72` of 2026-09-06 — forty
commits, taking that crate's `P7` (the decode footprint), `P8` (borrowed input)
and `M25`. `19.14` is unblocked: `xz_seek::Reader::decode_footprint()` is
callable, 9,471,776 B on the koji shape, and the charge that slice assembles no
longer needs a constant standing in for the decoder's own retention.

**The whole compile cost was two fields.** `StreamEntry` gained
`first_block_dict_size: Option<u64>`, which two synthetic table literals in
`io.rs` construct field-by-field; nothing else in the tree moved. That was
established before the sync rather than after, by vendoring into a throwaway
worktree and running `cargo check --workspace --all-targets` there — so the
question "what does this break" was answered while the working tree was still
clean.

**`FORMAT_VERSION` is 17, and the bump is load-bearing rather than tidy.** The
new field is inside the persisted `SeekTable`, so the rule on the constant —
bump whenever a persisted field is added, removed or reshaped — applies
directly. What makes it more than bookkeeping is the order in `read_cache_file`:
the envelope is `bincode`-decoded *whole* before the version is looked at, and
`bincode` is not self-describing, so an old cache read by the new binary
mis-frames every byte after the first stream entry. That decode may fail — an
`Option` tag byte that is neither 0 nor 1 — or it may succeed and hand back a
plausible-looking table. `format_version` is `CacheFile`'s **first** field, so
it decodes correctly whatever happens after it, and the check is what turns the
second case into `UnsupportedVersion` rather than a silently wrong table. Both
outcomes start cold. The price is a cold re-scan of the koji dump, accepted
knowingly when that crate's `P7` was specified.

**No figure went from green to red.** Three declare `vendor/xz-seek/src/` —
`xz-decode-scaling`, `parallel-scan-throughput`, `parallel-peak-rss` — and all
three were already stale on paths this change did not touch, `xz-decode-scaling`
on `scripts/generate_xz_input.py` since `4f573b7`. So the re-vendor adds a
reason to figures already red and owes no acknowledgement.

### The window route is refused against a local file, and the number is why

`xz-seek` guarantees that a block decodes out of a `Window` cut to its own
`compressed_range()` without copying the compressed bytes — `fill` asks for the
*block's* remaining tail, so the window holds it whole and lends it. Taking that
route here would close that crate's `KD3` for this caller: a positioned block
read costs two source reads, the header's and the payload's, and against a
window both come out of memory.

**It is not a memory saving, which is the premise that had to be corrected.**
The window is the block's whole compressed extent where the input chunk it
replaces is capped at 1 MiB, so a caller that takes it holds *more*, by an
amount that scales with the block size — on the two koji files, +242 KiB a
worker at 24 MiB blocks and **+5,487 KiB** at 128 MiB, which is 134.8 MB at a
twenty-four-worker ceiling against budgets that start at 256 MiB.

So the trade is a second source read against that memory, and against a local
file the read being spared is a `pread` out of page cache. `XzSource` keeps
handing `decode_into` a `std::fs::File`, which declines to lend, and charges
`decode_footprint()` whole — exact for a declining source, since the chunk is
genuinely allocated. Over ranged GETs the same saving is one fewer round trip
per block and the trade plausibly reverses, which is `P14`'s to decide: it is
filed in that phase's inbox with the arithmetic, and `Reader::decoder_bytes()`
is the divisor if it ever takes the route.

**Two doc comments were false in both directions and are corrected here.**
`Partitioning::partition_bytes` and [`../../design/architecture.md`](../../design/architecture.md),
"Execution model and API surface" both said `xz_seek::RangePlan::footprint`
excludes the dictionary and names 8 MiB a worker as the allowance. The
dictionary went *into* that plan at the crate's `7.5` and the input chunk came
*out* at its `8.3`, so both halves had gone wrong; what replaces them is that
the decoder's own retention is one number, `Reader::decode_footprint()`, and
that it is a very good estimate rather than a sound ceiling — `memlimit`, compared
against each block's own declared dictionary before any backend object is built,
is what cannot understate.

## The container was sized off a number that moved

`19.14` raised `measure.PARALLEL_BUDGET` 1 GiB → 2 GiB and left
`PARALLEL_MEMORY` at a literal `3g`. Against the old budget `3g` *was* the rule
the constant now states — budget plus 2 GiB of headroom — but written as a
number nothing recomputed, so the rise halved the headroom rather than moving
the container.

**What that costs is measured, not projected.** Four probes, `--jobs 24` in a
3g container on the release build, `getrusage(RUSAGE_CHILDREN)` — the harness's
own instrument, which reads 2110.4 MiB against the published table's 2111.58
for the leg they share:

| leg | figure | 1 GiB | 2 GiB |
|---|---|---|---|
| `control_xz128` `parse` | `parallel-peak-rss` | 2110.4 / 2090.6 MiB | **3067.1 / 3062.5 MiB** |
| `control_xz` `parse` | `parallel-peak-rss` | 1073.7 MiB | 1162.5 MiB |
| `control` `query-typed` | `parallel-scan-throughput` | 533.6 MiB | 878.8 MiB |

The widest `control_xz128` row sits **five megabytes under its 3072 MiB
limit**. The closing sweep would have found that as an OOM an hour in.

**The mechanism is that block-pool retention follows the budget, not the reader
count.** A block pool retains `clamp((budget - chunk) / unit, 1,
max(POOL_DEPTH, jobs))` decoded blocks, so above four workers the depth term is
the worker count and never binds; what binds is the budget divided by the
*file's* block size. At `control_xz128`'s 128 MiB unit that is seven slots at
1 GiB and fifteen at 2 GiB, +1024 MiB against the +957 measured. At
`control_xz`'s 24 MiB unit the depth term binds instead, so that leg is flat in
the budget and rose 89 MiB — which is why one shared constant hid the problem:
the leg that pays is not the leg the change was made for.

**The plain leg nobody was worried about was fine, and the compressed legs
nobody was worried about were not.** `24 × 72 MiB` was a *planning* charge — a
bound the budget divides by — and the leg holds 879 MiB of it.

`PARALLEL_MEMORY` is now derived rather than typed, and `PARALLEL_HEADROOM` is
the fixed 2 GiB. Sizing the container off the `--jobs` axis stays refused for
the reason its docstring already gave — the headroom there is glibc's per-CPU
arenas, an artifact of the measuring machine. Sizing off the *budget* is the
opposite case: the budget is a number the library is handed and promises to
bound its pools by, so `budget + headroom` states the library's contract and
travels.

**A published figure explained itself with the wrong mechanism.** That
section's closing paragraph credited the flat region to `POOL_DEPTH`, which
above four workers is the worker count and never binds. Raising the budget
moved the flat level 2110 → 3067 MiB, which is the direct refutation:
`POOL_DEPTH` did not change. The paragraph was also a **hand-edit the renderer
never emitted** — `run_parallel_peak_rss` stops after the per-rep readings — so
it is the divergence `CLAUDE.md` predicts for prose the harness does not own,
found the first time anyone checked the two against each other. It is deleted,
and the corrected explanation now lives in the renderer; `19.11`'s sweep is the
first sitting whose readings and stated budget agree, and is what prints it.

## The no-limit cap is affirmed, and a run says which mode it is in

The review of `19.13`'s open call found its arithmetic wrong in the direction
that mattered. It put an `xz -9 -T0` file's ask at ~9.6 GiB and concluded the
`MemAvailable` half-cap "does not bind" — but one reader of ~192 MiB blocks
holds `2 × 192 + 8 + decode_footprint`, and the footprint carries that level's
**64 MiB dictionary**, so the ask is ~456 MiB a reader and ~10.7 GiB at
twenty-four. Half of this machine's ~19 GiB `MemAvailable` reading is ~9.5 GiB.
**The cap binds**, and the case filed as "no hedge engages" is in fact the
hedge deciding the number.

The call stands. What the two arms owe is asymmetric and already written as a
standing rule ([`../../design/roadmap.md`](../../design/roadmap.md), "A default
runs as fast as the allocation permits"): under an orchestrator the operator
assigned an allocation and pgdq consumes it; with no limit found pgdq is a
guest on a shared workstation and plays nice; and neither arm may OOM. That
makes the fraction's *precision* beside the point — `MemAvailable` moves
between readings, so whether the cap binds is a property of the moment, and
half is a stated hedge rather than a tuned share. The reasoning is filed beside
the mechanism ([`../../design/architecture.md`](../../design/architecture.md),
"Execution model and API surface"), which also loses the claim that the cap
binds "only on a machine too small" — it binds on a large one whenever the
blocks are big enough.

What the review did change is that the mode is no longer silent. A run states
which of the two arrangements it is in and how many bytes it is taking under
it, so a recommendation the cap reduced is visible instead of surfacing as
unexplained slowness. That is `19.9`'s, which already owns the status line's
provenance, rather than a new item.

## The recommended pair has to be consistent

The review's second finding was an over-ask the entry had not looked for.
`XzSource::default_memory_bytes` is `block_reader_bytes() × default_workers()`
and `default_workers()` is the core count, but `stream::cut` caps pieces at the
block boundaries the file actually offers — so a 1 GiB file written with
192 MiB blocks has ~6 blocks, can run six readers, and asks for twenty-four
readers' worth. On this machine that is ~10.7 GiB requested against ~2.7 GiB
spendable, and the excess is not inert the way budget above `jobs × per-reader`
is: it is budget above what the *file* can supply work for.

The rule that settles it is two-sided and now stands as a standing bound
([`../../design/roadmap.md`](../../design/roadmap.md), "A default runs as fast
as the allocation permits"): **never allocate more memory than the workers can
use, and never allocate workers there is no memory for.** What makes it a pair
rather than two independent caps is that the answer must come out right on
machines of different *shape* — many cores and little memory, or few cores and
a great deal — so neither number can be chosen without the other.

Two facts make the repair cheap. `xz_seek::SeekTable::block_count()` already
exists and the table is held on the source, so the block bound costs nothing to
read. And the second half needs no new argument either — only that the source's
budget recommendation be stated **per worker** rather than as a total for its
own count, after which the composition multiplies by whatever count it is
considering and divides back when the allowance binds. Recovering `per-reader`
as `want / jobs` from a total was the first attempt and is wrong wherever
`--jobs` replaced the source's count, which is the case it would silently
reduce to one worker.

This supersedes one sentence of `19.8`'s rationale — *"this source's own block
count binds after that: a single-block file has no seam to cut, whatever this
says"* — which was written when nothing reported the count's provenance.
Once a run announces its mode and its allocation, a recommendation of
twenty-four workers beside a budget affording six is two numbers that
contradict each other in the same line, so the count is capped where it is
recommended rather than downstream. The spec's decision is not reversed on
preference: it is reversed because the mode report gives it a consequence it
did not have.

Folded into `19.13` rather than given an `M` number: that slice's box is still
open, `19.15` measures the rule next, and measuring a rule with a known
over-ask in it wastes the sitting. It landed with `Parallelism::fit`, and the
smoke table in
[`../../design/roadmap-P19.13-budget-discovery-notes.md`](../../design/roadmap-P19.13-budget-discovery-notes.md),
"What `19.15` runs against", was re-taken against it.

**Reviewed with the maintainer, and all three calls stand.** The per-worker
shape is affirmed on a ground the flagged entry had not reached: a total is a
total *for some count*, so the source would have to guess a count purely so the
caller could divide it back out, where the question it is being asked — what
does reading one block of this file cost — has no count in it at all. That also
lines the trait up with itself, `block_decode_bytes` having answered per-reader
since `19.14` deliberately made both the same `reader_bytes` call.

The count-lowering half was affirmed as a **separate** call rather than as
something riding on the units, because it is separable and it is the one with a
visible consequence. `stream::worker_count` is already
`jobs.min(budget / per-partition)` against that same charge, so the count `fit`
removes is a count nothing was going to run: the reduction is a *reporting*
change, and it belongs to the channel `19.9` owns. Both alternatives are filed
beside the mechanism ([`../../design/architecture.md`](../../design/architecture.md),
"Execution model and API surface"). Its consequence — that `jobs=` now reads
differently depending on whether the flag was typed — is `19.9`'s to state in
the mode report.

Two documents were still describing the total after the change and were amended
here as recording rather than reversal, no rationale in either being touched:
[`../../design/roadmap.md`](../../design/roadmap.md), "A default runs as fast as
the allocation permits", whose closing sentence had the source stating the
count's budget; and this phase's spec, whose no-limit paragraph was written in
`jobs × C` throughout. The spec's *"binds only on a machine too small to afford
the full worker count"* was corrected at the same time — `C` scales with the
block size, so a large-block file reaches the cap on a large machine too, which
is what `roadmap.md`'s own "Unstated is not unlimited" bullet already said.

## The provenance line is the CLI's, because the library cannot honestly fill the slot the spec named

`19.9` landed the mode report on a **second** status line rather than on
`scan started`'s existing `memory_bytes=` field, which the spec calls "a slot
that already exists". Every string the spec named is printed — `(stated)`,
`(discovered: …)`, `(default: no limit found)` — on a line the CLI emits at
resolve time, ahead of the library's.

The slot is the library's, and provenance splits into two halves neither of
which reaches it. Whether a flag was **typed** is knowable only at the CLI;
whether a limit was **read** only inside the walk that read it. `Parallelism`
carries a number and not its origin, so an embedder handing over
`Parallelism::default()` would be told `(default: no limit found)` about an
environment nobody had consulted — a status line asserting a reading that never
happened, which is the defect the marker exists to prevent rather than a new
spelling of it.

The two ways to reach the spec's wording literally were costed and refused:
widening `Parallelism`, a `Copy`, `PartialEq` value matched on in every read
loop, for a display fact nothing branches on; and a provenance field on
`ScanOptions`, the same widening paid in the options struct. Both are filed
beside the mechanism
([`../../design/architecture.md`](../../design/architecture.md), "Status
output"). The call was flagged under `STATUS.md`'s "Decisions worth another
look" and has since been reviewed and affirmed; the spec paragraph the slice
read differently was amended to match, below.

## The provenance call is affirmed, and `discover()` is single-tenant

Reviewed with the maintainer. The two-line split stands and both widenings —
`Parallelism` carrying provenance, or a provenance field on `ScanOptions` —
stay rejected. The argument that settles it is stronger than the one `19.9`
filed: the spec's plan is not merely awkward but **unimplementable as
written**, because `19.13` made an absent flag resolve to a discovered number
that reaches the library byte-identical to a stated one. The distinction
`scan started` was asked to print is destroyed before the library is called.
So `roadmap-P19-efficient-defaults.md`'s status-line paragraph was amended to
name the second line — a change of destination, not of rationale; every
distinction it specified ships.

**Discovery is the library's, not the CLI's**, which the entry obscured.
`discover_memory_limit`, `available_memory` and `Parallelism::discover` are all
public `io.rs` functions; the CLI adds only the record of whether a flag was
typed. So the library *can* report provenance — `MemoryLimit` already carries
the file — it simply does not thread it through the `Copy` value the read loops
match on.

That reframing is what turned up the real gap. `discover()` reads the
*process's* allocation, so N callers in one process resolve N times the same
allowance, and a DataFusion `TableProvider` is exactly that shape: a join
across three files is three provider objects and three `scan()` calls, with
nothing upstream to catch the overrun — DataFusion sizes no pool from the
machine or a cgroup, defaults to unbounded, and its memory-pool contract
excludes data sources by name. The count half is already solved
(`target_partitions` into `discover_for`); the budget half has no reading to
take, since the pool is session-wide and does not cover sources, so P6's answer
is a constructor parameter rather than a discovery.

Nothing oversubscribes today — the library's default is `Serial` and discovery
is opt-in — so this is a **property with a remedy in hand**, not a deficiency,
and it is written beside the mechanism
([`../../design/architecture.md`](../../design/architecture.md), "Execution
model and API surface"). The DataFusion evidence is filed for the phase that
will build it
([`../../design/roadmap-P6-embeddable-engine-inbox.md`](../../design/roadmap-P6-embeddable-engine-inbox.md)).
A `discover_reporting` sibling was refused in the same pass: the embedder that
appeared to want it must not discover at all.
