## P10 is grilled and sliced

The spec is
[`roadmap-P10-row-group-statistics.md`](../../design/roadmap-P10-row-group-statistics.md)
and the checklist is [`../STATUS.md`](../STATUS.md), "P10 progress"; the inbox
is drained there, its `xz-seek` entry refiled to P14's. P20 ("statistics
memory") was allocated in the same grilling and sits directly after P10.

The sketch was reversed or narrowed in these places, each decided by the
maintainer:

- **The phase is not shaped by one dump.** The sketch's koji-derived sizing and
  expected sorted columns bind nothing; the design argues from general
  PostgreSQL behaviour and fixture shapes.
- **Gathering is on by default.** `parse` gathers every statistic unless told
  `--statistics none`, where the sketch made it opt-in; a query never gathers.
- **Row groups are byte ranges, not 8192 rows**, because concurrent leader
  pieces cannot know global row indices; `SparseRowIndex` is struck.
- **Sortedness is an `Ascending`/`Descending`/`Unsorted` tri-state per block**,
  tracked while gathering and stored, where the sketch ranked a gathered flag
  ahead of min/max.
- **The identity check stays mandatory and is narrowed to the stored size.**
  The mtime cannot be controlled in every environment, so it stays advisory;
  a same-size file rewritten in place is knowingly pruned against stale
  statistics.
- **One cache file**, where the sketch wanted statistics discardable apart.
- **Dictionaries were added** (64 entries, 256 bytes), as a statistic and never
  an Arrow encoding, which extends equality pruning to text under any
  deterministic collation.
- **Resident memory is allowed to grow with the dump**, with coarse bumps to
  the reserve and the harness's expectations, refined by P20.

Pickup: slice 10.3.

## The in-binary arena cap stays refused

Reviewed with the maintainer; filed in
[`../../design/decisions.md`](../../design/decisions.md), "D13", on glibc
behaviour recorded as
[`../../design/runtime-invariants.md`](../../design/runtime-invariants.md), "RT10".

- **A cap keyed to the resolved count is a no-op**: the `reserve` figure's
  instrument legs read arenas at the readers plus one or two, so only a cap
  below the count saves bytes — on `.xz` only, at a contention cost no figure
  has taken. The roadmap's Future item "An allocator-contention figure for a
  capped arena count" is what would reopen it.
- **The earlier mechanical reason was wrong in its mechanism**: glibc latches
  its limit once `arena_test` arenas exist and ignores `mallopt` after; the
  `current_thread` runtime is what keeps a cap set at resolution ahead of that.
- **glibc 2.44 lowered the default ceiling** to `max(8, ncores)`; the figures'
  `postgres:16` runs 2.41, whose ceiling is `8 × ncores`.

## `KD27` is repaired ahead of P10

Reviewed with the maintainer: the `statistics` fixture's long value stays past
the shipped chunk on every major
([`../../design/roadmap-P10.1-fixture-shapes-notes.md`](../../design/roadmap-P10.1-fixture-shapes-notes.md),
"Negative results"), since `KD27` was a user cost and not only the suite's — a
raised `--max-line-bytes` for a 256 MB value, by the marker's `L² / (2 × chunk)`,
cost about 32 GiB of newline search at the shipped chunk (arithmetic, not a
reading). It landed as `M105`: a carry pass over a chunk with no newline short
of the end returns an empty span, in `ChunkCarry` alone, which
`CopyScanner::next_event` makes exactly equivalent; "D23"'s two passes stand.
`scan.rs`'s `a_line_many_chunks_long_is_scanned_once` counts bytes rather than
timing. `max_line_bytes.rs`'s default-chunk legs rely on the value exceeding the
shipped chunk.

## A block's filter refusal moves to the plan

Reviewed with the maintainer: a refusal `resolve_expr` raises is a plan fact,
raised before any row for the first refusing block in file order. 10.2 kept the
reached-block point only because its row was behaviour-preserving.

- **Only a mixed-schema key reaches the old point**: leaves loaded via their
  partition root (I2) share the root's names and types, so a filter refuses all
  or none; concatenated dumps under different column lists remain
  (`tests/stream.rs`, `a_later_blocks_refusal_is_raised_before_any_row`).
- **The refusal is plan-knowable, "D52"'s failures are not.** It depends on the
  header and the query alone; "D49" and "D48" already raise such facts before a
  row, and `type-handling.md` promises a mistyped value is refused "before any
  row is read", which that case broke.
- **A block with no column list still refuses where reached**: `pg_dump`'s
  `fmtCopyColumnList` omits it only for a table with no stored column, whose
  field count only a row says.
- **Landed as `M106` and `M107`**
  ([`../../design/out-of-band.md`](../../design/out-of-band.md)): the plan holds
  an entry for every block with a column list or refuses, in
  `resolve_for_query`'s order within a block. Stopping at filter refusals named
  the wrong block across kinds: `(a, b)` then `(a, c)` under `--filter 'b IS NOT
  NULL' --column c`, the second leg of the test above. `MetadataNotScanned` has
  no leg, no public entry point reaching it (`resolve_block`'s rustdoc).
