## P27 is being grilled; `KD45` moves to `M173`

The grilling's record so far is
[`roadmap-P27-dynamic-filters.md`](../../design/roadmap-P27-dynamic-filters.md),
written a round at a time; a session resuming it reads that file's
"Decisions" and continues from what they leave open.

`KD45`'s two stated reasons did not survive reading the code, and it leaves
P27:

- **Order.** The provider's summary is computed in Arrow semantics
  (`datafusion-pgdump/src/statistics.rs`, `table_statistics`), which for an
  enum reads the label-text set gathering keeps beside declaration order
  (`pgtype.rs`, `ComparisonPlan::bounds_read_by`; `decisions.md`, "D79") — the
  set the provider already declares an enum's ordering from
  (`tests/statistics.rs`, `enum_proved`).
- **Type.** Every reader of a column's `min_value`/`max_value` in DataFusion
  55.1 accepts the column's own `Dictionary(Int32, Utf8)`, which is what
  `bound` builds. `Utf8` is the wrong one: filter estimation fills a missing
  end with a `Dictionary` null and `Interval::try_new` refuses the pair
  (`physical-expr/src/analysis.rs`), and an uncoerced `MIN` returns the
  column's type. Coerced SQL answers `MIN(e), MAX(e)` from statistics only
  through the common-subexpression projection, which casts either type.

So `M173` is removing the early return, with a test answering `MIN(e)`,
`MAX(e)` and both together from statistics and planning a numeric-only filter
over a table holding an enum; it strikes `KD45`.

27.1's instrument landed in `4d9fb4b` and its readings from `2f94f14`, two

## A scan prints its whole filter as Parquet does

Reviewed with the maintainer: `PgDumpExec`'s `EXPLAIN` line carries one
`predicate=`, the conjunction of the static filter `scan()` answered `Exact`
and every dynamic filter it holds, as Parquet's `fmt_extra` writes it
(`datasource-parquet/src/source.rs`) — replacing 27.2's `dynamic_filter=`.
That key rested on the static filter being the logical plan's to print, which
holds only for `EXPLAIN FORMAT indent` (`TableScan … full_filters=[…]`).
`datafusion-cli`'s default tree `EXPLAIN` and `EXPLAIN ANALYZE` print the
physical plan alone, where no node names an `Exact` filter: `WHERE id < 50`
over `fixtures/16/statistics/default.sql` shows
`PgDumpExec: partitions=7, metrics=[row_groups_pruned_statistics=1 total → 1
matched, …]` and nothing of `id < 50`. Parquet's `pruning_predicate=` and
`required_guarantees=` are not copied: they exist because its `predicate=` is
not what it prunes with, and a static filter here is translated exactly.

The static part comes first, by bare column name in DataFusion's SQL form
(`stepped > 3`; `Expr::human_display` qualifies a column, so the qualifier is
dropped first), the dynamic parts after it as DataFusion renders each in each
view. Parquet's `stepped@2` indexes its table schema, which a scan here cannot
share: a static filter may name a column its projection drops, while a
dynamic filter's `@k` indexes the scan's output. The manual's "What a scan
skipped" paragraph names the static filter as the scan's `predicate=`; a
dynamic filter waits for 27.3's metrics, as the 27.2 notes say. `M175` is the
change, blocking P27 because every slice landed around `dynamic_filter=` adds
a reader of it.
