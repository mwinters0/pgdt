# 2026-10-02

## The parsing and decoding audit: five defects, one phase

A read of the parsing and decoding path — `copy.rs`, `decode.rs`,
`nested.rs`, `pgtype.rs`'s mapping, `preamble.rs`, `lex.rs`, `scan.rs`,
`map.rs`'s builder, `batch.rs`, `resolve.rs`, `unrepresentable.rs` — against
`pg_dump` 16.15's source and against real output taken from throwaway 16.15
and 18.6 containers (`runs/parse-audit-20261002/`: `schema.sql` is the probe,
`run.sh` and `connect.sh` took the dumps, and each `*.sql` beside them is one).
It did not read `statistics.rs`/`gather.rs`, `predicate.rs`'s literal
parsers, `pgtype.rs`'s comparison register, `pgdt`'s `--where` grammar or the
`INSERT` run.

Five defects, each confirmed on the probe dumps with the `13:19` release
build, each now owned by P31:

- **`KD64`** — an inheritance child's inherited columns resolve `NotDeclared`
  (`public.child`: `extra` is `Date32`, `id` and `name` are text, and a
  query prints `extra` first). `shouldPrintColumn` is the emitter.
- **`KD65`** — `CREATE UNLOGGED TABLE` is not classified; every column of
  `public.scratch` is text. `CREATE FOREIGN TABLE` under
  `--include-foreign-data` falls the same way, unprobed.
- **`KD66`** — a `--binary-upgrade` composite with a dropped attribute keeps
  the `/* dummy */` field, and `query --table public.trios` refuses its first
  row on both majors; `ALTER TYPE … DROP ATTRIBUTE` is read by nothing.
- **`KD67`** — under `bytea_output = escape`, set on the database, `pg_dump`
  writes `\000\377\\\011` and a typed `bytea` query refuses it
  (`16-bytea-escape.sql`). `pg_dump` pins no `bytea_output`.
- **`KD68`** — `CREATE DATABASE "My-App"` dumps as `\connect
  -reuse-previous=on "dbname='My-App'"`; `pgdt info` over its `pg_dumpall`
  lists `template1` and `postgres` only, the table landing in `template1`
  (`16-dumpall-myapp.sql`).

**What the probe cleared.** A zero-column table's empty rows, NBSP and a tab
inside `text[]` and composite values (neither `array_out` nor `record_out`
quotes a non-ASCII byte), `character(5)[]`, `"char"`, `interval day to
second(3)`, `timestamp(3)`, `time with time zone`, enum labels holding a
backslash and a newline, a default holding `ARRAY[1, 2]`, a `numeric(5,2)`
`NaN` beside unconstrained `Infinity`, a partition's full column list, and
`COMPRESSION`/identity written as separate `ALTER`s — every one reads as the
dump holds it.

**P31 is grilled and sliced**
([`roadmap-P31-correctness-evidence.md`](../../design/roadmap-P31-correctness-evidence.md)):
an emitter register read mechanically out of `pg_dump`'s source, a value
oracle, and the fixes for what they find. It owns `KD64`–`KD70`, `KD69` and
`KD70` filed by the grilling from its inbox, and a `KD` of its class found
later becomes a P31 slice without asking — the spec's opening note.

**P32 is allocated**, the schema model: the maintainer's aim is to capture
every object and property a dump declares, which P31 does not. Its sketch is
in [`roadmap.md`](../../design/roadmap.md), "P32 — The schema model: every
object and property a dump declares", and its inbox holds what the grilling
found; the maintainer sets its order.

## `M201`: a scale past the precision widens it

Landed as admitted, closing `KD63`: `map_numeric` types `numeric(p,s)` at
precision `max(p, s)`, and a typmod no Arrow decimal carries — a precision
or positive scale past 76, a scale below `-128` — as text compared by value.
`CACHE_FORMAT_VERSION` is 35, a scale past `i8` having been typed at scale 0
with statistics kept under that kind; neither pinned digest moved, no

## `M203`: a float literal reads what `float8in` reads

Admitted from 31.10's report and settled with the maintainer. **`*_out` is a
literal's floor and `*_in` its ceiling**, now a standing rule (`roadmap.md`,
"A literal is guaranteed in `*_out`'s form and never read past `*_in`'s") and
D55: a literal PostgreSQL refuses is refused, and between the two an `*_in`
spelling is read where that is free or simpler, no runtime spent refusing one. A float literal
compares by value, so the `float8in` spellings Rust's parse already reads stay
read; out of range is refused as `float8in` refuses it, but for the spellings
I57 says `*_out` writes for the largest finite value. `KD74` holds the defect;
`M203` does not block.

Facts it rests on. Rust's `f64`/`f32` parse, which reads the literal today,
accepts `inf`, `+inf`, `INF`, `infinity`, `nan`, `-nan` in any case, `+1.5`,
`.5`, `5.`, `1E5` and `1.50`. It reads `1e400` as infinity, which
`finite_spelling` then clamps to `DBL_MAX`, and `1e-400` as `0`. It refuses
`0x10`, a leading space and `1_0`. `float8in_internal`
(`src/backend/utils/adt/float.c`, v18.6) skips leading whitespace, takes
glibc's `strtod`, and falls back to case-insensitive `NaN`, `[+-]Infinity`
and `[+-]inf`. It raises "out of range for type double precision" on `ERANGE`
when the result is zero or `±HUGE_VAL`, which covers `1e400`, `1e-400` and
`1.79769313486232e+308`.

## Literals read past `*_in`: the audit, filed

A read-only audit of every `CompareKind`'s literal path against v18.6's input
functions, each refusal confirmed by casting on the koji replica (PG16), found
these accepted where the server refuses. Nested leaves inherit them through
`nested_key` → `order_key`. Filed one `KD` and one non-blocking `M<k>` per kind
(`KD76`–`KD80`, `M205`–`M209`), each landing with a test that feeds its kind's
refused inputs from `literals.tsv` to the literal path, the typmod rows
excepted. `M204`, the `pg-refuses` marker and its check, blocks P31 so 31.12
lands under it. The ceiling being the newest major's `*_in`, a v13 dump's
`numeric` reading `Infinity` and a v13–16 `interval` reading `infinity` are no
defect.

- **Integer width**: `70000` on `smallint`, `3000000000` on `integer`; every
  width parses as `i64` (`predicate.rs`, `order_key`).
- **Date and time fields**, all in `decode.rs`: an impossible calendar date
  (`2020-02-30` rolls to March 1); a year of zero or under three digits;
  a date outside the Julian range and a timestamp outside
  `MIN_TIMESTAMP`/`END_TIMESTAMP`; a `+` sign in a field; a time past
  `time_overflows`' bounds (`12:60:00` reads as 13:00); a zone offset past
  `±15:59:59`. And `12:-5:00`, which PG16 reads as 12:00 at zone `-5` and we as
  11:55.
- **Interval**: months or days past `i32` (checked on the field path only); a
  minute or second field past 59/60 (`00:90:00` reads as 01:30).
- **Numeric**, `numeric(p,s)` and a `jsonb` number: no cap at
  `numeric_in`'s dscale 16383 or its weight, so `1.` and 16384 zeros reads as 1.
- **`uuid`**: a hyphen anywhere, where `uuid_in` takes one only after a group of
  four digits.

Not over-acceptances, though the oracle's `E` cells say otherwise: a literal
compared with a `numeric(p,s)` or `char(n)` column is coerced without the typmod
on PG16 (`col = '12345678901'` on `numeric(10,2)` is false, not an error), and
`literals.tsv` casts with it. No test feeds the oracle's refused inputs to the
scalar literal path; only the range kinds assert a refusal through
`resolve_term`.

**The ceiling binds a field too** (the maintainer, outranking the floor): a
field spelled as I57's overflowing float is to be refused as `float8in`
refuses it, reversing what 31.10 landed, and the manual's float section is to
say why, so the refusal does not read as a fault. It is refused loudly at parse,
an error aborting the parse as a restore fails — `pgdt parse` being pgdt's
restore — and a query mapping the block itself fails the same way; the decode
gathering already runs at parse is where it is seen, so the check costs the
parse nothing it does not already pay. It is not an unrepresentable value:
unrepresentable means our front end cannot hold it (Arrow, DataFusion), not
that PostgreSQL refuses it. The audit's kinds bind a hand-written dump's fields
as well as literals, the input contract putting such a dump in scope. The parse
aborts at the first refused field, as `ON_ERROR_STOP` does, not finishing and
listing them as `pg_restore`'s default does. `--postgres-invalid-values=ignore`
ships with the refusal, fields only: an abort with no opt-out leaves a user no
way to read a dump they usually cannot regenerate, where a refused literal is
remedied by rewriting it. The flag is slice 31.13, split from 31.12's
core-path change by the review each needs. Its `default` refuses only what a
parse already decodes, which keeps the parse's cost; `strict`, slice 31.14,
decodes every field so a clean parse is a full check, nested leaves and declined
blocks being where the decode was skipped on purpose (D85, D89). All three land
before P31 wraps, and so do `M203`–`M209`, which block it: P31 wraps once all
of it is done. Run order is `M204` first, so every refusal lands marked, then
`M203` and `M205`–`M209`, each kind's decoder bounded, then 31.12, which turns
every refused field into a parse abort at once. The
literal ceiling governs the PostgreSQL semantics only. A future option reading
such a value as unrepresentable is wanted only once users ask. Filed as `KD75`,
owned by P31 as slice 31.12 under the spec's absorption rule ("What the register
finds, and when the phase ends"), so P31 wraps after it.


## `M204`: a refusal on PostgreSQL's terms is marked

Landed as admitted. `scripts/pg_refuses.py` resolves each `pg-refuses: I<n>`
marker to the function holding it and requires `I<n>`'s "Relied on by" to name
that function; its docstring says what counts as such a refusal, and
`test_pg_refuses` runs it over the tree in `mise run check`. Marked: `nested.rs`'s
four container grammars (I44) and `parse_int2vector` (I47); `predicate.rs`'s
`JsonCursor` `number`, `string` and `unicode_escape` (I41), `network_key`'s
`cidr` check (I40, which now records `cidr_in`'s refusal), and `make_range`
and `serialize_range` (I46). `M203` and `M205`–`M209` mark their refusals as
they land them, and 31.12 its field refusals. Whether a comparison PostgreSQL
refuses is marked too is under STATUS's "Decisions worth another look".

## `pg-refuses` and comparisons: affirmed, and `M210` admitted

Reviewed with the maintainer: the marker stays on refused values. No operator
refusal is the server's, `Unanswerable` included (the server answers its `=`),
and a comparison the server lacks is answered as text where this build can;
the reasoning is `scripts/pg_refuses.py`'s docstring, and `ComparisonPlan`'s
rustdoc names the case that reopens it. Found while reviewing: `nested_refusal`
tells the user PostgreSQL refuses the ordering for any uncomparable position,
which is false for an unmodelled element with a btree opclass (`money[]`,
`bit[]`, `tsvector[]`, a user base type) and true only for an `AsText` one
(`json[]`, I45's probe). `NestedCompare::Uncomparable` already carries the
divergence that tells them apart. Admitted as `M210`, blocking nothing in P31.
