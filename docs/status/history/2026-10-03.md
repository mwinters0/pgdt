# 2026-10-03

## `M205`: an integer literal is read at its column's width

Landed as admitted, closing `KD76`. `CompareKind::Int` carries its width in
bytes, and `predicate::int_literal` reads a `smallint`, `integer` or `bigint`
literal in PostgreSQL's semantics, refusing one past the width as `int2in`,
`int4in` and `int8in` refuse it (I60, marked `pg-refuses: I60`), at every
literal site `literal_key` and `equality_comparison` reach, so an array
element, a range bound and an `IN` value included. A field, and a literal in
DataFusion's semantics, are read as an `i64` unchanged: a field past its width
is 31.12's. `accepted_form` names the width's range. No persisted byte moved,
the cache keeping bounds as text, and no oracle file was regenerated:
`literals.tsv` already refuses one past each width at every major.

Evidence: `predicate.rs`'s
`an_integer_literal_past_its_width_is_refused_and_one_inside_it_read`,
`an_integer_literal_past_its_width_is_not_refused_in_datafusion_semantics`
and `oracle::an_integer_literal_is_read_as_the_server_reads_it`, every major.

## `M206`: a date, time or timestamp is bounded as `datetime.c` bounds it

Landed as admitted, closing `KD77`. The decoders a field and a literal share
(`decode::civil_days`, `parse_time_of_day`, `extract_offset`,
`decode_date32`, `timestamp_micros_wide`) refuse what I61 records the server
refusing: a day its month lacks, year zero, a time past `time_overflows`, a
zone past `±15:59:59`, a date or a timestamp's instant past the range. A part
carrying a sign is refused, so `12:-5:00`, which the server reads as a zone,
is refused rather than read; a year under three digits, a three-digit month and
a run-together `+0530` are refused as shortfalls (D55). A refused field is an
undecodable field, `FieldDecode` where it is read; a parse refusing it is
31.12's. `CACHE_FORMAT_VERSION` is 42: such a field, which a hand-written
dump can hold, now loses its group's bounds and leaves the unrepresentable
count where it was keyed or counted before; neither pinned digest moved. No
oracle file was regenerated: the koji replica (PG16) answered every probe I61
lists.

Evidence: `decode.rs`'s `a_date_the_calendar_does_not_hold_is_refused`,
`a_time_past_time_overflows_is_refused`,
`an_offset_past_fifteen_hours_is_refused`,
`a_timestamp_past_postgresqls_range_is_refused` and
`the_date_range_constants_are_julian_days_from_1970`; `predicate.rs`'s
`a_date_or_time_postgresql_refuses_is_refused_as_literal_and_field` and
`oracle::a_date_or_time_literal_is_read_as_the_server_reads_it`, every major.

## `M208`: a number is bounded as `numeric_in` bounds it

Landed closing `KD79`, short of the row's wording on one cell. A literal on
every `numeric` kind, in PostgreSQL's semantics, and a bare `numeric`'s field
are refused past I63's display scale and weight
(`decode::numeric_in_stores`), and a `jsonb` number, field and literal, past
them and an exponent past `PG_INT32_MAX / 2` (`JsonCursor::number`), which
replaces this build's own bound at a point position of 100000 — that refused
`1e100000`, which the server reads. **A `numeric(p,s)` field is not capped**:
`COPY` rounds it to the scale before the bounds are checked, so the server
reads `1.` and 16384 zeros as `1.00` and so does this build; capping it would
refuse a valid field, which 31.12 would make an abort no restore makes.
`accepted_form` names the bounds. `CACHE_FORMAT_VERSION` is 44: such a field
now loses its group's bounds, and a `jsonb` one past 100000 integer digits
gains them; neither pinned digest moved. No oracle file was regenerated: the
koji replica (PG16) answered every probe I63 lists.

**Filed as `KD81`, slice 31.15**: the rest of `apply_typmod` is not applied to
a `numeric(p,s)` field, so `1.005` in a `numeric(10,2)`, which `COPY` stores as
`1.01`, is refused on a typed column and read unrounded on a text-held one,
and a field past the precision is read. The refusal is a shortfall, not the
server's, and becomes a false abort if 31.12 lands first.

Evidence: `decode.rs`'s `numeric_in_stores_up_to_its_display_scale_and_weight`;
`predicate.rs`'s
`a_numeric_past_numeric_ins_bounds_is_refused_as_literal_and_bare_field`,
`a_jsonb_number_is_bounded_as_numeric_in_bounds_it` and
`oracle::a_numeric_literal_is_read_as_the_server_reads_it`, every major, whose
helper now lets the newest major's reading of a literal an older one refuses
bind (I35), as a v13 `numeric`'s `Infinity` is.

## `M209`: a `uuid` is read by `uuid_in`'s grammar

Landed closing `KD80`, and one step past the row's wording under D55's
ceiling. `decode::decode_uuid`, which a field and a literal share, now ports
`string_to_uuid` whole (I64, marked `pg-refuses: I64`): a hyphen is taken only
after a group of four digits but the last, so one leading, trailing, doubled or

`accepted_form` and the manual's refusal examples say so. A refused field is an
undecodable field; a parse refusing it is 31.12's. `CACHE_FORMAT_VERSION` is
45: such a field, which a hand-written dump can hold, now loses its group's
bounds, and a braced one gains them; neither pinned digest moved. No oracle
file was regenerated: `literals.tsv` holds the braced form at every major, and
the koji replica (PG16) answered every probe I64 lists.

Evidence: `decode.rs`'s `a_uuid_takes_a_hyphen_only_after_a_group_of_four` and

## 31.12 lands split

The row asked that any field `*_in` refuses fail the parse. This build tells a
refusal from a spelling it does not read only where a `pg-refuses` check makes
it (`decode::Unread`, D55); for `boolean`, an enum, `oid`, `inet`, `macaddr`
and `bytea` it cannot, no check being marked, and failing on every field read
as no value would abort on shortfalls a restore reads. Telling those apart is
each `*_in`'s grammar ported far enough to classify, an invariant for each and
its refusals marked: a review of its own against PostgreSQL's source, unlike
the mechanism, which carries the audited kinds' marks unchanged. So 31.12
landed the mechanism and every marked refusal, `KD75` closed, and the rest is
31.12.1, closing `KD83`, which runs next. The notes are
[`roadmap-P31.12-field-refusal-notes.md`](../../design/roadmap-P31.12-field-refusal-notes.md).

## A refused field is located as a restore locates it

`Error::FieldRefused` names the row by its byte offset alone, where
`roadmap.md`'s "A literal is guaranteed in `*_out`'s form and never read past
`*_in`'s" asks for its line. Settled: it names the line as the restore's own
error does, `COPY <table>, line N, column <c>` (`copyfrom.c`'s
`CopyFromErrorCallback`, `cur_lineno` counted from the block's first data
line), and keeps the offset beside it as the locator a dump this size can be
seeked to. A text `COPY` row is one line, a newline in it escaped, so the two
name the same row. N is the observer's rows before the refused one: a piece's
count added on `Gatherer::absorb`, which folds pieces in row order already, so
the count keeps running past a decline, a piece made before it able to refuse.

The dump file's line number was refused: no span keeps a line count, so it
costs a count persisted per span or a re-read of everything before the
refusal, and on a dump this size a line number is the worse thing to seek by.

`FieldDecode` keeps its offset, worded as `FieldRefused`'s: a query reading
from a kept group or a parallel chunk starts mid-block with no count of the
rows before it, which only a statistics-level map's group counts could supply,
so the message would vary with the mapping level. It mostly names a spelling
this build does not read, which no restore numbers. The work is slice 31.12.2,
earned by 31.12 shipping the offset alone, after 31.12.1; the standing rule's
"line" is spelled out by the change landing it, not before.

## 31.12.1 lands without the enum

The row named six kinds. Five are a grammar each, ported or classified beside
its reader (I65–I69), and landed. An enum's refusal is a label its type does
not declare, which is a refusal only where the preamble's label set is exact,
and the preamble does not know when it is: an `ALTER TYPE … RENAME VALUE`, an
`ADD VALUE IF NOT EXISTS` or a label it cannot lex leaves the set short with
no mark, and refusing on a miss would then abort a parse a restore completes.
Marking the set exact is preamble and cache work, a mechanism of its own, so
the row was rewritten to the five and the enum is 31.12.3, still closing
`KD83`. The notes are
[`roadmap-P31.12.1-input-function-ports-notes.md`](../../design/roadmap-P31.12.1-input-function-ports-notes.md).

## Red is the resting state

A figure `--stale` reports red is left red, through a phase wrap too; what is
owed is a re-take, or an acknowledgement an oracle settles, **before anything
reasons from it** ([`../../design/measurements.md`](../../design/measurements.md),
"A stale figure does not oblige a sweep"). No commit owes an acknowledgement
when it lands, so `gosub` no longer writes them and its rounds no longer report
the reds they leave. The entries already in `scripts/acknowledged.py` stand and
are spent by the next sweep as before.

Evidence: at `ccc092f0`, `--stale` held every figure but one red, most of them
behind acknowledgements it lists as inert, held red by a commit nobody had
excused; 55 of the 229 commits since 2026-09-26 were `Acknowledge …` commits.
A `mise run check --affected` after a one-line `pgdump_query` edit took 920 s
with the build directory on the SSD
(`runs/check/20261003-081907-959380b6d46a/`), so the check stays a per-round
cost and the acknowledgement round after it was the part to drop.

## A cache records the refusals an ignoring parse went past

31.13 states `--postgres-invalid-values` per run, on `parse` as well as D103's
four query surfaces, and no cache records anything of it. The flag stays on
`parse`, the refusal it opts out of being a parse's (31.12). What changes is
the cache: `StatisticsRequest::backfill` re-reads a block only for a column
with no bounds at all, and an ignoring parse blanks one group's bounds,
dictionary and the column's sums, so a later `default` parse over its cache
re-reads nothing and reports clean over a dump a restore refuses — the verdict
depending on which run gathered the cache, not on the dump. Nor can the cache
tell a group an ignored refusal blanked from one a shortfall did.

**The cache records the fact, not the mode**: each block keeps the refused
fields an ignoring parse went past, the first in full (table, column, `COPY`
line, offset, value) and a count. A `default` parse over such a block fails
with the recorded refusal, re-reading nothing and replacing nothing; `info`
reports them; a query is unaffected, reading each field under its own mode.
D103's rejection of recording the mode stands, nothing being imposed on a
reader; its "no cache records it" changes when the slice lands. This changes a
decision, so it is slice 31.13.1, 31.13 having shipped the contract without it,
and lands before 31.14, whose `strict` builds on the record.

**A refusal read from the cache is worded as one read from the dump**, every
field the same, with one clause added: an earlier parse went past it under
`--postgres-invalid-values=ignore`, nothing was re-read, and the cache is named.
**A `strict` parse checks the held blocks no strict parse checked**: it re-reads
each, decoding every field, and records on the block that it was checked in
full — adding to the cache, as the statistics back-fill does, never replacing
it — so a clean `strict` run means every field was checked whichever runs built
the cache. Refusing such a cache was rejected: it leaves only a re-parse from
scratch, which the library may not start by replacing the cache. The check
record joins 31.13.1's per-block record; 31.14 builds it.

## A recorded refusal is per column

31.13.1 records one first refused field and a count per block, so
`stream::refuse_recorded` fails a `default` parse whose request tracks the
block's table at all. A request keeping the table at the data level and the
refused column at the metadata level (`--statistics-level`'s column override)
then fails over an ignoring parse's cache and passes over a fresh one — the
verdict depending on which run gathered the cache, which the record exists to
end. **The record is per column**: each column holding a refusal keeps its
first in full and its count, a `default` parse fails exactly when it tracks
one, and the error quotes the first, in row then column order, among the
columns it tracks — the field a fresh read would have met. Rejected: the
per-block record, over-strict; per-block plus the set of refused columns, exact
in verdict but able to quote a field the request never keys. The width falls
only on a block holding a refusal; `info` prints a line per such column, in
column order. 31.13.1 shipped the wrong contract, so this is slice 31.13.2,
landing before 31.14, whose checked-in-full mark sits beside the record.

## A clean `strict` parse promises what the field and its declaration decide

31.14 shipped `strict` under the roadmap's "a clean parse means what a clean
restore does" ([`roadmap.md`](../../design/roadmap.md), "A literal is
guaranteed in `*_out`'s form and never read past `*_in`'s"), which no checking
reaches: a restore also refuses a `CHECK` (arbitrary SQL), an input its own
server decides (`xml_in`'s libxml and `xmloption`, `cash_in`'s `lc_monetary`,
which `pg_dump` does not set; a user type's C function), and a post-data
constraint under `ON_ERROR_STOP`. **The promise is now the field and its
column's declaration**: its type's `*_in`, its typmod and a `NOT NULL`, the
roadmap section rewritten to it and the manual listing what is outside.

Inside that boundary and unchecked at 31.14, each to be closed: `json`,
`bit`/`varbit` and the seven geometric types, held as text with no reader
(`predicate::field_refused` checks a `Text` kind for nothing); the length of a
`varchar(n)`, `char(n)`, `bit(n)` or `varbit(n)` value, where `numeric(p,s)`'s
typmod is already applied (`typmod_unscaled_digits`); and `NOT NULL`, which the
preamble does not read (`resolve_columns`: every Arrow field is nullable), on
the column, at the table (v18) or through a domain (D41's walk).

The gaps are P31's, the promise being 31.14's contract: slices 31.16–31.20
close them, the grammars first as self-contained, the `varchar(n)` length and
`NOT NULL` last as core-path changes, and P31 wraps after them. **Those two
apply under `default` too**, wherever a field is read, as `numeric(p,s)`'s
typmod already does: a parse refuses what it decodes, and either check is
nearly free on what is read already. 31.21 has `strict` name what it left
unchecked in the dump it read, which the promise is otherwise uncheckable
against.

## `P33` replaces `M212`: a line is bounded by PostgreSQL, not by a buffer

`M212` would have measured every line against `max_line_bytes`, so the
limit bound evenly; the maintainer's direction was the opposite, that no read
granularity decides whether a row PostgreSQL wrote is read. What `pg_dump`
writes is the floor and what PostgreSQL reads the ceiling, for a line as for a
value (`roadmap.md`, "The input contract is valid PostgreSQL, not `pg_dump`'s
output"), and both are one bound, I71. The default 64 MiB refuses a line under
it (`KD93`), and meeting it moves the memory model, the leader's split and
batch sizing, so it is a phase: `P33`, sketched with [its
inbox](../../design/roadmap-P33-line-bound-inbox.md). `M212` is withdrawn
unlanded, and the Future item "A query's line limit taken from the map" went
into that inbox.
