## 33.13.6 is cut whole by a grilling, and the readers are priced

The splits of 2026-11-08 each took one reader family from the scalar row and left the rest as one row nobody had
sized, three rounds running; `docs/process.md`, "Slice numbering", now says a split sizes its whole remainder. The
remainder is cut by the maintainer's grilling into 33.13.6 (a range's bounds), 33.13.7 (the floats), 33.13.8 (the
network types and `macaddr`), 33.13.9 (`ParseDateTime`'s lexer, the dates, times and timestamps) and 33.13.10

lexer's fields are a query batch's and the tier's too (`decode_date32` is `date_days(s).ok()`), so D149 reaches the
batch's decode and its count pair prices it there.

- **The bounds land first**: with `RangeWalk.bound` gone, a subtype with no push machine yet collects inside
  `KeyRead`, so `int4range` and `numrange` stop collecting at once.
- **Only 33.19's strict side needs every 33.13.x reader landed**, and 33.4–33.7 through it. 33.13.2, 33.20 and 33.16
  read no 33.13.x reader (sums are integer and decimal only, `statistics/stored.rs`; a counted scalar is bounded by
  `longest_counted`, `unrepresentable.rs`); 33.14 and 33.15 read them through `field_key` over an ordering term's
  elements and a multirange's bounds. So the order stands.
- **What is unbounded in each**: a float's blank, digit and `nan(…)` runs (I81); an IPv4 octet's and netmask's
  leading zeros, the family decided by a `:` anywhere (I67); `macaddr`'s `%x` runs and blanks (I68). A datetime's
  blank and punctuation runs, which `ParseDateTime` skips without workbuf space, so a blank-padded value of any length
  is read (I83); `interval`'s ISO 8601 fallback reads the raw text's digit runs with `strtod` (I84).

P33's spec adopts D108 for a slice changing what `field_key` or a query's batch reads with ("How it is shown"), and
each 33.13.x row but 33.13.6, which changes neither, owes a count pair. 33.13.4 and 33.13.5 moved `field_key`'s
integer, `oid`, `boolean`, enum, `uuid` and `numeric` readers and the batch's `uuid` and decimal decode onto push
machines unpriced. `--count-pair` takes only the tree's parent (`count_pair_refusal`), so 33.22 takes one pair per commit from a clean detached checkout.

Each 33.13.x reader answers as the one it replaces, held by a differential test, so no 33.13.x slice changes what a type
reads or bumps the cache format (spec, "How it is shown"): today's unparsed spellings, a float's blank-padded, hex and
`nan(…)` ones and `KD85`'s, stay unparsed.
