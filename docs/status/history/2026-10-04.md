## Line endings follow PostgreSQL's two readers; 31.28 and 31.29

A file's line endings are detected only where PostgreSQL detects them, which
is per `COPY` block: `CopyReadLine` fixes a block's terminator from its first
row and refuses a row ending otherwise (`copyfromparse.c`, v18.6). psql detects
nothing: a quoted literal keeps every byte, a CR included, `psql -f` opening
the script binary on every platform, and outside one a CR is whitespace
(`psqlscan.l`). So a literal keeps its CR in any file, a CRLF one included, the
value being what a restore of that file holds (31.28, `KD100`), and `COPY` rows
get per-block detection (31.29, `KD101`), the two sliced apart because only a
converted file needs the second. Settled by the maintainer.

## 31.29 lands without bare-CR blocks; 31.29.1 earned

31.29's row read a block's ending as LF, CR LF or bare CR. The first two
landed ([notes](../../design/roadmap-P31.29-row-endings-notes.md)); a block
whose first row holds a bare CR is read as before, and **31.29.1** holds it,
`KD101` rewritten to it. Two things set it apart, each settled by source and
the koji replica (I91). The interior split and a query's segments resync on
LF, and a bare-CR block holds none, so they would need the block's ending
from the cache: a rework of tested core paths. And psql frames a restore's
lines by LF and never finds `\.` CR, so the server discards everything after
that line up to psql's next `\.` line, bytes a restore never runs and the map
has no span for. Whether to build it is under STATUS's "Decisions worth
another look". A backslash before a raw LF or tab making it data is `KD104`,
and a `\.` ending the file with no LF after it, which a restore refuses,
`KD105`, both `(c)`.
