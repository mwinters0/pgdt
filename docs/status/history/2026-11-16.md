## A test's line bound crosses the crate boundary through `internal`: `M282`

Settled with the maintainer, reviewing STATUS's entry that a test states a line bound through a `test-support` field
rather than a crate-private argument (33.6, D164).

- **`ReadOptions::line_bound` is the one `test-support` item on an API path**: the cache's test encodings and
  `arrangement_of` (D83) are each re-exported from their crate's `internal`, which `scripts/layering.py` refuses an
  embedder and the embedder test; a `pub` field of `ReadOptions` (`scan/chunked.rs`) is outside that rule, so an
  embedder turning the feature on states a bound without naming the word.
- **A workspace test build unifies `pgdt-dump/test-support` into the `pgdt` binary** `crates/pgdt/tests/line_bound.rs`
  runs, pgdt-query's dev-dependency turning it on: the real-bound test reads `line_bound()`'s field arm, and the shipped
  build's constant arm is read by no test. Not checked against a build log.
- **Settled, not yet built**: the bound is a private field of `ReadOptions` in every build, `LINE_BOUND` from
  `Default`, and a test outside `pgdt-dump` states it only through a `test-support` function in `pgdt_dump::internal`;
  `line_bound()` has no `cfg` arm, so the real-bound test reads the code that ships. A struct literal or update over
  `ReadOptions` outside the crate no longer compiles in any build, `with_chunk_size` being the one way to state a
  chunk. `ChunkedScanner` already holds the bound as a field in every build (`chunked.rs`), so no per-chunk code
  changes. D164's `Code:` and 33.6's notes describe today's field until it lands.
- **Routed**: **`M282`** admitted, not blocking P33 — no production caller states a bound.

## The offset cut is installed only past the caps that already imply it: `M283`

Settled with the maintainer, reviewing STATUS's entry that the offset cut is a ceiling on `max_bytes`, unpriced (33.6,
D164).

- **The ceiling changed a default batch's per-row data**: `RowBatcher::new` (`batch.rs`) set `max_bytes` to
  `OFFSET_CUT_BYTES` for every offset-bounded schema, so `should_flush`'s byte test compares on each row of a default
  query over a `bytea`, array or enum column, where it found `None`; the spec's "costs nothing at the default" held only
  of the per-row test D164 rejects.
- **A span cap at or below the cut already bounds a batch's text**: `bytes_in_batch` counts the projected fields of
  pushed rows (`push_row`), each inside the batch's span (`count_row`), and the span trigger fires once the span reaches
  its cap, so before any row `bytes_in_batch ≤ span < max_source_span`. Every batcher holds a span:
  `plan_partitions` returns `charged_span.or(max_source_span)`, a partition-retaining source keeping the stated one.
- **Settled, not yet built**: the ceiling is installed only where neither `max_bytes` nor `max_source_span` is at or
  below `OFFSET_CUT_BYTES`, so a default batcher's options are its parent's and no count-pair row changes code or data;
  the cut binds where a caller lifted both. D164 then rejects the ceiling under every cap (a comparison on every
  default batch's rows) beside the per-row test. The property it rests on is asserted, not only stated: `push_row`
  debug-asserts `bytes_in_batch` within the span after `count_row`, as `push_counted_row` asserts its own, compiled
  out of the shipped build a count pair reads. D164 and `batch.rs` describe today's ceiling until it lands.
- **Routed**: **`M283`** admitted, not blocking P33 — `long-line-resident` and the count pair read at the default caps.
