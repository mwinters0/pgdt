# 2026-08-26

## 4.4's three unattended calls are reviewed; all three stand, and the section is empty

`STATUS.md`'s "Decisions worth another look" carried three entries from 4.4.
None is reversed; each leaves the section because its durable half now lives
where the fact belongs.

**The cache format version is irrelevant pre-1.0, so the first entry was
framed around a non-cost.** It led with the `v9 → v10` bump `Option<Vec<…>>`
forced, but three places already say a bump is free and nothing migrates —
`roadmap.md`'s "Pre-1.0", `architecture.md`'s "The cache", and `cache.rs`'s
`FORMAT_VERSION` doc comment, which states the mechanical rule ("bump whenever
a persisted field is added, removed or reshaped"). 4.4 complied with a written
rule; there was no decision there to review. What a bump *does* cost is
wall-clock: it kills the koji `.dqcache`, the one artifact here that takes ~54
minutes to rebuild. That is accepted with no rule attached — the cache is a
byproduct of a scan run for other reasons, and no work has ever planned around
one surviving. Recorded in `measurements.md`'s koji section so a future session
does not plan cache-only koji work around a stale file. (`runs/koji-throughput.dqcache`
is v9 — first bincode byte `9` — and was already dead when 4.4 landed.)

**With the version framing gone, the first two entries were one decision about
one unreachable state.** `parse_column_fragment` returns `None` only for an
empty fragment, a non-identifier name, or an empty type-word list, none of
which `pg_dump` emits — so `Composite { fields: None }` is representable and
unreachable, while `Some(vec![])` (I23, zero-field composite) is reachable and
has a fixture. The `Option` exists to keep those apart, and the unreachable arm
deliberately gets no `ColumnResolution` variant of its own. Both halves, and
the rejected alternative of dropping the whole `TypeDef` on an unparseable
body, are now in `architecture.md` under the all-or-nothing rule.

**Push mode's lost CLI coverage is close to nothing, but its lost *purpose* is
the real question.** `read_table` is a ~20-line drain over `table_stream`, so
the CLI's move to pull mode still exercises the entire shared scan loop; only
the drain and the `Break` → resume-token path lost their CLI caller, and
`tests/batch.rs` covers both. Buying that coverage back with a CLI flag would
put a test-shaped feature in a user-facing surface, so nothing is added. What
does survive is that push mode now has no non-test consumer at all, which is a
Phase 6 question — a `TableProvider` pulls, and the Python binding's shape is
undecided — and is filed in `roadmap-phase6-inbox.md`.

## The cache format version is now untracked, on purpose

Pre-1.0 the integer carries no information anyone can act on, and it had
accumulated in six documents — where its only effect was to invite another
round of "which slice takes which number". It now exists in exactly one place,
`cache.rs`'s `FORMAT_VERSION`, with `git log -p` as its history;
`architecture.md`'s cache section states that as the rule, and the phase-4
spec, its 4.4 notes, `STATUS.md` and `measurements.md` all name the *bump*
without naming the number. What survives is the mechanical rule that produces
one — bump whenever a persisted field is added, removed or reshaped.

## 4.4.1's scope is sharpened, and `pgdq info` is not currently wrong

`pgdq info` prints each column's declared PostgreSQL type, plus a
`resolution_label` under `--verbose` for columns that did not map; that label
covers every `ColumnResolution` arm including `OpaqueElementType`, in accurate
prose. So nothing `info` prints today is wrong, and `STATUS.md`'s 4.4.1 row —
which called the arm "compile-only" and the state "wrong until this lands" —
overstated it. The manual is the only wrong artifact.

What the flip did leave unanswerable is what a *successfully* mapped column
became: `payload text[]` reads identically whether it resolved to
`List<Utf8View>` or stayed a string. 4.4.1 therefore adds the resolved Arrow
type to the `--verbose` per-column line, for every column that is not
`Utf8View` — the maintainer's ruling, against a narrower proposal restricted to
non-`Scalar` plans. The wider rule makes `--verbose` a complete statement of
the Arrow schema and picks up the scalar mappings (`numeric` → `Decimal128`,
`timestamp` → `Timestamp(Microsecond)`) that were equally invisible and equally
consequential to a caller building against it.

**The obvious rendering fails on exactly the family this phase added.**
`arrow-schema` 59.2.0's `Display` is terse and `FromStr`-reversible, and a
composite's field names are the user's own — but the five-field range struct is
identical in every dump and renders as 137 characters
(`Struct("lower": Int32, "upper": Int32, "lower_inclusive": non-null Boolean,
…)`), 143 wrapped in a `List` for `int4range[]`. It collapses to `Range<T>`,
with the manual carrying the real layout once — which is what makes the elision
lossless, and is why that sentence is a 4.4.1 deliverable rather than the
census slice's. The substitution dispatches on the `NestedPlan`, never on the
field names, since a user composite may legally declare the same five;
`RANGE_STRUCT_FIELDS`'s doc comment already reserved that. A built-in
multirange and an array of its range render identically, which is right — they
*are* one Arrow type, and the declared PostgreSQL type on the same line
separates them.

## Phase 4's koji verification runs once, at wrap

The spec's Verification section listed the koji identity check without saying
when. It runs once after 4.6, detached, rather than per slice: the check is
identity of block/row/byte counts, so six passes are one pass. Koji holds zero
non-scalar values, which is exactly why the check is still worth an hour — it
exercises nothing this phase builds, so a count that moves means a slice
touched the scanner by accident.

## The shape census is two slices, and the split was earned inside 4.5

The spec wrote the census as one row. It is two, and the seam is the one the
spec already draws between 4.3 and 4.4: **recording** is new, type-blind, L1-only
machinery that nothing reads, while **consuming** it retypes an already-tested
resolution path and rewrites `tests/decode.rs`'s pinned refusal of a
multi-dimensional value. Bundling them forces one review to accept both at one
confidence. 4.5's spec row is rewritten to the recording half and the remainder
is the earned `4.5.1`, per the slice-numbering rule; the phase spec's slice
table says the split was earned.

## Reading an array's dimensionality needs no array parser

The census has to answer "how many dimensions does this value have" for every
field of every row of a full scan, which ruled out the obvious implementation —
decode the field, hand it to `nested.rs`. That is L2, needs the field
unescaped, and is far more work per row than the question deserves.

`array_out` settles it instead: the literal opens with exactly `ndim` braces,
and any element whose text contains a `{` is force-quoted, so no element can
extend the leading run — `{"c{d}"}` is one-dimensional, unambiguously. Neither
`{` nor anything in the `[lb:ub]=` prefix is in COPY TEXT's escape set, so the
run is legible in the raw, still-escaped field. That is now **I25**, verified
against v13.23–v18.6 source and observed live. The census reads bytes at the
front of a field and nothing else.

Its bound matters as much as its claim: `MAXDIM` is 6, so a longer run did not
come from `array_out` at all. `MAX_ARRAY_DIMS` carries that, and 4.5.1 must
treat a maximum above it as unusable rather than as a depth — otherwise a
hand-edited file can ask for a `List` nested 200 deep.

## The census is unconditional; a mapped block always carries one

4.5 censused only under `ScanExtent::Full`, on the reasoning that a cold query
would otherwise pay per-row work for a census `DumpIndex::is_complete` must
then reject. That is reversed. Every mapping pass censuses —
`build_index`, `build_map` and `stream::map_forward` under either extent — and
`CopyBlock::array_shapes` becomes a plain `Vec<ArrayShape>`. 4.5.1 carries the
change, and the phase spec's census section carries the rule.

**The premise the original call rested on was false.** It was written up as a
physical constraint — "a block's bytes are read once, there is no second visit
at which it could acquire a census" — and neither half holds:

- A cold query already receives every row of every block it maps.
  `map_forward` handles `Event::Row` by calling `builder.on_row(row.raw)`
  unconditionally (`src/stream.rs`); `on_row` was simply a no-op with the flag
  off. The rows are already delimited and the bytes are already in the buffer,
  so what was declined is the brace/bracket pre-filter and nothing else.
- The queried block is read twice regardless — once by the mapping pass, once
  by the replay pass. `src/stream.rs`'s module docs state that as the price of
  keeping the two passes separate. "No second visit" was true only of blocks
  the query passes *over*, and only because the first visit had been declined.

**What the flag actually bought was an unobservable hole.** `map_forward`
splices new spans onto a prefix it does not re-read, so a dump mapped by a cold
query and *then* by a `ScanExtent::Full` one came out `is_complete` — the
index's own statement that it is trustworthy — with its early blocks never
censused and no way to repair them short of deleting the cache. Every consumer
then had to carry a two-sided test forever to defend against a state we
manufactured.

**A mapped block is always a fully-walked block**, which is what makes the
field total. `scanned_through` advances only at a `CopyEnd` watermark or at
`finish(size)`, so a `CopyBlock` never reaches the map half-scanned under
either extent. With that, `Option` has nothing left to express: an empty
`Vec<ArrayShape>` means "censused, saw no array-shaped literal", and
`ArrayShape { dims: None }` already means "no value constrained this column".
`is_complete` survives on its own merits, at the *table* level — I2 lets one
table occupy several blocks, and a query that stops at its target never learns
what lies past it.

Consequences for 4.5.1:
`tests/census.rs::only_a_scan_that_reaches_eof_censuses` inverts into a test
that every mapping pass censuses, and
`tests/query_cache.rs::a_query_built_index_tiles_in_every_cache_state` gets its
span-for-span equality back — the `without_census` normalizer 4.5 added exists
only to paper over the asymmetry being removed here, and goes with it.

## A streamed schema needs no completeness test; `is_complete` is for a reported one

`is_complete` was carried into the census work from `roles`/`tablespaces`,
where it answers a question about the *file*. Applied to a query's schema it is
one scope too wide, and applying it would have left the `FieldDecode` refusal
in place for every cold query — the case the census exists to remove — while
the evidence sat in blocks the query had just walked.

`table_stream` runs its two passes strictly in order. `map_forward` returns,
*then* `matches` is collected from the map — every block bearing the target's
`(database, qualified name)` — and one schema commits from that set before a
row is emitted (`src/stream.rs`). So at commit time the set of blocks whose
rows the stream will hand back is fixed, and post-reversal every one of them
carries a census. Min-of-mins, max-of-maxes over that set is the evidence for
exactly those rows, and nothing outside it is ever emitted.

That holds even where the stop rule is fooled. `stream::target_settled` fires
only once no further block can share the name (I2: no partition-root marker,
no `\connect` anywhere), and the one shape it cannot detect — a plain first
segment with something concatenated after it, `STATUS.md`'s known gap — is
also a shape whose extra blocks the stream never replays. A schema true of the
rows handed back is the strongest claim available, and it is the one being
made.

`is_complete` keeps a real job on the other side of that line: `pgdq info`
answers "what is this table's schema" from an index alone, with no replay to
bound the claim, so a block past the frontier genuinely has no census and its
columns must read back optimistically. That is where the test belongs, and the
phase spec's "upgrade, not a gate" section is rewritten around the streamed /
reported split rather than the cold / full one.

**No CLI surface can currently reach a partial index's schema**, which is what
makes the reported half theoretical rather than a second code path. `pgdq info
--source` falls back to a full `build_index` whenever the loaded cache does not
cover the file (`pgdump_query-cli/src/main.rs`), and cache-only mode bails on
an `Incomplete` cache unless `--preamble-only`, which prints metadata and no
per-column resolution at all. So every index `print_index` is handed is
complete by construction. The exposure that remains is a *library* caller
holding a partial `DumpIndex` from a cold query and reading `array_shapes` off
its blocks directly — a Phase 6 concern, filed there.

**The resume path is the place this can silently diverge.** Of the three
`resolve_block` call sites in `src/stream.rs`, `resume_state`'s takes only
`metadata` — so a stream resumed mid-block would rebuild an optimistic schema
where the original had a retyped one, and the same query would return two
different Arrow schemas depending on whether it was interrupted. The index is
in scope at every call site, so 4.5.1 passes the block's census down rather
than widening the opaque `ResumeToken`.

**The cost is not measured on array-bearing rows and 4.6 is where it will be.**
`measurements.md` records the census as free on brace-free data — the koji
shape — and says explicitly that array-dense data is unmeasured. Making the
census unconditional widens that unmeasured cost to every cold query. It lands
anyway: the pre-filter is one pass over a row's bytes with no field splitting,
and the hit path counts leading braces on still-escaped fields, so there is no
order-of-magnitude regression available. 4.6 already exists to build the array
stress section and land the ratio, and it is the slice that will confirm or
reverse this.

## `pgdq info` will report what a partial index knows, and `--json` will carry resolution

Two decisions, taken together because they are the same instinct: the program
collects per-column resolution and an array-shape census, and currently throws
both away rather than emitting them in any form a script can read or in any
state short of complete.

**`--json` gains per-column resolution.** It exports `DumpIndex` today — an L1
structure with no resolved schema — so everything `pgdq info --verbose` prints
per column (the outcome, the declared type, and since 4.4.1 the resolved Arrow
type) is human-only. The text path already computes it: `print_index` calls
`resolve_columns` per block for `--verbose`, so the data exists and is
discarded at the JSON boundary.

**`info` becomes a pure cache reader and `parse` becomes the only scanner.**
Today the boundary is blurred in both directions: `pgdq info --source` falls
back to a full `build_index` whenever the loaded cache does not cover the file,
and cache-only mode bails on an `Incomplete` cache unless `--preamble-only`. So
an `info` can silently cost 54 minutes on koji, while a half-finished koji
cache can answer nothing about the half it holds. Both reverse. `info` reports
whatever the cache holds and marks the coverage; with no usable cache it errors
and says a `parse` is required, rather than starting one on the user's behalf.
`DumpIndex::is_complete` stops suppressing the reported answer and starts
labelling it.

**`--preamble-only` moves from `info` to `parse`.** It says how much of the
source to read, which is exactly `parse`'s subject. Keeping it on `info` would
leave the new rule with a single exception — a bounded scan, but a scan — and
the rule's whole value is that it is total. The bounded read itself is
unchanged (`index::preamble_only` already takes a `CacheMode`); only the verb
it hangs off moves, and `info` reads the preamble-only cache it leaves.

**That puts a new requirement on `parse`: it must resume.** It is the only
remaining route to a finished scan, and today it scans from byte 0 and ignores
any existing cache by design (`pgdump_query-cli/src/main.rs`). The machinery
exists — `stream::map_forward` already continues from a cache's frontier,
splicing new spans onto a prefix it does not re-read — so this is wiring an
existing mechanism into a second caller, not building one.

**`parse` persists after every completed block**, which is what makes resuming
worth building: today a koji parse killed at minute 50 leaves nothing at all,
because `build_index` scans to EOF and the cache is written only after it
returns. `map_forward` already saves per block, so this is the same loop reused
rather than new machinery. The unmeasured cost is write amplification — the
cache is serialized whole on each save, and a full scan has orders of magnitude
more blocks than an early-stopping query — so the phase measures it on koji.
A throttle is the fallback the measurement chooses, not a thing to design in
now.

**`parse` resumes by default and gets no `--restart` flag.** After this phase,
"finish the scan" is the overwhelmingly common reason to run `parse` twice on
one file, so it is what the bare command should do; removing or renaming the
cache file is the restart, and it says the same thing without a flag. This
replaces today's documented promise that `parse` always scans fresh and ignores
any existing cache.

**`info` names why a cache is unusable, so `CacheStatus::Absent` splits.** Its
four causes were collapsed because every caller answered them the same way —
scan it anyway. `info` no longer has that answer, so "never parsed" and "your
file changed" become different sentences. `mtime_changed`, which by design does
not invalidate a cache, becomes a warning line for the same reason: under the
old behaviour a suspicious cache was about to be overwritten by a rescan; now
it is the answer being reported.

**Coverage is stated once, not per record.** The human output gets a completion
line in the shape `Scan completion: 76% (12345 bytes)`; the JSON carries the
components as separate fields. Nothing below it is qualified, and that falls
out of the census reversal above: a block enters the map only at a `CopyEnd`
watermark and is censused when it does, so every record a partial index holds
is complete in itself. What a partial index lacks is records, not confidence —
a per-record flag would always carry the same value and would read as if it
could vary.

**Neither changes 4.5.1.** A streamed schema still needs no completeness test,
for the reason above; this is a second surface, not a gate on the first.

**`--json` gets no stability promise and no `version` field.** The shape stays
undocumented until after 1.0. A version field is exactly the compatibility shim
the roadmap's "Pre-1.0" section forbids, and it would be the only one in the
tree; `STATUS.md`'s existing "`--json` carries no shape promise at all" stands
unchanged.

**The export is keyed by `COPY` block, not by table.** Per block is the unit
the data actually has and is already computed — `ResolvedSchema` carries
`schema`, `columns`, `notes` and `plans`, and `print_index` builds one per
block for `--verbose` today. Each record identifies its block (`database`,
qualified name, `header_offset`) so a consumer can group them. Per table is
what a script most likely wants, and it is the shape that is not well-formed
yet: one table can span blocks (I2), and a header-less block takes placeholder
`column1…N` names from its first row (`batch::column_names`), so a rollup needs
a merge rule for disagreeing blocks and for column identity. Keying by block
leaves that question with the consumer, which is where it honestly sits until
Phase 6's `TableProvider` has to answer it. *Rejected:* shipping both, per-block
records plus a rollup that omits any table whose blocks disagree — that is the
same guess with a fallback bolted on, and adding the rollup later is purely
additive if grouping turns out to be the common case.

**It becomes Phase 9, running after Phase 4 and before Phase 5.** It is not
out-of-band — it changes decisions the phase-4 spec records and does not fit
one session — so it goes through grilling to a spec and numbered slices. It is
not a phase-4 slice either: phase 4's subject is composite value decoding, and
appending an output-contract change to its checklist is how a checklist stops
meaning "what this phase committed to". The number is 9 because 5–8 are taken
and this project does not renumber a tail; the roadmap's ordering carries the
sequence.

## `Error::FieldDecode` will name its one remaining remedy

After 4.5.1 the dimensionality refusal has exactly one reachable cause: an
array nested inside a composite, or inside another array's element type, where
the census — keyed by column — has no slot to record a shape. A top-level array
column is retyped before the schema commits and cannot reach it. So scanning
more of the file cannot help, `--schema-mode strings` is the only route to the
data, and the message names it. Stating that unconditionally is only safe
because the other cause is gone; while both were reachable the same sentence
would have been wrong half the time.

## `ColumnResolution` gains a seventh outcome for a block nobody read the DDL for

Resolving a block's columns needs the preamble of *that block's* database. A
partial cache always holds the first database's — `scan_preamble` runs before
anything else — but a `pg_dumpall` or `--create` dump whose scan stopped inside
a later database has blocks whose DDL was never read. The streaming path
already refuses that outright (`Error::MetadataNotScanned` rather than a silent
degradation to `NotDeclared`), and a reported export cannot do the same,
because one unresolvable block must not sink the whole document.

So `MetadataNotScanned` becomes a `ColumnResolution` variant. Reusing
`NotDeclared` would have been the cheap answer and is the wrong one: it means
"the dump never explained this column" and is final, where the new variant
means "finish the parse and ask again". Identical-looking output, opposite
advice.

## Phase 9's shape is settled

Four slices, ordered so the thing that produces partial caches lands first and
the reporting slices have real material to test against: `parse` resumes and
saves per block (with the koji write-amplification measurement); `info` stops
scanning; the coverage line; the per-block JSON resolution. `9.3` is small
enough to fold into `9.2` and is deliberately not — it is the phase's only
user-facing formatting decision. The spec is
[`../design/roadmap-phase9-partial-reporting.md`](../design/roadmap-phase9-partial-reporting.md);
`STATUS.md` carries the unchecked slice checklist.

A resumed `parse` prints one line naming where it resumed, then the whole
index. The listing describes the file's state after the run rather than the
invocation's diff, for the same reason `STATUS.md` describes what is — but a
full listing with no resume marker gives a user checking on an interrupted koji
scan no way to tell resuming from rescanning.

## 4.5.1's two unattended calls are reviewed; both stand, and the review found a defect

**The `MAX_ARRAY_DIMS` verdict stands.** 4.5's notes required only that a
maximum above `MAXDIM` be treated as "unusable rather than as a depth", which
admits two readings. It is read as *not evidence at all*: the column keeps its
optimistic type and the offending row surfaces as an `Error::FieldDecode`
naming table, column, offset and value. The alternative — degrading the column
to text — absorbs the damage into a column that reads fine, and the
discriminating case says why that is worse: a census of `(1, 200)` means most
rows are ordinary 1-D arrays and one row is not from `array_out` at all. What
this does *not* do is report the damage at scan time to someone who never
queries that column; the file-level `Diagnostic` channel is where that belongs
and it is filed under `roadmap.md`'s "Future".

**The spec's manual section is amended rather than left diverging.** Its
"What the manual must say" promised a two-path statement — optimistic by
default, exact after `pgdq parse`, plus "how to tell which path a given run is
on". The census reversal above deleted the distinction for a query, so that
bullet had no answer left to give a user. The spec's census section was
rewritten that day and this section was not; it now describes one path, and
notes that the two-path statement survives only for a *reported* schema over a
partial index, which is Phase 9.2's manual work.

**`MAXDIM`'s re-verification command was broken on v13.** I25 grepped
`src/include/utils/array.h`, where the `#define` lives on v14+; on v13 it is in
`src/include/c.h`. The value is 6 on all six majors either way, but the check
would have silently found nothing on the one version most worth checking. The
entry now greps both.

## An array whose element type is itself an array does not decode

Found while confirming that `retype_from_census`'s guard protects a reachable
case rather than a hypothetical one. It does — and the column it protects is
broken for a different reason.

PostgreSQL accepts `CREATE DOMAIN intarr AS integer[]` and then a column of
type `intarr[]`; `pg_dump` writes the declared type as `public.intarr[]` and
the value as `{"{1,2}","{3}"}` — **one brace deep**, because `array_out`
force-quotes any element whose text contains `{` (I25). That is now **I26**,
verified against real `pg_dump` output.

Resolution types the column `List<List<Int32>>`, which is right. The decoder
cannot fill it: `batch::append_typed`'s array arm decodes the whole field with
`nested::decode_array`, gets `ndim == 1`, compares it against
`array_depth(parts) == 2` and refuses. So every row of such a column is an
`Error::FieldDecode`, and has been since 4.4's resolution flip — the census
neither caused it nor can fix it, since the census reads `(1, 1)` here and is
correct to.

**The root cause is that `NestedPlan::Array(Array(…))` now means two different
things.** From the census it means *one literal, two dimensions*
(`{{1,2},{3,4}}`). From the DDL it means *one literal whose elements are
themselves array literals* (`{"{1,2}","{3}"}`). `append_typed` and
`render_field` implement only the first, and `array_depth` conflates the two by
construction. That is precisely the collision `NestedPlan` exists to prevent,
which is why the fix is a decision change — a spec amendment and a slice — and
not an out-of-band patch. `STATUS.md` carries it as an unaccepted, unscheduled
gap; the options weighed are refusing the shape at resolution (a `Utf8View`
fallback with its own `ColumnResolution`, cheap) versus teaching the plan and
the builders to tell the two meanings apart.

## The array-of-array-typed-element shape is refused, not supported, and it is 4.4.2

**Refused.** An array whose element type resolves through domains to an array
comes back as `Utf8View` with its own `ColumnResolution`, beside
`OpaqueElementType` — whose precedent is exact, since that refusal also exists
because the element's own literal grammar is not what the outer split assumes.

*Rejected:* splitting `NestedPlan::Array` into a dimensional variant and an
element-is-a-literal one, and teaching `append_typed`/`render_field` to
recurse per element. It is the complete answer and it is contained, but it buys
`List<List<T>>` over a shape almost nobody declares by putting a second meaning
into the one type whose whole purpose is keeping meanings apart, and it lands
in `batch.rs`. It stays available and is strictly additive: it would only ever
touch columns the refusal leaves as `Utf8View`.

**The refusal deletes a subtlety instead of documenting one.** With no nested
`Array` plan reachable, `resolve::retype_from_census`'s "only a plan of exactly
`Array(non-array)`" guard has nothing left to guard against and goes with it.

**It is 4.4.2, before 4.6.** 4.4 promised "nested columns decode end-to-end"
and for this shape nothing can fill the type it produced, so this is a slice
that shipped the wrong contract — a third level by the numbering rule, not a
renumbered tail. Ordering matters because 4.6 measures the array path, and
measuring it while a declared array shape is known-broken measures something
about to change.

**The fixture comes first, inside that slice.** `types/default.sql` gains the
column on all six majors. The absence of this shape is exactly why six majors
of round-trip tests went green over a broken column, and it is the same reason
4.1 and 4.1.1 existed: a hand-written dump proves a refusal fires, but only
real `pg_dump` output proves we predicted what it writes — which is the half
that was wrong here.

## The defect was swept for siblings; the rest of the mapping table is clean

Nine exotic declared shapes were built in a scratch database, dumped with real
`pg_dump` 16, and queried in both `SchemaMode`s. Three fail and they are one
defect wearing three hats — every one is an array-typed *element*:

| Declared | Result |
|---|---|
| `intarr[]` (domain over `integer[]`) | **fails** — `{"{1,2}","{3}"}` |
| `intarr2[]` (domain over domain over array) | **fails** — the chain is walked, so the same shape reaches it |
| a composite with an `intarr[]` field | **fails** — `(L,"{""{1,2}""}")` |
| `pointdom` (domain over composite) | ok |
| `pointdom[]` (array of domain over composite) | ok |
| a composite whose field is a composite | ok |
| `irange[]` (array of a user range) | ok |
| `irangedom` (domain over a range) | ok |
| `int4multirange` | ok |

**The composite-field case matters for 4.4.2's shape.** It fails today and it
needs no separate handling: `pgtype::resolve_nested` maps any non-`Mapped`
outcome to `Utf8View` *in that position*, so refusing the array-of-array
outcome inside `resolve_declared_type` makes a composite field of that type a
`Utf8View` field inside an otherwise typed `Struct` — the rule the spec's type
mapping already states for every leaf that does not map. The refusal composes
for free; only the outcome has to be produced in one place.

The domain chain is likewise already handled: whatever test 4.4.2 adds belongs
beside `element_is_opaque`, which walks domains transitively, and `intarr2[]`
proves the walk is what the shape needs.

## 4.4.2's shape: a new resolution outcome, one fixture table, two faces

**A new `ColumnResolution::NestedArrayElement`, not a reused
`OpaqueElementType`.** The mechanism is shared — both refuse an array because
the element's own literal grammar is not what the outer split assumes — but the
label would lie: `integer[]` is not opaque. It is the distinction 4.4 already
drew between `OpaqueElementType` and `OpaqueBaseType`, and it is the one a
reader acts on, since opaque means *never improves* while this means *yes, if
anyone needs it*.

**The fixture is a new `t_nested_array`, not a column on `t_array_shape`.**
`t_array_shape` is the census's fixture and is read as "these are the shapes
the census reports"; this column's census entry is `(1, 1)` — correct, and the
one place where reading it as an ordinary 1-D array is exactly the mistake. The
new table carries both faces the sweep found: the array-of-array column and a
composite with a field of that type.

**The domain-over-domain chain gets a unit test, not a fixture column.** Its
literal is byte-identical to the single-hop case, so there is no `pg_dump`
output shape left to predict — and predicting output is the half the fixtures
exist for. `pgtype.rs` pins the transitive walk directly.

## Fixture expansion is now a standing rule, not a per-slice judgement

`roadmap.md` gains "Expand the generated fixtures freely; never infer what
`pg_dump` writes", stated as closed. The bias is deliberately lopsided — a

That rule is why 4.4.2's table also picks up the five passing shapes rather
than only the failing one.

## The fixture rule's check, and the half it deliberately cannot cover

A standing rule with nothing enforcing it is already being violated somewhere,

## `pgdq parse` now types every database, which `pgdq query` still will not

A full scan recomputes `DumpMetadata` over the whole span list, so every
`\connect`ed database comes back `preamble_complete` — where before only the
first did, because that is all `scan_preamble`'s bounded prepass captures.

The recompute lives in `stream::map_file`, deliberately **not** in
`map_forward`. `preamble::dump_metadata_from_spans` may only be called at one
of two boundaries — EOF, or the current database's first `COPY` header (I1) —
and a `CopyEnd` watermark is neither: a trailing `Unscanned` tail would make
the last database's `preamble_complete` a lie. `map_file` runs at EOF; a query
never does, and clones `metadata` before mapping anyway, so the streaming path
is untouched. `Error::MetadataNotScanned` therefore still fires for a query
against a later database until a `parse` has run — which is exactly what
`tests/stream.rs`'s
`selecting_a_later_databases_table_needs_strings_mode_or_a_prior_full_scan`
already named as the remedy.

The reported half of the same condition became
`ColumnResolution::MetadataNotScanned` in 9.4. Two answers to one condition,
deliberately asymmetric — a stream refuses because a wrongly-typed row is a
wrong answer, a listing degrades because one block must not sink the document.
Filed into [`../../design/roadmap-phase6-inbox.md`](../../design/roadmap-phase6-inbox.md),
since the embedded API fronts a streaming scan with a reported schema and has
to pick.

## Loading a cache recomputes its diagnostics, because `info` no longer scans

`diagnostic.rs` has always said the file-level diagnostics are recomputed
rather than persisted — but nothing recomputed them on the *load* path, since
every consumer had just scanned. `pgdq info` no longer scans, so the

`cache::status_from_file` now re-derives the tiling check and the coverage

## The input contract is valid PostgreSQL, and `integer[][]` is refused wrongly because of it

Three standing decisions settled while grilling a 4.4.3 follow-up to 4.4.2.
They are in [`../../design/roadmap.md`](../../design/roadmap.md)'s standing
rules; the evidence is here.

**pgdq accepts any plain SQL a PostgreSQL server would accept.** `pg_dump` is
the producer we verify against, because it is the one we can run six versions
of — not the boundary of the input. Other `pg_dump`-compatible producers get
folded into the fixture generators as they are identified. The code had
already chosen this twice without stating it: `domain_terminal`'s iteration
bound exists so a hand-edited file fails rather than spins
(`pgtype.rs`), and `shape_verdict` decides a brace run longer than `MAXDIM`
means the file is damaged or hand-edited and picks the honest outcome
deliberately (`resolve.rs`). The preamble parser agrees — `parse_create_table`
handles arbitrary whitespace, quoted identifiers, trailing constraints and
block comments, so it is a general SQL parser and not a `pg_dump`-shaped one.

**Resolution reads a declared type as PostgreSQL's type system reads it**,
since that is the type the `COPY` block's values were written by. This is what
`resolve_declared_type` already does everywhere else — `int4` → `Int32`,
typmod splitting, the domain walk are all server semantics applied to text,
none of them facts the dump states. `layering.md`'s rule 5 ("the cache holds
what the dump said, never what we concluded") constrains the cache, which
stores declared-type strings verbatim; it does not reach resolution.

**The defect this exposes.** 4.4.2 refuses `integer[][]` as
`ColumnResolution::NestedArrayElement`, whose label reads "the array's element
type is itself an array". PostgreSQL does not agree: `integer[][]` *is*
`integer[]` — dimensionality is not in the type system, `format_type`
reconstructs one `[]` however the column was declared, and `attndims` is
discarded (I21, verified v13.23–v18.6). So the element type is `integer`, and
the refusal makes a false claim about the column rather than declining to
answer. The repo holds the demonstration: `fixture_schema_types.sql` declares
`v_multidim integer[][]`, `fixtures/*/types/default.sql` shows `pg_dump`
writing `integer[]`, and the census types that column `List(List(Int32))` and
round-trips `{{1,2},{3,4}}` today.

I26's shape — `d[]` over `CREATE DOMAIN d AS integer[]` — is untouched. Its
literal really is one brace deep and its element type really is an array; only
the syntactic spelling was over-caught.

**Where a fixture cannot exist, the invariant that proves it cannot stands in
for one.** No generator input makes `pg_dump` emit `integer[][]`, because
emitting `integer[]` instead is I21 itself. The fixture rule's target is
guessing what a producer writes; a verified invariant is the opposite of a
guess, so this behaviour is pinned by unit test over a hand-built `TypeDef`
list, citing the entry it rests on.

## Five of PostgreSQL's six array-declaration spellings do not resolve

`integer[][]` is one of six spellings the server accepts for an array-typed
column, and all six are the same type (I28, verified against the `Typename`
grammar in v13.23/v16.15/v18.6 and observed live on 16.15). Measured against
the current build:

| Declared | `pg_dump` writes it? | Resolves to |
|---|---|---|
| `integer[]` | yes | `List(Int32)` |
| `integer[3]` | never (I21) | `Unknown` |
| `integer[][]` | never (I21) | `NestedArrayElement` |
| `integer[3][4]` | never (I21) | `Unknown` |
| `integer ARRAY` | never | `Unknown` |
| `integer ARRAY[4]` | never | `Unknown` |

So the defect is the production, not the spelling — `integer[][]` is only the
member that fails with a false label rather than an honest `Unknown`. **4.4.3
normalizes the whole `Typename` array-bounds production**, since fixing one
sixth of it under a rule that just made valid PostgreSQL the input contract
would be arbitrary. The `ARRAY`/`ARRAY[n]` spellings are SQL-standard and
documented for user use, not obscure.

**The normalization lives in `pgtype.rs`, not `preamble.rs`.** One helper,
applied at the top of `resolve_declared_type` and inside `domain_terminal` —
the second because `CREATE DOMAIN d AS integer ARRAY` is equally legal and the
domain walk tests its terminal with `ends_with("[]")`. Normalizing at parse
time was rejected: `ColumnNote::declared` carries the raw declared string so
`pgdq info --verbose` can print what the file says beside what we made of it,
and a parse-time rewrite would have pgdq quietly editing the user's DDL in the
one place the raw text is the entire point.

A known limit, pre-existing and not widened by the slice: a quoted identifier
may contain brackets (`CREATE DOMAIN "weird[]" AS integer`), and the array
suffix test is not quote-aware. Named rather than fixed; fixing it means a real
type-name tokenizer.

## CSV `COPY` blocks are a Future item, not a permanent non-goal

The non-goal rested on "reading CSV would mean accepting input `pg_dump` never
emits", which the input-contract rule above retired. `psql` writes `COPY ...
WITH (FORMAT csv)` and it is valid PostgreSQL, so it is in contract and simply
not built; support is planned post-1.0 under alternate formats, with its own
fixtures. What it costs is a second field decoder plus fixtures, and `copy.rs`
being independent of its byte source is what keeps it a variant rather than a
rework.

## 4.4.3's shape: one helper, two call sites, two tests

**The normalization is one `pgtype.rs` helper at two call sites**, and that is
the whole reach. `resolve_nested` delegates to `resolve_declared_type`, and a
domain's base type resolves through it too, so a composite field declared
`integer ARRAY`, a domain over `integer[3]`, and a range bound all come right
from the entry-point call alone. `domain_terminal` needs the second because it
walks strings itself and tests its terminal with `ends_with("[]")`.

**Two tests, and the second is the one that matters.** The six spellings'
outcomes are a unit table over hand-built `TypeDef` lists, citing I28 per the
fixture rule's carve-out. Beyond that, one hand-built dump — `tests/decode.rs`
already builds dump text inline — with an `integer[][]` column of uniformly
2-D values and an `integer ARRAY[4]` column, asserting `List(List(Int32))` and
a `Strings`-mode round trip. That path crosses resolution, the census, and
`retype_from_census`, no generated fixture can ever reach it, and a future
change to the census transform would break it with every unit test still green.

**The carve-out's check is the citation.** Naming an `I<n>` at the test site is
what puts the behaviour inside the invariants register's re-verify ritual;
without the citation the carve-out would be a way to skip a fixture that was
perfectly possible. Recorded in the rule itself rather than left to practice.

The manual needs only the `ARRAY` spellings added — `type-handling.md` already
states that `integer[]`, `integer[][]` and `integer[3]` are all written
`integer[]`, and never claimed the spelling was refused.

## 4.4.3 changes nothing about koji, and the repo will prove the collapse itself

**koji is unaffected.** Its whole preamble (the first `COPY` starts inside the
first 3MB) carries six array declarations, every one spelled `[]`, and zero
`[n]`, `[][]` or `ARRAY` forms — as I21 predicts for any `pg_dump` output. The
phase-wrap koji run needs no adjustment for this slice.

**The helper strips only well-formed bounds.** Any number of trailing `[]`/`[n]`
pairs with no cap (the DDL bracket run is unbounded even though `MAXDIM` is 6 —
I28), and `ARRAY`/`ARRAY[n]` case-insensitively, since `ARRAY` is a keyword.
`SETOF` is ignored: it is a function-return-type prefix and cannot appear in a
column declaration. A malformed run — `integer[abc]`, `integer[` — is *not*
stripped and the type stays `Unknown`. There is no server behaviour to match
for text a server would reject, and inventing a type for it is the same failure
as reading a spelling more literally than the server does, pointed the other
way.

**The fixture generator gains two columns**, `integer ARRAY[4]` and
`integer[3]` in `t_array_shape`. `v_multidim integer[][]` already demonstrates
the collapse in checked-in bytes; these extend that to the spellings nothing in
the repo covers, and they carry a falsifiable prediction — the dumped DDL must
read `integer[]` in all six majors. The cost is the usual regeneration churn
(the block widens, `tests/decode.rs`'s positional resolution assertion moves,
4.4.2's counts go stale).

**`pg-dump-compatibility.md` gains a row for producers other than `pg_dump`** —
in contract, untested, no generator — and its CSV row moves from "Unsupported"
to planned post-1.0, since the reasoning that made it unsupported was the input
contract we just widened.

## The spelling fixtures get their own table, and the slice lands in two commits

**`t_array_spelling`, not `t_array_shape`.** The four non-`[]` spellings
(`integer[3]`, `integer[3][4]`, `integer ARRAY`, `integer ARRAY[4]`) hold
ordinary 1-D values and their census entries say nothing; `t_array_shape`'s
contract is "the shapes the census reports", which is the same reason 4.4.2
kept `v_nested_array` out of it. `v_multidim integer[][]` stays where it is —
its 2-D values are genuinely census material. Own table means each fixture
table keeps meaning one thing, and it covers all four spellings for the price
of the two a shared table would have taken.

**Two commits inside one slice.** The generator, the regenerated fixtures and
the count updates go first and prove I28 before any code depends on it; the
helper, the tests and the doc sweep follow. That is the review seam
`process.md` asks for without inventing a fourth level, and it matches the
phase's habit of landing evidence ahead of the code that rests on it.

Regeneration is not a long-running job here: all six `postgres:*-alpine`
images are already pulled locally, so a full run is minutes.

## Periodic refactoring is a standing rule, not a per-slice judgement

The maintainer's policy, given while grilling 4.4.3's unattended call: **the
1.0 architecture is to be as clean and elegant as we can make it, and a
refactor that would survive the roadmap — or at least its next several
phases — while reducing complexity or increasing flexibility is always taken,
not deferred.** Rushing to a done state without periodic refactoring is how the
code turns to spaghetti. Recorded in `roadmap.md`, "Standing rules", where it
binds every slice rather than only the one that produced it.

The immediate consequence is 4.4.3's flagged call: the choice is no longer
between two placements of the array-bounds normalization, but between keeping
either and removing the thing that made placement a question at all.

## Both placements of the array-bounds normalization are behaviourally identical

The call 4.4.3 flagged — normalizing inside `element_is_array` where the spec
said `domain_terminal` — turns out to cost nothing either way, which the
flagged entry's prose argument did not establish.

`element_is_opaque` and `element_is_array` are each called from exactly one
site, `resolve_declared_type`'s array arm, on the same `element`, opaque
first. Normalization can only ever *add* an array level to a terminal, so the
question is whether it changes an opaque verdict. It cannot: a terminal a
spelling would rewrite (`box ARRAY`, `mybase[3]`, `integer ARRAY`) normalizes
to `box[]`, `mybase[]`, `integer[]` — none of which is the literal name `box`,
and none of which is a `TypeDef.name`, since a name that looked like one would
have to be quoted in the DDL and would then carry its quotes. So
`element_is_opaque` answers `false` under both placements, and the array
refusal answers next under both.

The difference is therefore one `Cow` allocation on every domain walk against
one asymmetry in who normalizes. That is what makes the refactor the right
answer rather than either placement: it deletes the question.

## `array_element`'s quote-awareness paragraph documents a limit the code does not have

`pgtype.rs`'s "**Not quote-aware**" paragraph claims `CREATE DOMAIN "weird[]"
AS integer` reads as an array of `"weird`. It does not, and no input reaches
that shape.

`preamble::extract_type_words` splits on whitespace and rejoins, preserving
quotes verbatim, so the declared string is `public."weird[]"`. `strip_bound`
requires a trailing `]` and `strip_array_keyword` a trailing `ARRAY`; both bail
on the trailing `"`. Quoting *protects* `array_element` rather than defeating
it, and unquoted `weird[]` genuinely is an array of `weird` to PostgreSQL too.

The real quote weakness sits one layer up and is pre-existing, broader than
arrays, and untouched by 4.4.3: `TypeDef.name` is dequoted by `parse_ident`
while declared type strings keep their quotes, so
`types.iter().find(|t| t.name == terminal)` never matches a quoted type name at
all. The column falls out as `Unknown` rather than being misread.

`extract_type_words`'s whitespace splitting is *not* the second half of it, as
this entry first said. It splits and rejoins with a single space, so
`s."my type"` round-trips intact; truncation needs a quoted name containing a
`STOP_WORDS` token (`NOT`, `DEFAULT`, `COLLATE`, `GENERATED`, `PRIMARY`,
`REFERENCES`, `CHECK`, `UNIQUE`, `CONSTRAINT`) or whitespace that is not a
single space. That is a narrower and rarer shape than a name with a space in
it.

## Quoted type names: what PostgreSQL accepts and what pgdq does with it

The maintainer asked for the Known-gaps claim to rest on evidence rather than
on the assumption that PostgreSQL would accept such a type. It does; the
observation is **I29**, and a throwaway `postgres:16-alpine` produced both the
DDL and `pg_dump 16.14`'s rendering of it.

Run against that dump, `pgdq info --verbose` reports:

```
    a: unknown type — no mapping for this build      -- s."weird[]"   (enum)
    b: unknown type — no mapping for this build      -- s."my type"   (domain over integer)
    c: unknown type — no mapping for this build      -- s."x ARRAY"   (domain over integer)
    d: unknown type — no mapping for this build      -- s."d[3]"      (domain over integer)
    e: List(Utf8View)                                -- s."weird[]"[]
    f: List(Utf8View)                                -- s."my type"[]
    g: List(Utf8View)                                -- s."x ARRAY"[]
```

Three things this settles.

**No spelling is misread.** `c` and `d` are scalar columns whose *names* end in
`ARRAY` and `[3]`, and both come back `Unknown` rather than as arrays of
`s."x` and `s."d`. `array_element`'s helpers bail on the trailing `"`, which is
the empirical half of the correction above: the doc comment's "not quote-aware"
hazard is not reachable.

**The array wrapper is still read correctly.** `e`, `f` and `g` are recognized
as arrays — the `[]` falls outside the quotes — and only their *element* type
degrades. So the gap costs element typing, never array-ness.

**The cost is a weaker type, never a wrong one.** Four columns that should map
(one enum, three domains over `integer`) are `Unknown` and stay `Utf8View`;
three arrays that should be `List(Dictionary)` / `List(Int32)` are
`List(Utf8View)`. Every value still decodes, losslessly, as the text the file
holds. That is why this is a Known gap and a "Future" item rather than a
defect.


## 4.4.4 is earned, and it is what settles 4.4.3's flagged call

The placement question 4.4.3 flagged is answered by removing it. Slice
**4.4.4** replaces `element_is_opaque` and `element_is_array` with a single
`resolve_array(element, types) -> TypeOutcome` holding the whole array
decision — both refusals, the `resolve_nested` recursion, `list_of` and
`NestedPlan::Array` — over one domain walk instead of two, with the opaque test
first so I22's precedence stays visible in the body rather than argued in two
doc comments. `resolve_declared_type`'s array arm becomes a single delegation,
leaving it a dispatcher over the four declaration shapes.

**Why a slice and not an out-of-band row.** It is behaviour-preserving and
would have fitted the ledger, but it is a correction to earlier work *in the
same phase*, resting on discoveries made in that phase — which is the shape a
graded slice exists to make reviewable. It amends 4.4.3's spec row too: the
clause "inside `domain_terminal`" over-specified a placement that was never the
decision.

**What it survives.** The roadmap's "shape-general array representation" Future
item covers both `NestedArrayElement` and `VaryingArrayShape`; when it lands it
edits one function instead of two predicates, a `match` and a builder call. A
third element refusal, should one appear, is an arm rather than a fourth
`element_is_*` bool and a fourth `if`.

**What it may not do.** No new behavioural test — the existing suite is the
check — and the quoted type-name gap (I29) is out of scope even though the
corrected doc comment cites it. Fixing that changes behaviour and belongs to
the "real type-name tokenizer" Future item.

Phase 4's wrap runs the koji identity check once, detached, as the loop's last

round may block on it: 4.6's box does not depend on the identity check, and a
box left unticked while waiting on koji is a stop condition, not a slow round.

## Per-block cache saving is quadratic in block count, and the second regime is now measured

The "no save throttle" entry in `STATUS.md` says the quadratic half of its
reasoning is reasoned rather than measured, because koji has only 74 `COPY`
blocks. It is measured now, on a synthetic dump with many small blocks, and the
regime is real.

Generator (schema section first, then the data section, as `pg_dump` writes
them; four columns, three rows per table):

```python
# gen.py N OUT
import sys
n, out = int(sys.argv[1]), sys.argv[2]
head = ("--\n-- PostgreSQL database dump\n--\n\n"
        "-- Dumped from database version 16.15\n-- Dumped by pg_dump version 16.15\n\n"
        "SET statement_timeout = 0;\nSET client_encoding = 'UTF8';\n"
        "SELECT pg_catalog.set_config('search_path', '', false);\nSET row_security = off;\n\n")
ddl = ("--\n-- Name: t{i}; Type: TABLE; Schema: public; Owner: postgres\n--\n\n"
       "CREATE TABLE public.t{i} (\n    id integer,\n    name text,\n"
       "    created_at timestamp without time zone,\n    amount numeric(12,2)\n);\n\n\n"
       "ALTER TABLE public.t{i} OWNER TO postgres;\n\n")
data = ("--\n-- Data for Name: t{i}; Type: TABLE DATA; Schema: public; Owner: postgres\n--\n\n"
        "COPY public.t{i} (id, name, created_at, amount) FROM stdin;\n"
        "1\trow one\t2026-01-01 00:00:00\t1.00\n2\trow two\t2026-01-02 00:00:00\t2.00\n"
        "3\trow three\t2026-01-03 00:00:00\t3.00\n\\.\n\n\n")
with open(out, "w") as f:
    f.write(head)
    for i in range(n): f.write(ddl.format(i=i))
    for i in range(n): f.write(data.format(i=i))
    f.write("--\n-- PostgreSQL database dump complete\n--\n\n")
```

```sh
for n in 500 1000 2000 4000; do
  python gen.py $n /tmp/r$n.sql; rm -f /tmp/r$n.dqcache
  /usr/bin/time -f "n=$n wall=%es cpu=%P" \
    ./target/release/pgdq parse --source /tmp/r$n.sql --dqcache /tmp/r$n.dqcache >/dev/null
done
```

| blocks | dump | final cache | wall | vs. previous |
|---|---|---|---|---|
| 500 | 248 KB | 323 KB | 0.62s | — |
| 1000 | 496 KB | 648 KB | 2.54s | 4.1x |
| 2000 | 997 KB | 1.3 MB | 10.73s | 4.2x |
| 4000 | 1.9 MB | 2.6 MB | 44.36s | 4.1x |

Clean quadratic: each doubling of the block count costs 4x the wall. The
control is the same byte count in **one** `COPY` block — a 1.3 MB single-block
dump parses in under 10ms — so at 4000 blocks the saving overhead is some
three orders of magnitude above the scan it protects. Every run is 99% CPU:
the cost is *serializing* the whole index once per block, not the write. Bytes
written confirm the same shape — `strace -f -e trace=write` over a 1000-block
run sums to **105 MB written for a 331 KB input**, a 334x amplification, and
that quadruples with each doubling too.

Two things this does not overturn. The koji figure stands as measured (74
blocks, +1.5% wall, 18 MB written), and the pathology is invisible at
koji-scale *data* volumes even with many blocks — 4000 blocks against 784 GB
of rows would still be 44s against 3300s. What it costs is dumps that are
**block-rich and byte-poor**: a schema with thousands of tables, or one
partitioned table with a leaf per day over a decade, where the saves dominate
the scan outright.

## Three Phase 9 calls reviewed: the throttle is earned as 9.5, the metadata asymmetry is closed, the coverage line stands

**The save throttle is built after all, as slice 9.5.** The measurement above
is what the 9.1 spec asked for and koji could not supply: the cost is quadratic
in *block count*, and koji has 74 blocks. The rule is self-tuning rather than
an interval — skip a block's save unless the time since the last save is at
least `K` times what the last save took — so no constant has to be right in
both regimes, and koji's saving behaviour does not change at all. The
maintainer added the condition that makes it safe: **whatever has been scanned
is saved on the way out**, on `SIGINT` and `SIGTERM`, at the next resumable
point. The throttle widens the window an interrupt can lose, so the guard lands
in the same slice rather than after it — the container recipe in `CLAUDE.md`
stops with a `SIGTERM`, which is the case most likely to hit it.

**The `parse`/`query` metadata asymmetry is closed, not documented.** The entry
framed `map_file`'s whole-file `DumpMetadata` recomputation as strictly more
information. It is also a **cold/warm divergence in query answers**: a
`\connect` span disables early stopping (`stream::target_settled`), so a cold
query on a `pg_dumpall` file maps the entire thing and *still* leaves later
databases' columns untyped, because only `map_file` recomputes. Run `pgdq
parse` first and the same query against the same file returns typed columns.
The recomputation therefore moves into `map_forward`, where both paths get it.
It is out-of-band work: the divergence it removes was never a decision anyone
took, and the code already exists and is pure over spans.

**The coverage line keeps printing at 100%.** Suppressing it in text was
rejected on the grounds that its absence tells the user nothing — a missing
line reads as "this tool did not check" rather than "the scan is complete", and
leaving them to infer completeness from silence is worse than one line of
ceremony. `--json` needs no equivalent and gets none: it carries
`scanned_through` and `total_size` as fields, and a caller that wants a
percentage can divide.

## 9.5's shape: a flag read per chunk, a rule with one constant, and a fixed order to the end of both phases

**The guard is cooperative, because the alternative destroys what it is
saving.** `map_file` owns the `DumpIndex` for the duration of the scan, so a
CLI-side `tokio::select!` over `ctrl_c` and the scan future would cancel the
future and drop the map — the obvious form is the wrong one. Instead
`ScanOptions` carries an `Option<Arc<AtomicBool>>` (default `None`, so no
existing caller changes) and the chunk loop reads it each time round. Chunk
rather than `CopyEnd` granularity is the point: koji's largest block is
hundreds of gigabytes, and a Ctrl-C that waits for a block boundary cannot be
told from a hang. `SIGINT` and `SIGTERM` both set it, exit is 130/143 so a
script can tell an interrupt from a failure, and a second signal kills outright
rather than being swallowed.

**The guard makes the throttle nearly free in risk.** Every `CopyEnd` splices
the spans, extends the roles and tablespaces, and advances `scanned_through`
whether or not the save runs — so what a skipped save skips is only the *write*
of state the in-memory index still holds. A graceful interrupt therefore loses
the block in flight and nothing else, exactly as before the throttle, and the
throttle's window belongs to `SIGKILL`, power loss and panics alone.

**One rule, both callers, and every exit saves.** `map_forward` has two
callers, so `query` is throttled too — harmless, since it stops at its target,
except that the save at the last `CopyEnd` before an early stop is what
persists the map for the next query. Skipping that one would throw the scan
away, so the throttle governs mid-scan saves only. `K = 20` is a starting
constant to be checked against the block-count series, not defended in prose.

**Order to the end of both phases.** The out-of-band metadata move and 9.5
touch the same tail of `map_forward` and go in one round as two commits; then
**4.4.4**, then **4.6**. Phase 9 wraps as soon as 9.5 lands, Phase 4 after 4.6,
and Phase 4's wrap is where the detached koji identity check is launched for a
later session to read. 9.5 leads because it is a live pathology in shipped
behaviour rather than a cleanup, and because every later round's `parse` runs
are faster for it.

## The last three unattended calls stand, and the section is empty

**The diagnostics recompute on load is 3 ms.** The entry flagged an O(spans)
cost on every load, a cold query's included, without a number. Koji's cache is
833 spans and a whole `pgdq info --dqcache runs/koji-9.1.dqcache` — load,
recompute, render the table listing — takes 3 ms, so the cost is below process
startup on the largest sample here. A cold query pays it twice, once on the
load and again when `map_forward` recomputes at EOF; still 3 ms. The figure is
now in `architecture.md`'s cache section so the question is answered by a
number rather than re-derived. The doc, the test
(`diagnostics_do_not_round_trip_through_the_cache`) and the code were checked
against each other and agree.

**`info --dqcache none` stays an error, and gains a remedy.** With `info` no
longer scanning, a disabled cache leaves it no source of facts, and reporting
an empty index would read as "this dump has no tables". What the message
lacked is what `Error::FieldDecode` was given in 4.5.1 — the way out. It will
name `pgdq parse --dqcache <path>`, which is exactly what someone reaching for
`none` because the dump's directory is read-only needs to hear. Out-of-band,
riding with the 9.5 round.

**`v_empty_enum` needed no ruling, and neither will the next fixture.**
Fixture expansion is a standing rule, so an addition a spec row does not name
is licensed by default; this one was also load-bearing (`EmptyEnum` was the
only resolution outcome no generated fixture reached) and produced I27.
The durable lesson is about the section rather than the fixture: additions made
under a standing rule stop being logged as unattended calls, because flagging
each one dilutes a list meant for decisions.
