# 2026-09-22

## The session budget

Reviewed with the maintainer after 6.5 landed; 6.5.1 built what it changed
([`../STATUS.md`](../STATUS.md), "P6 progress").

- **A scan draws at plan time and holds the draw for its plan's life**, as 6.5
  built it; drawing at `execute` is rejected in `ScanBudget`'s rustdoc.
- **A late scan gets the remainder**, and the join shape that starves is
  `KD38`, unowned until a measured join shows the cost.
- **DataFusion's memory pool was left out of the allowance.** Its default is
  unbounded, but `datafusion-cli --memory-limit N` gives its operators N bytes
  (`MemoryPool::memory_limit` answering `Finite(N)`, 55.1.0), which the
  provider's scans could also draw. The spec's "Workers and memory" now takes
  a finite pool limit off the allowance, as 6.5.1 built it.
- **The no-limit carving differs from `pgdt`'s by design**, recorded on
  `ScanBudget::discover`.
- **The consistency scripts did not know the provider crate.** `KD38`'s marker
  is its first in `datafusion-pgdump/src`, and `deficiencies.py` scanned only
  `pgdump_query` and `pgdt`, so its `CODE_ROOTS` gained the crate here.
  `citations.py` and `repoint.py` gained it at `M129`, which moved the meter
  by the crate's comments; each script's tests assert its roots against
  `Cargo.toml`'s workspace members.

## The resident map

Reviewed with the maintainer after 6.5 landed. The map stays resident for a
registered dump's life, and a cache rebuilt after open waits for a reopen —
both on `PgDump`'s rustdoc. **Nothing billed that residency**: `pgdt`'s
`map_file` charges loaded statistics as `Term::Loaded`, the provider charged
nothing, and N registered dumps held N maps under `MEMORY_RESERVE` alone. The
spec's "Workers and memory" now takes each dump's loaded statistics off the
allowance, and 6.5.1 carries it beside the pool limit.

## Which bound the holdings come off

Reviewed with the maintainer after 6.5.1 landed. 6.5.1 takes the pool limit
and the resident statistics off both of `Parallelism::within_shared`'s bounds;
they come off the margin's ceiling alone, which 6.5.2 built.

- **`pgdt` already bills statistics this way** (D85, `statistics_allowance`),
  `Term::Loaded` included, and is safe because `MEMORY_UNPOOLED_BOUND` bounds
  a scan's excess over its budget. The cap's larger `MEMORY_RESERVE` is the
  scans' own, and neither a map nor a pool limit is part of it.
- **Where a scan's count can fall, the two rules differ only where the cap
  binds**, below `5 × (MEMORY_RESERVE − MEMORY_UNPOOLED_BOUND)`. Where it
  cannot — a source recommending no per-reader memory, whose count
  `Parallelism::fit` never bounds, and a count already at one worker — the
  holdings now leave the budget alone, where 6.5.1 lowered it
  ([`../../design/roadmap-P6.5.2-holdings-margin-notes.md`](../../design/roadmap-P6.5.2-holdings-margin-notes.md)).
  Closed by "The holdings at the floors", below.
- **Taking the holdings off the allowance instead is rejected**: the margin,
  a fraction of the smaller number, would let predicted resident pass it by
  that fraction of the holdings. Recorded on `ScanBudget`'s rustdoc.

## The holdings at the floors

Reviewed with the maintainer after 6.5.2 landed. Where a scan's count cannot
fall, 6.5.2 leaves its budget alone however much the session holds, so the
predicted resident can pass the margin, and the allowance, by one reader's
cost a scan. The margin holds there too: 6.5.3 builds it, and `M130` extends
it to `pgdt`.

- **Two floors.** `Parallelism::fit` returns `DEFAULT_MEMORY_BUDGET.min(cap)`
  for a source recommending no per-reader memory without reading the ceiling,
  and `affords` never goes below one reader, whose `at(1)` on a compressed
  source is a whole-block decode.
- **The rule**: holdings come off the ceiling, and whatever of them the
  ceiling's room cannot absorb at the resolved count comes off the budget, for
  every source. A budget pushed below a unit declines it (D4), a compressed
  scan losing block decode. The cap stays the reserve's. Rejected: 6.5.1's
  rule, which bills the holdings against the reserve's room where the cap
  binds; and a plain-source exception, what a plain budget is worth being
  `KD25`'s and `KD32`'s.
- **`pgdt` has the same gap for a loaded cache.** `map_file` bills
  `Term::Loaded` to the `StatisticsAccount`, which bounds only further
  gathering (D85), and the workers are carved before it
  (`statistics_allowance` reads the carved budget), so `Parallelism::within`
  passes `held = 0`. `M130` passes the loaded statistics as `held`, D85's
  order changing with it; it waits on 6.5.3's rule and blocks nothing in P6.
- **The provider's new exposure was the pool limit**, which `pgdt` has no
  analogue of and which can be gigabytes; the maps already matched `pgdt`.

## A `macaddr` literal in Arrow semantics

Reviewed with the maintainer after 6.6 landed, which left every `macaddr` term
to DataFusion. The defect is the library's: Arrow semantics keeps
`CompareKind::MacAddr` (`arrow_order`) and reads its literal in either case of
hex (D55), so `v = '08:00:2B:01:02:03'` matches `08:00:2b:01:02:03` where
DataFusion, comparing the `Utf8View`, does not. The spec already says the
`Utf8View` kinds compare bytewise ("Comparison means what DataFusion means");
6.2 shipped short of it, so the fix is **slice 6.2.2**, blocking nothing.

- **`MacAddr` moves to `Text` under `arrow_order`**, answering every literal
  as DataFusion does. Rejected: a lowercase-only literal, refusing the rest;
  and a per-literal switch keeping the octet key for a canonical one, the
  only such switch in `resolve_term`, to save range pruning.
- **It announces `ValueAsText`**, whose doc says a `macaddr`'s reaches only a
  literal not in the server's spelling, its order over the file's text
  agreeing. Every variant still affects ordering (`v < 'A0:…'`).
- **The oracle asserts that every kind emitted `Utf8View` or
  `Dictionary<Utf8>` is `Text` under `arrow_order`.** Its walk draws literals
  only from what the server wrote, which is why it never saw this.
- **What it costs is Arrow range pruning on `macaddr`**: `bounds_ordered_in`
  goes false, the dictionary keeping `=`. Gathering is unchanged, so no
  `CACHE_FORMAT_VERSION` bump (D78). 6.9 lands after it, and whether its
  bytewise gathering covers every kind Arrow compares as text — `macaddr`, a
  bare `numeric`, `timetz`, `inet`/`cidr`, `jsonb` — is its question.
- **The provider's exception goes** with it: `literal_text`'s doc and
  `compared_as_text` name no kind apart. D88 is unchanged.
