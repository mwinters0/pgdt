# 2026-09-08

## `M70`: the block pool is a retaining holder, so nothing grants it a wait

`XzSource::hint_wait_policy` now states the granted `WaitPolicy` to the **chunk**
pool alone. The block pool stays at `NeverWait` whatever a read loop permits,
which is what ends the `--jobs` 2-or-more deadlock over a block-decoding `.xz`
([2026-09-07](2026-09-07.md), "A `--jobs` parse of an `.xz` deadlocks on the
block pool's retained charges"). The mechanism and its rejected alternative are
beside the pool ([`architecture.md`](../../design/architecture.md), "Execution
model and API surface"); what is here is the evidence and the admission test.

**The classification is what was wrong, not the wait.** `16.4.1` states the
exemption by **holder class** — a holder that keeps a buffer past the read that
took it never waits, because the only task that could free its slot is the one
waiting on it. `BlockCache` is exactly that holder: it retains a decoded block
past the read, and the read is simultaneously holding a zero-copy view into the
same buffer, which is what makes a read inside one block a slice rather than a
copy. So `BlockCache::slot`'s drain to `slots() - 1` frees nothing for the
caller waiting on a slot, `charged` reaches `slots()` and stays there. The
policy was being forwarded to that pool anyway, and two paragraphs of
`architecture.md` argued it was safe there on the grounds that the cache's own
reference was the only one — which is false for every read that is served out
of a retained block, and that is all of them.

**Reproduced as a unit test before it was fixed.**
`io::tests::a_permitted_wait_never_reaches_the_block_pool` builds a 4 KiB-block
`.xz`, states a budget that affords two block slots, grants `MayWait`, takes one
live view per slot, and asks for a third block. It failed on the previous code
with a bounded receive rather than a hang — the third read runs on a detached
thread against `recv_timeout`, so a pool that starts charging block slots again
fails the suite instead of stopping it. That shape is deliberate: a deadlock
test that deadlocks is not a test.

**Confirmed end to end** on a 200 MiB plaintext dump compressed at koji's own
parameters (`xz -6`, 24 MiB blocks, 9 blocks). `pgdq parse` at `--jobs` 1, 2, 4
and 8 all complete and write **byte-identical** caches, and `pgdq query
--no-columns` returns the same row count at 1, 2 and 8 — so `16.12`'s
determinism property holds on a compressed source as well as on the plain ones
it was asserted over. The same command at `--jobs 2` did not terminate before
this change.

**What the fix costs is a bound restated, not a bound lost.** The block pool's
budget bounds what is **retained**; what concurrent readers hold live is
`stream::worker_count` blocks, which is `min(jobs, budget / partition_bytes)`
off the same stated number, so the second term is the library's too and stops
growing where the budget stops affording a worker. Measured on the file above
under the 64 MiB default: peak resident 64 MB serial, ~169 MB at `--jobs 2`, and
**flat** at 4, 8 and 16, because two workers is what 64 MiB affords against a
25 MiB partition. Those readings are a probe on a scratch file, not a figure —
`parallel-peak-rss` is the registered instrument and no document quotes these
numbers.

**The admission test was re-run before the work and it passes.** The spec's
prose paragraph ("Memory is bounded by a block pool with backpressure") says a
worker *blocks until a slot is free*; the spec's own `16.4.1` row already
replaced that with the holder-class exemption and a two-term bound, in the same
document, and says so. So this change applies a rule the spec records rather
than changing one, and the spec is left untouched. What it deliberately does
*not* do is give the block pool a working ceiling — an acquisition held for the
life of a reader's view would be a new bounding mechanism, which is a slice, not
an out-of-band row. That call was raised for review and settled the same day,
below.

## The block pool's bound is a divisor's job, not an acquisition's

`M70`'s exemption stands, and the per-view acquisition it declined is refused
rather than deferred. The reasoning is filed beside the mechanism
([`../../design/architecture.md`](../../design/architecture.md), "Execution
model and API surface"); what belongs here is the evidence and the two facts
the entry that raised it did not have.

**The work was already admitted.** `16.15` is the phase's row for "one stated
number bounds both memory terms", and two notes docs already defer memory
accounting to it by name — `16.10.2` on `POOL_DEPTH`, `16.16` on the same. So
the answer routes into an existing slice: no ledger row, no new number, and
`16.15`'s scope amended to say the divisor counts the block a worker decodes,
since it was written about a query's retained span and the live term on an
`.xz` source is one whole block per reader.

**A per-view acquisition is the wait under another name.** The view *is* the
retention — a `BlockView` holds the `Arc<DecodedBlock>` that owns the slot — so
releasing on the view's drop is releasing when that reader stops reading, and a
second reader blocking on it is `M70` with a different counter. Bounding the
live term by admitting fewer readers is what works on a retaining holder,
because it never makes one holder wait on another.

**The arithmetic, at the default, and why the probe read flat.** 64 MiB stated,
`POOL_DEPTH` 4, a 1 MiB chunk: the chunk pool takes 4 slots and 4 MiB, leaving
60 MiB against a 24 MiB unit, so the block pool's `slots()` is **2** and the
`max(POOL_DEPTH, jobs)` depth never binds. That is why `M70`'s probe read
~169 MB at `--jobs` 2 and did not move at 4, 8 or 16 — the slot count is
budget-derived, and `jobs` stopped mattering at two.

**A claim two documents made was never true.** Both said the byte budget bounds
the retained blocks and the free ones *together*. `BlockCache` holds `retained`
at `slots()` and `BufferPool::release` pools while `free.len() < slots()`, two
counts with nothing shared: the ceiling is `2 x slots x unit`, 96 MiB at the
default. The `charged` counter never coupled them either — it bounded
retained-plus-live, not the free list — so this predates `M70` rather than
following from it. Corrected in `architecture.md` and in `BlockCache`'s doc
comment; whether to cap the sum is `16.15`'s, because it changes what the
stated number means.

**`16.13.1` is taken before `16.15`, not after.** `parallel-peak-rss` plots
against a `--jobs` axis that flattens where the budget stops affording a
worker, so `16.15` moves the number the figure is plotting — but a figure
measures the arrangement that ships, and `16.15` is unspecified. Holding a real
reading behind an ungrilled slice trades it for a hypothetical one; `16.15`
re-takes the figure, and its checklist entry says so.

- **`16.14`'s run is finished and folded in**, so nothing here is waiting on a

  [`../../design/roadmap-P16.14-koji-verification-notes.md`](../../design/roadmap-P16.14-koji-verification-notes.md).
  What a *future* koji run inherits: the script does not resume a killed leg,
  so re-running it restarts leg 1 too, and it must be stopped by process group

- **`--stale` is unmoved.** The only declared path this touched is
  `pgdump_query/src/io.rs`, red on every figure that declares it; the diff is
  unreachable from every registered command shape twice over — no registered
  figure has a compressed input, and the announcement it stops making is
  `NeverWait` onto a pool already at `NeverWait`.
- **Driving a suspect `pgdq` with `timeout -s KILL` is still the rule.** The
  deadlock this closes is gone, but the reason it survived `SIGTERM` is not
  specific to it: the interrupt guard's flag is cooperative, so any thread
  parked in a blocking primitive never reads it.

## The `16.14` OOM is glibc's arenas, and a CPU limit is not the remedy

A detached job ran a serial (`--jobs 1`) and a `--jobs 4` parse of
`koji-2026-07-23.dump.multistream.xz`, meaning to compare them byte for byte.
Handoff: `runs/koji-xz-verify-20260908-0203/HANDOFF.md`; diagnosis:
`runs/koji-xz-verify-20260908-0203/FAILURE.md`.

**The job took two fresh legs rather than one against an old cache**, which
the review of this date affirmed — see the section below for why no reference
of that kind can exist at all.

**Why `multistream.xz` and not `blocks128.xz`.** The recompressed copy's
128 MiB blocks would need most of the 512 MB cgroup just to afford four
concurrent block buffers, leaving no room for anything else `pgdq` holds;
the real download's 24 MiB blocks fit several times over, which is what lets
`--jobs 4 --parallel-memory 268435456` (256 MiB) run genuinely 4-way
parallel rather than budget-clamped to two, as it would be at the 64 MiB
default (`M70`'s landing entry above has the arithmetic).

**What happened**: leg 1 (serial) completed cleanly in 2702s at the reference
counts (74 blocks, 19,575,829,920 rows). Leg 2 was killed by the kernel's
cgroup OOM killer 180s in — confirmed in `dmesg`, not inferred from the exit
code. Its stdout is empty, the scan summary being printed at the end, but its
cache is not: the throttled per-block save (`stream.rs`, `SaveThrottle`)
leaves a real index of the blocks a killed leg finished, 2,004,642 bytes
against leg 1's 2,144,936. So the orchestrator's `RESULT: caches DIFFER` line
compares a complete cache against a partial one; it carries no information
about determinism and is not evidence against `M70`.
**What the ~300 MiB the pools cannot account for actually is.** The block pool
alone never explained the kill: the depth ceiling (`POOL_DEPTH.max(jobs)` = 4)
caps leg 2's block pool at 4 slots however much of the 252 MiB it could
otherwise afford, so the uncoupled-pools bug of the section above predicts at
most 192 MiB against the 96 MiB intended — a real overshoot, and not enough on
its own to fill a 512 MB cgroup. Five bounded probes of leg 2's own shape
against the real file, at a 2 GiB limit so nothing was killed, sampling the
container's `memory.stat` and the process's thread and arena counts every ten
seconds, settle the rest (`runs/koji-oom-probe-20260908/`, one `.txt` per leg;
probes, not figures, and no document quotes them as measurements):

| leg | anon plateau | peak | threads | arenas |
|---|---|---|---|---|
| `--jobs 4 --parallel-memory 256 MiB` | 536 MiB | 581 | 31 | 29 |
| the same, `MALLOC_ARENA_MAX=2` | 328 MiB | 377 | 30 | 1 |
| the same, `--cpus 4` | 476 MiB | 523 | 10 | 8 |
| the same, `--cpus 4` and `MALLOC_ARENA_MAX=2` | 337 MiB | 377 | 10 | 1 |
| `--jobs 4 --parallel-memory 128 MiB`, `MALLOC_ARENA_MAX=2` | 328 MiB | 376 | 31 | 1 |

**`#[tokio::main]` is what makes the arenas, and it makes them before a byte is
scanned.** The runtime is sized from the CPUs the process can see, so a
container with no CPU restriction gets 24 workers here; the probe reads 24
arenas at `t=0`, with anon under 1 MiB. Each arena then retains what the thread
that owns it allocated, and freeing does not give it back.

**A CPU limit is the wrong lever, which is what the first attempt's note
guessed at and had backwards.** `--cpus 4` does reduce the runtime to four
workers and the arenas to eight — Rust's `available_parallelism` reads the
cgroup quota — and it still measures 476 MiB, because what an arena retains is
not proportional to how many there are. `MALLOC_ARENA_MAX=2` is what moves the
number, and adding the CPU limit on top of it moves nothing further.

**The stated budget is not a lever either.** 128 MiB stated measures the same
328 MiB as 256 MiB, because `BufferPool::slots()` clamps to `POOL_DEPTH.max(jobs)`
at either — so the block pool is 4 slots in both, and the budget stops
mattering above the point that affords four workers. That the process holds
328 MiB against a stated 128 is `16.15`'s to answer; it is not what killed
leg 2.

The property this leaves for a user in a memory-capped container is filed
beside the mechanism ([`../../design/architecture.md`](../../design/architecture.md),
"Execution model and API surface") and in the manual, since the remedy is one
an operator already has.

**The verification was relaunched the same day and passed.**
`MALLOC_ARENA_MAX=2` and `--cpus 4` on both legs — the CPU limit to hold the
thread count fixed for the whole scan rather than for headroom — plus per-leg
memory sampling, whose absence is why diagnosing the first attempt needed a
rerun at all. The parallel leg then plateaued at ~330 MiB anonymous with one
arena and peaked at 404 MiB inside the same 512 MB cgroup, which is the probe
table above holding over a whole scan rather than over a ten-minute sample. The
first attempt's caches and logs were archived under `runs/koji-xz-attempt1/`
rather than deleted, which bought a serial-versus-serial comparison across two
runs for nothing. The result is
[`../../design/measurements.md`](../../design/measurements.md), "koji full
scan"; the slice is
[`../../design/roadmap-P16.14-koji-verification-notes.md`](../../design/roadmap-P16.14-koji-verification-notes.md).

## A compressed cache and a plain one were never byte-comparable

`16.14`'s spec row asked for a `.xz` parse whose `.dqcache` is byte-identical
to the one the serial 784 GB scan of the plain dump produced. No such
comparison exists, and the reason is structural rather than circumstantial.

`CacheFile` carries `compression: Option<CompressionIndex>`, set at save from
`ByteRangeSource::seek_table()` — `Some(Xz(..))` holding a 31,150-entry seek
table for the multistream `.xz`, `None` for the plain dump. It carries
`identity: SourceIdentity::LocalFile { stored_size, mtime }`, and `stored_size`
is the size of the file actually opened: 40,397,009,888 against
784,019,857,152. Only `total_size`, the addressable length, agrees. The two
caches taken this date show it directly — `runs/pgdq-koji-xz-serial.dqcache` is
2,144,936 bytes where `runs/pgdq-koji.dqcache` is 248,479.

**The expired reference was the shallower objection.** `runs/pgdq-koji.dqcache`
(2026-09-05) does predate `FORMAT_VERSION`'s 15→16 bump (`5066c47`, 2026-09-06,
"13.2 Make `SourceIdentity` opaque…"), and `cache::load` refuses a version
mismatch before comparing anything else. But a surviving reference would not
have helped: within one format version the compressed and plain caches of one
dump still differ by construction. So the fresh pair is not a fallback after an
artifact expired — it is the only comparison that was ever meaningful, and the
spec row's wording named an artifact nothing produces.

The check therefore splits in two, and the spec row now says so: **across
arrangements**, two legs over the same file in one run, caches compared to each
other; **across formats**, each leg's reported counts compared to the plain
scan's published totals. The durable half is filed in
[`../../design/architecture.md`](../../design/architecture.md), "The cache";
the consequence for a koji run is in
[`../../design/measurements.md`](../../design/measurements.md), "koji full
scan".

**`M66` stays non-blocking for P16.** `16.14` now leans on those published
counts as its cross-format oracle, and `M66` is what would give an
outside-register section an invalidation edge. It is not needed here: the
counts are properties of a fixed 784 GB file, not readings off a moving build,
so an edge would never fire on them.

## A parse has phases, and nothing says which one it is in

Two slices are admitted to P16 — `16.18`, the `--verbose` → `--detail` rename,
and `16.19`, the CLI's status output. The decisions are in the spec
([`../../design/roadmap-P16-parallel-scan.md`](../../design/roadmap-P16-parallel-scan.md),
"A parse has phases now, so the CLI says which one it is in"); what is here is
why the phase absorbs them and what the day's evidence contributed.

**The phases are this phase's own doing.** `parse` was one span of work until
P16 gave it two: an `.xz` source walks the file's stream footers before the
first block is scanned, 85 s of silence on the koji download. `16.14` is what
made the cost of that silence concrete — its first attempt was diagnosed from
`dmesg` and a cgroup sample, because the leg that died printed nothing at all,
its scan summary being written at the end. A second run had to be taken to
learn what the first one held, and per-leg memory sampling was bolted onto the
orchestrator to get it. That is the observability gap, and it is not a
parallelism bug: nothing pgdq printed would have said which phase the process
was in either way.

**So the work is P16's rather than a phase of its own.** It fails the
out-of-band admission rule outright — it adds a dependency, changes every
command's default output, and creates an output contract, which is design work
([`../../process.md`](../../process.md), "Out-of-band work"). Against a new
phase, the argument is that the phases worth naming are the ones P16 created
and that `16.15` reads the same startup numbers a log line would state. The
cost accepted knowingly: a logging facade is cross-cutting where the rest of
this phase is not, so the disjoint-mechanisms property that lets two phases run
at once does not hold for it.

**`16.17` is spent and skipped.** It was allocated for a day to what became
`16.10.2`, and commit `f65f9f6`'s body says so in a sentence no rewrite may
touch ([2026-09-07](2026-09-07.md), "16.10.1 split again"). A number naming two
different slices across the record is the ambiguity the never-reuse rule
exists to prevent, so the admitted slices take `16.18` and `16.19`.

**The rename is split from the facade** because the two carry different
confidences and `../../process.md`'s "Working unattended" forbids one review
cycle for both. It is also wider than it looks: `--verbose` reaches
`measure.py`'s koji recipe and the `test_measure.py` assertion over it, so a
rename touches the measurement harness and not only the CLI and the manual.
The short `-v` was never bound to anything, so what is contested is the word,
not the letter.

**A logged duration is not a figure, and the rule is written before the first
one is printed.** The alternative is a command that manufactures timings with
no apparatus behind them, on whatever machine a user ran, in a project whose
own koji section is disqualified reading by reading at the number. Emitting
transitions without durations was the other way to close it and gives up half
of what the row is for, since subtracting two timestamps by hand is quoting a
duration with extra steps.

## The `16.14` apparatus is affirmed, and capping arenas is a Future item

The review of this date settled the open "Decisions worth another look" entry —
`16.14`'s container tuning — and closed it. Three findings, of which the third
is the one the entry never reached.

**The entry understated its own subject.** It named `MALLOC_ARENA_MAX=2`. The
run used `-m 512m --memory-swap 512m --cpus 4 -e MALLOC_ARENA_MAX=2`, which
[`../../design/measurements.md`](../../design/measurements.md), "koji full
scan" already describes as tuning *two* things the apparatus rule holds fixed.
The defence covers both, and for different reasons: the arena cap bounds what
glibc retains and cannot change a cache byte, and the CPU quota fixes the
thread count, which a byte-identical-cache claim is indifferent to.

**No re-take is owed.** The alternative — the legs run untuned in a raised
cgroup — reproduces a number already measured five ways at a 2 GiB limit, and
a one-rep resident-set reading off an unquieted machine is not a figure with
the cgroup raised any more than with it tuned. The reasoning is filed beside
the apparatus it governs, in that same section, because a probe table is only
a probe and why it suffices is not recoverable from it.

**What the entry did not consider is that pgdq could cap the arenas itself.**
`main.rs`'s bare `#[tokio::main]` builds one worker thread per visible CPU
whatever `--jobs` says — so a *serial* parse on a 24-CPU host still seeds 24
arenas before a byte is read — and a `mallopt(M_ARENA_MAX, …)` in the CLI's
`alloc.rs` would close the ~200 MiB gap with nothing set by the operator.
Sizing the runtime from `--jobs` is not the same lever and does not work:
`--cpus 4` reaches eight arenas and still measures ~476 MiB. It is admitted as
a **Future** item rather than a slice or an `M<k>`, because it changes a
decision `architecture.md` records — that the arena gap is a property with an
operator's remedy — and because it re-bases the apparatus of every registered
figure and needs a contention figure of its own before anyone adopts it
([`../../design/roadmap.md`](../../design/roadmap.md), "Future — wanted,
unscheduled").

`16.15`'s scope is unchanged by all three. Whether the stated number ought to
bound the process rather than the pools remains its question, exactly as
[`../../design/architecture.md`](../../design/architecture.md), "Execution
model and API surface" already routed it.
