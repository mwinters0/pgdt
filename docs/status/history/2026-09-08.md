# 2026-09-08

## `M70`: the block pool is a retaining holder, so nothing grants it a wait

`XzSource::hint_wait_policy` now states the granted `WaitPolicy` to the **chunk**
pool alone. The block pool stays at `NeverWait` whatever a read loop permits,
which is what ends the `--jobs` 2-or-more deadlock over a block-decoding `.xz`
([2026-09-07](2026-09-07.md), "A `--jobs` parse of an `.xz` deadlocks on the
block pool's retained charges"). The mechanism and its rejected alternative are
beside the pool ([`architecture.md`](../../design/architecture.md), "Execution
model and API surface"); what is here is the evidence and the admission test.

**The classification is what was wrong, not the wait.** `16.4.1` states the
exemption by **holder class** — a holder that keeps a buffer past the read that
took it never waits, because the only task that could free its slot is the one
waiting on it. `BlockCache` is exactly that holder: it retains a decoded block
past the read, and the read is simultaneously holding a zero-copy view into the
same buffer, which is what makes a read inside one block a slice rather than a
copy. So `BlockCache::slot`'s drain to `slots() - 1` frees nothing for the
caller waiting on a slot, `charged` reaches `slots()` and stays there. The
policy was being forwarded to that pool anyway, and two paragraphs of
`architecture.md` argued it was safe there on the grounds that the cache's own
reference was the only one — which is false for every read that is served out
of a retained block, and that is all of them.

**Reproduced as a unit test before it was fixed.**
`io::tests::a_permitted_wait_never_reaches_the_block_pool` builds a 4 KiB-block
`.xz`, states a budget that affords two block slots, grants `MayWait`, takes one
live view per slot, and asks for a third block. It failed on the previous code
with a bounded receive rather than a hang — the third read runs on a detached
thread against `recv_timeout`, so a pool that starts charging block slots again
fails the suite instead of stopping it. That shape is deliberate: a deadlock
test that deadlocks is not a test.

**Confirmed end to end** on a 200 MiB plaintext dump compressed at koji's own
parameters (`xz -6`, 24 MiB blocks, 9 blocks). `pgdq parse` at `--jobs` 1, 2, 4
and 8 all complete and write **byte-identical** caches, and `pgdq query
--no-columns` returns the same row count at 1, 2 and 8 — so `16.12`'s
determinism property holds on a compressed source as well as on the plain ones
it was asserted over. The same command at `--jobs 2` did not terminate before
this change.

**What the fix costs is a bound restated, not a bound lost.** The block pool's
budget bounds what is **retained**; what concurrent readers hold live is
`stream::worker_count` blocks, which is `min(jobs, budget / partition_bytes)`
off the same stated number, so the second term is the library's too and stops
growing where the budget stops affording a worker. Measured on the file above
under the 64 MiB default: peak resident 64 MB serial, ~169 MB at `--jobs 2`, and
**flat** at 4, 8 and 16, because two workers is what 64 MiB affords against a
25 MiB partition. Those readings are a probe on a scratch file, not a figure —
`parallel-peak-rss` is the registered instrument and no document quotes these
numbers.

**The admission test was re-run before the work and it passes.** The spec's
prose paragraph ("Memory is bounded by a block pool with backpressure") says a
worker *blocks until a slot is free*; the spec's own `16.4.1` row already
replaced that with the holder-class exemption and a two-term bound, in the same
document, and says so. So this change applies a rule the spec records rather
than changing one, and the spec is left untouched. What it deliberately does
*not* do is give the block pool a working ceiling — an acquisition held for the
life of a reader's view would be a new bounding mechanism, which is a slice, not
an out-of-band row. That call was raised for review and settled the same day,
below.

## The block pool's bound is a divisor's job, not an acquisition's

`M70`'s exemption stands, and the per-view acquisition it declined is refused
rather than deferred. The reasoning is filed beside the mechanism
([`../../design/architecture.md`](../../design/architecture.md), "Execution
model and API surface"); what belongs here is the evidence and the two facts
the entry that raised it did not have.

**The work was already admitted.** `16.15` is the phase's row for "one stated
number bounds both memory terms", and two notes docs already defer memory
accounting to it by name — `16.10.2` on `POOL_DEPTH`, `16.16` on the same. So
the answer routes into an existing slice: no ledger row, no new number, and
`16.15`'s scope amended to say the divisor counts the block a worker decodes,
since it was written about a query's retained span and the live term on an
`.xz` source is one whole block per reader.

**A per-view acquisition is the wait under another name.** The view *is* the
retention — a `BlockView` holds the `Arc<DecodedBlock>` that owns the slot — so
releasing on the view's drop is releasing when that reader stops reading, and a
second reader blocking on it is `M70` with a different counter. Bounding the
live term by admitting fewer readers is what works on a retaining holder,
because it never makes one holder wait on another.

**The arithmetic, at the default, and why the probe read flat.** 64 MiB stated,
`POOL_DEPTH` 4, a 1 MiB chunk: the chunk pool takes 4 slots and 4 MiB, leaving
60 MiB against a 24 MiB unit, so the block pool's `slots()` is **2** and the
`max(POOL_DEPTH, jobs)` depth never binds. That is why `M70`'s probe read
~169 MB at `--jobs` 2 and did not move at 4, 8 or 16 — the slot count is
budget-derived, and `jobs` stopped mattering at two.

**A claim two documents made was never true.** Both said the byte budget bounds
the retained blocks and the free ones *together*. `BlockCache` holds `retained`
at `slots()` and `BufferPool::release` pools while `free.len() < slots()`, two
counts with nothing shared: the ceiling is `2 x slots x unit`, 96 MiB at the
default. The `charged` counter never coupled them either — it bounded
retained-plus-live, not the free list — so this predates `M70` rather than
following from it. Corrected in `architecture.md` and in `BlockCache`'s doc
comment; whether to cap the sum is `16.15`'s, because it changes what the
stated number means.

**`16.13.1` is taken before `16.15`, not after.** `parallel-peak-rss` plots
against a `--jobs` axis that flattens where the budget stops affording a
worker, so `16.15` moves the number the figure is plotting — but a figure
measures the arrangement that ships, and `16.15` is unspecified. Holding a real
reading behind an ungrilled slice trades it for a hypothetical one; `16.15`
re-takes the figure, and its checklist entry says so.

## What a later session should pick up

- **`M70` has landed and P16 has no blocking ledger row.** `16.13.1` has since
  landed too (its own notes doc, no history entry needed), so the checklist's
  remaining order is `16.14`, `16.15`.
- **`--stale` is unmoved.** The only declared path this touched is
  `pgdump_query/src/io.rs`, red on every figure that declares it; the diff is
  unreachable from every registered command shape twice over — no registered
  figure has a compressed input, and the announcement it stops making is
  `NeverWait` onto a pool already at `NeverWait`.
- **Driving a suspect `pgdq` with `timeout -s KILL` is still the rule.** The
  deadlock this closes is gone, but the reason it survived `SIGTERM` is not
  specific to it: the interrupt guard's flag is cooperative, so any thread
  parked in a blocking primitive never reads it.

## `16.14`'s koji verification is launched, not landed

A detached job is running: a serial (`--jobs 1`) and a `--jobs 4` parse of
`koji-2026-07-23.dump.multistream.xz`, compared byte for byte. Handoff:
`runs/koji-xz-verify-20260908-0203/HANDOFF.md`.

**The job takes two fresh legs rather than one against an old cache**, which
the review of this date affirmed — see the section below for why no reference
of that kind can exist at all.

**Why `multistream.xz` and not `blocks128.xz`.** The recompressed copy's
128 MiB blocks would need most of the 512 MB cgroup just to afford four
concurrent block buffers, leaving no room for anything else `pgdq` holds;
the real download's 24 MiB blocks fit several times over, which is what lets
`--jobs 4 --parallel-memory 268435456` (256 MiB) run genuinely 4-way
parallel rather than budget-clamped to two, as it would be at the 64 MiB
default (`M70`'s landing entry above has the arithmetic).

## A compressed cache and a plain one were never byte-comparable

`16.14`'s spec row asked for a `.xz` parse whose `.dqcache` is byte-identical
to the one the serial 784 GB scan of the plain dump produced. No such
comparison exists, and the reason is structural rather than circumstantial.

`CacheFile` carries `compression: Option<CompressionIndex>`, set at save from
`ByteRangeSource::seek_table()` — `Some(Xz(..))` holding a 31,150-entry seek
table for the multistream `.xz`, `None` for the plain dump. It carries
`identity: SourceIdentity::LocalFile { stored_size, mtime }`, and `stored_size`
is the size of the file actually opened: 40,397,009,888 against
784,019,857,152. Only `total_size`, the addressable length, agrees. The two
caches taken this date show it directly — `runs/pgdq-koji-xz-serial.dqcache` is
2,007,281 bytes where `runs/pgdq-koji.dqcache` is 248,479.

**The expired reference was the shallower objection.** `runs/pgdq-koji.dqcache`
(2026-09-05) does predate `FORMAT_VERSION`'s 15→16 bump (`5066c47`, 2026-09-06,
"13.2 Make `SourceIdentity` opaque…"), and `cache::load` refuses a version
mismatch before comparing anything else. But a surviving reference would not
have helped: within one format version the compressed and plain caches of one
dump still differ by construction. So the fresh pair is not a fallback after an
artifact expired — it is the only comparison that was ever meaningful, and the
spec row's wording named an artifact nothing produces.

The check therefore splits in two, and the spec row now says so: **across
arrangements**, two legs over the same file in one run, caches compared to each
other; **across formats**, each leg's reported counts compared to the plain
scan's published totals. The durable half is filed in
[`../../design/architecture.md`](../../design/architecture.md), "The cache";
the consequence for a koji run is in
[`../../design/measurements.md`](../../design/measurements.md), "koji full
scan".

**`M66` stays non-blocking for P16.** `16.14` now leans on those published
counts as its cross-format oracle, and `M66` is what would give an
outside-register section an invalidation edge. It is not needed here: the
counts are properties of a fixed 784 GB file, not readings off a moving build,
so an edge would never fire on them.
