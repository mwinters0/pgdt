# 2026-09-08

## `M70`: the block pool is a retaining holder, so nothing grants it a wait

`XzSource::hint_wait_policy` now states the granted `WaitPolicy` to the **chunk**
pool alone. The block pool stays at `NeverWait` whatever a read loop permits,
which is what ends the `--jobs` 2-or-more deadlock over a block-decoding `.xz`
([2026-09-07](2026-09-07.md), "A `--jobs` parse of an `.xz` deadlocks on the
block pool's retained charges"). The mechanism and its rejected alternative are
beside the pool ([`architecture.md`](../../design/architecture.md), "Execution
model and API surface"); what is here is the evidence and the admission test.

**The classification is what was wrong, not the wait.** `16.4.1` states the
exemption by **holder class** — a holder that keeps a buffer past the read that
took it never waits, because the only task that could free its slot is the one
waiting on it. `BlockCache` is exactly that holder: it retains a decoded block
past the read, and the read is simultaneously holding a zero-copy view into the
same buffer, which is what makes a read inside one block a slice rather than a
copy. So `BlockCache::slot`'s drain to `slots() - 1` frees nothing for the
caller waiting on a slot, `charged` reaches `slots()` and stays there. The
policy was being forwarded to that pool anyway, and two paragraphs of
`architecture.md` argued it was safe there on the grounds that the cache's own
reference was the only one — which is false for every read that is served out
of a retained block, and that is all of them.

**Reproduced as a unit test before it was fixed.**
`io::tests::a_permitted_wait_never_reaches_the_block_pool` builds a 4 KiB-block
`.xz`, states a budget that affords two block slots, grants `MayWait`, takes one
live view per slot, and asks for a third block. It failed on the previous code
with a bounded receive rather than a hang — the third read runs on a detached
thread against `recv_timeout`, so a pool that starts charging block slots again
fails the suite instead of stopping it. That shape is deliberate: a deadlock
test that deadlocks is not a test.

**Confirmed end to end** on a 200 MiB plaintext dump compressed at koji's own
parameters (`xz -6`, 24 MiB blocks, 9 blocks). `pgdq parse` at `--jobs` 1, 2, 4
and 8 all complete and write **byte-identical** caches, and `pgdq query
--no-columns` returns the same row count at 1, 2 and 8 — so `16.12`'s
determinism property holds on a compressed source as well as on the plain ones
it was asserted over. The same command at `--jobs 2` did not terminate before
this change.

**What the fix costs is a bound restated, not a bound lost.** The block pool's
budget bounds what is **retained**; what concurrent readers hold live is
`stream::worker_count` blocks, which is `min(jobs, budget / partition_bytes)`
off the same stated number, so the second term is the library's too and stops
growing where the budget stops affording a worker. Measured on the file above
under the 64 MiB default: peak resident 64 MB serial, ~169 MB at `--jobs 2`, and
**flat** at 4, 8 and 16, because two workers is what 64 MiB affords against a
25 MiB partition. Those readings are a probe on a scratch file, not a figure —
`parallel-peak-rss` is the registered instrument and no document quotes these
numbers.

**The admission test was re-run before the work and it passes.** The spec's
prose paragraph ("Memory is bounded by a block pool with backpressure") says a
worker *blocks until a slot is free*; the spec's own `16.4.1` row already
replaced that with the holder-class exemption and a two-term bound, in the same
document, and says so. So this change applies a rule the spec records rather
than changing one, and the spec is left untouched. What it deliberately does
*not* do is give the block pool a working ceiling — an acquisition held for the
life of a reader's view would be a new bounding mechanism, which is a slice, not
an out-of-band row. That call was raised for review and settled the same day,
below.

## The block pool's bound is a divisor's job, not an acquisition's

`M70`'s exemption stands, and the per-view acquisition it declined is refused
rather than deferred. The reasoning is filed beside the mechanism
([`../../design/architecture.md`](../../design/architecture.md), "Execution
model and API surface"); what belongs here is the evidence and the two facts
the entry that raised it did not have.

**The work was already admitted.** `16.15` is the phase's row for "one stated
number bounds both memory terms", and two notes docs already defer memory
accounting to it by name — `16.10.2` on `POOL_DEPTH`, `16.16` on the same. So
the answer routes into an existing slice: no ledger row, no new number, and
`16.15`'s scope amended to say the divisor counts the block a worker decodes,
since it was written about a query's retained span and the live term on an
`.xz` source is one whole block per reader.

**A per-view acquisition is the wait under another name.** The view *is* the
retention — a `BlockView` holds the `Arc<DecodedBlock>` that owns the slot — so
releasing on the view's drop is releasing when that reader stops reading, and a
second reader blocking on it is `M70` with a different counter. Bounding the
live term by admitting fewer readers is what works on a retaining holder,
because it never makes one holder wait on another.

**The arithmetic, at the default, and why the probe read flat.** 64 MiB stated,
`POOL_DEPTH` 4, a 1 MiB chunk: the chunk pool takes 4 slots and 4 MiB, leaving
60 MiB against a 24 MiB unit, so the block pool's `slots()` is **2** and the
`max(POOL_DEPTH, jobs)` depth never binds. That is why `M70`'s probe read
~169 MB at `--jobs` 2 and did not move at 4, 8 or 16 — the slot count is
budget-derived, and `jobs` stopped mattering at two.

**A claim two documents made was never true.** Both said the byte budget bounds
the retained blocks and the free ones *together*. `BlockCache` holds `retained`
at `slots()` and `BufferPool::release` pools while `free.len() < slots()`, two
counts with nothing shared: the ceiling is `2 x slots x unit`, 96 MiB at the
default. The `charged` counter never coupled them either — it bounded
retained-plus-live, not the free list — so this predates `M70` rather than
following from it. Corrected in `architecture.md` and in `BlockCache`'s doc
comment; whether to cap the sum is `16.15`'s, because it changes what the
stated number means.

**`16.13.1` is taken before `16.15`, not after.** `parallel-peak-rss` plots
against a `--jobs` axis that flattens where the budget stops affording a
worker, so `16.15` moves the number the figure is plotting — but a figure
measures the arrangement that ships, and `16.15` is unspecified. Holding a real
reading behind an ungrilled slice trades it for a hypothetical one; `16.15`
re-takes the figure, and its checklist entry says so.

## The `16.14` OOM is glibc's arenas, and a CPU limit is not the remedy

A detached job ran a serial (`--jobs 1`) and a `--jobs 4` parse of
`koji-2026-07-23.dump.multistream.xz`, meaning to compare them byte for byte.
Handoff: `runs/koji-xz-verify-20260908-0203/HANDOFF.md`; diagnosis:
`runs/koji-xz-verify-20260908-0203/FAILURE.md`.

**The job took two fresh legs rather than one against an old cache**, which
the review of this date affirmed — see the section below for why no reference
of that kind can exist at all.

**Why `multistream.xz` and not `blocks128.xz`.** The recompressed copy's
128 MiB blocks would need most of the 512 MB cgroup just to afford four
concurrent block buffers, leaving no room for anything else `pgdq` holds;
the real download's 24 MiB blocks fit several times over, which is what lets
`--jobs 4 --parallel-memory 268435456` (256 MiB) run genuinely 4-way
parallel rather than budget-clamped to two, as it would be at the 64 MiB
default (`M70`'s landing entry above has the arithmetic).

**What happened**: leg 1 (serial) completed cleanly in 2702s at the reference
counts (74 blocks, 19,575,829,920 rows). Leg 2 was killed by the kernel's
cgroup OOM killer 180s in — confirmed in `dmesg`, not inferred from the exit
code. Its stdout is empty, the scan summary being printed at the end, but its
cache is not: the throttled per-block save (`stream.rs`, `SaveThrottle`)
leaves a real index of the blocks a killed leg finished, 2,004,642 bytes
against leg 1's 2,144,936. So the orchestrator's `RESULT: caches DIFFER` line
compares a complete cache against a partial one; it carries no information
about determinism and is not evidence against `M70`.
**What the ~300 MiB the pools cannot account for actually is.** The block pool
alone never explained the kill: the depth ceiling (`POOL_DEPTH.max(jobs)` = 4)
caps leg 2's block pool at 4 slots however much of the 252 MiB it could
otherwise afford, so the uncoupled-pools bug of the section above predicts at
most 192 MiB against the 96 MiB intended — a real overshoot, and not enough on
its own to fill a 512 MB cgroup. Five bounded probes of leg 2's own shape
against the real file, at a 2 GiB limit so nothing was killed, sampling the
container's `memory.stat` and the process's thread and arena counts every ten
seconds, settle the rest (`runs/koji-oom-probe-20260908/`, one `.txt` per leg;
probes, not figures, and no document quotes them as measurements):

| leg | anon plateau | peak | threads | arenas |
|---|---|---|---|---|
| `--jobs 4 --parallel-memory 256 MiB` | 536 MiB | 581 | 31 | 29 |
| the same, `MALLOC_ARENA_MAX=2` | 328 MiB | 377 | 30 | 1 |
| the same, `--cpus 4` | 476 MiB | 523 | 10 | 8 |
| the same, `--cpus 4` and `MALLOC_ARENA_MAX=2` | 337 MiB | 377 | 10 | 1 |
| `--jobs 4 --parallel-memory 128 MiB`, `MALLOC_ARENA_MAX=2` | 328 MiB | 376 | 31 | 1 |

**`#[tokio::main]` is what makes the arenas, and it makes them before a byte is
scanned.** The runtime is sized from the CPUs the process can see, so a
container with no CPU restriction gets 24 workers here; the probe reads 24
arenas at `t=0`, with anon under 1 MiB. Each arena then retains what the thread
that owns it allocated, and freeing does not give it back.

**A CPU limit is the wrong lever, which is what the first attempt's note
guessed at and had backwards.** `--cpus 4` does reduce the runtime to four
workers and the arenas to eight — Rust's `available_parallelism` reads the
cgroup quota — and it still measures 476 MiB, because what an arena retains is
not proportional to how many there are. `MALLOC_ARENA_MAX=2` is what moves the
number, and adding the CPU limit on top of it moves nothing further.

**The stated budget is not a lever either.** 128 MiB stated measures the same
328 MiB as 256 MiB, because `BufferPool::slots()` clamps to `POOL_DEPTH.max(jobs)`
at either — so the block pool is 4 slots in both, and the budget stops
mattering above the point that affords four workers. That the process holds
328 MiB against a stated 128 is `16.15`'s to answer; it is not what killed
leg 2.

The property this leaves for a user in a memory-capped container is filed
beside the mechanism ([`../../design/architecture.md`](../../design/architecture.md),
"Execution model and API surface") and in the manual, since the remedy is one
an operator already has.

**The verification was relaunched the same day and passed.**
`MALLOC_ARENA_MAX=2` and `--cpus 4` on both legs — the CPU limit to hold the
thread count fixed for the whole scan rather than for headroom — plus per-leg
memory sampling, whose absence is why diagnosing the first attempt needed a
rerun at all. The parallel leg then plateaued at ~330 MiB anonymous with one
arena and peaked at 404 MiB inside the same 512 MB cgroup, which is the probe
table above holding over a whole scan rather than over a ten-minute sample. The
first attempt's caches and logs were archived under `runs/koji-xz-attempt1/`
rather than deleted, which bought a serial-versus-serial comparison across two
runs for nothing. The result is
[`../../design/measurements.md`](../../design/measurements.md), "koji full
scan"; the slice is
[`../../design/roadmap-P16.14-koji-verification-notes.md`](../../design/roadmap-P16.14-koji-verification-notes.md).

## A compressed cache and a plain one were never byte-comparable

`16.14`'s spec row asked for a `.xz` parse whose `.dqcache` is byte-identical
to the one the serial 784 GB scan of the plain dump produced. No such
comparison exists, and the reason is structural rather than circumstantial.

`CacheFile` carries `compression: Option<CompressionIndex>`, set at save from
`ByteRangeSource::seek_table()` — `Some(Xz(..))` holding a 31,150-entry seek
table for the multistream `.xz`, `None` for the plain dump. It carries
`identity: SourceIdentity::LocalFile { stored_size, mtime }`, and `stored_size`
is the size of the file actually opened: 40,397,009,888 against
784,019,857,152. Only `total_size`, the addressable length, agrees. The two
caches taken this date show it directly — `runs/pgdq-koji-xz-serial.dqcache` is
2,144,936 bytes where `runs/pgdq-koji.dqcache` is 248,479.

**The expired reference was the shallower objection.** `runs/pgdq-koji.dqcache`
(2026-09-05) does predate `FORMAT_VERSION`'s 15→16 bump (`5066c47`, 2026-09-06,
"13.2 Make `SourceIdentity` opaque…"), and `cache::load` refuses a version
mismatch before comparing anything else. But a surviving reference would not
have helped: within one format version the compressed and plain caches of one
dump still differ by construction. So the fresh pair is not a fallback after an
artifact expired — it is the only comparison that was ever meaningful, and the
spec row's wording named an artifact nothing produces.

The check therefore splits in two, and the spec row now says so: **across
arrangements**, two legs over the same file in one run, caches compared to each
other; **across formats**, each leg's reported counts compared to the plain
scan's published totals. The durable half is filed in
[`../../design/architecture.md`](../../design/architecture.md), "The cache";
the consequence for a koji run is in
[`../../design/measurements.md`](../../design/measurements.md), "koji full
scan".

**`M66` stays non-blocking for P16.** `16.14` now leans on those published
counts as its cross-format oracle, and `M66` is what would give an
outside-register section an invalidation edge. It is not needed here: the
counts are properties of a fixed 784 GB file, not readings off a moving build,
so an edge would never fire on them.

## A parse has phases, and nothing says which one it is in

Two slices are admitted to P16 — `16.18`, the `--verbose` → `--detail` rename,
and `16.19`, the CLI's status output. The decisions are in the spec
([`../../design/roadmap-P16-parallel-scan.md`](../../design/roadmap-P16-parallel-scan.md),
"A parse has phases now, so the CLI says which one it is in"); what is here is
why the phase absorbs them and what the day's evidence contributed.

**The phases are this phase's own doing.** `parse` was one span of work until
P16 gave it two: an `.xz` source walks the file's stream footers before the
first block is scanned, 85 s of silence on the koji download. `16.14` is what
made the cost of that silence concrete — its first attempt was diagnosed from
`dmesg` and a cgroup sample, because the leg that died printed nothing at all,
its scan summary being written at the end. A second run had to be taken to
learn what the first one held, and per-leg memory sampling was bolted onto the
orchestrator to get it. That is the observability gap, and it is not a
parallelism bug: nothing pgdq printed would have said which phase the process
was in either way.

**So the work is P16's rather than a phase of its own.** It fails the
out-of-band admission rule outright — it adds a dependency, changes every
command's default output, and creates an output contract, which is design work
([`../../process.md`](../../process.md), "Out-of-band work"). Against a new
phase, the argument is that the phases worth naming are the ones P16 created
and that `16.15` reads the same startup numbers a log line would state. The
cost accepted knowingly: a logging facade is cross-cutting where the rest of
this phase is not, so the disjoint-mechanisms property that lets two phases run
at once does not hold for it.

**`16.17` is spent and skipped.** It was allocated for a day to what became
`16.10.2`, and commit `f65f9f6`'s body says so in a sentence no rewrite may
touch ([2026-09-07](2026-09-07.md), "16.10.1 split again"). A number naming two
different slices across the record is the ambiguity the never-reuse rule
exists to prevent, so the admitted slices take `16.18` and `16.19`.

**The rename is split from the facade** because the two carry different
confidences and `../../process.md`'s "Working unattended" forbids one review
cycle for both. It is also wider than it looks: `--verbose` reaches
`measure.py`'s koji recipe and the `test_measure.py` assertion over it, so a
rename touches the measurement harness and not only the CLI and the manual.
The short `-v` was never bound to anything, so what is contested is the word,
not the letter.

**A logged duration is not a figure, and the rule is written before the first
one is printed.** The alternative is a command that manufactures timings with
no apparatus behind them, on whatever machine a user ran, in a project whose
own koji section is disqualified reading by reading at the number. Emitting
transitions without durations was the other way to close it and gives up half
of what the row is for, since subtracting two timestamps by hand is quoting a
duration with extra steps.

## The `16.14` apparatus is affirmed, and capping arenas is a Future item

The review of this date settled the open "Decisions worth another look" entry —
`16.14`'s container tuning — and closed it. Three findings, of which the third
is the one the entry never reached.

**The entry understated its own subject.** It named `MALLOC_ARENA_MAX=2`. The
run used `-m 512m --memory-swap 512m --cpus 4 -e MALLOC_ARENA_MAX=2`, which
[`../../design/measurements.md`](../../design/measurements.md), "koji full
scan" already describes as tuning *two* things the apparatus rule holds fixed.
The defence covers both, and for different reasons: the arena cap bounds what
glibc retains and cannot change a cache byte, and the CPU quota fixes the
thread count, which a byte-identical-cache claim is indifferent to.

**No re-take is owed.** The alternative — the legs run untuned in a raised
cgroup — reproduces a number already measured five ways at a 2 GiB limit, and
a one-rep resident-set reading off an unquieted machine is not a figure with
the cgroup raised any more than with it tuned. The reasoning is filed beside
the apparatus it governs, in that same section, because a probe table is only
a probe and why it suffices is not recoverable from it.

**What the entry did not consider is that pgdq could cap the arenas itself.**
`main.rs`'s bare `#[tokio::main]` builds one worker thread per visible CPU
whatever `--jobs` says — so a *serial* parse on a 24-CPU host still seeds 24
arenas before a byte is read — and a `mallopt(M_ARENA_MAX, …)` in the CLI's
`alloc.rs` would close the ~200 MiB gap with nothing set by the operator.
Sizing the runtime from `--jobs` is not the same lever and does not work:
`--cpus 4` reaches eight arenas and still measures ~476 MiB. It is admitted as
a **Future** item rather than a slice or an `M<k>`, because it changes a
decision `architecture.md` records — that the arena gap is a property with an
operator's remedy — and because it re-bases the apparatus of every registered
figure and needs a contention figure of its own before anyone adopts it
([`../../design/roadmap.md`](../../design/roadmap.md), "Future — wanted,
unscheduled").

`16.15`'s scope is unchanged by all three. Whether the stated number ought to
bound the process rather than the pools was routed to it and is now settled —
see "`16.15` lands the divisor; the sitting is `16.15.1`" below: it does not,
and the arena question stays the Future item this entry admits.

## `16.15` lands the divisor; the sitting is `16.15.1`

`stream::plan_partitions`'s `worker_count` call now divides by
`partition_bytes + max_source_span` rather than `partition_bytes` alone —
`STATUS.md`'s row, landed. `leader::scan_region`'s own call (the mapping pass)
is unchanged, since a discovery worker retains nothing and has no second term
to add; the sum is computed at the query replay's call site rather than folded
into `worker_count` itself. Two further calls the row's amendment raised were
settled rather than left open: `BlockCache`'s retained cap and `BufferPool`'s
free-list cap stay separate, and `POOL_DEPTH` stays fixed at 4 — both filed as
rejected alternatives beside the mechanism
([`../../design/architecture.md`](../../design/architecture.md), "Execution
model and API surface"). Detail, and what `16.15.1` inherits:
[`../../design/roadmap-P16.15-stated-budget-notes.md`](../../design/roadmap-P16.15-stated-budget-notes.md).

**The figure re-take earned a third-level slice rather than landing in the
same round.** `scripts/measure.py` declares a dirty tree's changed paths
un-excusable and will not stamp a figure from one — the same reason `16.13`
split into `16.13.1` — and this round leaves no commit to name. So `16.15.1`
carries the sitting.

**The blast radius is not the one the admitting row named — it is a different
figure.** That row named `parallel-peak-rss`, written when the review centered
on memory retention. But every leg of that figure is `pgdq parse`, which
reaches `worker_count` through `leader::scan_region` and never calls the
changed function, so it is excused by reachability and `e29939c`'s table
stands. What the divisor does land on is `plan_partitions`, which
`parallel-scan-throughput` reaches through **both** its typed-`query` legs —
plain as well as `.xz`, the plain source's `partition_bytes` being one chunk
against a 64 MiB span term. So `16.15.1` re-takes that figure alone and files
the acknowledgement for the other.

## A `--jobs` the budget refuses is silent, and that is the defect

`16.15`'s divisor is right and its defaults do not move, but together they
make a stated `--jobs` unreachable at every shipped default: `--parallel-memory`
defaults to 64 MiB and `QueryOptions::max_source_span` to 64 MiB, so the span
term alone meets the budget and `pgdq query --jobs 24` plans one sub-stream.
Nothing says so. The arithmetic is a consequence the phase committed to; the
silence is not, and it is the same failure `M67` was admitted against — the
budget-declined `.xz` fallback, which that row makes announce itself "so the
flag that says *raise it* also says what to raise it to". A worker count
reduced to one by a budget is that failure with the same remedy already
specified for its sibling.

Found while grilling the `PARALLEL_BUDGET` entry under "Decisions worth
another look", which never raised it: the entry weighed what the *figure*
should measure and not what a user gets.

**The row blocks P16, and `16.19` is why.** That slice prints the stated
`--jobs` and the stated budget once at startup, "so a log says what arrangement
produced it" — and at every shipped default that sentence is false: the
arrangement is one sub-stream and the line says twenty-four. Landing `16.19`
first therefore does not leave this defect where it is; it promotes silence into
a printed misstatement, on by default, in the log the slice exists to make
trustworthy. Startup is also too early to say anything truer, the plan not
existing until the mapping pass has run, so the honest number can only come from
`plan_partitions` — which is this row. With it landed first, `16.19`'s claim is
true as written and needs no amendment.

**So it leaves P19's inbox.** The entry filed hours earlier put `M67` and `M72`
together as that phase's subject; `M67` stays there and this row does not,
landing as out-of-band work under P16 instead — it still meets the admission
rule, changing no decision any spec records and fitting one session, which is
what it was admitted under this morning.

**`M65` and `M71` were weighed the same way and are not blocking.** Neither
touches a flag rename or a log facade, so P16's remaining slices can be landed
around both. What they do carry is an ordering P19 owns: that phase ends in a
sweep, and the RSS attribution's table cannot be published outside one, its
first leg being read against `peak-rss`'s `blocks4000` row and its instrument
taken from that figure's shape, which is a `shares` edge and disqualifies it
from publication outside a sweep. That half is `M74`; `M65` is the instrument
and closed the same day. Filed in that phase's inbox rather than in the
`Blocks` column, which names the open phase and nothing else.

## The parallel-vs-serial comparison is anchored at four workers

`parallel-scan-throughput` is a parallel-versus-serial measurement — every cell
is a speedup over its own one-job row — and the arrangement it compares against
serial is **four workers**. That is the count the shipped system actually
delivers on a plain source, `POOL_DEPTH` clamping the chunk pool to four slots,
and the count `16.14`'s koji verification ran its parallel leg at. The budget
may rise to afford it; it does not have to, because it already does.

`PARALLEL_BUDGET`'s 1 GiB affords four workers on every leg with room to spare,
the widest divisor being the `.xz` typed-`query` leg's `25 MiB + 64 MiB`, so
`4 × 89 MiB ≈ 356 MiB`. What 1 GiB does not afford is four workers' *worth* of
headroom at the top of the axis: the same leg wants `24 × 89 MiB ≈ 2.14 GiB` at
twenty-four, which `PARALLEL_MEMORY`'s 3 GiB container cannot hold once the
decoded blocks, the pinned chunks, the LZMA2 dictionaries and the Arrow batches
are counted. So the axis keeps its shape and the rows above the affordable
count are restated rather than footnoted, per the rule now beside
`PARALLEL_BUDGET`.

The axis itself does not move. `PARALLEL_JOBS` is pinned by three couplings in
`test_measure.py` — it must contain 4, must run past it so the `POOL_DEPTH`
ceiling is in the table, and must equal `DECODE_WORKERS` — and it is shared with
`parallel-peak-rss`, whose `parse` legs the divisor never reached and whose
wide curve is the whole content of that figure.

**So the rows above four on the typed-`query` legs state what they achieved.**
The budget clamps them to about eleven sub-streams on the `.xz` leg and
fourteen on the plain one, and each such cell carries that count beside its
wall clock, computed arithmetically from block size, span and budget exactly as
the table's existing `POOL_DEPTH` note is. Splitting the query legs into a
second registered figure, and dropping their top rows to leave a ragged table,
were both weighed: the first buys two clean claims and costs a permanent second
apparatus to keep in step, and the second deletes a real reading — what a
budget-bound parallel query does — because the bound happens to be the
harness's. Stating the bound is cheaper than either, and it keeps the
`.xz`-versus-plain and `parse`-versus-`query` comparisons the four columns were
built for on one page.

## The tool discovers what it was allocated

**P16's rejection of reading the cgroup limit is reversed**, and the reversal
is a changed decision rather than a clarification
([`../../design/roadmap-P16-parallel-scan.md`](../../design/roadmap-P16-parallel-scan.md),
"The caller sets workers or bytes, whichever binds first"). The rejection
weighed an unverified kernel interface against a conservative constant and
chose the constant. What it did not weigh is the deployment case: under an
orchestrator the process is *given* a memory and CPU allocation, is the only
party that knows it, and cannot be asked to have it restated on the command
line — restating it is what an operator gets wrong, and getting it wrong is the
OOM. The posture to match is `xz -T0`: discover the allocation, take it.

The rejection's condition survives intact and is now work rather than an
objection. Nothing here has verified how a cgroup limit is read, and there is
no register for an external interface outside PostgreSQL —
`docs/design/postgres-invariants.md` has no sibling — so one is owed before any
code reads `/sys/fs/cgroup`.

**Half of it is already done and was not noticed.** Rust's
`available_parallelism` reads the cgroup CPU quota, which is why the `16.14`
probe at `--cpus 4` seeded eight arenas rather than twenty-four (see "The
`16.14` OOM is glibc's arenas" above). So CPU discovery is `std`'s and needs no
register entry; memory discovery is the part with no equivalent.

**Arena capping is the same subject and comes out of `Future`.** `pgdq caps its
own glibc arenas, so the stated budget bounds the process` was filed as a
Future item on the grounds that it changes a decision `architecture.md` records
and re-bases every figure's apparatus. Both remain true; what changed is that a
phase now owns "the stated budget bounds the process", and a budget discovered
from the cgroup that is then blown by arenas the process seeded before reading
a byte is not a sound default in the sense this work is being admitted under.

## The parallel default is source-dependent, and that is forward-looking

One `--jobs` default cannot be right: `parallel-scan-throughput` reads
**0.76×** for a plain `parse` at twenty-four workers — a regression already
present at two, below `POOL_DEPTH`'s clamp — against **5.93×** for the same
scan on `.xz`. So the default resolves after source recognition rather than
being one constant, and `--jobs` keeps one stated meaning while its default
becomes a function of what the file is.

**It is registered as a source's answer rather than as a test for `.xz`**
because the set of sources is still growing: the gzip work, the zstd/lz4 work
and format coverage each add a decoder or a container whose right default is
its own, and a conditional written against the one compressed source in the
tree today would have to be reopened by each of them. The machinery already
exists — `ByteRangeSource::partitions` is the source describing what it can do
— and this is the same answer one level up.

## `P19` is allocated: P16 builds the mechanism, P19 ships it set correctly

The efficiency-and-defaults work is its own phase rather than an amendment to
P16's thesis. The reason is context, not subject: P16's spec already carries
three amendments and nineteen slices, so a second thesis there is read by every
session that touches the first, while a separate phase lets P16 wrap — deleting
its checklist and consolidating nineteen slice notes into one — which is a
permanent reduction. It is also the process's own ordering one level up: a
phase whose evidence is another phase's completed figures, and `16.13.1`'s
table is that evidence.

**What the split costs is a claim, and the roadmap says so rather than letting
either row carry it.** P16 reaching `Complete` does not mean parallelization is
finished; it means the mechanism exists. P16 keeps `16.15.1`, `16.18` and
`16.19` and then wraps.

`P19` takes: resource discovery, the arena cap out of `Future`, the
source-dependent `--jobs` default, the span term and `M67`. Its facts are filed
in
[`../../design/roadmap-P19-efficient-defaults-inbox.md`](../../design/roadmap-P19-efficient-defaults-inbox.md),
which its grilling drains. That ledger row is struck when the spec records it
and not before, so nothing is owned by neither. `M72` was filed there too and
has since moved: it blocks P16 (above), which lands it as out-of-band work.

**Its first slice is evidence: a runtime invariants register.** P16's rejection
of reading the cgroup limit named its own condition — an assumptions register
for an external interface outside PostgreSQL, which does not exist —
and that condition survives the reversal as work.
`docs/design/runtime-invariants.md` is `postgres-invariants.md`'s sibling,
named for the runtime environment rather than for Linux so a future
container-less or non-Linux answer has the same home, and `CLAUDE.md` gains a
read-trigger beside the Postgres one.

**The order inside the phase is bound, and it is not the obvious one.**
Discovery does not come first. `--parallel-memory` bounds the *pools*, while
the process also holds glibc's arenas, the Arrow batches in flight, the tokio
runtime and the decoder's dictionaries — `16.14` measured 328 MiB resident
against a stated 128 MiB — so a budget set to a discovered limit OOMs by
construction, which is the failure this phase exists to prevent. Cap the
process's overhead first, so that resident set becomes a bounded function of
the stated budget; then discover; then set the default as a fraction of what
was discovered, with the fraction measured rather than chosen.

## The library offers discovery; it does not take it as a default

`P16`'s "the library defaults to serial — an embeddable component does not
spawn threads by surprise" is **not** reversed by the discovery work, and does
not have to be. The library carries the mechanism, beside `Parallelism`, for an
embedder who wants it; nothing calls it for them, and `ParallelArgs::resolve`
is this repo's one caller. That keeps discovery next to the type it configures
rather than duplicated in the CLI, and leaves an embedder who has already made
their own allocation decision entirely unaffected.

The remaining two calls: the phase **ends in a sweep**, because a
`mallopt(M_ARENA_MAX, …)` re-bases every registered figure's apparatus and one
sitting after the defaults are set costs less than two — which also means
`16.15.1` takes its own sitting first, under the current apparatus, as a `P16`
figure that must stay comparable to `e29939c`. And **an unlimited environment
falls back to today's constant** rather than to a fraction of physical RAM: it
makes discovery strictly additive, so a machine with no cgroup behaves exactly
as it does now, and it keeps the register's claim to "how a stated limit is
read" rather than the much larger "what physical RAM means".

## A hand-edited table has no oracle

`16.15.1`'s sub-stream annotation is a *presentation* change to a renderer,
decided after its readings were taken. Before `M73` there was no way to re-emit
a table without re-measuring, so the annotation was applied by hand to the
section already pasted into `measurements.md` — and it landed one column left of
the leg it described. Both `.xz` counts sat under `.xz`, `parse`, which plans no
sub-streams at all; the leg the spec row named carried none; and the prose
directly beneath said "both typed-`query` legs", which the table contradicted.
Every individual number was right.

The defect is not the misplacement. It is that a pasted table is the one artifact
in this harness with no oracle: `--check` reconciles markers, `--stale`
reconciles paths, `test_measure.py` holds the register, and none of them reads a
cell. A renderer that changes after a sitting therefore had two authorities on
what the table says, and the doc's copy was the one nobody could re-derive.

So `raw.json` now records what a render needs — the header verbatim, the
allocator, each input's size, the RSS and reported-line maps, and the figure id
on every run record — and `measure.py --render <run-dir>` rebuilds `tables.md`
from it, measuring nothing. `ReplaySession` raises if a renderer tries to take a
reading or drop the page cache, and stands a **sparse file of the recorded size**
in for each staged input: every renderer asks an input for its size and never for
its contents, so a stand-in of the right length reproduces the byte counts
exactly without the cache, the tmpfs staging, or the disk they needed. A sitting
that predates those fields is refused by name rather than rendered on guesses.

Two things came out of applying it. The doc's section is now byte-identical to
the render, which meant folding the figure's two doc-only sentences — the
`architecture.md` citation and the anchoring claim — back into the harness, since
prose the harness does not emit is the same divergence in slower motion. And the
whole-section paste dragged in the harness's own fold-in note, a line addressed
to the session doing the fold-in and not to a reader; `--check` now refuses that
class of leak (`measure.SCAFFOLDING`).

The renderer's own mapping is pinned by tests that run it over synthetic
readings and assert the annotation lands in the typed-`query` columns and no
others — verified by reintroducing the defect and watching them fail. Assertions
about `PARALLEL_LEGS` alone would not have caught it, the original code having
been correct.

## `M72` lands: `plan_partitions` names why a plan fell short

`stream::plan_partitions` now returns the sub-stream groups **and** a list of
`PlanNote`s alongside them — empty on every path that does not limit, one
`PlanNoteKind::ParallelismBudgetLimited` whenever the stated memory budget
plans fewer sub-streams than `--jobs` asked for. It names `requested`,
`planned`, and the two terms `worker_count`'s divisor sums — the widest
touched block's decode footprint and `QueryOptions::max_source_span` — beside
the `memory_bytes` that declined them, so raising the budget or lowering the
span is stated rather than left for someone to re-derive from the arithmetic.
`TableStream::plan_notes` is where it surfaces: settled once, before any
sub-stream is built, and identical across every one of them, so a caller reads
it off the first without polling. `pgdq query` announces it once on stderr,
right after `table_stream_partitions` returns and before the first row, since
unlike `comparison_notes` it needs no block to have resolved first.

**It is a new type, not a `DiagnosticKind` variant, and that was the live
question this round settled.** The obvious placement — folding it into the
existing `Diagnostic`/`DiagnosticKind` L1 channel, since `NonSeekableCompressedSource`
already warns about a related budget decision — was tried first and reverted.
`diagnostic.rs`'s own module docs state the invariant plainly: every
`DiagnosticKind` that exists is a property of the *file*. A budget-limited
worker count is not: two queries against the same file with different `--jobs`
or `--parallel-memory` get different answers, so it is a property of *one
query's plan*. `architecture.md`'s "Diagnostics: one severity scale, two
types" already had precedent for exactly this shape — `ComparisonNote` is a
third channel, deliberately not folded into either of the first two because
it is per-term and conditional on a predicate — so `PlanNote`/`PlanNoteKind`
is the fourth, following the same reasoning and living beside `TableStream`
in `stream.rs` for the same reason `ComparisonNote` lives beside the predicate
code that produces it.

Tests: `pgdump_query/tests/partitioned_replay.rs` gained
`a_budget_bound_worker_count_announces_why` (the shipped-defaults case named
above, `--jobs 8` at `DEFAULT_MEMORY_BUDGET` plans one sub-stream) and
`a_budget_that_affords_every_worker_is_silent`; the two existing tight-budget
tests now also assert the note's exact numbers.

**The row blocks no phase any more.** `M72`'s ledger row named `P16` because
`16.19` prints the stated `--jobs` and budget at startup "so a log says what
arrangement produced it," which was false at every shipped default before this
landed. `16.19` can now print a number this mechanism agrees with.

## `M65` lands its instrument; `M74` owns the sitting

`scripts/rss_attribution.py` is folded into `scripts/measure.py` and the
attribution is a registered figure — `rss-attribution`, with its own `depends`
and `quoted_by` edges, its four new command shapes and its nine legs at two
block counts. That is `M65`, and it is closed. It sits in `measure.UNTAKEN`
rather than in `FIGURES`, and the section in
[`measurements.md`](../../design/measurements.md), "What the per-block resident
growth is made of", keeps its `outside-register` declaration. Publishing the
table is a separate item, `M74`, and it belongs to a sweep.

**The two tables disagree today, which is what the borrow is for.** The
attribution's first leg and `peak-rss` run the same binary, the same
`parse-rss` shape and the same two inputs, but readings are keyed by figure
*and* spec, so nothing makes them one number: `peak-rss` publishes
**9.73 MiB** at `blocks500` and **43.78 MiB** at `blocks4000`, the attribution
**9.58 MiB** and **44.26 MiB**, from entirely separate runs. Two numbers for
one measurement, one section apart. The `Shared` edge collapses them by making
the attribution consume `peak-rss`'s reading rather than take its own, and
that is why the edge belongs — not merely to satisfy the closure rules.

**Declaring it early closes nothing, which is what decided the split.** A
`<!-- figure: <id> -->` marker asserts the session stamp's first clause —
*taken by `scripts/measure.py`* — and the nine medians the doc carries were
printed by the standalone script at `41c96bb`, with a leg shape that has since
changed (the `info` leg now builds its cache inside its own container rather
than from one staged beforehand). So the marker cannot go on until a sitting
replaces those numbers, whatever the borrow graph says. Declaring the edge
now would additionally fail `--check` with exit 1 — `peak-rss` carries its own
`41c96bb` sitting marker, and an entangled figure may not — for as long as it
took to reach a sweep, buying visibility the `UNTAKEN` entry and
`test_a_taken_attribution_declares_its_borrow` already provide. A failing gate
is not the same as a `--stale` figure left red with its reason written down,
which is the rule that governs the other direction.

**What `M74` is, in one change:** take `--figure rss-attribution` inside a
sweep, declare the `Shared` edge (which makes `--figure` pull `peak-rss` in),
paste the emitted section, delete the `outside-register` marker and the
`measure.NOT_OURS` row, and re-generate the stamp's accounting sentence.
`scripts/test_measure.py`'s `test_a_taken_attribution_declares_its_borrow`
holds the two halves together rather than a comment: an `rss-attribution`
promoted into `FIGURES` without the borrow fails. The `--check` shape to
expect until then is "Built, not taken: rss-attribution" beside the three
declared outside sections.

**The manual's sentence is licensed by two figures, not one.**
[`dump-inspection.md`](../../manual/dump-inspection.md), "`--chunk-size`", says
resident memory "does not grow with the *size* of the dump … but it does grow
with the number of tables in it, by roughly 10 KB each". The first half is
`peak-rss`'s two byte rows; the second is per-*table* and `peak-rss` cannot
license it, because `blocks4000` gives every table exactly one `COPY` block and
the two axes coincide in its inputs. So the file is in both figures'
`quoted_by` and each register comment says which half it answers for — `M65`'s
row said "moves the citation", and the citation turns out to be shared rather
than misfiled.

## `M66`: a declared section carries an invalidation edge

A `measurements.md` section outside the figure register now declares what
invalidates it, and `--stale` names it. `measure.Outside` gains `depends`, the
same field a `Figure` carries and read by the same predicate
(`declared_hits`), and the section's `<!-- outside-register: <id> -->` marker
gains a `taken at` clause naming the commit its readings came from.

**What the field separates is registration-for-sweeping from
registration-for-staleness.** Being outside the register says the harness
cannot re-take the readings — koji is 784 GB on the HDD and an hour. It was
also saying, silently, that nothing would ever be told when they went wrong:
`--stale` walked `ALL_BY_ID`, so no declared section could go red however far
its inputs moved. That is the blind spot the koji RSS row sat a megabyte wrong
in for a whole slice, which is what put `peak-rss` in the register
([2026-09-07](2026-09-07.md), "The RSS attribution is a figure, and what
decides that"). Registering the attribution did not close it for koji, and
nothing else was going to.

**koji reads red as of this change, and that is the finding rather than a
side effect.** Its marker names `f5768e7`, the commit the block/row/byte counts
were confirmed at; the parallel-scan campaign has since moved the read path,
the scanner, the map, the cache, the preamble, type resolution and the CLI —
nine declared paths in all. No acknowledgement is writable against that: those
changes are exactly the kind a byte-identity check exists to test, so the red
is discharged by the next koji run and by nothing cheaper. It is red with the
reason written down, which is the state `measurements.md` asks for.

**The commit goes in the doc, not in `measure.py`.** `session-drift` declares
`scripts/measure.py`, so recording a koji run's provenance there would mark a
figure stale for recording where another reading came from — every time koji is
re-run. That is the argument the figure sittings already settled one level up,
and the marker was already the doc's convention for provenance. `--check` holds
the pair in both directions: paths without a commit are an edge `--stale` has no
range to intersect, and a commit without paths is a provenance nothing reads.

**An acknowledgement may name a declared section.** The excuse machinery is
keyed by id and was already indifferent to what kind of reading sits behind
one, so `--check` resolves an entry's names against `NOT_OURS` as well as the
register, and spentness is computed from the section's own base. Without it a
declared section's red would have exactly one discharge — a run the harness
cannot make — which is the shape of a light that is always on.

**`benches` declares nothing, and the empty tuple is the claim.** It publishes
no number the design quotes, which is the same sentence that puts it outside
the register, so there is nothing a diff could falsify and no commit to date.
`rss-attribution`'s edge is read off the registered instrument rather than
copied, so the two cannot drift in the window before `M74` deletes the row.
