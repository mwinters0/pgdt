## P19 is specified and sliced, and its grilling reversed two filed positions

The spec is [`../../design/roadmap-P19-efficient-defaults.md`](../../design/roadmap-P19-efficient-defaults.md),
eleven slices, roadmap row `Current`, inbox drained and deleted. Most of it
follows from what 2026-09-08 settled; two things do not, and one of them is a
decision the phase was convened to *adopt*.

**The in-binary arena cap is declined, not adopted.** It came out of `Future`
into this phase on the grounds that a budget discovered from the cgroup and then
blown by arenas seeded at startup is not a sound default. That reasoning stands;
what fails is every available implementation. `mallopt(M_ARENA_MAX, …)` bounds
arena *creation* and frees nothing already made, and glibc seeds an arena per
thread at that thread's first allocation — so a cap keyed to the resolved worker
count removes none of the arenas that already exist by the time it could run,
and the count this phase resolves is the source-dependent one, which is
downstream of source recognition, which is I/O. A cap keyed to the *stated*
`--jobs` is reachable early and is not the number that matters. What is left is
a constant, which re-bases every registered figure's apparatus in exchange for a
value that cannot follow the worker count.

**What replaces it reaches the same place by not creating the threads.** The
CLI moves to a `current_thread` tokio runtime — the library dispatches through
`spawn_blocking` and has never required `rt-multi-thread` — so the threads that
exist are the blocking pool's, created on demand, and the arena count follows
the concurrency dispatched rather than the host's CPU count. `MALLOC_ARENA_MAX`
becomes a published deployment setting for the residual. The price is charged
where it falls: the shipped reserve is sized for the operator who did *not* set
it, so the operator who did gets a smaller budget than their machine could
support, and the spec says so rather than leaving it to be rediscovered.

**`available_parallelism` gets a register entry, against what the inbox filed.**
The inbox concluded the CPU side needed none because the behaviour is `std`'s.
The register's trigger is a decision depending on external behaviour *we do not
control*, and someone else's code is more external, not less: this phase's whole
CPU default rests on `available_parallelism` continuing to read the cgroup
quota, and without an entry a future toolchain moves that default silently.

**Two inbox positions were sharpened rather than reversed.** The span-allowance
entry proposed dividing one allowance among sub-streams; the arithmetic says
that buys no sub-stream at the shipped defaults — `(budget − max_source_span) /
footprint` is zero at 64 MiB against 64 MiB — and that a **plain** source plans
one sub-stream there too, which the entry framed as the compressed case's
problem. The real defect is that the span term is a chunk-shaped source's cost
being charged to a block-shaped one whose `partition_bytes` already covers it,
so the retained unit becomes the source's own to state. And the discovered
budget is `limit − reserve` rather than a fraction of the limit, because the
overhead above a stated budget is measured constant, not proportional — 128 MiB
stated reads the same ~328 MiB resident as 256 MiB stated.

**`KD16` moves to `(b)`, owned by P19 and paired with slice 19.4.** Closing it
re-bases `parallel-scan-throughput`'s one-job row, which runs at the library's
64 MiB default precisely because of the collapse `KD16` describes; that lands
inside the phase's closing sweep.

## `19.2`: the plain `parse` regression is a double read

**A plain `parse` at `--jobs ≥ 2` reads every byte of the file twice.** Summing
`pread64` returns over the 3.00 GiB warm control: 3.02 GiB read at `--jobs 1`,
**6.02 GiB** at `--jobs 2`, and the ratio is flat in the worker count (6143
calls at two workers, 6147 at four, at the shipped 1 MiB chunk). A plain
source's partition is exactly one read chunk (`LocalFileSource::partitions`
answers `Partitioning::anywhere(pool.slot_bytes())`), and `scan_partition`'s
mandatory tail read is another whole `options.chunk_size` — so each piece's tail
re-reads the next piece's body in full. On a block-shaped `.xz` source the same
tail is 1 MiB against a 24 MiB partition and costs 4%, which is why the
compressed legs scale and the plain one does not.

It is charged in **system** time, which is where a warm `parse` already lives —
0.28 s of a 0.38 s serial run. That is also why the profile the spec asked for
could not see it: `perf_event_paranoid = 2` gives `exclude_kernel = 1`, so a
`perf record` here samples user space only, and total *user* cycles rise only
8% between the two legs. **A profile of a syscall-bound shape on this machine is
blind to its own answer** — worth knowing before the next one is commissioned.

The account, the two candidate repairs and what the closing session owes are in
[`../../design/roadmap-P19.2-plain-path-account-notes.md`](../../design/roadmap-P19.2-plain-path-account-notes.md).

## The plain-path fork routes to both branches

**The sitting was read and the spec's fork turned out not to be exclusive.** It
asks whether the account lands on the pool depth *or* on coordination; the
account names three costs, and forcing them into one arm is what made the

## The plain partition's cap, reviewed

`19.5` sized a plain partition at `PLAIN_PARTITION_CHUNKS` read chunks capped
at `POOL_MAX_BYTES` and filed the size under "Decisions worth another look",
weighing three alternatives that all asked where to put the ceiling. The review
read the mechanism cold and the framing did not survive; the code did.

**The cap is a symptom of a single-unit pool.** `BufferPool` keeps exactly one
announced read length, and the parallel plain path has two read units —
`leader::scan_partition` reads `[start, end)` in a single `read_range` and only
then falls to chunk-sized tail reads. The partition read therefore cannot be
the announced length and survives release only under the ceiling. Every
alternative ceiling answers the wrong question. The arrangement that answers it
is the one `XzSource` already runs — two pools dividing one stated budget
through `held_bytes()` — so it is a Future item ("A two-unit plain source")
rather than a phase-19 slice: it changes what a source is, and P19 is about
defaults.

**Two things the entry did not consider.** `BufferPool::pick` takes the
smallest free buffer with `buf.len() >= len` and `POOL_DEPTH` slots are shared
between partition and tail reads, so the cap makes pooling *possible* without
making it happen, and no reading exists for the hit rate. And the pool's
accounting under-reports this path eightfold: `slots()` counts at
`slot_bytes()`, the announced 1 MiB chunk, while `keeps` admits anything up to
the 8 MiB ceiling and `release` never rescales by bytes — so four 8 MiB
partition buffers on the free list are 32 MiB that `held_bytes()` calls 4 MiB.
`held_bytes()` is what `XzSource::apportion` divides a budget with, so a budget
rule would trust it. **`19.7`'s spec row was amended to cover it**, since that
is the slice writing the budget rule and a separate item would have to land
first while changing the same decision.

**The shipped default sits exactly on the cap**, `SCAN_CHUNK_DEFAULT_SIZE_BYTES * 8`
being `POOL_MAX_BYTES` to the byte, with the three constants independently
justified. `a_shipped_plain_partition_is_eight_whole_chunks` makes the
coincidence a checked relationship; deriving one constant from another was
refused because it reads as though one causes the other.

## `19.6`: the reserve is a constant on one path and a multiple on the other

The budget rule `P19` ships is `budget = min(fraction × limit, limit −
reserve)`, and the spec calls the reserve the one number it rests on and the
fraction a ceiling that "bounds nothing anyone has measured". The diagnostic
sitting that was to choose the constant says that is the wrong way round.

**Plain sources have a reserve; block-decoding `.xz` sources have a
multiplier.** At `--jobs 24` a plain `parse` holds 37.4 MiB whatever budget is
stated — `POOL_DEPTH` slots of `POOL_MAX_BYTES` is 32 MiB and the pool does not
grow past it — so the stated number over-states that path by 27 to 475 MiB
across the axis. The same run over a 24 MiB-block `.xz` reads 243 MiB resident
at a 64 MiB budget and 1242 MiB at 512 MiB. `stream::worker_count` divides the
budget by a 25 MiB divisor, so those rows plan 2, 5, 10 and 20 sub-streams, and
the line through them is `160 MiB + 54 MiB` a sub-stream: **the pool holds
about 2.2× what the divisor charges a worker**. The wall clocks corroborate the
counts against `parallel-scan-throughput`'s published `--jobs` axis
independently of the resident readings.

That a compressed parallel scan holds more than the budget names is a documented
property, not a defect. What is new is that the excess is **proportional**,
which is what a constant subtraction cannot absorb: substituting the worst cell
into a 3 GiB limit gives a budget whose own line reads about 5 GiB. The
mechanism behind the multiple is the block pool's doubled ceiling, not a
per-worker cost — see "The reserve rule's two entries, closed" below.

**The three `MALLOC_ARENA_MAX` legs agree.** Uncapped, the worker count plus
one, and 2 — the value the manual publishes — are inside the per-rep spreads at
all eight cells, and the single pair whose ranges are disjoint reverses sign one
row later. `19.3`'s `current_thread` runtime is the explanation: the threads are
the blocking pool's and are created on demand, so a cap at or above the
dispatched concurrency binds nothing. This is not a controlled refutation of the
koji probe that produced the spec's 200 MiB — different file, different scale,
`rt-multi-thread` — so the claim is the bounded one, and the spec and the manual
were left alone.

The spec was not amended: reversing a spec rationale is outside what an
unattended session settles. Both consequences are filed under `STATUS.md`'s
"Decisions worth another look", and the sitting is `runs/measure-20260909T084032`
(`--alone`, NOT PUBLISHABLE — no document may quote it as a measurement). The
instrument is `measure.UNTAKEN`'s `reserve` entry and the reading is owed again
after `19.7`, which changes the accounting a budget rule trusts.

## The reserve rule's two entries, closed

`19.6` left two calls under `STATUS.md`'s "Decisions worth another look" — what
`19.7` does now that the compressed path appeared to refute `limit − reserve`,
and whether the arena cap's price still stands. Both were reviewed with the
maintainer and closed; the review reached past the entries, because each rested
on an attribution that turns out to be wrong.

### The multiple is the pool's doubled ceiling, not a per-worker cost

`19.6` reported `160 MiB + 54 MiB` a sub-stream against a divisor charging
25 MiB and attributed the excess to an 8 MiB LZMA2 dictionary, a compressed
input window and a batch in flight. The shape measured is `parse`, which builds
no batches at all, so one of those three cannot have been present. The real
mechanism was already written down in the code and in
[`../../design/architecture.md`](../../design/architecture.md), "The compressed
source": the block pool's free list and its retained list are **separate
counts, each held at `slots()`**, so its ceiling is `2 × slots × unit` —
2 × 24 MiB a slot against a charged 24 + 1, which is the measured 54 with no
further term needed.

**Resident is a function of the stated budget, not of the worker count.**
`XzSource::apportion` gives the block pool `budget − chunk_pool.held_bytes()`
at depth `POOL_DEPTH.max(jobs)`, and `slots()` is `(budget / slot_bytes)`
clamped into it. At `--jobs 24` the depth clamp is slack, so the sitting's
slot counts (2, 5, 10, 21) and its sub-stream counts (2, 5, 10, 20) are the
same division of the same budget run twice, not a cause and an effect —
halving the worker count would leave resident where it was.

**The spec's premise and `19.6`'s reading sit on opposite sides of that
clamp.** The spec ruled the fraction out because 128 MiB stated measured the
same ~328 MiB as 256 MiB; that probe was `--jobs 4`, where the clamp binds at
both budgets. `19.6` ran `--jobs 24`, where it does not. The overhead is
constant below the clamp and proportional above it, and neither
`limit − reserve` nor `fraction × limit` describes that.

**So the repair is the coupling `architecture.md` had already rejected, and the
rejection named its own reversing condition.** It said to leave the counts
separate *unless a reading shows the transient itself, not the admitted-worker
count, is what a real workload hits* — resting on `worker_count`'s divisor
tightening the bound from outside, and on a serial forward scan holding its free
list at zero or one. Neither survives: the divisor cannot bound a pool that
sizes itself from the budget, and with N readers one worker's release refills
the free list while another retains, so the window is open for the length of the
run rather than between two acquisitions. `19.7` couples the counts, and the
budget rule then ships unamended — resident becomes the budget plus a constant,
which is what a reserve is. The option of charging a compressed worker the
54 MiB it appears to hold was rejected in the same breath: it would admit fewer
readers for exactly the same resident set.

### The arena cap's price cannot be read off a `--jobs 24` sitting

Recomputed from the sitting's own `raw.json` rather than from its summary,
uncapped against `MALLOC_ARENA_MAX=2` on the `.xz` control: 243.4 → 245.3,
465.5 → **404.1** (the one disjoint pair), 698.6 → 675.8, 1241.8 → 1258.1 MiB.
The plain control reads 37.2–37.6 MiB at all twelve cells while running 8 to 24
workers. Two cells favour the cap by 23 and 61 MiB, two go the other way inside
noise, and the best case is 61 MiB against the manual's 208.

**That sitting's own spreads run to 62 MiB over three reps**, which is the size
of the effect `M76` went on to measure — so it never had the resolution to
report a price, and "no direction to read" is what a null of that shape means.
The section below is the controlled reading; the price the manual once stated
is *not* recovered by it, and neither is the reading that `19.3` had removed it.

**What this review changed, and where.** The spec's "The reserve is a figure,
and it is measured uncapped" keeps measuring both ways and keeps shipping the
uncapped number — but on the ground that it is the safe direction, not that it
is the larger one; its price paragraph, and with it the claim that this was "the
strongest argument for reversing" the in-binary `mallopt` refusal, is gone,
since the price is far smaller than the 208 MiB that argument was carried by.
`architecture.md`'s arena paragraph carries the bounded finding beside its
200 MiB probe. The **manual** was corrected here rather than at `19.10`, that
rule binding absolutely (`../../process.md`, "Where does this fact go?"): the
536/328 numbers and the "a few hundred megabytes" margin are out, the mechanism
and the headroom advice stay, and the margin is now described as a multiple of
the budget rather than a fixed figure.

The apparatus is **not** gaining `MALLOC_ARENA_MAX`. The ground under that
call moved when `M76` measured the term, and it was re-reviewed on the new
evidence and refused again — "The arena cap stays off the apparatus", below.

### What the repair costs, and why it lands in three slices

**A coupled count of one is the shape the pool rejects by name**, so
`BlockCache::affordable` moves with the coupling: it asks whether the budget
affords **two** units rather than one, which is the same sentence as "the
coupled count is at least two" and introduces no constant. The user-visible
consequence is that whole-block decode is declined for a file whose largest
block exceeds *half* the budget rather than the whole of it — koji's 24 MiB
blocks still decode at the 64 MiB default, and `--parallel-memory` still
reverses a decline. `19.10` says so in the manual.

**The reserve stays one constant, taken from the compressed leg.** The two
paths' fixed terms are a factor of thirty apart — 5.86 MiB above the plain
pool, a few hundred megabytes above the block pool — so one constant
over-reserves a plain scan by most of that difference. It is still one number,
because `Parallelism::discover()` answers before anything is open and a source's
own answer is downstream of recognition, which is I/O: the same argument that
makes the *worker* default source-dependent makes the reserve not. Over-reserving
is the safe direction.

**`19.7` was re-scoped and split, and the two new rows take `19.12` and
`19.13`.** As specified it carried the accounting change, the discovery
primitives and the budget rule together; the accounting change grew when the
coupling and the affordability move joined it, and the rule's one constant can
only be read off the build that change produces — a loop the single row could
not hold. So: `19.7` lands the accounting, `19.12` re-takes the reserve
diagnostically against it and chooses the constant, `19.13` ships discovery and
the rule. That ordering now binds, and is written into the spec's "Slice order"
section beside the four that already did. The alternative — one slice taking its
own mid-slice sitting — keeps the review question whole and was refused because
the accounting half is a rework of an already-tested concurrent structure and
earns a review of its own. No deficiency-register entry named `19.7`, so the
split re-targets nothing.

### The figure keeps two arena legs

`19.6` registered three — uncapped, the worker count plus one, and `2`. `19.12`
drops the middle one, and that does not wait on `M76`: after `19.3` a cap set at
or above the concurrency actually dispatched cannot bind, which is a mechanism
rather than a reading, so the leg measures a setting inert by construction. The
remaining pair is what the shipped default is sized for against the tightest
value an operator would plausibly set, and **both survive even if `M76` finds no
effect** — a one-leg figure cannot report a null, and this phase has now twice
found an arena claim outliving the build it was measured on.

## `M76`: the arena cap is not the runtime's

`control_xz` — 3.00 GiB of plaintext in 129 24 MiB blocks — parsed at the koji
probe's own arrangement, `--jobs 4 --parallel-memory 268435456`, in a 3 GB
cgroup with no CPU restriction, capped at `MALLOC_ARENA_MAX=2` and uncapped, on
`eec9159` and on `f58aed4`, the commit before `19.3`. Seven interleaved reps a
leg, peak RSS through the measurement harness's own `getrusage` wrapper. The
script and the raw readings are `runs/m76-arena-probe.{sh,log}`; they are a
probe, and no document quotes them as a measurement.

| leg | median | min–max |
|---|---|---|
| current, uncapped | 418.7 MiB | 391.3–440.7 |
| current, `MALLOC_ARENA_MAX=2` | 362.7 MiB | 340.0–370.3 |
| pre-`19.3`, uncapped | 425.4 MiB | 364.2–496.8 |
| pre-`19.3`, `MALLOC_ARENA_MAX=2` | 362.4 MiB | 340.1–374.9 |

**The manipulation took and the outcome is a null.** Polled to a maximum on the
same command, the current binary runs **6** threads and the pre-`19.3` one
**29** — so the twenty-odd `rt-multi-thread` workers the hypothesis blamed are
present in one leg and absent in the other. They cost nothing measurable
resident: the builds differ by −6.7 MiB uncapped and +0.3 MiB capped, both
inside a single leg's own range.

**What the cap is worth is ~50–60 MiB, on both builds.** Paired by rep, the
uncapped-minus-capped difference is positive in all fourteen pairs — median
63.2 MiB on the current build, 50.5 on the pre-`19.3` one. So the effect is
real and the direction is not in doubt; what is refuted is the attribution.
`19.3` did not delete the retention a cap reclaims, because a build that still
creates those threads reclaims the same amount.

**What is left to explain the 208-against-60 gap is what this probe held
constant.** The koji probe and this one differ in file, scale and duration —
an eight-second scan of 3.00 GiB against an hour over 40 GB — and in the
instrument, `memory.stat`'s anonymous plateau against `getrusage`'s peak. The
runtime was the one variable it was worth isolating, because it was the one a
change of ours had moved; having isolated it, the remaining candidates are all
properties of the workload, which is why no fixed number belongs in the manual.
`19.10` writes it that way: the cap is worth having, it is worth more on a
longer scan, and it is not a margin anybody can quote.

**Costs nothing else.** No shipped code, no figure, no spec amendment — the
spec had already delegated the outcome to `19.10` and kept both arena legs
against either answer.

## The arena cap stays off the apparatus

Reviewed with the maintainer and refused. The apparatus pins the allocator and
not its arena count; the reasoning is filed beside the rule that makes the
allocator apparatus at all
([`../../design/measurements.md`](../../design/measurements.md), "The
apparatus"). The three facts that decided it, none of which the entry proposing
the review had:

**The cost of pinning runs against the parallel figures, not merely against a
re-take.** `MALLOC_ARENA_MAX=2` buys resident bytes by paying allocator
contention, and the tables with enough threads for that term to exist are the
ones sweeping `PARALLEL_JOBS` to 24. A pin motivated by a resident reading
would therefore measure this library's parallel scaling under a deliberately
contended allocator — a worse apparatus, not a more controlled one. The
magnitude is unmeasured; the sign is what the setting trades against.

**So the only pin that could ever be right is regime-scoped.** This document
already scopes its resolution floors per regime, which is the shape a
resident-only pin would take. Recorded because the next session to re-open this
will otherwise re-derive it as a global setting and price it against the whole
register.

**The re-basing argument the review inherited is unfounded.** `SWEEP_JOBS` is
1, so seventeen tables run a single worker on a `current_thread` runtime, and
whether the cap binds a process of that shape has never been measured — `M76`
read it at four workers. The apparatus stays unpinned either way, so the number
was not worth an afternoon; what was worth recording is that the stated ground
was a claim nobody had checked.

One loose end, left where it is: the harness pins no CPU count
(`grep -n cpus scripts/measure.py` is empty), so the arena ceiling behind every
figure is `8 x ncores` of this host. The section's blanket "all figures are on
the hardware `CLAUDE.local.md` describes" covers it, and it only matters at all
to someone pinning, which is the thing refused above. No ledger row.

## The partition-pooling call, reviewed

`19.7` tightened `BufferPool::keeps` to `len <= slot_bytes()` and the parallel
plain path lost its partition-buffer pooling with it. The call was flagged and
is affirmed: what a ceiling would have kept is the *report* of pooling, not
pooling, and that report is the number one stated budget is divided with.

**The under-report was live on the serial default path too**, which the entry
did not say. `map::attach_text` reads a whole contiguous run of text-storing
spans in one call — `want = min(run bytes, n × SPAN_STORED_TEXT_MAX_BYTES)` — and runs from the
ordinary mapping pass, so any dump whose schema run exceeds a chunk was putting
a multi-megabyte buffer on the free list counted as one slot. The tightening
repairs that as well; the pooling it costs there is one allocation per scan.

**Both routes the entry named were already foreclosed, by decisions rather
than by judgement.** Promoting the two-unit source into P19 is refused by the
spec — a repair reaching `leader::scan_partition` changes what the leader does
per piece for every source, which is out of a phase about defaults. Pricing the
loss before the plain worker default ships cannot change it either: that
default's stated reopening condition is a reading showing plain parallel
beating serial, and this makes plain parallel slower. No probe was taken, for
the same reason — it would license nothing.

**The grilling turned up a remedy nobody had recorded**, now filed inside the
Future item "A two-unit plain source": read the partition in chunk-sized reads
instead. The plain source has two read units only because the partition body is
one call, and `scan_partition`'s loop already continues chunk-wise after it, so
a single-unit source is reachable without a second pool — and with the cap on
the partition product gone, the multiple survives a raised `--chunk-size`,
which is the item's other half. Unmeasured, and it costs eight times the
`spawn_blocking` hops per partition.

**Where an unbuilt option goes, and why.** The Future section is the durable
home: no keystone strikes it and an item leaves only by acquiring a phase
number, where a phase spec or a slice notes doc is struck with the phase. That
is now written in the section's preamble, along with what it is for — the
maintainer iterates through it once the product is feature-complete.

## `19.12`: the coupling did not return the bytes

The reserve figure re-taken against `19.7`'s build —
`runs/measure-20260909T171423`, `--alone`, three reps, `--jobs 24`,
`postgres:16` at `-m 3g`, every reading accepted at the first attempt. A
diagnostic; no document quotes it as a measurement. The table and the fits are
[`../../design/roadmap-P19.12-reserve-retake-notes.md`](../../design/roadmap-P19.12-reserve-retake-notes.md).

**The compressed legs were predicted to halve and rose a tenth.** Fitted
against the sub-stream count — unchanged at 2, 5, 10, 20, the divisor still
`cache.unit + chunk_bytes` and the wall clocks within 5% of `19.6`'s — the
uncapped line moved from `160 MiB + 54.3 MiB` a sub-stream to
`180 MiB + 59.4 MiB`. `19.7` removed a ceiling of `2 × slots × unit` that was
arithmetically the right size for the excess `19.6` found, and removing it
returned no bytes.

**What the pool declines to keep, the thread's arena keeps.** That is the
account the same sitting's arena legs carry, and it is why the null `19.6` and
`M76` both reported is now reversed. A plain scan is `16 MiB + 8.0 MiB` a
worker uncapped — 8 MiB being `POOL_MAX_BYTES` exactly, the partition buffer
`19.7`'s tightened `keeps` stopped pooling — and **flat** at 78–86 MiB under
`MALLOC_ARENA_MAX=2`, across the whole worker axis. On the compressed source
the cap takes ~77 MiB off the *fixed* term and leaves the per-sub-stream term
alone, that term being decoded blocks the pool genuinely holds and no arena
setting reaches.

**Two consequences, both filed under "Decisions worth another look" rather than
acted on.** The constant `19.13` carries is read as the fixed term — 180 MiB,
taken as **256** — rather than as the worst cell the renderer names, since
resident is flat in the budget on neither source and the term that scales is
what the rule's fraction exists for. And the spec's fraction, described there as
"a ceiling only" that "bounds nothing anyone has measured", is now the only
thing bounding a compressed parallel scan: the arithmetic wants about **0.25**,
and below roughly a 300 MiB limit the 180 MiB fixed term means no fraction makes
a 24-worker compressed parse fit at all.

**`19.10` inherits a live recommendation again.** After `19.6` the manual's
`MALLOC_ARENA_MAX` advice was half-stale because the cap bought nothing this
instrument could see. On this build it buys 129 MiB on a 24-worker plain scan
and ~77 MiB on a compressed one. The number a document may state comes from
`19.11`'s sitting, not from this one.

## The reserve entries, reviewed: the divisor is wrong, not the rule

`19.12` filed two entries — which reading of its sitting gives the reserve
constant, and whether the spec's rationale for the fraction reopens. Both turn
on a fact neither entry checked, and with it in hand both answers change shape:
**the compressed path's per-reader charge is wrong, and the budget rule is
right.**

**The compressed divisor is out by 2.4× and the plain one is exact.**
`XzSource::partition_advice` charges `cache.unit + chunk_bytes` = 25 MiB a
sub-stream, and `stream::worker_count` divides the stated budget by it.
`19.12` measures a sub-stream costing **59.4 MiB**. The plain path charges
`POOL_MAX_BYTES` = 8 MiB a worker and measures **8.03**. One instrument, one
rule, one source's accounting right to 0.4% and the other's out by a factor.

**The code already says a reader holds two units.** `BlockCache::affordable`
requires `2 × unit ≤ budget` and `BlockCache::slot` drains the retention list
to `slots() - 1` so that a reader can hold one block while the next decodes —
both `19.7`'s, and both saying the same thing. Two units, the chunk, and an
8 MiB LZMA2 dictionary is 57 MiB against a measured 59.4. `19.7` moved
`affordable` to two units and left the divisor charging one.

**The sentence that rejected this repair is falsified by the plain leg.** "The
multiple is the pool's doubled ceiling" refused to charge a compressed worker
what it holds — "it would admit fewer readers for exactly the same resident
set" — resting on *resident is a function of the stated budget, not of the
worker count*. The plain leg saturates at 24 workers and goes flat: **208.96 →
208.38 MiB while the budget doubles from 256 to 512**. Resident tracks the
count. The compressed leg cannot show this, its count never saturating below a
512 MiB budget.

**Corrected, the rule comes out true as written.** A charge of `c` a
sub-stream gives `n = budget / c` and resident `180 + c·n = 180 + budget` — the
budget plus a constant, which is what a reserve is, and exactly what the
coupling was predicted to deliver and did not.

**Two arithmetic facts about the entries' own proposal, which is why it is not
taken.** With reserve 256 MiB and fraction 0.25, `limit − reserve` is the
binding term only over limits in **[320, 341) MiB** — below 320 the result is
under the floor — so the spec's declared primary instrument would be inert
across every other allocation. And at a 512 MiB limit the rule plans a 128 MiB
budget, whose measured cell is **494.78 MiB against 512**: 3.3% headroom,
against a per-rep spread of ±10% at the neighbouring cell. A fraction chosen to
compensate for the charge does not survive the reading it was chosen from.

**The dictionary term is not free to charge.** `dict_size` sits on the block
*header*; `SeekTable::from_source` walks stream footers and reads no block
header, so `partition_advice` can reach `2 × unit + chunk_bytes` = 49 MiB from
the table alone and not the remaining ~10 MiB. Whether `19.14` reads one header
at open or carries a constant is `19.14`'s to settle.

**What was decided.** The divisor is corrected — `19.14`, and it lands *before*
`19.13`, since the rule's constant is read off a build whose plan charges
honestly. The budget rule ships unamended and the fraction stays a ceiling; the
reserve constant stays the fixed term. `19.13` gains a validation leg in
containers at 256 MiB, 512 MiB and 1 GiB — `19.15` — because every reserve
reading in this phase was taken at `-m 3g` with the budget *stated*, and
discovery exists for the small allocation nothing has ever run in. And the
plain path's regression, priced by `19.12` at 8 MiB of arena retention a
worker, is registered as `KD18` rather than left as an adjective beside a
roadmap Future item.

**`KD18` is `(c) unowned`, not `(b)`.** A `(b)` stance names a phase in the
roadmap index, and "A two-unit plain source" is a Future item rather than a
phase — so the entry names it as the trigger that would promote it, which is
what the register's unowned stance is for.

**What `19.14` costs, stated rather than discovered.** At a 512 MiB budget the
plan admits **8** sub-streams where it now admits 20, and "What a second scan
worker buys" (5.82× at twenty-four workers) was measured at a budget that would
no longer admit twenty-four. The present count is reached by spending 2.4× the
memory the caller allowed, so what the correction removes is an over-spend, not
a capability: `--parallel-memory` buys the workers back at a number the caller
states and can see.

**Two things `19.14` forces, found while closing the entries above.** The
harness states `PARALLEL_BUDGET = 1 GiB` on every row of both `parallel-*`
figures, sized so that twenty-four workers over 24 MiB blocks are admitted at
25 MiB a partition — "below this the widest rows would be silently clamped by
`worker_count`, and a clamped row is a lower count wearing a higher label".
A corrected charge wants 24 × 49 MiB = 1176 MiB, so the constant has to rise
and both parallel figures are re-taken with it. And at the library's 64 MiB
`DEFAULT_MEMORY_BUDGET` a corrected divisor admits **one** sub-stream, so
`XzSource::default_workers`' `available_parallelism()` is overridden to serial
unless the budget rises with it — which makes `19.8`'s source default and
"an unlimited environment falls back to today's constant" combine to a serial
flagless `.xz` scan on an unlimited host.

**The dictionary term cannot be read.** `xz_seek::BlockHeader` and
`read_header` are `pub(crate)`, so `dict_size` is reachable only through an
upstream change to the crate and a re-vendor; `2 × unit + chunk_bytes` = 49 MiB
is what a `SeekTable` alone affords.

**`19.14` blocks on `xz-seek` rather than shipping a constant, and the phase
waits behind it.** `BlockTask::decode_into` takes a source and an output slice;
everything a concurrent decode allocates besides that slice — the LZMA2
dictionary among it — is invisible to a caller, which is why this repo's charge
was assembled by guesswork and came out 2.4× light. A stated 8 MiB constant
would have unblocked `19.14` immediately and left the same approximation one
slice further along, in the phase convened to remove it. So the request goes
upstream and the frontier idles until the crate answers and
`scripts/vendor_xz_seek.py` has run.

**What `xz-seek` answered, and what it corrects.** The request is that repo's
`P7` (`decode-footprint`). Three facts came back that change the shape of the
ask rather than its substance:

- **`decode_into` retains three terms beyond the `out` slice**: the backend's
  decoder (the declared `dict_size` plus the backend's own state), a compressed
  input chunk at `min(1 MiB, total_size − header_size)` allocated lazily on
  first fill, and under a kilobyte of check state. `header.filters` does not
  survive `start`. Only the dictionary varies per block. Their decomposition
  against our reading — 24 + 24 + 1 (ours) + 8 + ~1 (theirs) ≈ 58 against a
  fitted 59.4 — agrees inside our sitting's noise, which says the backend's own
  state is single-digit MiB rather than tens, and does not bound it tighter
  than that.
- **A dictionary bounds a *stream*, not a file.** Within one stream every block
  declares the same filter chain; across streams they can differ, and a `cat` of
  a `-1` and a `-9` stream decodes happily with blocks declaring 1 MiB and
  64 MiB. So an exact file-wide maximum costs one block-header read **per
  stream** — *one* on our recompressed koji file and 31,150 on the upstream
  download, not the per-block count assumed when the request went out.
- **An understated bound cannot overrun silently.** `memlimit` is compared
  against each block's own declared dictionary before any backend object is
  built, so a bound that is wrong for a later block raises
  `MemoryLimitExceeded`.

**We asked for the number on `SeekTable`, reversing what the request said.**
The request asked to keep it off the table to spare our cache envelope a
version bump; that optimises the wrong thing. We persist their table as
`CompressionIndex::Xz` and inject it back at recognition precisely so the
85 s multistream footer walk is paid once per file rather than once per
command — so a `max_dictionary()` living *off* the table costs 31,150 header
reads at every open, while anything we would have to persist separately is the
same envelope bump plus new plumbing. We also asked that filling it not make
the walk itself eager, which would double that 85 s for every caller.

**And that the number be a conservative upper bound including backend state.**
`worker_count` divides a budget a cgroup stated, so the two errors are not
symmetric: under-charging spends more than the caller allowed, which is the
defect we arrived with, while over-charging admits fewer workers and is bought
back visibly with `--parallel-memory`. Precision is not wanted — our slot is
24 MiB — so a rounded-up bound is preferred to a tight estimate.

**`xz-seek`'s `P7` is specified, and what `19.14` will consume is settled.**
A per-stream `StreamEntry.first_block_dict_size` rides the seek table, so it
reaches us through the persist-and-inject path with no per-open header walk,
and a file-wide **footprint** query — a conservative upper bound on what one
`decode_into` retains beyond `out`, backend state included and rounded up —
sits on top of it. Their slices `7.3` and `7.4` are what unblock us, ahead of
their own CLI and figure work. Eager filling turned out free: their backfill
already reads 4084 bytes below a stream's twelve-byte header, and the first
block header sits a kilobyte inside that window, so the walk stays at
`streams + 1` reads and the lazy field this side offered to trade for was
refused on its own merits.

**Three consequences here, all cheaper than the request assumed.** The cache
envelope bumps and **must** fail loudly rather than defaulting — zero is a
legitimate dictionary, so a `#[serde(default)]` absorbing the new field would
silently understate the footprint and reproduce the 2.4×-light divisor. That
costs one line: `CACHE_FORMAT_VERSION` 16 → 17, with bincode already failing the old
bytes to `CacheStatus::Unreadable` and both paths already starting cold. The
price is a fresh ~1 h koji scan, accepted knowingly under the pre-1.0 rule.
`RangePlan::fits()` shifting reaches nothing here — this repo has no
`RangePlan` caller — beyond a doc comment on `Partitioning::partition_bytes`
claiming the dictionary is excluded from `RangePlan::footprint`, which `19.14`
rewrites. And the divisor `19.14` writes is
`2 × max_block_uncompressed + chunk_bytes + footprint`, the two slots being
this side's own retention rule.

**We inherit one of their deficiencies, deliberately.** Their bound rests on
within-stream filter-chain uniformity, so a file whose later block in a stream
declares a larger dictionary than its first is bounded too low — the plan
reports `fits()` and the decode then refuses with `MemoryLimitExceeded`, and
raising `-M` fixes the decode without fixing the footprint. Their stance is (a),
the exact answer costing a header read per block, and `xz` writes no such file.
Our divisor rests on it, so `19.14` records it as a property beside the
mechanism; the koji corpus is the likeliest place here to meet one.

**The footprint call is `Reader::decode_footprint()`, taken at construction.**
It is `xz-seek`'s whole public surface: the table derivation
`SeekTable::decode_footprint(backend)` stays `pub(crate)`, withdrawn on this
review's argument that a caller passing a backend it does not own reintroduces
the silent wrong charge the argument was added to prevent — the same line that
crate had already drawn by keeping `BlockDecode` private and having
`BlockTask` carry its resolved check. Nothing here wanted the table form: every
site in this repo holding a bare table outside tests gets it from
`ByteRangeSource::seek_table()`, and `cache::claim`'s injected table goes
straight into `XzSource::with_table`, so there is no table-without-reader path
— the cache-only `pgdq info --dqcache` included, which starts no workers and
wants no footprint. The
dictionary and the input chunk are derivable over a table, but which backend
decodes it is a property of the `Reader`, and the crate ships two with
materially different allocation. That argument found a hole here: this repo
names **no** backend anywhere, building its reader with `Reader::new` and
`Builder::new().open_with_table` on crate defaults, so a `partition_advice`
passing a `Backend` would be asserting a fact it does not own and could drift
from the object doing the decoding.

So `19.14` calls the reader form instead, and gets the property the pure one
was asked for anyway: both `XzSource` constructors build the reader *locally*
before wrapping it in `Arc<Mutex<…>>`, so the call is made on an owned reader
with no lock taken, and the `u64` is stored on `XzSource` for
`partition_advice` to divide by. One statement of the backend, made by the
object that will use it.

**What could still move the design is their `7.1`, not their schedule.** The
bound rests on within-stream filter-chain uniformity, so far observed rather
than traced; if liblzma's source does not support it the bound's *shape*
changes and what the query means changes with it, which reaches `19.14`'s
design rather than its date.

## The default posture, and the three calls it settled

**pgdq's defaults run as fast as the machine or the cgroup permits.** Stated as
a standing rule ([`../../design/roadmap.md`](../../design/roadmap.md), "A
default runs as fast as the allocation permits") rather than as a
`P19` decision, because it decides the gzip, zstd/lz4 and format-coverage
phases' defaults too — each adds a source, and each source answers for its own
worker count *and* its own budget. Its three bounds are what keep it from
meaning "take everything": a stated flag wins outright, the library's own
default stays `Serial`, and we do not take an allocation we cannot show we use,
which is what the budget rule's fraction is in code.

Three calls follow from it, closing the questions `19.12`'s reading opened.

**`19.14` owes no reserve sitting of its own.** The ordering chain that binds
`19.7 → 19.12 → 19.14 → 19.13` is about the *rule's* constant, and `19.14` does
not move it: `19.12` fitted `resident(n) = 180 + 59.4n` over sub-stream
*counts*, and a corrected divisor changes only the map from budget to count,
not what one reader holds. `resident(budget)` is therefore re-derived from that
fit, the corrected counts interpolating inside its range rather than
extrapolating past it, and admitting fewer readers can only lower resident by
lowering the thread and arena count — so the derivation errs conservative.
`19.15`'s containers are what would falsify it, which is cheaper than a third
`--alone` hour to confirm arithmetic.

**`BlockCache::affordable` is restated against the same cost the divisor uses,
inside `19.14`.** Today they are two sentences about affording the same thing:
`affordable` is `unit × 2 ≤ block_pool_budget`, which at the 1 MiB chunk is
`budget ≥ 52 MiB`, while a corrected reader costs ~59 MiB — so between 52 and
58 MiB pgdq decides to decode blocks and then `worker_count(…).max(1)` floors
to one reader overspending the stated number. Narrow, and the same defect class
this phase exists to close. One sentence replaces both: a reader costs `C`,
block decode is affordable iff `budget ≥ C`, and `budget / C` readers are
admitted. It moves the whole-block-decode threshold again — blocks above about
a *third* of the budget are declined where `19.7` left it at a half — which
`19.10` describes and which changes the number
`PlanNoteKind::CompressedBlockPathDeclined` advertises.

**A source recommends a budget as it recommends a worker count**, folded into
`19.13` because it is one review question with the budget rule: what a flagless
invocation ends up with. Without it a corrected divisor makes the 64 MiB
constant admit one sub-stream, overriding `19.8`'s `available_parallelism()` to
serial on the host most likely to run this. It qualifies "an unlimited
environment falls back to today's constant" rather than reversing it —
discovery's fallback is unchanged; a *source* may recommend more, through the
mechanism `19.8` built.

## The fraction is dropped, and three documents that asserted it are corrected

**The budget rule is `budget = limit − reserve`, floored, with no fractional
ceiling.** The spec specified `min(fraction × limit, limit − reserve)` and
defended the fraction as "we do not take an allocation we cannot show we use".
Once the divisor charges honestly that sentence has an exact expression —
`jobs × C` — and the mechanism already enforces it from two sides:
`stream::worker_count` is `min(jobs, budget / C)` and `BufferPool::slots`
clamps at `POOL_DEPTH.max(jobs)`. Resident therefore saturates at
`180 MiB + jobs × C` and every byte above that is taken by nothing, at any
limit and on any machine — at 256 cores against a 128 GiB limit, ~15 GiB. A
number that provably never binds is worse than no number, because it reads as a
safety margin and is not one.

**What replaces it is a coupling, stated beside the clamp it depends on.** The
inertness rests on `slots()` clamping at `POOL_DEPTH.max(jobs)`, so a change
that unclamps it makes a large budget suddenly real; that is recorded in
[`../../design/architecture.md`](../../design/architecture.md), "Execution
model and API surface", where the clamp is, rather than hedged against by a
fraction guarding a change nobody has proposed.

**Three documents asserted the fraction and are corrected rather than
annotated.** `19.6`'s notes said the fraction ceiling is "the term that
actually bounds the process"; `19.12`'s said it "is now the term that binds"
and tabulated a largest-safe `f` per limit; `STATUS.md`'s `19.12` line said the
fraction stays a ceiling. All three are true only of a build whose plan
under-charges, and each now says so and points here. What survives from
`19.12`'s reading is the fit — `180 MiB + 59.4` a sub-stream, which `19.13`'s
constant comes from — and the floor problem, that below roughly a 300 MiB limit
no budget makes a twenty-four-worker compressed parse fit, the worker count
being the only lever that reaches the fixed term.

**The apparatus and the evidence move with it.** `measure.PARALLEL_BUDGET`
rises 1 GiB → 2 GiB in `19.14`, the old value no longer admitting the widest
row's twenty-four workers at a corrected charge, and both `parallel-*` figures
are re-taken in `19.11` — the phase's one measurement event, which is already
owed. And `19.15` gains a leg stating `--jobs` on a *plain* file: `KD18` prices
that shape at 8 MiB of arena retention a worker, reaching 209 MiB at
twenty-four, and no reading has ever put it against a real limit because every
reserve sitting ran at `-m 3g`. If it turns out a plain parallel scan simply
cannot run in a small cgroup, that promotes `KD18` from unowned to something
the phase says out loud.

## Within-stream chain uniformity is an encoder property, and `xz` can break it

**From `xz-seek`'s `7.1`, which is the slice that owed this message.** Their
bound rests on every block of a stream declaring the same LZMA2 dictionary as its
first. Traced to source, that holds because `liblzma`'s Stream encoders keep
**one** filter chain and re-use it for every block — the single-threaded one
points `block_options.filters` at a single array, the threaded one copies that
array into each worker. It is a property of the encoders, not of the `.xz`
format, which gives every block its own Filter Flags and constrains none of them
against its neighbours.

**And `xz` reaches the escape hatch.** `split_block()` calls
`lzma_filters_update()` whenever consecutive `--block-list` entries name
different `--filtersN=` chains, so

```sh
xz -T1 --filters1=lzma2:dict=1MiB --filters2=lzma2:dict=16MiB \
       --block-list=1:2MiB,2:2MiB,2:0 -c file > mixed.xz
```

writes one stream whose first block declares 1 MiB and whose later blocks declare
16 MiB, under `-T1` and `-T4` alike, and `xz -dc` round-trips it. Their entry is
`I23`.

**What this corrects here is one sentence, not the divisor.** The plan recorded
above says we inherit their deficiency "and `xz` writes no such file"; that half
is false, and `19.14`'s property paragraph must not repeat it. What is unchanged
is everything the divisor actually rests on: a first block's dictionary still
bounds its stream for every ordinary invocation, an understating bound is still a
clean `MemoryLimitExceeded` from their `memlimit` check rather than an overrun,
and the exact answer still costs a block-header read per block. The koji dump is
written by plain `xz` invocations, so neither koji file is in this shape.

**Their backend-state term is 33 KB, not the ~1 MiB the fit implied.** `I24`
measures one decoder's allocation beyond the declared dictionary at 32,928 B
under `liblzma` and 30,680 B under `xz4rust`, both chain-independent, taken by
counting every byte the library asks for through `lzma_stream`'s own allocator
hook. So `decode_footprint()` on the koji shape will come out at about
**9.03 MiB** — 8 MiB of dictionary, 1 MiB of chunk, and 33 KB — against the
~10 MiB `19.12`'s residual predicted. That is inside a ±10% four-point fit and
confirms the shape; what it says for `19.14` is that the compressed charge is
dictionary plus chunk and the backend term is rounding. Their `7.4` still owes
the RSS-delta measurement that confirms it against a live decode.

## The reserve's headroom is thin where variance is widest

**The no-fraction argument is about mean resident and says nothing about
variance, which is what a cgroup actually kills on** — it kills on one run's
peak, not on the median of three. `19.12`'s per-rep spreads, read off
`runs/measure-20260909T171423/raw.json` rather than the one cell its notes
quote, are **10.1%, 6.5%, 19.8% and 7.0%** across the compressed uncapped
leg's four cells: proportional to resident rather than a fixed jitter, the
absolute spread growing 27 MiB → 160 MiB across the axis.

A constant reserve leaves constant headroom against that. Under
`budget = limit − 256` with a corrected divisor:

| limit | budget | readers | resident | headroom |
|---|---|---|---|---|
| 512 MiB | 256 | 4 | 418 | 94 (18.4%) |
| 768 MiB | 512 | 8 | 655 | 113 (14.7%) |
| 1 GiB | 768 | 12 | 893 | 131 (12.8%) |
| 1.25 GiB | 1024 | 17 | 1190 | 90 (**7.0%**) |
| 1.5 GiB | 1280 | 21 | 1427 | 109 (**7.1%**) |
| 1.75 GiB | 1536 | 24 | 1606 | 186 (10.4%) |
| 2 GiB | 1792 | 24 | 1606 | 442 (21.6%) |

The band around 1.25–1.5 GiB is where the worker-count cap has not yet lifted
the headroom, and there the margin is below the median observed spread.

**It is accepted for now, with `19.15` as the named trigger.** Raising the
constant does not fix the shape — 20% at 1.8 GiB wants a ~540 MiB reserve,
which puts a 600 MiB cgroup below the floor — so the alternative is a
proportional term reintroduced for a *measured* reason rather than as the
unmeasured ceiling that was dropped. Taking it now would mean picking a number
from four cells of a diagnostic sitting on a build `19.14` is about to replace.
`19.15` runs at 256 MiB, 512 MiB and 1 GiB against the shipped rule; if the
headroom does not survive, the reserve reopens and the proportional term is
what it reopens to. The cost of that ordering is stated rather than hidden:
`19.15` follows `19.13`, so the rule ships before the check.

**Two smaller things settled with it.** The composition of discovery and the
source's recommendation is **not** a `min` — written that way, an unlimited
host takes `min(source, 64 MiB constant)` and goes serial again, which is the
case the recommendation exists for. It is
`environment_cap.map(|cap| want.min(cap)).unwrap_or(want)`, where the cap is
`None` when nothing was discovered. And below the reserve the arrangement is
*named* rather than emerging from three independent floors — `worker_count`'s
`.max(1)`, `slots()`' clamp to one, and `affordable()` refusing block decode:
the budget is one reader's worth on the streaming path, `19.9` tests it, and
the below-floor `PlanNote` says the allocation bound the scan.

## Unstated is not unlimited

**A cgroup limit is permission; a machine merely observed is not.** The posture
rule as first written said the defaults run as fast as the machine or the
cgroup permits, which quietly assumes the machine is ours. It is not: pgdq
shares this host, and early iterations of the parallel work OOMed it. So the
rule is amended and retitled — a default runs as fast as *the allocation*
permits — with the two cases explicitly asymmetric: **where a limit is
discovered the default fills it, and where none is, the default stays modest**
whatever the core count suggests.

**So the unlimited recommendation is `min(cores, 4) × C` — about 236 MiB.**
Without the cap `XzSource` would recommend `jobs × C`: ~1.4 GiB here and
~7.5 GiB on a 128-core host, an appetite sized from hardware nobody granted.
Four is the roadmap's own baseline count, it is what `POOL_DEPTH` already
delivers on a plain source, and it is well clear of the failure the cap exists
to avoid — four sub-streams rather than the single one a 64 MiB constant
admits — at roughly a sixth of what the host's core count would have taken.
Reading `MemTotal` as a last-resort cap was rejected: it reverses the going-in
refusal, owes a `runtime-invariants.md` entry, and answers the wrong question,
since total memory is not this process's memory on a machine it shares.

**`19.15` exercises the unlimited arm without an unbounded run**, for the same
safety reason. The `None` branch is a unit test over a fixture root carrying no
limit files — `19.9` builds that tree anyway for `RT4` — and the at-scale
reading uses a limit set high enough that the source's recommendation is what
binds, which reaches the same arithmetic outcome with a bounded blast radius.
Nothing in this phase runs pgdq unbounded on a shared machine.

**The premise under all of it: pgdq is expected to run in a container.** The
discovered-limit path is therefore the normal one and "no limit found" is an
anomaly rather than a second mode to tune for — a state in which nothing has
said what pgdq may take while it shares the host. That is why filling a
discovered limit is the default rather than an option, why the unlimited
recommendation is deliberately modest, and why the status line's
`(default: no limit found)` doubles as a configuration check: an operator who
expected a container and reads it has learned their allocation is not being
enforced.

**`19.15` becomes a gate rather than a follow-up.** Under the container premise
the 1.25–1.5 GiB band where the reserve's headroom falls to ~7% is an ordinary
allocation size, not a point on an axis, so a check that runs after `19.13`
ships runs behind the risk. It instead runs against a **scratch build** of the
rule before `19.13` lands — the pattern `19.2` used against a clamp-lifted
build and `19.6`/`19.12` used `--alone` — so `19.13` carries a constant this
phase has watched survive a real cgroup. `19.13`'s code is written first and
its box ticked second; the two stay separate slices, which is what
`../../process.md`'s warning about bundling a mechanism with its own evidence
asks for.

**Detecting a container was considered and rejected.** It is a weaker version
of the modest unlimited default rather than an addition to it: what binds a
process is the limit, not the namespace, and "was an allocation stated" is
already read completely and is right in all four combinations — container with
a limit, fill it; container without one, stay modest; bare host with a systemd
`MemoryMax`, fill it; bare host with nothing, stay modest. Container-ness
changes the answer only in the two middle rows and changes it wrongly in both.
As a diagnostic it is the incomplete-environment check this phase already
refused for the arena cap: `/.dockerenv` is docker's and absent under
containerd, and `/proc/self/cgroup` reads `0::/` in some containers and a real
path in others — on this host it reads
`0::/user.slice/user-1000.slice/…`. The sentence worth
saying needs no detection, because **no limit found already means no limit is
enforced**; `19.9` puts that in the status line.

## Fast by default, and the no-limit cap

**The default is fast, not safe** — filling a discovered allocation is the
point, and "safe" is a mode somebody might opt into rather than the posture the
defaults take. That retires the `min(cores, 4) × C` ≈ 236 MiB no-limit default
recorded earlier the same day: it caps a roomy twenty-four-core host at four
readers with nothing contended, and a constant cannot tell a 128-core server
with 256 GiB from a 128-core one with 8.

**The no-limit budget is `min(jobs × C, ½ × MemAvailable)`.** Because resident
saturates at `jobs × C`, the cap costs nothing wherever there is room — half of
this host's ~20 GiB available is ~10 GiB, which plans the same twenty-four
workers a 1.4 GiB budget does, everything above `jobs × C` being structurally
inert. It binds only on a machine too small to afford the count it asked for.
Fast where the machine allows it, bounded where it does not.

**`RT8` is what makes that a read rather than a guess**, and it was measured
rather than assumed: `/proc/meminfo` reports the **host's** memory inside a
container — a `-m 512m` container on this 32 GiB host reads `MemTotal
32774304 kB` and `MemAvailable 20043708 kB` while its own
`/sys/fs/cgroup/memory.max` correctly reads `536870912`. So free memory is
consultable **only** after `RT1`–`RT6` have established no limit binds;
consulted first it would target ~10 GiB against a 512 MiB allocation, on
precisely the deployment this project assumes. `MemFree` is unusable for a
second reason — it excludes reclaimable page cache and read 7.4× lower than
`MemAvailable` on an otherwise idle host — and *half* rather than all because
`MemAvailable` is an estimate that two processes reading at once each see the
whole of.

**This reverses the going-in refusal to size from physical memory, graded as a
reversal.** That refusal held while the fallback was a 64 MiB constant that
could not hurt anyone; the fallback now scales with the core count, so an
unbounded one sizes pgdq's appetite from hardware nobody granted. The register
entry is the price of reversing it.

**What "fast" does not reach is the reserve.** Fitting inside an allocation
somebody stated is correctness, not caution — being OOM-killed there is a
defect — so the reserve stays conservative and `19.15` stays a gate ahead of
`19.13` rather than a follow-up. Shrinking the reserve deliberately once
`19.15` has measured the margin is available; skipping the measurement is not.

**A safe mode is filed as a Future item rather than taken here.** Applying a
fraction to a *discovered* limit is a different intent from setting the
defaults correctly — it is for an operator who knows they share the cgroup —
and what it needs grilling about is what it composes with: an explicit
`--parallel-memory`, the reserve, and the below-floor path, where a fraction of
a small allocation lands immediately.

## `xz-seek`'s `decode_footprint()` is callable, and `19.14` is unblocked

**From `xz-seek`'s `7.4`, which is the slice that owed this message.**
`Reader::decode_footprint() -> u64` is on the reader, takes no argument, costs no
source read and no decode, and is the same number whatever range is read — so it
is asked once, in each constructor, before the reader is wrapped in
`Arc<Mutex<…>>`, and the `u64` is stored. No lock is taken on the advisory path
and none is needed. `19.14` no longer has to approximate the dictionary with an
8 MiB constant, which is the whole reason it was held.

**The number on the koji shape is 9,471,776 B** — 8 MiB of dictionary, 1 MiB of
chunk, 34,592 B of `liblzma` state — against the ~10 MiB `19.12`'s residual
predicted. The prediction is confirmed at the level it was made: the compressed
charge is dictionary plus chunk, and the backend term is 0.4% of it. Under
`xz4rust` the same file is 9,467,864 B.

**It is a very good estimate and not a sound ceiling**, and their register says
so in those words: a stream whose *later* block declares a larger dictionary than
its first is understated, which is their `KD10` and follows from `I23` above. A
stream whose first block header did not parse is charged the reader's `memlimit`
outright. The backstop is unchanged and unconditional — `memlimit` is compared
against each block's own declared dictionary before any backend object is built —
so an understating charge is a clean `MemoryLimitExceeded` naming the offset,
what was required and what was allowed, and never an overrun. The number that
cannot understate is still `-M` itself.

**What the doc comment on `Partitioning::partition_bytes` now says is false.** It
states that the dictionary is excluded from `RangePlan::footprint` and names
8 MiB a worker as the allowance. The first half is still true of *their plan* —
folding the footprint into `RangePlan` is their `7.5`, not yet landed — but the
8 MiB allowance is ours to stop asserting the moment `19.14` divides by the
published number instead. Theirs to land, ours to stop repeating.

**Their cache envelope's shape moved twice** while this was built:
`StreamEntry` gained `first_block_dict_size: Option<u64>`, so a persisted table
written by an older build must fail to deserialize rather than default. A
bincode failure and a `CACHE_FORMAT_VERSION` bump are two independent catches here and
neither has a per-field default path, so the price is a cold re-scan of the koji
dump — accepted knowingly when `P7` was specified.
