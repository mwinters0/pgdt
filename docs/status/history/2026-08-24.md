# 2026-08-24

## Spans are statement-anchored; the spec said object-anchored, and the fix is inheritance

Found during the end-of-phase grilling, by reading `pgdq info --map`'s actual
output against the spec's claims.

**The measurement.** `fixtures/16/objects/default.sql` produces **137 spans**:
16 `framing`, **52 bare `unparsed`**, and 69 carrying a TOC header. The 52 are
not junk — each is a follow-on statement of the object immediately before it:

```
[522, 613) SCHEMA objects
[613, 654) unparsed          ALTER SCHEMA objects OWNER TO postgres;
[3611, 3803) TEXT SEARCH CONFIGURATION simple_config
[3803, 3914) unparsed        ALTER … ADD MAPPING FOR asciiword …
[3914, 4007) unparsed        ALTER … ADD MAPPING FOR word …            (×20 more)
[16632, 16679) unparsed      ALTER EVENT TRIGGER objects_ddl_log DISABLE;
```

`map::Builder` returns to `Mode::Idle` on `statement_complete`, so the
governing header is dropped and the next statement opens a fresh `toc: None`
span. One `pg_dump` archive entry routinely emits several statements and
comments only the first.

**Two consequences.** The spec's "Span boundaries" section claimed span count
would equal object count plus framing — it does not, and cannot, because a TOC
entry is not one statement. And `index::toc_coverage_diagnostic`, which counts
header-*bearing* spans over total spans, therefore reports **69/137 ≈ 50% on a
healthy, fully-TOC'd real dump** — useless as the "this map is running
degraded" signal it exists to be.

**Decision: inherit, don't merge.** A follow-on statement keeps its own span
and inherits the governing entry's `TocHeader`; `Span::toc` becomes *the entry
this span belongs to*, with a separate record of whether the span carried the
header text. Merging follow-ons into the object's span would have made the
spec's original sentence true, but it reduces specificity — which the phase's
own "coverage increases monotonically" standing rule forbids — and discards
statement boundaries. Inheritance is enrichment, which that rule permits. Spec
amended in place: "Span boundaries", "TOC coverage", and the degradation claim
under "Two signals close a span".

**Two details that fall out of it.** `pgdq info`'s `object kinds:` breakdown
must switch to header-bearing spans, or inheritance double-counts every object
that has an owner statement — and that is the right reading anyway: it is an
object census, so the figure that was misleading as *coverage* is exactly
correct as a *census*, relocated rather than discarded. And
`Framing`/`Connect`/`VersionHeader` spans never inherit, so mid-file framing
is not attributed to the object before it.

**Not yet implemented.** This is a decision, not a landed change; it lands as
slice 3.3.1.

## I18's fixture gap is closeable, and the reason recorded for it was wrong

`STATUS.md` said a non-default tablespace fixture "needs filesystem access the
fixture generator doesn't have". It does have it:
`scripts/generate_fixtures.py` drives a throwaway per-version Postgres
container entirely through `sudo docker exec` (`start_container`, `createdb`,

Neither shape I18 claims exists in the fixture tree at all — `rg "Statistics
for Name:"` and `rg "Tablespace:"` both return nothing across all 96 files,
including the six v18 sets (`postgres:18.6-alpine` is in the routine set;

exactly the TOC-header parsing whose shapes 3.1.1 verifies, so a surprise in
the real `Tablespace:` output is much cheaper found first. The pre-wrap order
is 3.1.1 → 3.3.1 → M1+M2 → wrap.

## Out-of-band work gets a ledger, not a slice number

Phase 3 produced the project's first user-facing surface, and the first work
item that belongs to no phase: real users will try `pgdq info` and their
feedback will be a session's worth of CLI changes. Making those slices of
whatever phase happens to be open would stop a phase's checklist meaning "what
this phase committed to", and between phases there is nothing to append to.

The mechanism: a standing ledger in [`../../design/roadmap.md`](../../design/roadmap.md),
items numbered `M<k>`, **one terse line each** — the section grows for the life
of the project, so it is an index, never an account. No spec (no intent doc
existed) and no notes doc: the dated history entry *is* the notes, which is
sound only because out-of-band work is by definition not inherited by a later
phase — and where it turns out to be, the fact goes in that phase's inbox.
The admission rule carries the design: out-of-band means *changes no decision
any spec records, and fits one session*. Anything else goes back through
grilling → spec amendment → slice. Written into
[`../../process.md`](../../process.md) as well, since it is a process
mechanism rather than a `pgdump_query` fact.

First three items, all to land before Phase 3 wraps. **M1**, refusing a cache
that does not cover the whole file; **M2**, printing
`DumpIndex::diagnostics` — which today means a tiling failure on real input is
entirely silent; both are already in `STATUS.md`'s known gaps, and they share
one review cycle. **M3**, a synthetic `INSERT`-run throughput measurement on
the SSD, on the model of 3.6's large-object bench: the phase claims the scan
walks only schema-sized regions *for every* `pg_dump` output, and the
`--inserts` half of that claim has never been measured. M3 is also the
admission rule's first real test — a confirming number changes no decision, a
bad one earns `INSERT` runs a scanner-level path, which does, and escalates
the item to a slice.

## Slice 3.2.1 was mis-sized

3.2.1's spec row bundled two changes of different confidence. Landed as
scoped: `DumpIndex::spans` as the primary structure (`blocks()`/`blocks_for`
derived, `Span::Data` holding `CopyBlock` inline), the cache format storing
spans (format version 2 → 3), `build_index` producing spans in its existing
scan pass by driving `map::Builder` directly instead of `build_map` costing a
second pass, and `scan_preamble`/`preamble_only` producing a real
`SpanBody::Unscanned` tail for the one genuinely partial scan that exists
today. See `docs/design/roadmap-phase3-object-inventory-notes.md`.

Split out as 3.2.1.1: `DumpMetadata` as a derived view over `spans`, and
`crate::stream::table_stream`'s live segment classifying the DDL between
discovered blocks so a query-built `DumpIndex` tiles the way `build_index`'s
does. Both pieces turned out to need real design work, not just plumbing,
once inside the slice — see the next section for how 3.2.1.1 itself then
split again over exactly this distinction.

Recorder's interim state (each live-discovered block recorded as its own
`Span::Data`, with no span for the DDL between them) does not tile — accepted
for now since nothing yet reads a non-`Data` span back out of a query-built
`DumpIndex`; `check_tiling` is exercised only against `build_index`'s output
(always a full scan) until 3.2.1.2.1 lands.

## Slice 3.2.1.1 was mis-sized the same way

Scoped as landed above, 3.2.1.1 still bundled `DumpMetadata`'s derived-view
rework with `stream.rs`'s live-segment DDL classification. The first turned
out self-contained and fully verifiable: `SpanBody` needed three new variants
(`Connect`, `VersionHeader`, `AlterTypeAddValue`) to carry what `Framing`/
`Unparsed` couldn't, and `dump_metadata_from_spans` mirrors the deleted
`PreambleBuilder`'s state machine exactly, keyed on span kinds instead of
line prefixes — checked by running it against `PreambleBuilder`'s own output
across every fixture (96 files) plus `edge_cases.sql` before deleting
`PreambleBuilder`, which is what made the deletion safe rather than a leap of
faith. See `docs/design/roadmap-phase3-object-inventory-notes.md`.

The second piece surfaced a real blocker, not just risk: `stream.rs`'s
`Recorder` persists progress after *every* completed block (so a caller that
stops polling partway through still keeps what it saw), but `map::Builder::finish`
consumes `self` and can only produce spans once, at true end of scan. Wiring
`map::Builder` into the live segment for real tiling needs a non-consuming
"spans so far" capability that doesn't exist yet — a design gap, not a
review-confidence gap, and a stronger reason to split than 3.2.1.1's own
split from 3.2.1 was. Moved to 3.2.1.2.

## Slice 3.2.1.2 was mis-sized the same way again

Scoped as landed above, 3.2.1.2 still bundled the `map::Builder` capability
(`snapshot`) with wiring it into `stream.rs`. The capability turned out
self-contained and directly testable against `Builder`'s existing state
machine on its own: `push_span` fixing up the previous span's `end` at push
time (rather than deferring every span's `end` to `finish`'s single
end-of-scan pass) is what makes a non-consuming snapshot possible, and
`snapshot` is provably sound at any boundary where `mode` is `Idle` — which
`on_copy_end` always leaves it at. This settles the previous round's open
question: the capability belongs on `Builder` itself, not as a change to
`Recorder`'s per-block persistence model.

Wiring it into `stream.rs`, by contrast, is a rework of an already-tested
core path (resume tokens, ambiguous-table detection, `Recorder`). Moved to
3.2.1.2.1 — whose scope then changed; see below.

## Interleaving map-building with row emission is the thing to stop doing

3.2.1.2.1 was originally scoped as "feed the live segment's events to a
`map::Builder` and splice its snapshot in". Every hard question that scoping
produced turned out to be a consequence of the interleaving itself, so the
slice was rewritten to remove the interleaving instead of to reconcile it.
The decision is in
[`../../design/roadmap-phase3-object-inventory.md`](../../design/roadmap-phase3-object-inventory.md),
"Mapping and streaming are separate passes"; the evidence is here.

**The unmapped hole is real, but it is schema-sized, not arbitrary.** A
`Recorder` persists after *every* completed block, matching or not, so a live
segment's frontier advances block by block. When a caller pauses mid-block-K,
the frontier is block-(K−1)'s `end_offset` and the unmapped region is
`[frontier, header_offset_K)` — the DDL gap between two adjacent blocks, which
this phase's own cost argument already assumes is schema-sized. An earlier
reading of this put the frontier back at `preamble_end` (which would have made
the hole arbitrarily large, up to hundreds of GB on koji) and that is wrong.

**But the hole exists at all only because a `yield` beats the recorder to the
punch.** Row batches are flushed inside the `Row` and `CopyEnd` arms, and the
generator suspends at the `yield` *before* `rec.record`/`rec.persist` run at
the end of the `CopyEnd` arm. So a caller that takes a token and drops the
stream leaves the just-finished block unrecorded — reachable even when the
token's offset is exactly a block's `end_offset`, not only mid-block.

**A resume offset is only ever one of two things**, which is what makes the
alternative tractable: tokens are captured only at a batch flush, and flushes
happen only in the `Row` and `CopyEnd` arms, so the offset is either
mid-`COPY`-block or exactly some block's `end_offset`. Where the region below
it is already mapped, splicing needs no synthetic `CopyStart` — anchoring the
builder's floor at the *containing span's* `end` works, because the events
between the token offset and that end are `Row`s (ignored) and one `CopyEnd`
(a no-op with no `pending_data`). It is only the unmapped case that needs
repair, and repairing it silently produces a non-tiling cache rather than an
error.

**A cold query already costs a full scan.** `Segment::Live` is built with
`seg_end = size`, so a cold `table_stream` walks to EOF even after the queried
block has been drained — "the table I want is the first one in a 1TB file"
costs 1TB today. Bounding a cold query to `[0, target.end_offset)` is a
separate decision from the split and is taken with it.

**I2 was false, and it is what the stop rule turns on.** It claimed a
schema-qualified name owns at most one `COPY` block per dump, several blocks
under one name coming only from concatenation. Its proof was about `TABLE
DATA` *archive entries* (one per table — still true) and missed that
`dumpTableData()` writes the header from the **root** table's name whenever
load-via-partition-root applies. Probed against a live server with pg_dump
16.15 and **no flags**: a table hash-partitioned on an enum column produces
two `COPY public.feelings` headers, because `forcePartitionRootLoad()` turns
the mode on by itself for that partitioning scheme. Rewritten in
[`../../design/postgres-invariants.md`](../../design/postgres-invariants.md); a
compatibility-matrix row and the corollaries went in with it: the TOC entry
names the partition while the header names the root, a `-- load via partition
root` marker line sits between them, and — the one that closes off the
appealing cheap fix — **the blocks are not contiguous.** Reading forward from
one matching block until the next block names a different table does not
enumerate a name's blocks, because `DOTypeNameCompare()` sorts `TABLE DATA`
entries by the *partition's* own name, so any unrelated table sorting between
two partition names is emitted between their blocks (observed, flagless:
`feel_a` → `COPY public.feel`, `feel_m` → `COPY public.feel_m`, `feel_z` →
`COPY public.feel`). Only reaching EOF enumerates them. The marker itself
survives `--no-comments`, `--data-only` and `--inserts`, which is what makes
it usable as a "there are more blocks under this name" signal.

**The marker is what makes an early stop safe, so it lands as data.** A cold
query stops when the queried table's block closes, unless that block carried
`-- load via partition root`, in which case it runs to EOF. `CopyBlock` gains
`partition_root: Option<String>` rather than `stream.rs` sniffing the line
itself: the marker is something the dump said, so it belongs in L1's stored
vocabulary, and persisting it means a warm cache answers without re-reading.
The fixture goes in a **new** `fixture_schema_partitions.sql` under
`{default, --load-via-partition-root}` rather than being folded into
`objects`, so the twelve existing `objects` fixtures don't churn; all six
routine majors have `forcePartitionRootLoad`, so the `default` set produces
the multi-block shape on every one of them.

**The interleaved form is deferred, not rejected.** `ResumeToken` is opaque
and process-local, so it could carry the live segment's in-flight spans and
open `CopyStart`, closing the hole with no repair and keeping single-read
streaming. Filed under `roadmap.md`'s "Future — wanted, unscheduled" to
revisit once the feature set is settled, rather than optimized for now.

## A pre-existing `pgdq info` cache-trust bug, found incidentally

`Command::Info` (no `--preamble-only`) trusts any cache `CacheMode::load`
returns and never checks whether it actually covers the whole file: running
`pgdq info <file> --preamble-only` followed by `pgdq info <file>` prints the
preamble-only cache's `DumpMetadata` (correct) but zero `COPY` blocks
(wrong) instead of running `build_index`'s full scan. Reproduced against
`main` before this slice's changes (`git stash`), so it predates Phase 3.2.1
and isn't part of its contract — recorded in `STATUS.md`'s "Known gaps" for
a future slice to fix (likely: compare `scanned_through` against the source
size before trusting a loaded cache as complete).

## The diagnostic vocabulary is a scale, not a type

The phase spec asked for one `Diagnostic` carrying a severity and a kind, so
that the per-column resolution outcomes, the cache-identity warning, the
TOC-coverage figure and an unrecognized span would all speak one vocabulary.
Building it showed the sentence cannot be satisfied literally: `DumpIndex` is
L1, `resolve::ColumnResolution` is an L2 conclusion about PostgreSQL type
semantics, and a `DiagnosticKind` variant carrying one would have L1 name an
L2 type. The alternatives are worse — moving `ColumnResolution` down to L1
contradicts L1's "parses a declared type as an opaque string and never
interprets it", and flattening the column payload into a rendered string
trades structure `pgdq info` needs for a uniformity nothing consumes yet.

What is actually shared between the two is the **severity scale**, so that is
what got shared. `diagnostic::Diagnostic` (L1) is the file-level channel;
`resolve::ColumnNote` (L2) is the per-column record. Spec amended in place.

Two things fell out of doing it, both worth keeping:

- **The L2 type was misnamed.** There is one per column, always, and the
  ordinary case is a column that resolved cleanly — that is a record, not an
  exception report, and the field holding it was already called `notes`. It
  also forced the file-level type to be exported as `FileDiagnostic`, which
  had the aliasing backwards. `ColumnNote` fixes both.
- **Severity is derived, not stored.** It is a pure function of `resolution`,
  so a stored field would be the same fact in two places — the thing this
  project rejects for `DumpMetadata` (a view over spans) and `blocks()` (a
  filter, not a field). It is a method. A note whose severity is *not*
  derivable earns a field when one exists.

Unifying at the drain point stays open and is where it belongs: the Phase 6
caller-supplied sink can take both types.

## Slice 3.6 is complete; the koji regression scan finished confounded by disk contention

The detached re-scan launched earlier this day (`pgdq-koji-3.6`) finished
`exit=0`: 74 `COPY` block(s), 19,575,829,920 row(s), 784,019,857,152 bytes
scanned — byte-for-byte identical to the pre-3.6 baseline
(`docs/status/history/2026-08-22.md`), including every block's offsets. That
identity is the regression check's real evidence, because the raw throughput
figure turned out not to be a clean comparison: wall time gives ~110MB/s
against the baseline's 243MB/s.

`node_exporter`'s Prometheus history (`instance="cid.snowshoe-chicken.ts.net:9100"`,
`device="sdb"`, the physical disk under `/mnt/wd12t`) shows why. During the
3.6 scan window, `node_disk_read_bytes_total` sustained ~120-130MB/s (matching
the wall-clock figure) while `node_disk_written_bytes_total` simultaneously
sustained ~30MB/s of *writes* to the same disk — traffic entirely absent
during the 2026-08-22 baseline window. `sdb`'s `node_disk_io_time_seconds_total`
shows ~93-95% busy in both windows, so the disk itself wasn't idle either
time; the 3.6 run was sharing a near-saturated HDD with an unrelated writer,
which costs far more in seek overhead on a single spinning disk than the raw
byte split suggests. `koji-pg`'s own container logs for the same interval
show why: a Postgres restore running against `/mnt/wd12t/fedora/koji/pgdata`
(same physical disk as the koji dump file), checkpointing every 10-25 seconds
at `distance=~540MB` each time — confirmed directly by the maintainer
mid-session as an active restore on the HDD.

Read together — identical scanned output down to the byte, an unchanged
control-flow argument (this slice's code touches only the DDL *between*
blocks, not `COPY`-block parsing itself), and a root-caused confound on the
one number that moved — slice 3.6 is recorded as a clean pass in
`STATUS.md`, with the confound and reasoning also flagged under "Decisions
worth another look" since the throughput figure itself was never
re-measured cleanly. Full writeup:
`docs/design/roadmap-phase3-object-inventory-notes.md`,
"Verification".

Code and tests for the `Data`-span fast path (`INSERT` runs,
`crate::map::DataBlock::InsertRun`; the large-object region,
`crate::map::DataBlock::LargeObjects` plus a new `crate::scan::CopyScanner`
state that skips it unread) are in, all pre-existing tests still pass
unchanged beyond the `SpanBody::Data` payload type, and the synthetic
large-object measurement is done — see
`docs/design/roadmap-phase3-object-inventory-notes.md` for what
landed and why the large-object merge rule needed less machinery than the
phase spec's prose ("walking past every consecutive `BLOB METADATA`/`BLOBS`
TOC header") suggested: I12's priority-band proof (`pg_dump_sort.c`) already
guarantees nothing but another `BLOBS` entry can arrive between two of a
file's large-object data entries, so "no span was pushed since the last
`COMMIT;`" is the whole merge condition — no re-inspection of each entry's
own `Type:` field needed. `docs/design/postgres-invariants.md`'s I12 entry
and `docs/design/pg-dump-compatibility.md`'s large-objects/`--inserts` rows
were updated to match.

The synthetic large-object measurement (the phase's other gating
measurement) is done: `scripts/generate_large_object_bench.py`
generated a 3GB `BEGIN;`/`lo_open`/`lowrite*`/`lo_close`/`COMMIT;` region at
`/mnt/ssd/fedora/pgdump_query-bench/large_object_bench.sql` (kept, not
committed — regenerate with `--seed 42` for the same bytes). `pgdq info
--verbose --cache-path none` against it, in a 512MB-limited container:
~1.6-1.7s wall time twice in a row, ~1.9GB/s — an order of magnitude above
the 243MB/s `COPY`-decode baseline, which itself does real decode work this
pure line-skip doesn't. That gap, plus the run completing at all inside a
512MB memory limit, is the "skipped, not walked" evidence: walking the
region statement-by-statement (the pre-3.6 behavior) would mean one
`Unparsed` span *and one stored text string* per `lowrite` call — several
hundred thousand of them for a region this size.

## Slice 3.1.1 landed; the flag this project called `--with-statistics` does not exist

Real fixtures now exist for the three shapes I18/I19 had only read from
source: a non-default tablespace (`objects.tablespaced_table`, via
`generate_fixtures.py`'s new `prepare_tablespace_dir` — `docker exec ...
mkdir`/`chown` the `CREATE TABLESPACE` directory before the schema SQL runs),
a solo `REVOKE` (`objects.no_public_execute()`'s default-PUBLIC-`EXECUTE`
revoke, the one ACL shape whose diff needs no offsetting `GRANT`), and
`TOC_PREFIX_STATS` (`fixtures/18/objects/stats.sql`, a new version-gated
`objects/stats` flag set, v18 only).

Generating the last one required finding the actual flag, and `pg_dump.c`'s
long-option table has no `--with-statistics` in any version 13-18 — the real
flag is `--statistics` (`{"statistics", no_argument, NULL, 22}`). Every prior
reference to `--with-statistics` in this project (the phase spec's slice
table, I18, `STATUS.md`, the fixture schema's own header comment) was wrong
in the same way, presumably a guess extrapolated from `--no-statistics`
rather than checked against source. Corrected in `postgres-invariants.md`,
`pg-dump-compatibility.md`, `map.rs`'s doc comments, and
`roadmap-phase3-object-inventory-notes.md`; the phase spec's own prose
is left as originally written, since this is a factual correction rather
than a design decision changing. `map::parse_toc_header_line` still doesn't
recognize `TOC_PREFIX_STATS` — that was always a deliberate deferral, not
something this fixture-only slice was scoped to close, and the new fixture
tiles correctly as an ordinary unattributed span either way. Full writeup:
`docs/design/roadmap-phase3-object-inventory-notes.md`.
