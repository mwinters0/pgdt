# 2026-08-24

## Slice 3.2.1 was mis-sized

3.2.1's spec row bundled two changes of different confidence. Landed as
scoped: `DumpIndex::spans` as the primary structure (`blocks()`/`blocks_for`
derived, `Span::Data` holding `CopyBlock` inline), the cache format storing
spans (format version 2 → 3), `build_index` producing spans in its existing
scan pass by driving `map::Builder` directly instead of `build_map` costing a
second pass, and `scan_preamble`/`preamble_only` producing a real
`SpanBody::Unscanned` tail for the one genuinely partial scan that exists
today. See `docs/design/roadmap-phase3.2.1-span-wiring-notes.md`.

Split out as 3.2.1.1: `DumpMetadata` as a derived view over `spans`, and
`crate::stream::table_stream`'s live segment classifying the DDL between
discovered blocks so a query-built `DumpIndex` tiles the way `build_index`'s
does. Both pieces turned out to need real design work, not just plumbing,
once inside the slice — see the next section for how 3.2.1.1 itself then
split again over exactly this distinction.

Recorder's interim state (each live-discovered block recorded as its own
`Span::Data`, with no span for the DDL between them) does not tile — accepted
for now since nothing yet reads a non-`Data` span back out of a query-built
`DumpIndex`; `check_tiling` is exercised only against `build_index`'s output
(always a full scan) until 3.2.1.2.1 lands.

## Slice 3.2.1.1 was mis-sized the same way

Scoped as landed above, 3.2.1.1 still bundled `DumpMetadata`'s derived-view
rework with `stream.rs`'s live-segment DDL classification. The first turned
out self-contained and fully verifiable: `SpanBody` needed three new variants
(`Connect`, `VersionHeader`, `AlterTypeAddValue`) to carry what `Framing`/
`Unparsed` couldn't, and `dump_metadata_from_spans` mirrors the deleted
`PreambleBuilder`'s state machine exactly, keyed on span kinds instead of
line prefixes — checked by running it against `PreambleBuilder`'s own output
across every fixture (96 files) plus `edge_cases.sql` before deleting
`PreambleBuilder`, which is what made the deletion safe rather than a leap of
faith. See `docs/design/roadmap-phase3.2.1.1-metadata-derived-view-notes.md`.

The second piece surfaced a real blocker, not just risk: `stream.rs`'s
`Recorder` persists progress after *every* completed block (so a caller that
stops polling partway through still keeps what it saw), but `map::Builder::finish`
consumes `self` and can only produce spans once, at true end of scan. Wiring
`map::Builder` into the live segment for real tiling needs a non-consuming
"spans so far" capability that doesn't exist yet — a design gap, not a
review-confidence gap, and a stronger reason to split than 3.2.1.1's own
split from 3.2.1 was. Moved to 3.2.1.2.

## Slice 3.2.1.2 was mis-sized the same way again

Scoped as landed above, 3.2.1.2 still bundled the `map::Builder` capability
(`snapshot`) with wiring it into `stream.rs`. The capability turned out
self-contained and directly testable against `Builder`'s existing state
machine on its own: `push_span` fixing up the previous span's `end` at push
time (rather than deferring every span's `end` to `finish`'s single
end-of-scan pass) is what makes a non-consuming snapshot possible, and
`snapshot` is provably sound at any boundary where `mode` is `Idle` — which
`on_copy_end` always leaves it at. This settles the previous round's open
question: the capability belongs on `Builder` itself, not as a change to
`Recorder`'s per-block persistence model.

Wiring it into `stream.rs`, by contrast, is a rework of an already-tested
core path (resume tokens, ambiguous-table detection, `Recorder`). Moved to
3.2.1.2.1 — whose scope then changed; see below.

## Interleaving map-building with row emission is the thing to stop doing

3.2.1.2.1 was originally scoped as "feed the live segment's events to a
`map::Builder` and splice its snapshot in". Every hard question that scoping
produced turned out to be a consequence of the interleaving itself, so the
slice was rewritten to remove the interleaving instead of to reconcile it.
The decision is in
[`../design/roadmap-phase3-object-inventory.md`](../design/roadmap-phase3-object-inventory.md),
"Mapping and streaming are separate passes"; the evidence is here.

**The unmapped hole is real, but it is schema-sized, not arbitrary.** A
`Recorder` persists after *every* completed block, matching or not, so a live
segment's frontier advances block by block. When a caller pauses mid-block-K,
the frontier is block-(K−1)'s `end_offset` and the unmapped region is
`[frontier, header_offset_K)` — the DDL gap between two adjacent blocks, which
this phase's own cost argument already assumes is schema-sized. An earlier
reading of this put the frontier back at `preamble_end` (which would have made
the hole arbitrarily large, up to hundreds of GB on koji) and that is wrong.

**But the hole exists at all only because a `yield` beats the recorder to the
punch.** Row batches are flushed inside the `Row` and `CopyEnd` arms, and the
generator suspends at the `yield` *before* `rec.record`/`rec.persist` run at
the end of the `CopyEnd` arm. So a caller that takes a token and drops the
stream leaves the just-finished block unrecorded — reachable even when the
token's offset is exactly a block's `end_offset`, not only mid-block.

**A resume offset is only ever one of two things**, which is what makes the
alternative tractable: tokens are captured only at a batch flush, and flushes
happen only in the `Row` and `CopyEnd` arms, so the offset is either
mid-`COPY`-block or exactly some block's `end_offset`. Where the region below
it is already mapped, splicing needs no synthetic `CopyStart` — anchoring the
builder's floor at the *containing span's* `end` works, because the events
between the token offset and that end are `Row`s (ignored) and one `CopyEnd`
(a no-op with no `pending_data`). It is only the unmapped case that needs
repair, and repairing it silently produces a non-tiling cache rather than an
error.

**A cold query already costs a full scan.** `Segment::Live` is built with
`seg_end = size`, so a cold `table_stream` walks to EOF even after the queried
block has been drained — "the table I want is the first one in a 1TB file"
costs 1TB today. Bounding a cold query to `[0, target.end_offset)` is a
separate decision from the split and is taken with it.

**I2 was false, and it is what the stop rule turns on.** It claimed a
schema-qualified name owns at most one `COPY` block per dump, several blocks
under one name coming only from concatenation. Its proof was about `TABLE
DATA` *archive entries* (one per table — still true) and missed that
`dumpTableData()` writes the header from the **root** table's name whenever
load-via-partition-root applies. Probed against a live server with pg_dump
16.15 and **no flags**: a table hash-partitioned on an enum column produces
two `COPY public.feelings` headers, because `forcePartitionRootLoad()` turns
the mode on by itself for that partitioning scheme. Rewritten in
[`../design/postgres-invariants.md`](../design/postgres-invariants.md); a
compatibility-matrix row and the corollaries went in with it: the TOC entry
names the partition while the header names the root, a `-- load via partition
root` marker line sits between them, and — the one that closes off the
appealing cheap fix — **the blocks are not contiguous.** Reading forward from
one matching block until the next block names a different table does not
enumerate a name's blocks, because `DOTypeNameCompare()` sorts `TABLE DATA`
entries by the *partition's* own name, so any unrelated table sorting between
two partition names is emitted between their blocks (observed, flagless:
`feel_a` → `COPY public.feel`, `feel_m` → `COPY public.feel_m`, `feel_z` →
`COPY public.feel`). Only reaching EOF enumerates them. The marker itself
survives `--no-comments`, `--data-only` and `--inserts`, which is what makes
it usable as a "there are more blocks under this name" signal.

**The marker is what makes an early stop safe, so it lands as data.** A cold
query stops when the queried table's block closes, unless that block carried
`-- load via partition root`, in which case it runs to EOF. `CopyBlock` gains
`partition_root: Option<String>` rather than `stream.rs` sniffing the line
itself: the marker is something the dump said, so it belongs in L1's stored
vocabulary, and persisting it means a warm cache answers without re-reading.
The fixture goes in a **new** `fixture_schema_partitions.sql` under
`{default, --load-via-partition-root}` rather than being folded into
`objects`, so the twelve existing `objects` fixtures don't churn; all six
routine majors have `forcePartitionRootLoad`, so the `default` set produces
the multi-block shape on every one of them.

**The interleaved form is deferred, not rejected.** `ResumeToken` is opaque
and process-local, so it could carry the live segment's in-flight spans and
open `CopyStart`, closing the hole with no repair and keeping single-read
streaming. Filed under `roadmap.md`'s "Future — wanted, unscheduled" to
revisit once the feature set is settled, rather than optimized for now.

## A pre-existing `pgdq info` cache-trust bug, found incidentally

`Command::Info` (no `--preamble-only`) trusts any cache `CacheMode::load`
returns and never checks whether it actually covers the whole file: running
`pgdq info <file> --preamble-only` followed by `pgdq info <file>` prints the
preamble-only cache's `DumpMetadata` (correct) but zero `COPY` blocks
(wrong) instead of running `build_index`'s full scan. Reproduced against
`main` before this slice's changes (`git stash`), so it predates Phase 3.2.1
and isn't part of its contract — recorded in `STATUS.md`'s "Known gaps" for
a future slice to fix (likely: compare `scanned_through` against the source
size before trusting a loaded cache as complete).
