# 2026-09-05

## 7.16's residual is admitted as 7.17, and its stated closure path was wrong

The review of 7.16's "Decisions worth another look" entry settled three things:
the +3.8% array-render residual is closed rather than filed as a property, the
closure named in 7.16's notes was aimed at the wrong structure, and the work is
scoped to the array arm alone.

**The residual is larger than the number it was reported as.** The entry read
the +3.8% as the wrapper split — an element passing through `render_field` and
then `render_field_into` where one function used to do. Reading the arm itself
says the split is the smaller part of it. `render_field_into`'s `Array` arm is
`out.push_str(&render_array(column, row, child)?)`, so an array-bearing row pays
a `String` per element, the `Vec` collecting them, a whole-array `String` that
`nested::render_array` starts at `String::new()` and grows by `push_str`, and
then a copy of the finished text into the caller's buffer. That
un-presized-`String` growth is the same pathology 7.16 diagnosed and fixed in
`push_padded` and in `render_field`'s wrapper; the array path kept it. What
makes it worth a row rather than a property is where the mass is:
`projection-widths` prices the two array columns at **+13.21 µs a row**, 93% of
what all three nested columns cost together and more than every scalar column in
that table.

**The `Cow` is not the lever, and reshaping it would have cost the decode
reading.** 7.16's notes named the closure as reworking `nested::ArrayLiteral` so
an element need not own its text. `batch::collect_array` fills `elements` with
`render_field(..)?.map(Cow::Owned)` — unconditionally owned, because it renders
an Arrow value rather than slicing a literal — so the lifetime that arm carries
does no work on the render path at all. It does work on the decode path, which
is what `measurements.md`'s "Nested decode costs what it copies" measures at the
77 ns / 48 ns per-element split, so a session following the notes as written
would have reworked the structure holding a published reading in order to buy
nothing. Both the notes and `architecture.md`'s "The nested literal codec" now
say the borrow serves decode only. The shape that does close it is to not build
an `ArrayLiteral` on the render side: write each element through
`render_field_into` while walking the Arrow list, against a scratch buffer
reused across elements — a scratch is required rather than incidental, because
`push_token` decides quoting from the finished element text.

**The scope is the array arm, on evidence rather than symmetry.** All five
nested arms stop at the same boundary — `Multirange` builds a `Vec<String>` and
joins it, `Record` and `Range` build their literals and push the rendered text,
`Int2Vector` likewise — so the fix has an obvious generalisation and the
generalisation is not admitted. `projection-widths` prices the whole composite
column at **+0.98 µs a row**, decode, build and render together, and the other
three render one value a row against the arrays' fifty. 7.17 takes whichever of
the four fall out of the same shape at no extra risk and promises a measurement
for arrays only; "push the sink through every nested form" would be a refactor
with a measured win on one arm and hope on four.

7.17 runs ahead of `7.12` under the standing rule already in the phase spec —
any row admitted after spec time against a typed-query profile does — and owes a
control that renders nothing, which is `parse`: 7.16 established that a
`strings` query reaches `render_field` for its sixteen text columns, so 7.15's
control cannot serve a render-path row.

## The census-off binary is apparatus, and nothing was checking its age

**It was 40 commits stale when the sweep's preflight found it.**
`runs/pgdq-nocensus` dated from 2026-09-03, before 7.6, 7.7.1, 7.9, 7.10,
7.13, 7.13.1, 7.14, 7.15, 7.16 and 7.17. `census-brace-free` and
`census-arrays` compare it against a freshly built `target/release/pgdq`, so
the sweep would have attributed every one of those slices to the census —
`census-arrays` is already the cell that is wrong by a factor of six, and this
would have been a second, larger error in the same table with no signal
distinguishing it. It is rebuilt at `f5768e7` from the recipe in
[`../../design/measurements.md`](../../design/measurements.md) ("The census-off
binary is a source patch"), `map.rs` reverted, and checked two ways: the two
binaries differ, and a `parse` of `fixtures/16/types/default.sql` writes a
smaller cache under the patched one.

**Why nothing caught it is a gap in the apparatus, not in the discipline.** The
harness deliberately refuses to build that binary — a source patch no harness
should perform — but it also records nothing about which source the binary it is
handed came from, where every *generated input* carries a `.stamp` naming its
generator revision. The two halves do not have to move together: refusing to
build it and refusing to trust an unstamped one are different rules, and taking
the second costs a stamp file and a comparison. That is `M56`, admitted with
`Blocks` empty because the binary in the tree is correct today and the pending
sweep can be taken against it.

## The koji section is outside the figure register, and only its prose said so

Both of the day's "Decisions worth another look" entries were about the koji
section, and the first one's premise did not hold. It asked whether a
deliberately disqualified wall-clock reading belongs "in the figure register" —
but koji is not in the register and cannot enter it. There are seventeen
`<!-- figure: … -->` markers and seventeen figures, none of them koji;
`--check` never sees the section, `--stale` cannot name a reading in it, and no
figure's `quoted_by` reaches it. The harness prints koji's invocation and never
runs it, which is exactly the standing `measure.py` gives the profiling recipe
and says so in its own comment.

Sharper still: the section's existing headline numbers already fail the doc's
**first** standing rule, "every figure is a ratio, never a disk throughput".
The ~238–243 MB/s rows are disk throughputs with no `cat`-to-`/dev/null` floor,
which that prose admits. So the 62.7-minute reading is not an intrusion into a
clean register — it is the fourth non-figure in a section made of them, and the
first to carry its own disqualification in writing. The call stands, and the
reasoning is now filed at the section itself rather than only here, together
with the rejected alternative of withholding the number.

What the entry did stumble onto without naming is a real defect: the exclusion
lives in one prose sentence eleven paragraphs from the numbers, while the
document's preamble asserts "every figure below was taken by `scripts/measure.py`"
over a section that was not. Every *figure* announces itself with a marker and an
apparatus line; a section outside the register announces itself with nothing.
Admitted as `M57` — a declared marker, `--check` asserting such a section carries
no figure marker, and the preamble scoped to what the register holds.

The third thing settled here is smaller and lands with this closure: the
disclaimer pointed the reader at ~241 MB/s as the reference, and that number is
musl's (the pre-2026-09-05 runs are `postgres:16-alpine`; this one is
`postgres:16`), predates eleven P7 slices, and was taken uncontended. So the
paragraph instructed a difference across exactly the boundary the paragraph above
it declares uncrossable. It now names all three boundaries in the same breath as
the comparison, which also stops the *next* glibc run being read as a regression
against musl.

## The RSS row was resting a design claim on the input least able to test it

The second entry offered "capture peak RSS in `--koji-recipe`, or strike the
row". Both options were too narrow.

**Striking is not available.** The ~9 MiB figure has four live consumers and
none of them is a passing mention: `architecture.md`'s double-buffered-readahead
rejection rests on "the flat ~9 MiB RSS this design is built on", `M55`'s bound
is "64 MiB against the ~9 MiB above", and `roadmap-P7-scan-performance.md` and
`roadmap-P7.8.1`'s notes lean on it four more times. Nothing protects them,
because a non-figure has no `quoted_by` edge.

**And the row is wrong on a second axis nobody named.** 7.13.1's notes already
recorded it — "`measurements.md`'s koji row … is now overstated by about a
megabyte. It is a figure, so it is not edited here: 7.12's koji regression run is
what re-takes it." The re-take was written down, aimed at the run that has now
happened, and that run could not take it: the recipe captures no memory figure at
all. So the row is simultaneously musl's *and* a megabyte high, and its designated
correction failed silently.

The answer is to move the claim rather than re-take it where it sits. The row
bundles two assertions — nothing accumulates per byte, nothing accumulates per
block — and this document's own standing rule says koji cannot test the second,
being byte-rich and block-poor at 74 blocks over 784 GB. Both halves are cheap on
inputs the harness already stages: a 3.00 GiB `parse` for the first (7.13.1
already has 6.0 MB), the 4000-block generated input for the second. As a
registered figure the claim acquires a `depends` edge on `io.rs` that goes red
when the read path moves, which is the mechanism whose absence let it go a
megabyte wrong for a full slice.

Two instrument facts, found rather than assumed. The container cgroup's
`memory.peak` exists on this kernel but is the **wrong instrument** — it is
charged the page cache of a 784 GB read, so it reports the 512 MB limit, not the
process. `VmHWM` in `/proc/<pid>/status` is the right one: `pgdq` is PID 1 by the
recipe's `exec`, `nerdctl inspect -f '{{.State.Pid}}'` gives the host pid, and
the kernel maintains the high-water mark, so one read before exit covers
everything up to it — and it adds nothing to the `exec`'d command, leaving all
three load-bearing recipe details untouched. The 2026-09-05 container has since
exited, so that run's RSS is unrecoverable either way.

Admitted as `M58`, which is the whole item: the figure, the koji row struck, the
four consumers repointed, and the recipe capture so koji's own record keeps one.

Both rows have `Blocks` empty — 7.12's fold-in can complete without either. They
should nonetheless land **after** it, since both edit `measurements.md`'s
structure and `M57` touches `--check`, which the fold-in runs.
