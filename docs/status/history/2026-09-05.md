## 7.16's residual is admitted as 7.17, and its stated closure path was wrong

The review of 7.16's "Decisions worth another look" entry settled three things:
the +3.8% array-render residual is closed rather than filed as a property, the
closure named in 7.16's notes was aimed at the wrong structure, and the work is
scoped to the array arm alone.

**The residual is larger than the number it was reported as.** The entry read
the +3.8% as the wrapper split — an element passing through `render_field` and
then `render_field_into` where one function used to do. Reading the arm itself
says the split is the smaller part of it. `render_field_into`'s `Array` arm is
`out.push_str(&render_array(column, row, child)?)`, so an array-bearing row pays
a `String` per element, the `Vec` collecting them, a whole-array `String` that
`nested::render_array` starts at `String::new()` and grows by `push_str`, and
then a copy of the finished text into the caller's buffer. That
un-presized-`String` growth is the same pathology 7.16 diagnosed and fixed in
`push_padded` and in `render_field`'s wrapper; the array path kept it. What
makes it worth a row rather than a property is where the mass is:
`projection-widths` prices the two array columns at **+13.21 µs a row**, 93% of
what all three nested columns cost together and more than every scalar column in
that table.

**The `Cow` is not the lever, and reshaping it would have cost the decode
reading.** 7.16's notes named the closure as reworking `nested::ArrayLiteral` so
an element need not own its text. `batch::collect_array` fills `elements` with
`render_field(..)?.map(Cow::Owned)` — unconditionally owned, because it renders
an Arrow value rather than slicing a literal — so the lifetime that arm carries
does no work on the render path at all. It does work on the decode path, which
is what `measurements.md`'s "Nested decode costs what it copies" measures at the
77 ns / 48 ns per-element split, so a session following the notes as written
would have reworked the structure holding a published reading in order to buy
nothing. Both the notes and `architecture.md`'s "The nested literal codec" now
say the borrow serves decode only. The shape that does close it is to not build
an `ArrayLiteral` on the render side: write each element through
`render_field_into` while walking the Arrow list, against a scratch buffer
reused across elements — a scratch is required rather than incidental, because
`push_token` decides quoting from the finished element text.

**The scope is the array arm, on evidence rather than symmetry.** All five
nested arms stop at the same boundary — `Multirange` builds a `Vec<String>` and
joins it, `Record` and `Range` build their literals and push the rendered text,
`Int2Vector` likewise — so the fix has an obvious generalisation and the
generalisation is not admitted. `projection-widths` prices the whole composite
column at **+0.98 µs a row**, decode, build and render together, and the other
three render one value a row against the arrays' fifty. 7.17 takes whichever of
the four fall out of the same shape at no extra risk and promises a measurement
for arrays only; "push the sink through every nested form" would be a refactor
with a measured win on one arm and hope on four.

7.17 runs ahead of `7.12` under the standing rule already in the phase spec —
any row admitted after spec time against a typed-query profile does — and owes a
control that renders nothing, which is `parse`: 7.16 established that a
`strings` query reaches `render_field` for its sixteen text columns, so 7.15's
control cannot serve a render-path row.

second costs a stamp file and a comparison.

**`M56` took it.** `runs/pgdq-nocensus.stamp` names the commit the binary was

[`../../design/measurements.md`](../../design/measurements.md) ("The census-off

different files.

What the rule buys is exactly *age*, and no more: a stamp is only as honest as

whole of the failure that happened, though, and it is the one nothing else can
see. Two neighbours stay out of scope for reasons worth keeping: a dirty tree,
which the session stamp already declares, and `runs/pgdq-before-throttle`, which
is a build of a fixed historical commit — deliberately not HEAD — and which the
harness builds itself and therefore knows the provenance of.

**The binary in the tree is `f5768e7` and now says so**, which is behind
`9ce7865`, so a census figure is refused here today. That is the rule working
rather than a defect: the next census sitting rebuilds the binary and re-stamps

The exact-equality threshold above is what `M59` loosens — see "The census

## The koji section is outside the figure register, and only its prose said so

Both of the day's "Decisions worth another look" entries were about the koji
section, and the first one's premise did not hold. It asked whether a
deliberately disqualified wall-clock reading belongs "in the figure register" —
but koji is not in the register and cannot enter it. There are seventeen
`<!-- figure: … -->` markers and seventeen figures, none of them koji;
`--check` never sees the section, `--stale` cannot name a reading in it, and no
figure's `quoted_by` reaches it. The harness prints koji's invocation and never
runs it, which is exactly the standing `measure.py` gives the profiling recipe
and says so in its own comment.

Sharper still: the section's existing headline numbers already fail the doc's
**first** standing rule, "every figure is a ratio, never a disk throughput".
The ~238–243 MB/s rows are disk throughputs with no `cat`-to-`/dev/null` floor,
which that prose admits. So the 62.7-minute reading is not an intrusion into a
clean register — it is the fourth non-figure in a section made of them, and the
first to carry its own disqualification in writing. The call stands, and the
reasoning is now filed at the section itself rather than only here, together
with the rejected alternative of withholding the number.

What the entry did stumble onto without naming is a real defect: the exclusion
lived in one prose sentence eleven paragraphs from the numbers, while the
document's preamble asserted "every figure below was taken by `scripts/measure.py`"
over a section that was not. Every *figure* announces itself with a marker and an
apparatus line; a section outside the register announced itself with nothing.

`M57` closes that, and the shape it took is what a later session needs. A section
outside the register now carries an `<!-- outside-register: <id> -->` marker
under its heading — `koji` and `benches`, which are exactly the two entries the
harness already listed under `--list`'s "Not emitted here, deliberately", so
`measure.NOT_OURS` became a slugged register rather than a free-text note.
`--check` resolves the doc's declarations against it **both ways** and fails on
a declared section that also carries a figure marker; the session stamp, emitted
by `session_stamp` and therefore carried into the doc by the next fold-in, is
scoped to "every section carrying a `<!-- figure: … -->` marker, and no other".

The two-way reconciliation is the part that was not obvious. A doc-only check —
assert a declared section holds no figure marker — meets the row as written and
passes a doc that has quietly deleted the declaration, which is the exact state
`M57` exists to make visible. Two details are asserted rather than remembered
(`scripts/test_measure.py`, `RegisterBoundary`): a declaration covers its own
subheadings, and heading detection skips fenced code, because this document
publishes a `sh` block whose first line reads as a level-1 heading and would
otherwise end the section it is printed inside. The scope clause is written with
`…` rather than an id, so `markers_in` does not read the stamp as an
eighteenth marker.

The third thing settled here is smaller and lands with this closure: the
disclaimer pointed the reader at ~241 MB/s as the reference, and that number is
musl's (the pre-2026-09-05 runs are `postgres:16-alpine`; this one is
`postgres:16`), predates eleven P7 slices, and was taken uncontended. So the
paragraph instructed a difference across exactly the boundary the paragraph above
it declares uncrossable. It now names all three boundaries in the same breath as
the comparison, which also stops the *next* glibc run being read as a regression
against musl.

## The RSS row was resting a design claim on the input least able to test it

The second entry offered "capture peak RSS in `--koji-recipe`, or strike the
row". Both options were too narrow.

**Striking is not available.** The ~9 MiB figure has live consumers and none of
them is a passing mention: `architecture.md`'s buffer-pool bound, its
double-buffered-readahead rejection ("the flat ~9 MiB RSS this design is built
on") and `M55`'s "64 MiB against the ~9 MiB above", plus `io.rs`'s own doc
comment. Nothing protects them, because a non-figure has no `quoted_by` edge.

**And the row is wrong on a second axis nobody named.** 7.13.1's notes already
recorded it — "`measurements.md`'s koji row … is now overstated by about a
megabyte. It is a figure, so it is not edited here: 7.12's koji regression run is
what re-takes it." The re-take was written down, aimed at the run that has now
happened, and that run could not take it: the recipe captures no memory figure at
all. So the row is simultaneously musl's *and* a megabyte high, and its designated
correction failed silently.

The answer is to move the claim rather than re-take it where it sits. The row
bundles two assertions — nothing accumulates per byte, nothing accumulates per
block — and this document's own standing rule says koji cannot test the second,
being byte-rich and block-poor at 74 blocks over 784 GB. Both halves are cheap on
inputs the harness already stages: a 3.00 GiB `parse` for the first (7.13.1
already has 6.0 MB), the 4000-block generated input for the second. As a
registered figure the claim acquires a `depends` edge on `io.rs` that goes red
when the read path moves, which is the mechanism whose absence let it go a
megabyte wrong for a full slice.

Two instrument facts, found rather than assumed. The container cgroup's
`memory.peak` exists on this kernel but is the **wrong instrument** — it is
charged the page cache of a 784 GB read, so it reports the 512 MB limit, not the
process. `VmHWM` in `/proc/<pid>/status` is the right one: `pgdq` is PID 1 by the
recipe's `exec`, `nerdctl inspect -f '{{.State.Pid}}'` gives the host pid, and
the kernel maintains the high-water mark, so one read before exit covers
everything up to it — and it adds nothing to the `exec`'d command, leaving all
three load-bearing recipe details untouched. The 2026-09-05 container has since
exited, so that run's RSS is unrecoverable either way.

`M57` and `M58` both landed with `Blocks` empty: 7.12's fold-in could complete
without either, and both were held until after it, since both edit
`measurements.md`'s structure and `M57` touches `--check`, which the fold-in
runs.

**The figure found the claim half wrong, and the half it found wrong is the one
koji could not have caught.** Peak resident set is flat in *bytes* — 1535× the
bytes of a one-block dump moves the reading by less than the readings' own
spread — and it is not flat in *blocks*: ~7.7 KB a block at 500 and ~9.9 KB at
4,000, so a 4,000-block `parse` sits at **43.6 MiB** where a one-block one sits
at 5.9 MiB. "Flat ~9 MiB" was therefore never a statement about a scan; it was a
statement about a *74-block* scan, and the design paragraphs that quoted it now
quote the one-block reading and say which axis it is. The per-block growth is
`KD14`, unowned: three mechanisms could produce it — the span list, `splice`'s
whole-list clone (`KD5`), and glibc returning little of what a churn of clones
frees — and the figure separates none of them. Attributing it is a second
measurement this item deliberately did not take, since widening an out-of-band
row is the review its admission rule exists to force.

**The instrument is `getrusage(RUSAGE_CHILDREN)` inside the container, not a
`/proc` poll.** `postgres:16` carries no `/usr/bin/time`, and `/usr/bin/time
-f %M` around `nerdctl run` reports the client's peak anyway; a `VmHWM` poll is
the wrong instrument *for this figure*, because the `Vm*` lines are gone the
moment the process becomes a zombie and a `parse` writes its cache last, which
is exactly where a late peak would sit. So the timed command wraps pgdq in a
four-line `perl` that forks, `exec`s, waits and reads `ru_maxrss`. `exec`
installs a fresh `mm`, so the interpreter's own 5.4 MiB is not in the reading:
the same wrapper around `/bin/true` reports 1.9 MiB. koji keeps the `VmHWM`
poll, because there the process runs for an hour and is read while it is still
running.

**It was taken alone, so the doc's stamp no longer covers every figure.**
`peak-rss` is the eighteenth, taken at `7ee5db5` rather than in the `af15eac`
sweep; it borrows nothing, republishes nothing and is the only table denominated
in bytes, so no absolute in the doc is differenced across the two sittings. What
it costs is that `--stale` reads one commit for the whole document and calls
this figure stale against changes it postdates. That call was reviewed and
stands, with the rule and the mechanism it owes below — "A figure may be
published outside a sweep, and its sitting becomes data".

## `quoted_by` names a document and cannot say a sentence went false

P7's wrap audit found four things the slices had learned that the subject-filed
docs did not carry, and **three of the four were the `af15eac` fold-in's own
consumer re-read stopping short**. The `allocator` figure declares
`architecture.md` in `quoted_by`, the fold-in re-read that file, and the
section it points at still said "nothing beats the platform allocator
anywhere" — the sentence the sweep had just falsified — under the *previous*
stamp's ranking. The census reconciliation number, three of the projection
table's per-column deltas and the whole closing paragraph of the
`query-profile` section were stale the same way.

**The mechanism did what it promises and the promise is narrower than it
reads.** `quoted_by` names a *document*; a fold-in then has to find, inside a
6,700-line file, every sentence that a number moved. The three misses are all
sentences that quote a figure without naming it: "nothing beats it anywhere" is
a claim licensed by the allocator table and contains none of its numbers, and
the projection deltas sit in a paragraph the fold-in did update — it changed
the three numbers that appear in the figure's own table and left the three that
are arithmetic over it. So the failure is not laziness; it is that the unit of
the edge is a file and the unit of the error is a clause.

**No check is proposed, and the reason is the same one that already applies to
the manual.** A mechanical version would reconcile numerals in a consumer
against the figure's cells, and measured against these four instances it would
have caught the projection deltas and missed the two that carry no digits.
Keying on the claim rather than on the number is what a second attempt has to
do. Until one exists this is discipline, and the honest statement of it is:
**a `quoted_by` re-read is a re-read of the argument, not of the numerals**, and
the sentences most likely to go false are the ones that state a conclusion the
figure licenses rather than a figure it quotes.

**Two inbox entries had gone stale in fact for the same reason**, which is the
sharper half: P6's inbox asserted `print_batch` at 34.0% and 62.8% of the two
query modes and the allocator spread as a factor, and P16's asserted the I/O
prize at 0.125 s of 1.406 s and row extraction at 13.3× the floor. Every one of
those was true when filed and every one had been moved by work that never
looked at an inbox, because an inbox is filed by *destination* and nothing
about landing a slice re-reads one. The keystone sweep is what caught them,
which is exactly the case `process.md` names — "the inbox of a phase the struck
one never mentioned" — met in the wild rather than in the rule.

annotated again"). Two things had changed by the time it came up. `7.17` landed
after `profile-query-*-control-after-716`, so those files are not the shipped
binary — the array arm moves the control by +0.14%, which is exactly the kind
of caveat this item exists to retire. And no sitting in `runs/` recorded
wall/user/system for the control at all, so the table's own header row could not
have been filled from a file. `runs/m53-query-profile.sh` takes both halves in
one window: five timed runs a mode with no `perf` on them, then the two
`--call-graph fp` profiles the shares are read off. The whole thing is minutes,
and a profile is not a figure — it needs no quiet machine and publishes no
median.

**The fresh shares agree with the after-716 pair to about a point**, `poll_next`
61.5% against 62.51% typed and 73.5% against 73.07% for `strings`, which is what
says `7.17` reached this file no more than its +0.14% claimed.

**The re-take doubles as a check on the per-row budget below it.** That budget
is an earlier sitting and states 2.42 µs and 3.10 µs a row for the library; the
new table converts to 2.37 and 3.03 on its own shares and user times, within 3%
— over a run whose typed user time is 4.01 s against the budget's 9.10, because
everything between them was render path. A library figure that survives the
CLI's cost halving is the evidence that the render-path work took nothing out of
`poll_next`, and the budget's numbers stand without being re-derived.

**One row is gone rather than re-taken.** The `read_range` thread had been
carried as `7.2% → —`; with no frame under `read_exact_at` above the profile's
floor in either mode, it is a sentence about what the buffer pool and the carry
removed, not a row of zeroes.

**`session-drift` stays red, and no acknowledgement is written.** It declares
`scripts/measure.py` because the harness's own timing path is the apparatus it
measures, and this change adds executable lines to that file — so the
reachability oracle does not apply, even though every one of them runs once
before the sampler starts and before the first input is staged. The rule is that
a figure with no mechanical evidence stays stale with the reason written down
rather than being excused on judgement, and this is the reason. The figure is
derived across two sweeps in any case, so nothing here obliges one.

## `M55`: the pool keeps the chunk size the caller asked for

The read path's buffer pool no longer decides what to keep by length alone.
**`ByteRangeSource::hint_read_size` is a third, advisory method**, defaulted to
doing nothing, through which each of the three read loops — `scan::scan`,
`stream::map_forward` and the replay loop in `stream::table_stream` — announces
its `ScanOptions::chunk_size` once before it starts. `io::BufferPool` keeps a
released buffer that is under the 8 MiB ceiling *or* exactly the announced
length, so a raised `--chunk-size` is pooled like any other and the cliff behind
the flag is gone. The cost is the one the admitting entry priced: `POOL_SLOTS`
is 4, so a 16 MiB chunk can hold 64 MiB against the flat ~9 MiB a scan
otherwise sits at.

**Exactly the announced length, not "up to" it.** A span read smaller than a
large chunk is still the one-off allocation the ceiling exists to drop, so it is
dropped; `attach_text`'s coalesced read is unaffected whatever `chunk_size` is.

**The hint is on the trait because `ScanOptions` is where the size is
configured.** A `LocalFileSource`-only setter called by the CLI would leave a
library embedder configuring one thing in two places and losing pooling
silently, which is the failure being closed. It is deliberately outside the
`object_store` surface the other two methods mirror, and an `object_store`
backend that takes the default behaves exactly as it would without it — which
is also the thing P14 must not inherit by accident, and is filed in that
phase's inbox. Both alternatives, including inferring the chunk size from
repeated lengths inside the pool, are beside the mechanism
([`architecture.md`](../../design/architecture.md), "Execution model and API
surface").

**The admission rule was re-tested against the work rather than the
description**, and it holds: the fix is the one the architecture doc already
named, it changes no decision any live spec records, and it fits one session.

**Sixteen figures went red and no sweep was launched.** The diff adds
executable lines to `io.rs`, `scan.rs`, `stream.rs` and the CLI, so neither
mechanical oracle reaches it and no acknowledgement is written. One published
number actually moves — the `chunk-size` table's 16 MiB row, taken when a chunk
that large missed the pool — and it is called out both in that table's prose and
beside the mechanism, rather than being replaced by a partial sitting that would
spend the `af15eac` stamp's one-sitting property for one row. A stale figure
obliges no sweep; the next full one re-takes them
([`measurements.md`](../../design/measurements.md), "A stale figure does not
oblige a sweep"). The 1.83× itself is kept as what a pool miss costs on a real
file, which nothing else in the register states.

**Five documents said the old thing and were corrected in the same change**:
the manual's `--chunk-size` section, `parse --chunk-size`'s help,
`DEFAULT_CHUNK_SIZE`'s doc comment, `STATUS.md`'s CLI row, and the fact entries
in P14's and P16's inboxes, whose numbers were also two stamps old.

## Both `M55` decisions reviewed: the trait keeps its advisory method, and the stale row keeps its place

The two entries `M55` left under "Decisions worth another look" were put to the
maintainer and both calls stand. Their reasoning is filed beside the mechanisms
they govern — the trait's in
[`architecture.md`](../../design/architecture.md), "Execution model and API
surface", as a third rejected alternative; the figure's in the `chunk-size`
section of [`measurements.md`](../../design/measurements.md) — and the entries
are deleted. What the review found that the entries had not is below.

**The `object_store` mirror is an argument about the three *required*
methods.** A defaulted method sits outside it by construction: a ranged backend
inherits the do-nothing body and is exactly where it would be without the
method, so refusing one buys a trait describable in a sentence and costs the
announcement its only home outside a single implementation's inherent API —
which is the setter already rejected. Deleting the method later is mechanical,
where finding that a remote backend wanted the caller's read length and having
nowhere to put it is not; P14's and P16's inboxes already carry entries that
depend on it existing.

**`BufferPool::keeps` is a disjunction, and its comment claimed an exactness
the code has only above the ceiling.** The comment said a span read smaller
than a large chunk is still dropped; `len <= POOL_MAX_BYTES || len == hinted`
keeps *any* buffer under 8 MiB, hint or no hint, and `take` picks the smallest
buffer that fits — so a sub-ceiling span read can be pooled and then handed to
a chunk read and retained. That is unchanged from before `M55` and bounded, but
it makes the pool's real ceiling `4 × max(8 MiB, announced)` rather than four
chunks. Corrected in the comment, in `POOL_SLOTS`'s bound, and beside the
mechanism, where the flat-RSS claim can see it — `M58`, still queued, re-homes
that claim into a registered figure and inherits the corrected bound. The code
was left alone: making the hint authoritative would drop pooling for the map
path's own reads and move behaviour a second time, for a hazard no RSS reading
has shown.

**The stale 16 MiB row was carrying an argument, not just a number.** Besides
the 1.83× price of a pool miss, which is deliberately kept as history, the
`fadvise` refusal rested on that row being the slowest cold-NVMe reading by a
clear margin. Its cold penalty (0.54 s) is the same order as its warm one
(0.42 s), so plausibly the whole of it is the per-chunk `calloc` and a re-take
could bring it back to a tie. The refusal survives either way, but the sentence
carrying it would not have, so the paragraph now rests on the 4 MiB and 8 MiB
rows — which run at or below the pool ceiling and cannot have moved — and says
what a tie would and would not change. That is the third option neither entry
considered: leave the row stale *and* repair what leans on it, which costs
nothing and needed no sitting.

**No partial sitting was taken, and none is admitted.** `chunk-size` declares
no `shares` and no derived consumer, so a sitting of it alone would strand
nobody — the cost is only that `measurements.md` stops being one sitting, which
a full sweep restores anyway and which sixteen red figures make likely enough
to wait for.

## The census stamp tolerates a commit that moves nothing it measures

`M56` landed an exact-equality rule: a `census-*` figure is refused unless
`runs/pgdq-nocensus.stamp` is HEAD. That is stricter than what it protects.
The hazard is a *reading* moved by source differing between the two binaries a
census figure subtracts, and a commit touching no path the figure declares
cannot move one — so under exact equality a doc-only commit costs a hand
rebuild (patch `map.rs`, build, copy, revert, re-stamp). The friction lands on
a ritual whose failure mode is a session reaching for the old binary instead of
rebuilding, which is the failure `M56` exists to stop.

**The rule becomes: the stamp is an ancestor of HEAD, and no path the census
figures being taken declare changed between the two.** `M59` takes it. The
threshold moves; nothing else about the refusal does — still one check, still
`parser.error` in the first second, still before the run directory exists.

Three things the entry proposing this had not considered, each settled here:

**A stamp that is not an ancestor of HEAD stays refused.** A divergent or ahead
commit has no "in between" to inspect, so "no declared path changed" would be
computed over a diff that does not mean what it says. The binary then comes
from a tree outside this one's history and its provenance is exactly as unknown
as an unstamped binary's.

**The check becomes per-sitting, because it reads the selected figures'
declared paths.** `census-brace-free` and `census-arrays` both declare
`(*MAP, *SCAN, *READ, *GEN_PERF)` today, so the two sets coincide; the check
consults the selection rather than a fixed list, which is what lets the refusal
name the declared path that actually moved.

**It reuses the predicate `--stale` already argues staleness from**, rather
than writing a second one. The entry's own objection to loosening was that the
check would need a second authority over what can move a reading; reusing
`figures_touched`'s prefix match is what makes it the same authority instead.

**Two neighbours are unchanged, for the reasons `M56` gave.** A dirty tree
stays out of scope — the session stamp already declares uncommitted changes
under a measured path, and that is unaffected by which commits the stamp
tolerates. `runs/pgdq-before-throttle` needs none of this: it is a build of a
fixed historical commit by design, and the harness builds it itself.

**The binary in the tree is refused here either way.** It is `f5768e7`, and
`M55` changed the read path between that and HEAD — a path every census figure
declares — so the rebuild owed today is owed under the loose rule too. The
loosening buys nothing retroactively and is not meant to.

## A figure may be published outside a sweep, and its sitting becomes data

The `peak-rss` call is settled: publishing a figure from its own single-figure
sitting is allowed, under a condition the register can check, and the
provenance that says so stops being prose.

**The rule is conditional, not "sweep only".** What one sitting buys is stated
at the stamp — *"One sweep, one apparatus — which is what lets these tables be
differenced against each other"* — so what a cross-sitting figure endangers is
**differencing**, not publication. The condition is therefore the borrow graph:
a figure may enter the doc from its own sitting when it participates in **no
`shares` edge in either direction and no derivation edge**. `peak-rss`
satisfies all three, so the property the stamp protects was never at risk. The
strict rule was refused because it states the prohibition in a stronger form
than the reason behind it, which is the same correction `M57` had already
applied to this sentence once — scoping "every figure below" to the register
rather than to everything printed under it.

**Three facts made the case, and two of them contradict how the open entry
framed it.** First, the figure's staleness is not "a red with a reason": every
path `--stale` reports for `peak-rss` was last touched by a commit the sitting
**postdates** (`43623c0`, `9ce7865`, `6b90905`), and the only commit after it is
`30bc173`, whose `io.rs` diff is three lines of doc comment. So all four reds
are false positives. Second, reversal is not cheap: "nothing else depends on it"
holds for the borrow graph and fails for the prose — striking the table would
falsify `KD14`'s detail paragraph, `architecture.md`'s three sites, the manual,
the README and `io.rs`'s doc comment, all repointed by the same change. Third,
the register already has a category for a figure a sweep does not produce
(`DERIVED`, which `session-drift` uses), and `UNTAKEN` is deliberately not in
`ALL_FIGURES`, so registering `peak-rss` there would have left the doc with no
table — which is what the entry said, and it checks out.

**The provenance becomes harness data.** "Taken at `7ee5db5`" currently exists
only as English, in three places — the stamp's "seventeen of the eighteen", the
sentence naming the eighteenth, and the table's own paragraph — and `--stale`
cannot read any of them, which is why the figure is red against changes it
postdates. A figure's sitting commit is therefore recorded where the harness
writes and reads it, so `--stale` ranges each figure from its own commit and
`--check` reconciles the doc's prose against the register. Two things fall out:
the harness-generated stamp sentence, which today claims all eighteen markers
and is **false**, is scoped to what the sitting took; and a sweep that re-takes
`peak-rss` cannot leave the three prose sentences behind, because the marker
that carried them is the one it rewrites.

**The acknowledgement ledger is the wrong tool here, and it is the tempting
one.** Acknowledging `43623c0` for `peak-rss` would clear the red in one line.
It would also assert "this commit moved no reading", which nobody verified and
which is not what happened — the reading was taken afterwards. Clearing a
missing mechanism with a false entry in the mechanism next to it is worse than
the red.

**The rule lives beside the twelve, and in the harness.** It governs what the
*document* may contain, so it is written with `measurements.md`'s standing
rules, and checked where the fold-in happens. Not in `process.md`: a session
folding a table in is reading `measurements.md` and running the harness, and a
rule filed in a third document is one nobody is looking at during the minute it
applies.

**The datum goes in the doc, inside the existing marker, and only where it
differs.** In the doc rather than in `measure.py` for the reason
`acknowledged.py` was carved out: `session-drift` declares `measure.py`, so a
commit recording "`peak-rss` was taken at X" would mark stale the figure whose
provenance it was recording, and no such record can name its own sha. Nothing
declares `measurements.md`, and `stamped_commit()` already reads provenance
back out of it. Inside the existing `<!-- figure: … -->` marker rather than in a
sibling, because a sibling can go missing on its own and its absence is silent —
the figure would read as stamp-sitting. Present only where the sitting differs
from the stamp, which is the convention `outside-register` already uses: a
section that declares nothing is in the register, and a figure that declares
nothing came from the sweep. Always-present would put the stamp's commit in the
doc nineteen times, which is nineteen places it can disagree with the stamp.

**Two checks fail, one sentence is generated, and the run-time case refuses.**
`--check` **fails** where a figure carrying a sitting marker has a `shares` edge
in either direction or a derivation edge — that is the doc asserting a
differencing that crosses sittings, the same class as a section declared outside
the register while carrying a figure marker. The stamp's accounting sentence —
today's hand-written "seventeen of the eighteen … the eighteenth is `peak-rss`,
taken alone at `7ee5db5`" — is **generated** from the markers rather than
reconciled, since `session_stamp()` already computes the harder half and a
hand-maintained count is exactly what goes wrong silently. And `--figure`
**refuses** a selection that would publish outside the stamp while failing the
condition, rather than warning: there is no partial version of it, and `--alone`
is already the way to ask for something the harness would otherwise refuse.

**The thirteenth standing rule lands with the check, not before it.** The rule
is true today and `peak-rss` complies with it today, but writing it into
`measurements.md` now would state a rule nothing enforces — and an honest
unchecked rule has to be written the way `process.md`'s "Nothing checks this,
and the obvious check was costed and refused" is written, only to be deleted in
the very next change. There is no reader in between: nobody folds a table in
before the item lands. Until then this entry is where the rule lives.

**Every reader of the stamp follows the sitting, not just `--stale`.** Two
others read it and both are wrong for a figure taken elsewhere. `--check` calls
an acknowledgement spent when its commit is an ancestor of the stamp, so an ack
for `peak-rss` at a commit between `af15eac` and `7ee5db5` is spent for that
figure and live for the other seventeen; spentness becomes per figure.
`--verify-additive` regenerates a published figure's inputs at the stamp on the
stated ground that *"the figure was taken at the stamp, so they existed then"* —
a sentence `peak-rss` already falsifies — so it regenerates at each figure's own
base and the comment is replaced by the rule. Half-applying this is the worse
outcome available: two mechanisms still reasoning from a commit the doc itself
says is not the figure's is the same defect one level down.

**A sitting must be a descendant of the stamp, and `--check` fails otherwise.**
An older sitting cannot legitimately exist — a sweep replaces every table at
once, so a figure the stamped sweep took carries no marker and a figure it did
not take was folded in later. A marker that is not a descendant therefore means
a sweep left a stale marker behind or someone hand-edited one, and both
republish a fresh table under a lying provenance, which reads entirely plausible
and puts `--stale` back on the wrong commit. It is the `pgdq-nocensus` failure
in another mechanism, and it costs one `is_ancestor` call.

**The item records where `peak-rss` was taken; it does not re-take it.** Its
four reds clear without a measurement and without an acknowledgement, which is a
third way for a figure to go green and is deliberate: the reds are false
positives, since the sitting postdates every commit holding them red, so a
re-take would spend a measurement to conceal that the *range* was the defect.
The distinction is the one the ledger cannot express — an acknowledgement says
"this commit moved no reading", and this says "this commit is not in this
figure's range at all". What is left afterwards is `30bc173`'s comment-only
`io.rs` diff, the one commit genuinely inside `peak-rss`'s range, which is an
ordinary acknowledgement for whoever wants the figure fully green before a
sweep.
