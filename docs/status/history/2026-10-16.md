# 2026-10-16

## 36.4's refusal: attribute exactly, then rework or accept

36.4.2 left 36.4's rise unattributed and offered the maintainer three ways out:
an exact count, acceptance, or a revert. The answer is the exact count, as
36.4.3, with its reading fixed in its STATUS row before it runs. Neither
acceptance nor a revert was chosen before the rise is placed.

- **No profile taken so far rules out the key path.** The per-symbol
  sampling error is about ±300 samples (36.4.2's notes, the `observe_row`
  example). That is the size of the split between changed and identical code
  that the profile reads, so the split is unresolved. Only the total is.
- **A key-path cost of this size is plausible.** `control.sql` is one table
  of 814,379 rows and 16 columns, so the rise comes to about 38 instructions
  per field. That is more than one added branch, and about what a change in
  inlining around `stored_order`'s new `Key` match and `Option` would cost.
  The gatherer builds only `Key::Scalar`.
- **The count answers either way.** Code cost does not depend on addresses,
  so callgrind reproduces it exactly. A total callgrind does not reproduce
  depends on addresses, which is layout. A layout outcome means the
  identical-sources pair (36.1.1) could not have caught it: a rebuild of one
  source moves no heap address. `--count-pair` would then be pricing layout,
  so how it is read is reopened before another slice is counted.
- **The instrument stands.** 36.4.3 put the whole rise in 36.4's own code
  ([its notes](../../design/roadmap-P36.4.3-callgrind-notes.md)), so
  `--count-pair` is read as before. `pgdt-dump` does not depend on
  `pgdt-codec`, so 36.5 was linked to 36.4 only through that instrument.
  36.4.1 waits on 36.4's rework or acceptance, because it reshapes the
  match the count prices.
- **A cost in 36.4's own code is reworked only into a shape as clean, and
  otherwise accepted.** This phase's goal is the architecture, and the rise
  is minor. One candidate to weigh: the gatherer never holds a nested key
  and already reaches the key code through `internal`, so it could keep the
  scalar key without the wrapper's match. The amendment is the spec's "What
  a hot-path slice owes".

## 36.4's rework recovers the data-level rise; the summary reads by kind

The rework holds the statistics gatherer to `internal`'s scalar key, so its
accounting and its comparisons no longer pass through `ValueKey`'s wrapper
([notes](../../design/roadmap-P36.4-value-key-notes.md), "The rework: the
gatherer off the wrapper"). The maintainer affirmed it, and the summary is
reworked the same way.

- **Its count is `runs/count-pair-36.4-rework-20261016-0430/`**, read as the
  notes wrote it in advance. The gate held, and the data-level `parse` falls
  below `a7b6ef0e`'s (notes, "The rework's count: the data-level rise
  recovered").
- **`runs/attr-36.4-rework-20261016-callgrind/` counts both rows exactly**
  against `a7b6ef0e`. The rework's shipped binary is kept beside 36.4.2's
  two, where its `run.sh` names it. The `pgdt sql` row's rise is the
  summary keying each stored bound through `ValueKey::of` (notes, "Both rows
  counted exactly against `a7b6ef0e`").
- **The gatherer holding `OrderKey` is the shape D106 already describes**:
  a crate above reaches what is not API through `internal`, and the
  predicate already holds `internal`'s `OrderKey` and `NestedKey`, never
  `ValueKey` (`pgdt-query/src/predicate/resolve.rs`, `Ordered`). So no
  revert would have left one key type above the codec. The type also stops
  the gatherer holding a nested key, which D79 never gathers. Inlining
  `ValueKey`'s methods was refused, because it keeps that unreachable state
  and its saving rests on inlining choices 36.4.3 showed move.
- **The summary reads a stored bound by the set's kind, not by the plan.**
  `fold` and `column_order` already choose the set by a kind from
  `bounds_read_by`, then key each bound with `ValueKey::of`, which derives
  that kind a second time. Both derivations agree wherever `fold` runs: they
  differ only on a divergent plan under PostgreSQL's semantics, where
  `bounds_read_by` gives `None` and nothing is folded. So the summary keys by
  the kind it already holds, as D79 says a set is read. The rise recovered
  follows from that; it is not the reason.
- **`ValueKey` stays the embedder's key, without `stored_order`.** After the
  summary's rework nothing in the tree calls it, which D106 says does not
  decide what is API. `of`, `literal`, `compare` and `heap_bytes` are what
  the spec's "A key for every value" delivers. The stored order, which
  places a float's `-0` below `0`, is the cache's to keep (D79 equates the
  zeros in every term), so it stays `internal`'s `compare_keys_stored` and
  leaves the API with the summary's rework.
- **The gatherer's rework is its own commit, `0152fe56`**, ahead of the
  summary's, so the summary's `--count-pair HEAD~1` prices the summary
  alone.

## 36.4 lands, its last remainder accepted

The summary keys each stored bound by the set's kind, and `ValueKey` has no
`stored_order` (36.4's notes, "The summary off the wrapper"). Its count is
`runs/count-pair-36.4-summary-20261016-0635/`, and the exact count of what
it leaves on `pgdt sql` against `a7b6ef0e` is
`runs/attr-36.4-summary-20261016-callgrind/`. The tree binary is kept
beside 36.4.2's, where that job's `run.sh` names it. The remainder is
36.4's own code and is accepted, and 36.4 is ticked. The maintainer
affirmed that acceptance. The one candidate shape, `compare_keys_stored`
over `compare_keys`, is the cleaner shape on structure alone:
`order_keys_stored` outlived the `Option` it gave `stored_order`. So 36.4.1
takes it and its count prices it (notes, "The summary's count: the last of
the rise, counted and accepted"). 36.4.1 is next, counted against 36.4's
commit.
