## A `parse` over a gzip first pass, reviewed

The maintainer reviewed the entry 15.5.3's round raised on a `parse` not
announcing a gzip first pass.

- **A cold gzip `parse` says nothing of why it is serial**: `jobs=1
  (recommended by the source)` with `--jobs` omitted, `scan arrangement …
  bound_by="source"` above one, the first pass's `PlanNote` reaching only a
  query (`fixtures/16/edge_cases/compress.sql.gz`, parsed cold in a container).
- **The gzip source announces its first pass**, started and complete, as the
  `.xz` walk is (`crates/pgdt-io/src/source/compressed/xz.rs`); the spec's
  "A first pass is a `PlanNote`, not a diagnostic" says what each line names.
  The `.xz` line exists so a silent wait does not read as a hang; a gzip pass
  is no silent wait, its scan lines running, so what the line adds is the
  reason and that it is paid once. Rejected: the reason folded into
  `resolved the arrangement`'s provenance and `scan arrangement`, which would
  put codec knowledge in the arrangement.
- **It is slice 15.12**, a spec decision amended and so no out-of-band row,
  placed next, before 15.5.4 and 15.7's manual. 15.6's walk is announced the
  same way, being the silent wait the `.xz` line exists for, and 15.8
  rewrites the started line where the pass is no longer serial
  (`../../design/roadmap-P15-gzip.md`, "Slice order").

## The fetched BGZF walk, reviewed

The maintainer reviewed the entry 15.6's round raised on announcing the
fetched BGZF walk at `info`.

- **The walk reads the whole file on both arms**: each read runs on to
  `WALK_CHUNK`, 1 MiB, and a member is at most 64 KiB
  (`crates/pgdt-io/src/source/compressed/deflate/walk.rs`); the scan then
  reads it again. A fetched source recommends one reader
  (`FetchedCompressedSource::default_workers`, D2), so a cold fetched BGZF
  file downloads twice where a single-member `.gz` downloads once.
- **The fetched arm reads BGZF by a first pass**, the local arm still
  walking; the announcement level follows whether the cost goes beyond the
  scan's own; 15.8 takes a fetched BGZF file's units from its members'
  headers (`../../design/roadmap-P15-gzip.md`, "A fetched BGZF file is read
  by a first pass, not walked", and "Slice order").
- **It is slice 15.13**, a spec decision amended, placed before 15.8. It
  rewrites D64's BGZF sentence, now true of both arms at `info`, to name the
  arm and the rule, and the rustdoc of `open_remote`
  (`crates/pgdt-io/src/source/remote.rs`) and `walk.rs` saying the walk is
  fetched; 15.7's manual writes gzip into "Reading a dump over HTTP", which
  names only `.xz`.

## Lint coverage by feature, reviewed

The maintainer reviewed the entry `M247`'s round raised on linting each
library at its own features only.

- **Three feature families are linted by no build**: `introspect`, 56 `cfg`
  sites in seven crates, compiled only by the instrument build; `pgdt`'s
  `jemalloc` and `system` legs; `gz-seek`'s `zlib-ng` and `zlib` legs. The
  workspace build takes `pgdt`'s defaults and no member's dependency turns
  them on, so a warning there surfaces nowhere and an error only when a
  figure is taken.
- **The round lints every build the project makes or names to an embedder**,
  each set named, and a test holds every declared feature to some linted
  build. Rejected: `cargo-hack --each-feature`, which refuses this workspace
  until told its exclusive features — `gz-seek`'s one inflater
  (`crates/gz-seek/src/zlib.rs`) and `pgdt`'s one allocator
  (`crates/pgdt/src/alloc.rs`), each a `compile_error!` — and so names the
  sets in another tool's syntax, then lints combinations nobody builds; the
  sets at a wrap only, a backlog by the time it runs.
- **It is `M248`**, blocking nothing of P15. `check.py`'s "Each library is
  linted alone too" states the rule when it lands.
