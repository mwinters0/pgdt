## The leaf grammar is not the output form, and three docs said it was

Reviewing 12.6's "Decisions worth another look" entry found its premise false.
The entry claimed an `int2vector` literal's *elements* are read more loosely
than any other container's leaf, because `int2vectorin` reads them itself where
every other container hands its elements to their own type's output form.

`predicate.rs`'s `nested_key` takes an `input` flag and threads it through the
**container** arms only; the leaf arm is `order_key(kind, text)`, which takes no
flag, so a dump field and a filter literal go through one function. For the
integer kinds that function is `str::parse`, and Rust's integer parse accepts a
leading `+` and unlimited leading zeros. Verified against
`fixtures/16/types/default.sql`:

| query | result |
|---|---|
| `v_empty = '{+1,02,0003}'` on `integer[]` | matches `{1,2,3}` |
| `v_smallint = '+0'` / `'-0'` / `'0000'` / `'032767'` (scalar column) | all match |
| `v_vec = '+1 0002 3'` on `int2vector` | matches `1 2 3` |
| `v_vec = '32768'` on `int2vector` | refused |
| `v_empty = '{99999999999}'` on `integer[]` | no error, no match |

So the leniency is neither new nor container-specific, and on the one axis
where the two genuinely differ `int2vector` is the **stricter** one: it
range-checks each element to `int16`, where an Int leaf is parsed as `i64`
whatever the column's width. That asymmetry is kept — the reasoning is beside
the codec in [`../../design/architecture.md`](../../design/architecture.md) —
because an `int2vector`'s element width comes from the type rather than from a
column, so there is no wider value for an out-of-range literal to order
against.

What the review changed is the record. `architecture.md` asserted the output-form
rule in three places; all three now say what the code does, and the property
"A literal is read in the type's own output form and no wider" carries its one
real exception beside it, along with the consequence on the *field* side — a
dump field spelled `+1` is taken quietly rather than flagged — which is accepted
so that one shared function keeps a field and a literal denoting the same value
comparable.

The same false rule was printed to users by `nested_accepted_form`'s trailing
clause. That was kept out of this closure — it is a wording change to a
diagnostic and changes no decision — and landed as `M45`, below.

## `M45`: the nested refusal gives the dump's form as advice, not as a boundary

`nested_accepted_form` builds the clause `Error::PredicateValueDecode` prints
after "which is written". Its trailing half claimed to be the boundary of what
is accepted — *"with every element, field or bound written in its own type's
output form"* — and `order_key` does not enforce that: its integer arms are
`str::parse`, so `+1` and `02` are read as `1` and `2` at every depth. It now
reads *"with each element, field or bound spelled as the dump spells it, in

be refused. `predicate.rs`'s
`a_nested_literal_is_lenient_about_the_container_and_strict_about_the_leaf`

## P7's grilling: the phase is re-aimed at row extraction, and parallelism is P16

The phase doc was a sketch written before any of the figures existed, and the
`ba2fc12` sweep re-prices its two central assumptions.

**Discovery is not where the time is.** On the 3.00 GiB control, warm on
tmpfs: `dd` 0.332 s, `pgdq parse` 0.558 s (1.68× the floor), a `strings` query
4.42 s (13.3×), a `typed` query 10.36 s (31×). Cold on the SSD `parse` is
5.78 s against a 5.75 s floor — 1.01×, the device hiding it entirely. So the
whole prize in structure discovery is a quarter-second per 3 GiB, and an order
of magnitude of the project's device-bound goal sits in the row path. The spec
now targets row extraction, and keeps three discovery items on their own
evidence: `KD9`, `KD5`, and the I/O defaults.

**The `\.` needle search is not free, and what it costs is two consumers.**
`CopyEnd::row_count` and the array-shape census both look at every row a skip
would jump over. Counting rows without enumerating them is available
(`memchr::count` over the block extent); the census is not, since it needs the
bytes. Adopting the search therefore means deciding what happens to the census
— for a quarter-second per 3 GiB.

**Readahead's prize is `min(device time, parse time)`, which bounds it to one
device class.** The spec called double-buffered readahead "the single most
likely reason the current scan sits at 33% CPU"; on koji that 67% is disk wait,
which no overlap removes. Cold SATA SSD caps the win at 4%, and the cold table
already reads `parse` at 1.01× the floor, so the kernel's own readahead is
evidently doing it. tmpfs has no I/O to overlap. NVMe is the one device class
where the two are within a small factor — ~0.9 s of device against 0.55 s of
parse CPU per 3 GiB — so it is added as a third regime **for that decision
only**, staged at `/var/tmp/pgdump_query` (`CLAUDE.local.md`). An HDD
throughput figure was rejected: koji already answers the only HDD question the
design has, and a 3 GiB file on a rotational disk measures one file's layout.

**Parallelism is carved out as `P16`.** It multiplies a loop rather than fixing
one, and its blast radius is three already-tested mechanisms — `stream::splice`'s
contiguous-prefix assumption, the census's per-block accumulation, and the
interrupt guard's "bank the last completed block" promise — which cannot share
a review cycle with self-contained per-byte work. It also has two source shapes
to serve once P13 lands, not one. P7 owes it the sparse row index and a written
statement of what a splitter needs from coverage and from the census; the three
P7 inbox entries that were about parallelism moved whole into
[`../../design/roadmap-P16-parallel-scan-inbox.md`](../../design/roadmap-P16-parallel-scan-inbox.md).

**Three more of the phase's decisions, from the same grilling.** It commits to
**no numeric target**: the goals are the cheap optimizations and a solid
understanding of where the time goes, so that a later phase can set a target
against evidence. It is done when every named lever is landed-with-a-figure or
rejected-with-a-figure, and when the cost decomposition of the `strings` and
`typed` paths is published — the durable half, worth having even if every lever
turns out to be worth little. It **measures the allocator early** (glibc against
`jemalloc` and `mimalloc`), so that every later figure is taken under the one it
ships; the choice belongs to `pgdump_query-cli` and never to the library, since
a `#[global_allocator]` there would bind every embedder, and the consequence —
that a published figure is a CLI figure — is stated in the apparatus rather
than hidden. And the **sparse row index moves to P16**, whose splits are the
first thing that reads one; P10 needs the same interval, so whichever runs
first settles it.

**The instrument is a profiler, not a sweep, and "done" means measured rather
than landed.** A whole-file figure costs a machine that has other work, so P7's
primary instrument is a **sampling profile** — seconds per run, attribution per
function rather than per subtraction, and no quiet machine needed to read a
proportion. A profile is a `runs/` artifact and never a figure; a
`measurements.md` table is taken only for a landed lever's before-and-after.
Subtraction across projection widths and the census-off binary stays as the
fallback for what a profile cannot answer, chiefly the device-versus-CPU split.
`[profile.profiling]` inherits `release` and adds line tables and frame
pointers, leaving the profile every published figure is taken with untouched,
and profiles run on the host against tmpfs rather than inside the 512 MB
container.

Deterministic instruction counting (`callgrind`, or `iai-callgrind` as a
dev-dependency) was considered for exactly the shared-machine reason and
rejected as the default: the allocator, zero-copy views and chunk sizing change
*memory behaviour* rather than instruction count, so it would report this
phase's headline levers as free. It stays available for a lever that turns out
to be instruction-bound.

The definition of done follows: **every lever is measured, and every obvious or
cheap win is taken.** No lever is excluded from measurement by its
implementation cost — only from landing. That admits the viewing builder for
`List<Utf8View>`, the largest single prize on the list at ~7.3 µs/row and the
most delicate change on it, as a measured candidate that lands only as its own
final slice with its own review.

**`KD5` is discharged by the gate the throttle already owns.** `stream::splice`
moves inside `if settled || cancelled || throttle.due()`, taking the 4000-block
map from 19.0 s to about 1 s. (That condition could not be written literally —
see "7.4: the gate needed a third opener, and the two costs were multiplying"
below.) The interrupt's promise changes from "banks the
last completed block" to "banks the last spliced watermark", and the cost is
bounded by time rather than block count because the throttle is self-tuning:
105 saves across a 20.8 s scan is ~0.2 s of scanning lost. On koji the gate
clears at every `CopyEnd` — blocks 45 s apart, sub-second saves — so the shape
where a lost block is expensive is unaffected. The appendable-spans rework goes
to P16 if a residual survives.

**Two more, and the first is about how the phase runs.** It does not waterfall:
the lever list is what it is committed to *measuring*, and which levers become
code — and in what order — follows the profile, a hunch the profile then
settles included. A lever row is satisfied by a rejection carrying its reading
and its instrument's floor. Where the spec names a hypothesis rather than a
decision it says so, and the `INSERT` fast path is the worked example: `KD9`'s
entry claims the fix is "a second scanner-level fast path", and the code says
the expensive part is `map.rs`'s `Mode::InsertRun` pushing every line into a
`String`, with the large-object region's 0.442 s against `COPY`'s 0.558 as the
supporting reading. Which layer takes the fix is the profile's call, and `KD9`
is corrected in whichever change lands it.

**The chunk-size default is one measured constant.** Runtime probing of
`/sys/block/<dev>/queue/rotational` is rejected: Linux-only, masked inside
containers, and a walk with several ways to be wrong on LVM, dm-crypt, MD, NFS
or an overlay — for a knob whose measured spread nobody has seen yet. The
per-class numbers are published and `ScanOptions::chunk_size` stays tunable.

**The lever table gained the largest bucket, and the phase is sliced.** On the
control, `strings` is 4.42 s and `typed` 10.36 s over 814,362 rows, so scalar
decode plus the typed Arrow build is **7.3 µs of a 12.7 µs row — 57% of a typed
read**, over sixteen ordinary columns with no nesting. Every other lever
targets the shared row machinery or the nested path, so the table read as a
decision not to look at the shape most dumps actually have; it is now a row of
its own, split by the profile into a `decode.rs` half and a builder-append
half, since those have different remedies. A lever the profile finds and the
table does not name is admitted if it is obvious and cheap, by amending the
table with the reasoning here — filing every unlisted finding forward would
read as discipline and would really be a way of not acting on the evidence the
phase exists to gather.

The twelve slices are in `STATUS.md`. **7.1 and 7.2 are ordered and the rest is
allocation order rather than schedule**, stated in both documents, so a slice
landing out of numeric order is the plan working rather than slipping; `7.3` is
the one exception, since an allocator adopted after a figure invalidates it.
`KD5` and `KD9` name slices 7.4 and 7.5 and are named back, and both entries'
detail paragraphs moved out of the drained inbox to sit beside their
mechanisms in `architecture.md` — the `INSERT` one beside "Bulk regions", now

## Two premises under the profiler's symbol fetch were wrong

into `perf`'s build-id cache, and raised the cache's location for review. The
review overturned the framing rather than settling it: three of the claims the

**`~/.debug` is `perf`'s build-id cache, not a location the recipe
introduces.** `perf record` populates it on every run unless given
`--no-buildid`, so it already holds the profiled binaries themselves — 82 MB
after 7.1's six profiles, of which exactly one file came from the fetch. The
question as posed was whether to accept a fourth out-of-repo place or install
with root; neither branch was real, because the directory appears the moment
anyone profiles here.

**`perf` does expose a debuginfod flag.** `perf buildid-cache
--debuginfod[=URLs] -a <dso>` is documented and works — verified against
`/usr/lib/libz.so.1`, which downloaded by build-id and cached `debug`, `elf`
and `probes` in the same place the hand-rolled fetch writes to. What is true is
narrower: the flag is absent from `perf` top-level and from `perf report`, both
of which reject it, and the first version generalised from those two.

**Arch ships `glibc-debug`, in a repo that is not enabled by default.**
`glibc-debug-2.44+r24+g16be1518495f-1` matches the installed `glibc` exactly,
costs 18 MB down and 122 MB installed, and covers `libc`, `libm` and
`ld-linux` together (`%BASE%` is `glibc`). Installed under `/usr/lib/debug`, it
is found through the `.gnu_debuglink` already in `libc.so.6` — no network, no
cache, no environment variable — and `pacman -Syu` keeps it in lockstep with
libc, which a manual fetch does not. It is now installed, and verified the only
way that proves anything: with `~/.debug` moved aside entirely, a profile still
names `__libc_read` and `__libc_start_call_main`, inlined frames included.

**Reaching the debug repository took a second attempt, and the first one is the
instructive half.** Probing `geo.mirror.pkgbuild.com` showed `core-debug` and
`extra-debug` served, and that was generalised into `Include =
/etc/pacman.d/mirrorlist` — which fails, because most mirrors in that list
return a flat 404 for those repos. The debug repository has to name a server
checked to serve it. (`built.archlinux.org`, which the wiki's instructions
name, does not resolve from this machine at all.) One mirror answering is not
the mirror list answering — the same shape of error as the `perf` claim above,
where two subcommands rejecting a flag was generalised into `perf` not having
one.

So an installed package is the better source and a fetch is the fallback for
the machine without one and the DSO no package offers, and the fetch should be
`perf`'s own command rather than five lines re-deriving `perf`'s cache layout
from outside — a path construction that fails silently, putting the `debug`
file somewhere `perf` does not read and yielding bare addresses with no error.
That is `M47`, and the recipe now reads:

```sh
LIBC=$(ldd <binary> | awk '/libc\.so/{print $3}')
BID=$(readelf -n "$LIBC" | awk '/Build ID/{print $NF}')
DBG=/usr/lib/debug/.build-id/$(printf %.2s "$BID")/$(printf %s "$BID" | cut -c3-).debug
if [ -e "$DBG" ]; then
  echo "libc symbols: installed package, $DBG"
else
  echo "libc symbols: no package for build ID $BID; fetching"
  perf buildid-cache --debuginfod=<url> -a "$LIBC"
fi
```

Three of its properties are load-bearing, and `test_measure.py` asserts each.
**It keys on the build ID rather than on `.gnu_debuglink`.** Both paths are
installed by the same package on every distribution that ships one, but only
the build-ID path distinguishes symbols that *match* from symbols that merely
have the right filename — which is exactly the skew `CONTRIBUTING.md` warns
resolves nothing without warning. **The fetch is `perf`'s own**, so `perf`
writes the cache whose layout it owns. **Both branches print the source**,
because a skewed package and a failed fetch are indistinguishable from success
in everything else a profile shows.

`PGDQ_PROFILE_DEBUGINFOD` set empty still skips the step whole rather than
leaving the lookup behind. The escape hatch is for a libc that carries its own
symbols, and there the package lookup would report a miss it has no fetch to
answer — a false alarm in place of the silent failure it was added against.

The change touches `scripts/measure.py`, which `session-drift` declares, so it
owes an `ACKNOWLEDGED` entry on the reachability oracle: `--profile-recipe` is
a subcommand no sweep command shape reaches, and no figure's input, invocation
or timing moved. That entry names a sha, so it is written by the commit after
the one that lands this, as `393a50f` did for `305af4b`.

**The documentation half produced a `CONTRIBUTING.md`, because the doc set had
no home for it.** Two of the three places this was written do not survive —
`CLAUDE.local.md` is machine-local and a slice notes doc is struck at the
phase's keystone — and the third, `CLAUDE.md`, is addressed to an agent working
in the repo rather than to a person setting a machine up. Setup instructions
for a human developer had nowhere to go, which is why they had drifted into a
gitignored file. `CONTRIBUTING.md` now holds the profiling requirement stated
distribution-agnostically, with the two details that cost an hour to
rediscover: the debug repository is often absent from the general mirrors, and
a version-skewed package resolves nothing without warning. `CLAUDE.md`'s
profiling paragraph points at it with a read trigger, `README.md` indexes it,
and `CLAUDE.local.md` is cut back to the fact that the setup is done here.

`docs/process.md`'s doc-set table has no row for this file and was left alone:
it is project-agnostic, and adding one is a process change nobody asked for.

## The decomposition re-prices the lever table, and the `INSERT` +10% is layout

7.2 read the call graphs 7.1 left and took four more profiles. Three of its
findings change the plan rather than only describing it, and all three come
from the same correction.

**Every share in a `perf` profile here is a share of *user* time.**
`perf_event_paranoid = 2` permits user-space sampling only, so the event is
`cpu/cycles/Pu`. A warm 3.00 GiB `parse` is 0.60 s of wall made of 0.30 s
system and 0.29 s user, and `dd` over the same file is 0.29 s that is entirely
system — so a `parse` profile covers slightly under half the scan. Uncorrected,
`memchr::Two` at 17.2% looks like it contradicts the census figure's +0.030 s;
corrected it is 0.050 s, which is the same measurement. Everything below rests
on that.

**The `INSERT` +10% is code layout, and there was nothing to bisect to.** The
spec asked for a differential profile and predicted that two indistinguishable
profiles would be the answer. They were nearly indistinguishable, and
`perf stat` turned that into an attribution: `release` builds at `b70589f` and
at the stamp retire **114.62 G against 114.66 G instructions** — 0.03% apart —
and spend **35.8 G against 40.0 G cycles**, with branch misses, cache misses,
L1-icache misses and frontend stalls all flat or lower on the slower one and
the clock identical to within 0.5%. The whole 4.2 G-cycle difference sits inside
`preamble::scan_buf`, whose source is unchanged across the range and whose 293
machine instructions are byte-identical between the two binaries, differing only
in address. Building both with `-C llvm-args=-align-all-functions=6` collapses
the gap to −1.5% and takes both *below* the faster unaligned build; the same
flag moves the control's `parse`, `strings` and `typed` shapes not at all. So
it is one tight character loop's placement, the flag is not a lever, and what
the finding leaves behind is a rule about reading figures rather than a fix —
[`../../design/measurements.md`](../../design/measurements.md), "Two builds of
one source can differ by layout", with the working beside the mechanism in
[`../../design/architecture.md`](../../design/architecture.md), "Bulk regions".
The `profiling` build reverses the sign of that same difference, which is the
counterexample behind the same rule's second half.

**Two lever rows were sized by a subtraction that was measuring the CLI.** The
`typed` − `strings` gap of 7.3 µs a row was filed as "scalar decode and the
typed column build", and the viewing builder for `List<Utf8View>` was admitted

against the profile, which is what
[`../../design/roadmap-P7-scan-performance.md`](../../design/roadmap-P7-scan-performance.md)
authorises; **the slice list was left alone**, and the maintainer re-cut it —
see "The slice list is re-cut against the decomposition" below.

**Three measure-only rows are answered.** `attach_text` takes **zero samples**

The double read is exactly one extra pass, counted with `strace` rather than

the profile on the array-bearing one.

**The `INSERT` fast path goes in `map.rs`, and it is not close.** 58.2% of that

## The slice list is re-cut against the decomposition, and a CLI subtraction is not a library stake

**The read path's zero and copy is `7.13`, not 7.8's.** 7.2's paragraph put it
with the I/O defaults on the grounds that it "belongs to whichever pass reads
bytes". Reading the code says otherwise: 7.8 is three tunable constants

the kernel and the scanner, carrying three decisions an `fadvise` review would
not ask.

- The copy is in **three** read loops — `scan.rs:398`, `stream.rs:499` and
  `stream.rs:1243` — each with its own `drain(..used)` carry discipline.
- `ByteRangeSource::read_range` is deliberately shaped to mirror
  `object_store::get_range` *so that backend stays additive*, and its doc

  allocation either departs from that shape or pools behind it, and that is a
  choice about a future backend, not about a constant.
- In query mode the chunk is **also retained**, in `batch.rs`'s

  `push_utf8view_field`'s straddling-field fallback and on
  `invalidate_block_cache`, which is L3 machinery.

It is reviewed alone, and it runs **ahead of 7.6 and 7.7**, both of which
rework how a row is walked inside the buffer it replaces. Being the largest
single `parse` lever on the list — 54.6% of user time — is why it earns its own
review, not why it earns a slice.

order after the evidence slices is allocation order, not schedule. Both were in

**What was affirmed, and changed nothing.** The 7.2 session's own call — amend
the lever table, which the spec authorises in as many words, and leave the

## The allocator lever's stake did not survive being measured, and jemalloc's worst number belongs to 7.13

The lever table's `Allocator` row was sized at **1.8–2.4×**, from the glibc/musl
comparison that made the allocator part of the apparatus in the first place.
Measured against two allocators actually tuned for this shape of work, what is

| Warm, on tmpfs, 3.00 GiB control | `system` | `jemalloc` | `mimalloc` |
|---|---|---|---|
| `pgdq parse` | 0.544 s | 1.016 s — 1.87× | 0.535 s — 0.98× |

| `query --schema-mode typed` | 10.21 s | 10.90 s — 1.07× | 9.77 s — 0.96× |

So a stock libc's malloc being 1.8–2.4× off another stock libc's says nothing
about whether a *replacement* beats it, which is exactly what the spec said

**mimalloc's 4% is a finding, and the tempting move was to call it noise.** The
`typed` spreads do not overlap (9.75–9.79 against 10.14–10.44), and the sign
reproduced in two independent sittings the same day (0.97× then 0.96×). The
floor that would have dismissed it is the decomposition's own — two builds of
one source differing ~10% by code layout — and that reading was taken on
`insert_run`, where the same alignment flag that collapsed the gap moved the
control's three shapes not at all. Dismissing a 4% by quoting a floor measured
on a different input would have been the apparatus being used backwards.

What decided against adopting it is what adoption costs, which is not the
one-line feature flip: every other table in `measurements.md` becomes a figure
of a binary no longer shipped, with no mechanical oracle available to
acknowledge it, so the whole document reads stale until the wrap's sweep pair.

**And jemalloc's 1.87× on `parse` is not an allocator result at all.** It is
all system time — 0.27 s → 0.80 s on the host, with user time *lower* (0.23 s →

`madvise` calls against glibc's 50 and mimalloc's 62**, over a file read in
3,072 chunks. That is `LocalFileSource::read_range`'s per-chunk
`vec![0u8; 1 MiB]` returned to the kernel and re-faulted once per chunk. glibc
wins there because its arena keeps the region, so `calloc` hands back pages the
kernel already zeroed.

Two consequences, both filed: the ranking is dominated on one of its three
shapes by an allocation **slice 7.13 removes**, so 7.13 owes a `--figure
allocator` re-take and adoption is a post-7.13 question rather than a settled
one; and a `perf_event_paranoid = 2` profile cannot see this at all, since the
whole difference is in the kernel — the two binaries' flat user-space profiles
are close to indistinguishable. The decision is beside the mechanism
([`../../design/architecture.md`](../../design/architecture.md), "The allocator
is the binary's choice"), the table is
[`../../design/measurements.md`](../../design/measurements.md), "Which
allocator a figure was taken under", and the apparatus is
[`../../design/roadmap-P7.3-allocator-notes.md`](../../design/roadmap-P7.3-allocator-notes.md).

**`QUERY_CLI` became the directory in the same change.** `measurements.md`
already carried the rule that a declared path is matched by prefix, so whatever
splits the CLI widens the declaration — and it had already been broken by
`where_expr.rs`. Adding `alloc.rs` made it two, so the declaration is now
`pgdump_query-cli/src/`, and five query figures that used to go stale only on

## 7.4: the gate needed a third opener, and the two costs were multiplying

**The gate as specified could not be written.** `settled` is
`target_settled(index, …)`, which reads `index.spans` — the list the splice
rebuilds — so evaluating it before splicing reads a map that stops at the last
gate opening and can never contain the block that just closed. A literal
implementation compiles, passes every existing test, and silently costs a
query's early stop. What shipped has a third opener: a completed block whose
`COPY` header names the queried table, matched on the header alone, which is
deliberately a superset of `target_settled`'s own test. Instrumented over a
40-block dump, 39 of 40 blocks report the gate closed and the settling block
opens it on that third term alone.

**The measured win is 184×, not the ~20× the spec priced.** A 4000-block
`parse` falls 20.75 s → 0.113 s, and its save count 105 → 5. The two costs were
multiplying rather than adding: `SaveThrottle` is a ratio against *elapsed scan
time*, so a scan inflated by per-block splicing keeps earning further saves.
Removing the rebuild shortened the scan, and the shorter scan earned fewer
saves. One consequence is that the interrupt's window is far smaller than the
spec budgeted — five gate openings across a 0.113 s scan, so ~20 ms rather than
~0.2 s.

**A residual survived, so `KD5` was rewritten rather than struck**, and it is
measured rather than argued: `--dqcache none` makes the save a no-op, so the
throttle has nothing to amortize, the gate never closes, and the map is rebuilt
per block exactly as before — `map-only` reads 19.07 s at 4000 blocks against
19.03 s before. That is why `map-only` was re-taken beside the figure the change
was expected to move. Giving the throttle a floor so a disabled cache throttles
too was refused: `map_file` under a disabled cache hands its `DumpIndex` back to
the caller, so a gate that never opens hands back a map of nothing
([`../../design/architecture.md`](../../design/architecture.md), "`parse`
resumes, and saves as it goes"). The entry is re-homed onto P16, which the P7
spec already named as the destination for the appendable-spans rework.

**Three figures were blind to the file they measure.** `per-block-quadratic`
and `map-only` declared `pgdump_query/src/map.rs` and not
`pgdump_query/src/stream.rs`, where `splice` lives, so this change would have
read green against the two tables it moved by two orders of magnitude; both now
declare a `MAP_BUILD` constant that is the pair. `preamble-prepass` was blind a
second way: its second row is `per-block-quadratic`'s 4000-block reading,
borrowed rather than measured, and a borrowed row carries the lending figure's
edges — which it declared none of. It now declares them. The generalisation for
the next figure registered: `depends` names every file on the path the figure
times *and* the edges of every reading it borrows, not the file the mechanism
is named after.

## `KD9` reviewed: struck, then restored to its residual

Slice 7.5 struck `KD9` and filed the remaining 4.3× beside the mechanism as a
property. The review reversed that: the entry is live again, `(c) unowned`,
rewritten to the residual — the same shape 7.4 gave `KD5` a day earlier.

**The strike proved a claim nobody disputed.** Its argument was that the ratio
*cannot be 1×*, which is true and now stands on its own beside the mechanism: a
`COPY` block's terminator is a line-anchored needle it can skip to, an `INSERT`
run's is not, so every byte has to be crossed quote-aware. But the register's
bar for `(c)` is "a defect with a known fix and no owner", and the same slice's
notes doc named **two** — feeding the scan only the bytes past the
already-matched `INSERT INTO <table>` prefix, and dropping the paren-depth pass
that no `INSERT` statement's end depends on. The written record asserted the
residual had no fix and listed two on the next page. Neither is a different
algorithm; both land on `memchr`, which is nearly 80% of the after-profile.

The register's only written test for property-hood is also not met: a property
is "a limitation whose remedy the user already has today", and the remedy here
would be a `COPY`-format dump, which is the producer's choice made before the
file existed.

**The device evidence was read past its device.** "Cold, the difference is
gone" is a claim about the SATA SSD at ~557 MB/s, against a path running at
1422 MB/s warm. It does not carry to the NVMe, where the read no longer hides
the CPU — and `roadmap.md`'s goal names "HDD through NVMe" for the bulk-row
path, which an `INSERT` run is. Slice **7.8** already takes the cold-NVMe
figure, so the evidence that decides this is scheduled inside the phase. The
entry and 7.8's checklist line now name each other, which is what makes that
reading happen rather than be hoped for: leaving the entry struck would have
relied on a future slice noticing that a *struck* number should come back, and
`deficiencies.py` reconciles live entries only.

**What P16 inherits is the sharper find, and it is not about scan time.** An
`INSERT` run cannot be split speculatively at all: where a statement ends
depends on quote, dollar-quote and comment state accumulated from the run's
start, so an arbitrary offset inside one is uninterpretable, and a worker
cannot tell a `);` inside a string from the one that ends the statement. The
most CPU-hungry shape the scanner has is the one region kind cores cannot be
thrown at. Filed to
[`../../design/roadmap-P16-parallel-scan-inbox.md`](../../design/roadmap-P16-parallel-scan-inbox.md),
where it should be read against the sparse-row-index entry already there — an
index covering `INSERT` runs turns the split into a lookup, which is the only
one of the three ways out that is not either trivial or self-defeating. The
same fact bounds P13, whose compressed-block boundaries land mid-statement for
the same reason.

That is also why the restored entry is `(c) unowned` rather than `(b) owned by
P16`, unlike `KD5`: the phase that would naturally absorb a CPU-bound scan is
the one phase structurally unable to absorb this one.

A code marker now sits on `StatementScan::feed`'s paren pass — the cut that is
invisible from the code, since a reader meets a deliberate second `memchr`
pass with a comment explaining why it is fast and nothing saying an `INSERT`
run does not need it at all.

## 7.13: the read path's allocation, and the seam that earned 7.13.1

**The slice was cut in two, and the seam was only visible from inside it.**
7.13's spec row read "`read_range`'s per-chunk zeroed allocation **and** the
copy into each read loop's own buffer, over all three loops". Those are two
different review questions. The allocation is a contained change to one module
that touches no scanner, no map and no batch code, and the whole existing suite
is its check. The copy is a rework of `scan::scan`, `stream::map_forward` and
the replay loop in `stream::table_stream` — three already-tested core paths,
each carrying its own `drain(..used)` — which is precisely the pairing
`process.md`'s sizing rule says is two slices, and precisely what an unattended
session may not put in one review cycle. The row is rewritten to the half that
landed and `7.13.1` carries the rest, with the "ahead of 7.6 and 7.7" ordering
re-targeted onto it, since it is the buffer those two rework a row inside.

**What the allocation half was worth, and what it was not.** A warm 3.00 GiB
`parse` loses 9.4% of its user instructions — 1,882,404,237 → 1,705,902,670,
each side at ±0.00% over five reps, which is the instrument to quote because a
profile is a proportion and this machine was not quiet. Wall time does not
move: 0.55 s → 0.54 s. That is the phase spec's own prediction working, not a
disappointment — the spec says this lever's prize is *inside* the quarter-second
discovery already sits within rather than additional to it.

**The allocator question closed the other way from where the argument stood.**
7.3 measured `jemalloc` at 1.87×/1.19×/1.07× and `mimalloc` at
0.98×/0.96×/0.96×, deferred adoption, and named this slice as owing the
re-take. Re-taken on the pooled read path: `jemalloc` 1.02×/1.11×/1.06× and
`mimalloc` 1.00×/0.99×/1.01×. Both of the cells the decision hung on were this
allocation rather than an allocator — jemalloc's `parse` was 3,161 `madvise`
calls returning a 1 MiB buffer to the kernel once per chunk, and mimalloc's
3–4% `typed` win, the one cell that had reproduced its magnitude across two
sittings, is gone with its spread now above the reference's. The platform
allocator stays, and the deadline 7.3 set — settle before the wrap's sweep pair
— is discharged.

**A figure was nearly published of two different sources.**
`ensure_allocator_binary` short-circuited on `runs/pgdq-alloc-<leg>` existing,
and that file outlives a session: the first re-take here timed the *previous*
session's jemalloc and mimalloc binaries against this session's reference and
reported it as a comparison of allocators. Nothing downstream could notice,
because a stale leg still answers `--version` with its own allocator name,
which was the check in place. The build is now memoized per process, and every
leg is built before the first reading rather than at the rep that first wants
one — a `cargo` build across 24 cores moves the number the next rep takes.
`scripts/test_measure.py` holds both halves.

**And `io.rs` was declared by no figure at all.** Every table that times a
`pgdq` run reads its bytes through it, so this change — the largest single term
in a warm `parse`'s user time — would have read green against all twelve. It is
now its own `READ` mechanism rather than part of `SCAN`, because
`nested-end-to-end` and `census-attribution` declare no scanner path and are
moved by it all the same.

## The allocator table's partial sitting, reviewed

The call stands; the reason recorded for it does not, and the review replaced
it. What 7.13 wrote was that the honest sitting is five figures, "most of a
sweep, an hour of a quiet machine". Both halves are wrong, measurably.

**The closure is four figures, not five, and its cost is 13–27 minutes.**
`allocator` borrows from `census-brace-free` and `nested-end-to-end`; the two
throughput tables borrow the census reading in turn, so re-taking it drags
them. That is the whole graph — there are exactly three `session.borrow` call
sites in `scripts/measure.py`. `census-arrays`, which 7.13's remedy list named,
is in none of them. Durations from `runs/*.log`: `allocator` 278 s,
`census-brace-free` 130–448 s, `nested-end-to-end` 301–621 s,
`scan-throughput-cold` 64–220 s, `scan-throughput-warm` 27–47 s. Every input is
already staged on the SSD, and `--figure` is `action="append"` and
comma-separated, so the set is one invocation.

**What actually decides it is shelf life.** All four are already stale on
`pgdump_query/src/io.rs` — 7.13's own change — as is every other figure that
times a `pgdq` run. A sitting run today produces a self-consistent set the wrap
sweep overwrites inside this phase, and buys the table's **ratios** nothing,
those being within-sitting however the reference column was obtained. The
reasoning is filed beside the table in
[`../../design/measurements.md`](../../design/measurements.md), "Which
allocator a figure was taken under", as a rejected alternative.

## The harness's partial-sweep note understates its own closure

`run_allocator`'s note names the two figures it borrows from directly. The set
a reader must actually re-take is four, because `_throughput_figure` borrows
`census-brace-free` transitively — so the advice printed at the moment someone
is deciding whether to fold in is short by half, which is how 7.13 came to
compute the cost by hand and get it wrong.

The graph is not declared anywhere the harness can read it: `Figure` carries
`depends` and `quoted_by`, both edges of *staleness*, and the *sharing*
relation lives only inside run-function bodies. So `--check` cannot reconcile
it, `--figure` cannot offer the closure, and each run function assembles its
provenance paragraph by hand. Declaring it is out-of-band `M48`, `Blocks`
empty: 7.6–7.11 never touch the harness, and 7.12 — the wrap sweep — is the
slice that wants it.

**The convention it broke was never written down.** Every prior "Taken in its
own sitting" apparatus line names the figures its table was taken *with*; the
allocator's is the first that cannot, because it was taken alone. That is now a
stated rule in `measurements.md`'s apparatus section rather than a practice
with four instances, along with the requirement that a table whose shared
reading was measured alone carries the harness's note into the doc — which 7.13
did, and which is the condition that makes a partial sitting publishable.

## 7.13.1: the read-path lever, read whole — and the wall time 7.13 could not see

**The 54.6% lever is now spent, and the pair's result is not what either half
reads like alone.** 7.13 removed the per-chunk zeroing and reported, correctly,
that wall time did not move; 7.13.1 removed the copy and wall time moved by
17% — 0.48 s → 0.40 s on interleaved reps, with user 0.17 s → 0.11 s, system
flat at 0.30 s and peak RSS 7.9 → 6.0 MB. Only that pair is a wall comparison:
7.13's own 0.55 s → 0.54 s was taken in another window, and the three readings
may not be chained. The instruction counts may, and they are below. The
phase spec's prediction stands as written — the prize was inside the
quarter-second discovery already sat within, not additional to it — but "wall
does not move" was a statement about the allocation, and reading it as a
statement about the lever would be wrong.

The instruction counts are the instrument, five reps a side, spreads under
0.003%: 1,882,404,237 → 1,705,902,670 (7.13) → 1,403,769,503 (7.13.1), −25.4%
over the pair. The `before` leg is a `release` build of `9f3ce5c` in a throwaway
git worktree with its own target dir, which is the shape the harness already
uses for `pgdq-before-throttle`. **The timings are interleaved before/after reps
in one window**, not two runs of five: the machine moved measurably quieter
between the first attempt and the second, and a wall-clock comparison across two
windows on this box is not one.

**The saving is per byte of file, and the brace-bearing shape is the check.**
`--arrays` loses 0.2996 G instructions against the control's 0.2998 G over the
same 3.00 GiB. Only the share differs, because that file spends 20× as long per
byte. A `query` pays it too, smaller for the same reason: −2.1% `strings`,
−1.4% `typed`, whole-run.

**The query path's chunk retention needed no decision.** The spec's 7.13.1 row
asked for it to be "settled explicitly", expecting a conflict between scanning
a chunk in place and `batch::SourceChunk` holding it for zero-copy views. There
is none, for two reasons that were both already true: eviction keys on
`scanner.position()`, which cannot pass a chunk while a row straddling its far
edge is still being carried; and `push_utf8view_field` locates a field's chunk
by *absolute file offset*, so it never depended on which buffer the row was
read out of. Filed beside the mechanism —
[`../../design/architecture.md`](../../design/architecture.md), "The scanner
never owns the bytes it scans".

**A `parse` profile can no longer be read one row at a time, and that is a rule
for 7.6 and 7.7.** With the memmove gone, the two remaining hot rows are
`memchr::One` (the LF search) and `memchr::Two` (the census pre-filter), and
`perf` cannot reliably split them: across eight consecutive profiles `One` spans
39.8–51.8% and `Two` 28.8–37.8%, anti-correlated, which is sample skid between
two adjacent hot loops. Their sum is 78.7% ± 3 and reproduces. Both of the
slices that remain on the `strings` path quote exactly those rows, so each owes
its own set of eight rather than the three that sufficed while a 38% memmove
row sat above them.
