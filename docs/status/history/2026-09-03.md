## The leaf grammar is not the output form, and three docs said it was

Reviewing 12.6's "Decisions worth another look" entry found its premise false.
The entry claimed an `int2vector` literal's *elements* are read more loosely
than any other container's leaf, because `int2vectorin` reads them itself where
every other container hands its elements to their own type's output form.

`predicate.rs`'s `nested_key` takes an `input` flag and threads it through the
**container** arms only; the leaf arm is `order_key(kind, text)`, which takes no
flag, so a dump field and a filter literal go through one function. For the
integer kinds that function is `str::parse`, and Rust's integer parse accepts a
leading `+` and unlimited leading zeros. Verified against
`fixtures/16/types/default.sql`:

| query | result |
|---|---|
| `v_empty = '{+1,02,0003}'` on `integer[]` | matches `{1,2,3}` |
| `v_smallint = '+0'` / `'-0'` / `'0000'` / `'032767'` (scalar column) | all match |
| `v_vec = '+1 0002 3'` on `int2vector` | matches `1 2 3` |
| `v_vec = '32768'` on `int2vector` | refused |
| `v_empty = '{99999999999}'` on `integer[]` | no error, no match |

So the leniency is neither new nor container-specific, and on the one axis
where the two genuinely differ `int2vector` is the **stricter** one: it
range-checks each element to `int16`, where an Int leaf is parsed as `i64`
whatever the column's width. That asymmetry is kept — the reasoning is beside
the codec in [`../../design/architecture.md`](../../design/architecture.md) —
because an `int2vector`'s element width comes from the type rather than from a
column, so there is no wider value for an out-of-range literal to order
against.

What the review changed is the record. `architecture.md` asserted the output-form
rule in three places; all three now say what the code does, and the property
"A literal is read in the type's own output form and no wider" carries its one
real exception beside it, along with the consequence on the *field* side — a
dump field spelled `+1` is taken quietly rather than flagged — which is accepted
so that one shared function keeps a field and a literal denoting the same value
comparable.

The same false rule was printed to users by `nested_accepted_form`'s trailing
clause. That was kept out of this closure — it is a wording change to a
diagnostic and changes no decision — and landed as `M45`, below.

## `M45`: the nested refusal gives the dump's form as advice, not as a boundary

`nested_accepted_form` builds the clause `Error::PredicateValueDecode` prints
after "which is written". Its trailing half claimed to be the boundary of what
is accepted — *"with every element, field or bound written in its own type's
output form"* — and `order_key` does not enforce that: its integer arms are
`str::parse`, so `+1` and `02` are read as `1` and `2` at every depth. It now
reads *"with each element, field or bound spelled as the dump spells it, in

be refused. `predicate.rs`'s
`a_nested_literal_is_lenient_about_the_container_and_strict_about_the_leaf`

## P7's grilling: the phase is re-aimed at row extraction, and parallelism is P16

The phase doc was a sketch written before any of the figures existed, and the
`ba2fc12` sweep re-prices its two central assumptions.

**Discovery is not where the time is.** On the 3.00 GiB control, warm on
tmpfs: `dd` 0.332 s, `pgdq parse` 0.558 s (1.68× the floor), a `strings` query
4.42 s (13.3×), a `typed` query 10.36 s (31×). Cold on the SSD `parse` is
5.78 s against a 5.75 s floor — 1.01×, the device hiding it entirely. So the
whole prize in structure discovery is a quarter-second per 3 GiB, and an order
of magnitude of the project's device-bound goal sits in the row path. The spec
now targets row extraction, and keeps three discovery items on their own
evidence: `KD9`, `KD5`, and the I/O defaults.

**The `\.` needle search is not free, and what it costs is two consumers.**
`CopyEnd::row_count` and the array-shape census both look at every row a skip
would jump over. Counting rows without enumerating them is available
(`memchr::count` over the block extent); the census is not, since it needs the
bytes. Adopting the search therefore means deciding what happens to the census
— for a quarter-second per 3 GiB.

**Readahead's prize is `min(device time, parse time)`, which bounds it to one
device class.** The spec called double-buffered readahead "the single most
likely reason the current scan sits at 33% CPU"; on koji that 67% is disk wait,
which no overlap removes. Cold SATA SSD caps the win at 4%, and the cold table
already reads `parse` at 1.01× the floor, so the kernel's own readahead is
evidently doing it. tmpfs has no I/O to overlap. NVMe is the one device class
where the two are within a small factor — ~0.9 s of device against 0.55 s of
parse CPU per 3 GiB — so it is added as a third regime **for that decision
only**, staged at `/var/tmp/pgdump_query` (`CLAUDE.local.md`). An HDD
throughput figure was rejected: koji already answers the only HDD question the
design has, and a 3 GiB file on a rotational disk measures one file's layout.

**Parallelism is carved out as `P16`.** It multiplies a loop rather than fixing
one, and its blast radius is three already-tested mechanisms — `stream::splice`'s
contiguous-prefix assumption, the census's per-block accumulation, and the
interrupt guard's "bank the last completed block" promise — which cannot share
a review cycle with self-contained per-byte work. It also has two source shapes
to serve once P13 lands, not one. P7 owes it the sparse row index and a written
statement of what a splitter needs from coverage and from the census; the three
P7 inbox entries that were about parallelism moved whole into
[`../../design/roadmap-P16-parallel-scan-inbox.md`](../../design/roadmap-P16-parallel-scan-inbox.md).

**Three more of the phase's decisions, from the same grilling.** It commits to
**no numeric target**: the goals are the cheap optimizations and a solid
understanding of where the time goes, so that a later phase can set a target
against evidence. It is done when every named lever is landed-with-a-figure or
rejected-with-a-figure, and when the cost decomposition of the `strings` and
`typed` paths is published — the durable half, worth having even if every lever
turns out to be worth little. It **measures the allocator early** (glibc against
`jemalloc` and `mimalloc`), so that every later figure is taken under the one it
ships; the choice belongs to `pgdump_query-cli` and never to the library, since
a `#[global_allocator]` there would bind every embedder, and the consequence —
that a published figure is a CLI figure — is stated in the apparatus rather
than hidden. And the **sparse row index moves to P16**, whose splits are the
first thing that reads one; P10 needs the same interval, so whichever runs
first settles it.

**The instrument is a profiler, not a sweep, and "done" means measured rather
than landed.** A whole-file figure costs a machine that has other work, so P7's
primary instrument is a **sampling profile** — seconds per run, attribution per
function rather than per subtraction, and no quiet machine needed to read a
proportion. A profile is a `runs/` artifact and never a figure; a
`measurements.md` table is taken only for a landed lever's before-and-after.
Subtraction across projection widths and the census-off binary stays as the
fallback for what a profile cannot answer, chiefly the device-versus-CPU split.
`[profile.profiling]` inherits `release` and adds line tables and frame
pointers, leaving the profile every published figure is taken with untouched,
and profiles run on the host against tmpfs rather than inside the 512 MB
container.

Deterministic instruction counting (`callgrind`, or `iai-callgrind` as a
dev-dependency) was considered for exactly the shared-machine reason and
rejected as the default: the allocator, zero-copy views and chunk sizing change
*memory behaviour* rather than instruction count, so it would report this
phase's headline levers as free. It stays available for a lever that turns out
to be instruction-bound.

The definition of done follows: **every lever is measured, and every obvious or
cheap win is taken.** No lever is excluded from measurement by its
implementation cost — only from landing. That admits the viewing builder for
`List<Utf8View>`, the largest single prize on the list at ~7.3 µs/row and the
most delicate change on it, as a measured candidate that lands only as its own
final slice with its own review.

**`KD5` is discharged by the gate the throttle already owns.** `stream::splice`
moves inside `if settled || cancelled || throttle.due()`, taking the 4000-block
map from 19.0 s to about 1 s. The interrupt's promise changes from "banks the
last completed block" to "banks the last spliced watermark", and the cost is
bounded by time rather than block count because the throttle is self-tuning:
105 saves across a 20.8 s scan is ~0.2 s of scanning lost. On koji the gate
clears at every `CopyEnd` — blocks 45 s apart, sub-second saves — so the shape
where a lost block is expensive is unaffected. The appendable-spans rework goes
to P16 if a residual survives.

**Two more, and the first is about how the phase runs.** It does not waterfall:
the lever list is what it is committed to *measuring*, and which levers become
code — and in what order — follows the profile, a hunch the profile then
settles included. A lever row is satisfied by a rejection carrying its reading
and its instrument's floor. Where the spec names a hypothesis rather than a
decision it says so, and the `INSERT` fast path is the worked example: `KD9`'s
entry claims the fix is "a second scanner-level fast path", and the code says
the expensive part is `map.rs`'s `Mode::InsertRun` pushing every line into a
`String`, with the large-object region's 0.442 s against `COPY`'s 0.558 as the
supporting reading. Which layer takes the fix is the profile's call, and `KD9`
is corrected in whichever change lands it.

**The chunk-size default is one measured constant.** Runtime probing of
`/sys/block/<dev>/queue/rotational` is rejected: Linux-only, masked inside
containers, and a walk with several ways to be wrong on LVM, dm-crypt, MD, NFS
or an overlay — for a knob whose measured spread nobody has seen yet. The
per-class numbers are published and `ScanOptions::chunk_size` stays tunable.

**The lever table gained the largest bucket, and the phase is sliced.** On the
control, `strings` is 4.42 s and `typed` 10.36 s over 814,362 rows, so scalar
decode plus the typed Arrow build is **7.3 µs of a 12.7 µs row — 57% of a typed
read**, over sixteen ordinary columns with no nesting. Every other lever
targets the shared row machinery or the nested path, so the table read as a
decision not to look at the shape most dumps actually have; it is now a row of
its own, split by the profile into a `decode.rs` half and a builder-append
half, since those have different remedies. A lever the profile finds and the
table does not name is admitted if it is obvious and cheap, by amending the
table with the reasoning here — filing every unlisted finding forward would
read as discipline and would really be a way of not acting on the evidence the
phase exists to gather.

The twelve slices are in `STATUS.md`. **7.1 and 7.2 are ordered and the rest is
allocation order rather than schedule**, stated in both documents, so a slice
landing out of numeric order is the plan working rather than slipping; `7.3` is
the one exception, since an allocator adopted after a figure invalidates it.
`KD5` and `KD9` name slices 7.4 and 7.5 and are named back, and both entries'
detail paragraphs moved out of the drained inbox to sit beside their
mechanisms in `architecture.md` — the `INSERT` one beside "Bulk regions", now
carrying both candidate layers, and the map one beside "`parse` resumes, and

## Two premises under the profiler's symbol fetch were wrong

7.1's apparatus fetched libc's detached debug symbols with an explicit `curl`
into `perf`'s build-id cache, and raised the cache's location for review. The
review overturned the framing rather than settling it: three of the claims the
question rested on do not hold, and checking them is what produced `M47`, which
has now replaced that fetch.

**`~/.debug` is `perf`'s build-id cache, not a location the recipe
introduces.** `perf record` populates it on every run unless given
`--no-buildid`, so it already holds the profiled binaries themselves — 82 MB
after 7.1's six profiles, of which exactly one file came from the fetch. The
question as posed was whether to accept a fourth out-of-repo place or install
with root; neither branch was real, because the directory appears the moment
anyone profiles here.

**`perf` does expose a debuginfod flag.** `perf buildid-cache
--debuginfod[=URLs] -a <dso>` is documented and works — verified against
`/usr/lib/libz.so.1`, which downloaded by build-id and cached `debug`, `elf`
and `probes` in the same place the hand-rolled fetch writes to. What is true is
narrower: the flag is absent from `perf` top-level and from `perf report`, both
of which reject it, and the first version generalised from those two.

**Arch ships `glibc-debug`, in a repo that is not enabled by default.**
`glibc-debug-2.44+r24+g16be1518495f-1` matches the installed `glibc` exactly,
costs 18 MB down and 122 MB installed, and covers `libc`, `libm` and
`ld-linux` together (`%BASE%` is `glibc`). Installed under `/usr/lib/debug`, it
is found through the `.gnu_debuglink` already in `libc.so.6` — no network, no
cache, no environment variable — and `pacman -Syu` keeps it in lockstep with
libc, which a manual fetch does not. It is now installed, and verified the only
way that proves anything: with `~/.debug` moved aside entirely, a profile still
names `__libc_read` and `__libc_start_call_main`, inlined frames included.

**Reaching the debug repository took a second attempt, and the first one is the
instructive half.** Probing `geo.mirror.pkgbuild.com` showed `core-debug` and
`extra-debug` served, and that was generalised into `Include =
/etc/pacman.d/mirrorlist` — which fails, because most mirrors in that list
return a flat 404 for those repos. The debug repository has to name a server
checked to serve it. (`built.archlinux.org`, which the wiki's instructions
name, does not resolve from this machine at all.) One mirror answering is not
the mirror list answering — the same shape of error as the `perf` claim above,
where two subcommands rejecting a flag was generalised into `perf` not having
one.

So an installed package is the better source and a fetch is the fallback for
the machine without one and the DSO no package offers, and the fetch should be
`perf`'s own command rather than five lines re-deriving `perf`'s cache layout
from outside — a path construction that fails silently, putting the `debug`
file somewhere `perf` does not read and yielding bare addresses with no error.
That is `M47`, and the recipe now reads:

```sh
LIBC=$(ldd <binary> | awk '/libc\.so/{print $3}')
BID=$(readelf -n "$LIBC" | awk '/Build ID/{print $NF}')
DBG=/usr/lib/debug/.build-id/$(printf %.2s "$BID")/$(printf %s "$BID" | cut -c3-).debug
if [ -e "$DBG" ]; then
  echo "libc symbols: installed package, $DBG"
else
  echo "libc symbols: no package for build ID $BID; fetching"
  perf buildid-cache --debuginfod=<url> -a "$LIBC"
fi
```

Three of its properties are load-bearing, and `test_measure.py` asserts each.
**It keys on the build ID rather than on `.gnu_debuglink`.** Both paths are
installed by the same package on every distribution that ships one, but only
the build-ID path distinguishes symbols that *match* from symbols that merely
have the right filename — which is exactly the skew `CONTRIBUTING.md` warns
resolves nothing without warning. **The fetch is `perf`'s own**, so `perf`
writes the cache whose layout it owns. **Both branches print the source**,
because a skewed package and a failed fetch are indistinguishable from success
in everything else a profile shows.

`PGDQ_PROFILE_DEBUGINFOD` set empty still skips the step whole rather than
leaving the lookup behind. The escape hatch is for a libc that carries its own
symbols, and there the package lookup would report a miss it has no fetch to
answer — a false alarm in place of the silent failure it was added against.

The change touches `scripts/measure.py`, which `session-drift` declares, so it
owes an `ACKNOWLEDGED` entry on the reachability oracle: `--profile-recipe` is
a subcommand no sweep command shape reaches, and no figure's input, invocation
or timing moved. That entry names a sha, so it is written by the commit after
the one that lands this, as `393a50f` did for `305af4b`.

**The documentation half produced a `CONTRIBUTING.md`, because the doc set had
no home for it.** Two of the three places this was written do not survive —
`CLAUDE.local.md` is machine-local and a slice notes doc is struck at the
phase's keystone — and the third, `CLAUDE.md`, is addressed to an agent working
in the repo rather than to a person setting a machine up. Setup instructions
for a human developer had nowhere to go, which is why they had drifted into a
gitignored file. `CONTRIBUTING.md` now holds the profiling requirement stated
distribution-agnostically, with the two details that cost an hour to
rediscover: the debug repository is often absent from the general mirrors, and
a version-skewed package resolves nothing without warning. `CLAUDE.md`'s
profiling paragraph points at it with a read trigger, `README.md` indexes it,
and `CLAUDE.local.md` is cut back to the fact that the setup is done here.

`docs/process.md`'s doc-set table has no row for this file and was left alone:
it is project-agnostic, and adding one is a process change nobody asked for.

## The decomposition re-prices the lever table, and the `INSERT` +10% is layout

7.2 read the call graphs 7.1 left and took four more profiles. Three of its
findings change the plan rather than only describing it, and all three come
from the same correction.

**Every share in a `perf` profile here is a share of *user* time.**
`perf_event_paranoid = 2` permits user-space sampling only, so the event is
`cpu/cycles/Pu`. A warm 3.00 GiB `parse` is 0.60 s of wall made of 0.30 s
system and 0.29 s user, and `dd` over the same file is 0.29 s that is entirely
system — so a `parse` profile covers slightly under half the scan. Uncorrected,
`memchr::Two` at 17.2% looks like it contradicts the census figure's +0.030 s;
corrected it is 0.050 s, which is the same measurement. Everything below rests
on that.

**The `INSERT` +10% is code layout, and there was nothing to bisect to.** The
spec asked for a differential profile and predicted that two indistinguishable
profiles would be the answer. They were nearly indistinguishable, and
`perf stat` turned that into an attribution: `release` builds at `b70589f` and
at the stamp retire **114.62 G against 114.66 G instructions** — 0.03% apart —
and spend **35.8 G against 40.0 G cycles**, with branch misses, cache misses,
L1-icache misses and frontend stalls all flat or lower on the slower one and
the clock identical to within 0.5%. The whole 4.2 G-cycle difference sits inside
`preamble::scan_buf`, whose source is unchanged across the range and whose 293
machine instructions are byte-identical between the two binaries, differing only
in address. Building both with `-C llvm-args=-align-all-functions=6` collapses
the gap to −1.5% and takes both *below* the faster unaligned build; the same
flag moves the control's `parse`, `strings` and `typed` shapes not at all. So
it is one tight character loop's placement, the flag is not a lever, and what
the finding leaves behind is a rule about reading figures rather than a fix —
[`../../design/measurements.md`](../../design/measurements.md), "Two builds of
one source can differ by layout", with the working beside the mechanism in
[`../../design/architecture.md`](../../design/architecture.md), "Bulk regions".
The `profiling` build reverses the sign of that same difference, which is the
counterexample behind the same rule's second half.

**Two lever rows were sized by a subtraction that was measuring the CLI.** The
`typed` − `strings` gap of 7.3 µs a row was filed as "scalar decode and the
typed column build", and the viewing builder for `List<Utf8View>` was admitted
as "the largest single prize on the list" on the same arithmetic. The profile
puts **79% of that gap in `pgdq::print_batch`** — the CLI turning the batch back
into TSV, which no embedder pays and no library change removes. The library's
own typed extraction is 4.06 µs a row against `strings`'s 2.48, a factor of 1.6
where the wall times show 2.3. Both rows are re-stated in the lever table
against the profile, which is what
[`../../design/roadmap-P7-scan-performance.md`](../../design/roadmap-P7-scan-performance.md)
authorises; **the slice list was left alone**, and whether 7.10 and 7.11 still
have the scope they were given is under `STATUS.md`'s "Decisions worth another
look".

**A lever the table did not name is admitted.** `LocalFileSource::read_range`
allocates `vec![0u8; len]` per chunk — the kernel zeroes 1 MiB, `read_exact_at`
overwrites all of it — and the scanner copies the result into a second buffer
it owns. That is 54.6% of a warm `parse`'s user time, 0.158 s of the 0.60 s scan it was
taken beside — about half the distance between `parse` and the `dd` floor — and
~9% of a warm `strings` query. It has a lever row and no slice, which is the second half of
the same open question.

**Three measure-only rows are answered.** `attach_text` takes **zero samples**
in a 100,000-sample profile of the 4000-block `parse` — rejected with a reading.
The double read is exactly one extra pass, counted with `strace` rather than
estimated: 2.0000× the file's bytes with `--dqcache none` against 1.0000× with
a cache, so it is only ever paid by a query that has not been given one. The
census reconciles with its own figure on the brace-free control and is 81.4% of
the profile on the array-bearing one.

**The `INSERT` fast path goes in `map.rs`, and it is not close.** 58.2% of that
scan is `preamble::scan_buf` under `statement_complete`, 17.3% is
`feed_line`'s opening `from_utf8_lossy(raw).into_owned()`, and
`CopyScanner::next_event` is 0.6% — so the scanner-level candidate the `KD9`
inbox entry named would buy under a percent. `KD9`'s index line and the
"Bulk regions" paragraph both now say so.
