## The v18 statistics prefix was worth fixing, because its degradation was misleading rather than graceful

`TOC_PREFIX_STATS` (`"Statistics for "`, the v18+ `--statistics` component)
stood unrecognized as a deliberate deferral, on the grounds that it degrades
gracefully. The number said otherwise: `fixtures/18/objects/stats.sql` reported
**TOC coverage 126/175 (72%)** where the same schema without statistics
reported **126/147 (86%)**. Each of the 14 `Statistics for Name: …` entries
left two unattributed spans, so the one diagnostic whose job is to tell a user
how much of their file the map understood read 14 points worse than the truth.

It is opt-in, which is why the fix was out-of-band and not a slice:
`InitDumpOptions` sets `dumpStatistics = false` in both v18.6 and master, and
only `--statistics` / `--statistics-only` turn it on, so a default `pg_dump 18`
emits none and the tiling was byte-exact either way. It landed as **M6** — see
"Two out-of-band drive-bys" below.

## The block-count quadratic is two costs, and the throttle only owns one

9.5's throttle does exactly what it was designed to do — 4000-block saves fall
from 4003 to 195, the `1/K` bound, and ~21 s of saving becomes ~1.2 s — and the
series **still** quadruples per doubling: 0.32 / 1.30 / 5.66 / 23.56 s at
500 / 1000 / 2000 / 4000 blocks.

The 2026-08-26 attribution ("the cost is serializing the whole index once per
block, not the write") was half the story. The other half is that every
`CopyEnd` rebuilds the span list whole — `map::Builder::snapshot` clones the
builder's spans, `stream::splice` clones the prefix — so the *map* is
O(blocks²) independent of the cache. The control that separates them is a scan
that never saves at all: `query --dqcache none` over the same files costs
1.02 / 4.58 / 19.67 s at 1000 / 2000 / 4000 blocks. So at 4000 blocks the
cache was ~21 s of 44 s and the map is the remaining ~20 s.

Both series, the save counts and their commands are in
[`../../design/measurements.md`](../../design/measurements.md); the map half is
filed into [`roadmap-phase7-inbox.md`](../../design/roadmap-phase7-inbox.md),
where it meets the entry that already flags `stream::splice` for assuming
coverage is a contiguous prefix. Those two are the same code and should be one
decision, which is why the fix did not ride along here.

## Chunk-granular cancellation alone leaves a block-rich scan unresponsive

The 9.5 spec's guard was "a cooperative flag, checked once per chunk", argued
*against* `CopyEnd` granularity because koji's largest block is hundreds of
gigabytes. The first end-to-end test of it found the opposite extreme: a
4000-block 2 MB dump is **two chunks**, so a scan that takes 23 seconds checks
the flag twice, and a `SIGTERM` sent three seconds in was swallowed — the run
finished normally and exited 0.

The guard now reads the flag at both points. They are complements, not
alternatives: chunk granularity bounds the response inside one enormous block,
`CopyEnd` granularity bounds it inside one enormous chunk, and together the
response is the shorter of the two. The cost is one relaxed atomic load per
block. The spec's sentence is amended in place, per "Spec vs. notes"; the entry
in `STATUS.md`'s "Decisions worth another look" is there because it amends a
sentence the maintainer grilled.

Verified afterwards on the same file with the real binary: `SIGTERM` → exit
143, `SIGINT` → exit 130, both leaving a cache `pgdq info` reports at 57%, and
resuming it produced a cache **byte-identical** to a straight-through parse's.

## An interrupted `parse` gives every column the opposite advice, and that is 9.5.1

`map_file` runs no preamble prepass — `table_stream` does, `parse` does not,
because a full scan recomputes `DumpMetadata` over every span at EOF anyway. So
a `parse` stopped partway leaves a cache whose `metadata` is `None`, and
`resolve_columns` documents what that means: no metadata at all is
`NotDeclared` for every column. `pgdq info --verbose` on a Ctrl-C'd parse
therefore prints

```
    id: not declared — no DDL explained this column
```

for columns whose `CREATE TABLE` is sitting in the same cache's spans. The
truthful answer is `metadata not scanned — finish the parse`, which is exactly
the variant 9.4 added to keep these two apart, and 9.4 could not have caught
this: it asserted the variant against hand-built truncated caches, which carry
the metadata a *query*'s prepass captured. The resolver is right; the producer
is wrong.

The fix is the prepass `table_stream` already runs, moved into `map_file` under
the same "if the first database's preamble is not already complete" guard. It
did not land with 9.5 because it changes what every cold `parse` does before
mapping — a second review surface, and the reason 9.5 was made to land alone in
the first place. It is slice **9.5.1**, and Phase 9 stays open for it.

## The 9.5 review

**The two-granularity guard stands, and the finding is about the spec's form.**
The amendment itself was never in doubt; what the review added is why it was
needed. A spec that *enumerates* check points ("once per chunk") is a spec the
next loop invalidates, so both `roadmap-phase9-partial-reporting.md` and
`architecture.md` now state the principle — read the flag wherever the loop can
cheaply reach it — with the chunk and `CopyEnd` checks as its current
instances. Two limits found while confirming this, both now recorded: the flag
is read *before* `ByteRangeSource::read_range`, so a scan blocked in a slow read
notices only when it returns; and `scan::scan`, hence `index::scan_preamble`,
ignores the flag deliberately — a stop there is indistinguishable from reaching
the first `COPY` header, so a truncated preamble would be cached as a complete
one and its DDL believed. The preamble is an uncancellable region bounded by
its own length. The remote-storage half of both went to the Phase 6 inbox,
where a ranged GET can hang and the prepass is the first thing a cold query
does.

**The map's quadratic half: the cheap fix was found, priced, and declined.**
`index.spans` is rebuilt at every `CopyEnd` (`stream.rs`, `splice` over
`Builder::snapshot`), but for `pgdq parse` nothing reads it between saves —
`target` is `None`, so `target_settled` never runs, and the only consumers of a
current `index` are the throttled save and the chunk-top interrupt save. Gating
the splice on the throttle the way the save is already gated would fire it
`n/20` times instead of `n`: ~19.7 s → ~1 s at 4000 blocks, using the gate 9.5
had just built. It is not taken. It would make an interrupt bank the last
*saved* watermark rather than the last *completed block*, reversing the
guarantee 9.5 spent the slice establishing, and the coupling cannot be dodged
locally because `Builder::snapshot` asserts `Mode::Idle` — the chunk-top check
cannot re-derive the spans mid-block. Phase 7 may still take it, as a
deliberate change to the interrupt's promise rather than as a cleanup; the
analysis is in its inbox so it is not re-derived.

**9.5.1 keeps the prepass as its fix.** The alternative considered was to leave
`parse` alone and fix the *reporting* — teach `resolve_columns` that
`metadata: None` on an index with `scanned_through < size` means
`MetadataNotScanned`, not `NotDeclared` (`resolve.rs` documents the collapse
deliberately, under an assumption that predates interrupted caches). It was
rejected on the facts: `scan_preamble` breaks at the first `CopyStart` and the
prepass sets `scanned_through = preamble_end`, which `map_forward` resumes
from, so running it in `parse` costs **one** read of the preamble, not two; and
the prepass saves before `map_forward`'s first flag check, so an interrupt
during the preamble is honoured immediately after with metadata already banked.
The prepass therefore makes an interrupted cache genuinely *typed* rather than
merely correctly labelled, which is what 9.4's partial reporting was for, and
it leaves no case the relabelling would have covered.

**9.5.1's scope, and what it absorbs.** The invariant that decides this is in
`preamble.rs`: `dump_metadata_from_spans` may be called at EOF, or at the start
of the current database's first `COPY` block (I1), and nowhere else — anywhere
else "would make the trailing database's `preamble_complete` a lie". The second
kind of point **recurs**, once per `\connect`ed database, and `map_forward`
already sees the event with the governing database tracked. So the slice is not
"run the prepass" but "state the metadata at every legal boundary": without the
recurring half, a `pg_dumpall` parse interrupted inside database 3 would hold
DDL for database 1 alone, having read database 2's entire preamble. It costs one
recompute per database and nothing at all on a single-database dump. Because
that places the recompute inside `map_forward`, the slice absorbs the queued
out-of-band item that moved the EOF recompute out of `map_file` — the same code,
and the divergence it removed (a cold query and a warm one typing a `pg_dumpall`
alike) is this defect seen from the other end. Two drive-bys still ride together
afterwards: the `--dqcache none` error text and `TOC_PREFIX_STATS`.

**Order after 9.5.1.** The koji wrap run goes first — detached, logged under
`runs/`, read by a later session — because it is an hour of wall time nothing
else depends on and 4.6's measurement wants its log; serializing it behind two
phases of work would only delay it. Then the two drive-bys, while Phase 9's
context is fresh and reviewing them together is cheap, then Phase 4's **4.4.4**
and **4.6**, then the wrap. Phase 9 has no unticked slices once 9.5.1 lands, so
that point is a phase boundary: an unattended loop stops there, and the next
phase needs grilling and a spec before it has slices at all.

**Two traps named for 9.5.1 before it is dispatched.** The recompute must fire
**once per database**, keyed on a `CopyStart` whose governing database differs
from the one last covered — recomputing at every `CopyStart` and relying on
idempotence would put a third quadratic in the loop this same day measured two
in. And the recurring half needs its own test, because a prepass-only
implementation passes every prepass test: `edge_cases/dumpall.sql` spans more
than one database and 9.5's `CancelsPast` trips the cancel flag at a chosen file
offset, so cancelling inside the second database's data is deterministic. koji
cannot stand in for it — it is single-database — but the koji wrap run does
carry the real-scale half of the prepass, that an interrupted cache comes back
typed.

## A cold query types every database, and the rejection that said it could not has been rewritten

9.5.1 put the `DumpMetadata` recompute inside `stream::map_forward`, at each
`\connect`ed database's first `COPY` block. Because that loop has two callers,
`table_stream` gets it too — it now reads `index.metadata` *after* the mapping
pass rather than before — so a cold query on a `pg_dumpall` types a later
database's blocks exactly as a query after `pgdq parse` does. That is the
divergence the 2026-08-26 review asked to remove, and removing it is what the
absorbed out-of-band item was.

`architecture.md` carried a standing rejection against this shape: *"having the
live scan accumulate preamble as it goes … the stream would learn a column's
type partway through its own run and the schema would again depend on how far
the scan had got."* The rejection was written before mapping and streaming
became separate passes. Today the map is finished before the first batch, and a
file containing any `\connect` is never early-stopped
(`stream::target_settled`), so the map that answers is always the whole file's:
the schema depends on a deterministic function of the file, never on replay
progress. The paragraph now rejects the narrower thing that is still wrong —
the **row replay** reading DDL as it passes it — and says why the mapping pass
doing so is a different claim.

**The consequence worth writing down: neither `MetadataNotScanned` is
reachable from a mapping scan any more.** A database's DDL is stated strictly
before any of its blocks can be banked, so a block in the map always has its
database covered. `Error::MetadataNotScanned` (streaming refuses) and
`ColumnResolution::MetadataNotScanned` (reporting degrades) both stay: they are
the right answers for a caller presenting metadata some other scan built — an
embedder's own index, or a `ResumeToken` carried across one — and deleting
either would settle, by default, the Phase 6 question of which answer an
embedder gets. The narrowing is filed into
[`../../design/roadmap-phase6-inbox.md`](../../design/roadmap-phase6-inbox.md).
I1's "Relied on by" now names both mechanisms and says which half of the
invariant licenses each: the *scope limit* (per database, not per file) is what
makes the recurring boundary exist at all.

## Grilling 9.5.1's three unattended calls

**The prepass's "bounded by its own length" now has numbers.** koji's preamble
is **63,333 bytes** of 784,019,857,152 — the whole uncancellable region is one
read. The most preamble-heavy shape that can be constructed, a 4000-table
bench file that is 49% preamble by bytes, maps in **0.04 s** against ~20 s for
its full `parse`. So the region grows with the schema, not with the data, and
running it unconditionally — even when the cancel flag is already set — costs
nothing a user can perceive on a local file. Both figures and their commands
are in [`../../design/measurements.md`](../../design/measurements.md). The
remote case is untouched by this and stays a Phase 6 question: 63 KB is still
one ranged GET that can hang.

**`Error::MetadataNotScanned` is unreachable, not merely narrow — the slice's
own STATUS entry was wrong.** It claimed a `ResumeToken` carried across a
re-scan could still present the condition. It cannot: `stream::resolve_block`
is private, its three call sites are all in `table_stream`, and all three use
the `metadata` read *after* that call's own `map_forward` — `resume_state`
included. A block being replayed is in the map, so its database is covered.
`ColumnResolution::MetadataNotScanned` is the half that stays reachable, and
for a different reason: `resolve_columns` is `pub` and takes caller-supplied
metadata.

Both are kept. The check is what stands between a future reordering — moving
that metadata read back above the mapping pass — and a silently wrongly-typed
row, which is the failure the whole streaming/reporting asymmetry exists to
prevent. Deleting it would also settle by default the Phase 6 question of which
answer an embedder gets. But the test that used to exercise it was the one
9.5.1 rewrote, so it was untested defence, which is how a guard gets deleted as
dead six months later: `stream.rs` now has a unit test calling `resolve_block`
directly with metadata missing the block's database.

**`pg_dumpall` orders its databases `template1` first, then by `datname`.**
`ORDER BY (datname <> 'template1'), datname` in `pg_dumpall.c`'s
`dumpDatabases` query — identical in v13.23, v18.6 and master. That makes a
fixture's database sequence predictable by name, which is what lets a second
data-carrying database be placed deliberately: `pgdq_fixture_2` sorts between
`pgdq_fixture` and `postgres`, giving two consecutive databases with blocks
followed by an empty one. The empty trailing database is worth having on its
own — it is the case only the EOF recompute covers, since no `COPY` header ever
arrives for it.

**The fixture work is out-of-band, in its own round.** It changes no decision
any spec records — 9.5.1's contract is delivered and unchanged, and this
strengthens its verification — which is the admission rule's line, so it is not
an earned `9.5.2`. It is kept out of the round carrying the `--dqcache none`
error text and `TOC_PREFIX_STATS` for a review reason rather than a scoping
one: a six-major fixture regeneration and two error-message changes in one diff
is one diff where the reviewer has to read thousands of regenerated lines to
reach two one-liners.

**Three details the fixture decision pinned.** The second database is
`pgdq_tenant`, not `pgdq_fixture_2` — the latter is what all three synthetic
concatenation helpers already rename their copy to, and both constructions are
about to sit in one test file, where a failure naming `pgdq_fixture_2` would
not say which it came from. It is created and dropped for the `edge_cases`
schema only, gated in `create_fixture_db`/`drop_fixture_db` the way
`prepare_tablespace_dir` is already gated on `objects`, so `dump_flag_set`
stays a pure dump-and-write function rather than growing a side-effecting
special case. And the concatenated helper is kept beside the real fixture in
`map_file.rs` rather than replaced by it: I9 makes the two genuinely different
shapes, and a bare concatenation is what `cat a.sql b.sql` produces, which no
other fixture covers.

`pgdq_tenant`'s DDL goes in `scripts/fixture_schema_edge_cases_tenant.sql`,
loaded by an explicit second call in `create_fixture_db`'s `edge_cases` branch.
`schema_file()` maps a fixture *directory* to a file, so
`fixture_schema_pgdq_tenant.sql` would read as a fifth fixture set that does
not exist; the compound name says the file belongs to `edge_cases`. Rejected: a
`SECOND_DB` table generalising it — a mechanism for one caller with no second
use in sight, where the generator's existing style is explicit per-schema
branches. Rejected: inlining the DDL as a Python constant — every other
fixture's DDL is a readable `.sql` file, which is what makes the fixture set
reviewable.

## The koji wrap run is launched, and it needed two container facts nobody had

`runs/koji-wrap.sh` drives the wrap run in one detached pass: a cold `parse`,
`SIGTERM` twenty minutes in, a report on the interrupted cache, a resume to
completion, and a report on the finished one. It is host-side and
gitignored — a one-off orchestration around a machine path — and everything a
later session needs is stated inline in `runs/koji-wrap.log`, which names each
check's verdict rather than leaving it to be re-derived from the scan output.

Two facts about the container recipe were wrong in `CLAUDE.md` and are now
corrected there, both found by dry-running the plumbing against koji for ten
seconds before spending an hour on it:

**`sh -c '/pgdq …; echo exit=$?'` makes `sh` the signal's recipient.** The
recipe as written leaves `sh` as PID 1; it does not forward, so the runtime's
`SIGKILL` follows and the guard never runs. The run must `exec` the binary,
which costs the `echo exit=$?` line — the exit code comes from
`sudo nerdctl inspect -f '{{.State.ExitCode}}'` instead.

**The `postgres` images set `STOPSIGNAL SIGINT`.** So `nerdctl stop` on the
documented recipe exercises the `SIGINT` path and exits **130**, not the 143
`CLAUDE.md` claimed. Both paths are guarded and both were verified by 9.5 at
fixture scale, so nothing is wrong with the binary; what was wrong was the
sentence that said which one a container stop reaches. The wrap run passes
`--stop-signal SIGTERM` explicitly, so it tests the path the docs describe.

## Two out-of-band drive-bys: M5 and M6

**M5 — `info --dqcache none` names its remedy.** The message now names
`pgdq parse --source <file> --dqcache <path>`, the way `Error::FieldDecode`
names `--schema-mode strings`. It is formed in the CLI rather than in
`Error::CacheDisabled`, because the remedy is command-specific: `parse` rejects
the same flag for the opposite reason, and the library error is shared. The
manual gains the two-line recipe for the case that motivates it — a read-only
directory beside the dump.

**M6 — `TOC_PREFIX_STATS` is recognized.** `parse_toc_header_line` now strips
`"Statistics for "` as it already stripped `"Data for "`. The second half is
the one that is not symmetric: `looks_like_toc_name_line`, the boundary signal,
accepts the stats prefix and still refuses the data one. A statistics entry
heads an ordinary `pg_restore_relation_stats()` statement, so the comment's
span must run into it; a data entry heads a `COPY` block, which arrives as its
own scanner event and opens its own span. Treating the two alike in *both*
functions is the mistake available here, and it would have split every `COPY`
block's header off from its data.

`fixtures/18/objects/stats.sql` reports TOC coverage **140/161 (87%)** where it
read 126/175 (72%), and `STATISTICS DATA: 14` now appears in the object census.
The tiling was byte-exact throughout and is unchanged — the 14 points were the
diagnostic under-reporting itself, which is what made this worth doing rather
than leaving as graceful degradation.

## Grilling M6 found the reason recorded for it was wrong, and a gap behind it

The asymmetry M6 introduced — `looks_like_toc_name_line` accepts
`"Statistics for "` and refuses `"Data for "` — was first justified as "a data
entry heads a `COPY` block, which arrives as its own scanner event". That is
**false under `--inserts`**, where a `-- Data for Name: …; Type: TABLE DATA`
comment heads an `INSERT` run, a statement like any other
(`fixtures/16/edge_cases/inserts.sql`).

The asymmetry is still right, for a reason one level down.
`Builder::on_copy_start` reads the pending `TocHeader` out of its
`Mode::Comment` arm; its `Mode::Statement` arm pushes a separate span and
passes `None`. `saw_name` is what routes a comment block from the first mode
into the second, so accepting `"Data for "` in the boundary signal would make
**every `COPY` block in the file lose its TOC entry** — koji's 74 included.
Forced, not chosen, which is why the record now says so in `map.rs`,
`architecture.md` and the `STATUS.md` entry.

**The gap the counterexample exposed.** In an `--inserts` dump the `Data for`
comment closes as a `Framing` span that *owns* the TOC entry, and
`push_span` clears `governing_toc` for a `Framing` body — so the `INSERT` run
after it carries `toc: None`. That is exactly the two-spans-one-attributed
shape M6 closed for statistics: `edge_cases/inserts.sql` reported TOC coverage
**30/52 (58%)**. The `COPY`
path is unaffected (`edge_cases/default.sql`: 31/48, all six `TABLE DATA`
entries attributed), tiling is byte-exact either way, and the object census is
already correct because it counts the owning `Framing` span. Queued as **M7**
and closed the same day — see "M7 attributes an `--inserts` dump's rows"
below.

**One further consequence of M6, and the structural reason it is safe.**
`feed_line` calls `looks_like_toc_name_line` outside the mode machine, to clear
a pending `-- load via partition root` marker whenever a new TOC entry starts
(I2). A `Statistics for` line now clears it too. The question that matters is
whether a statistics entry can land *between* a marker and the `COPY` header it
belongs to, which would drop a partition's root attribution. It cannot: the
marker sits inside a single TOC entry's own output, after its
`-- Data for Name:` comment block and immediately before its `COPY` header
(`fixtures/16/partitions/default.sql:242-247`), and `_printTocEntry()` writes
one entry's header and body contiguously — no other entry's header line can
occur inside that window. Empirically the fixture agrees: every `Statistics
for` entry in `fixtures/18/objects/stats.sql` is past the last `COPY` block.
So the change can only discard an already-superseded marker, and a test for the
interleaving would be a test for something the format cannot produce.

## The wrap run's rulings

**The real-scale interrupt test stands as taken, down the `SIGINT` arm.** Leg 1
was meant to exercise `SIGTERM` and exercised `SIGINT` instead, because
nerdctl ignored `--stop-signal`. Not re-run: the two arms differ by four lines

## M7 attributes an `--inserts` dump's rows, and the predicted figure was wrong

**The change.** `Builder::step`'s `Mode::Comment` close arm now opens
`Mode::InsertRun` directly when the line closing the block is an `INSERT INTO`,
at the *comment's* own offset and carrying its `TocHeader`. Exactly the shape
`on_copy_start`'s `Mode::Comment` arm already produces for a `COPY` block, and
the only route available: `looks_like_toc_name_line` has to keep refusing
`"Data for "` (see the M6 grilling above), so the comment would otherwise close
as a `Framing` span, and `Framing` is one of the three kinds `governing_toc`
inheritance never crosses. `governing_toc`'s rule is untouched, which is what
kept this out-of-band.

Absorption is unconditional, like `on_copy_start`'s: a comment block carrying no
TOC header is folded in the same way. The version-header block is unreachable
here for the same reason it is there — `pg_dump` always writes its `SET`
statements between the header and any data — so the `server_version` /
`pg_dump_version` fields that arm drops cannot be live.

**The predicted 35/52 was wrong; it is 30/47.** The queued description expected
the attributed count to rise against a fixed denominator. Absorbing the comment
*removes* a span instead: the five `Framing` spans that held the entries are
gone, the five `Data` spans that hold the rows now hold the entries, and
`fixtures/16/edge_cases/inserts.sql` goes 30/52 (58%) → 30/47 (64%).
`column-inserts.sql` moves identically. `data-only.sql` is `COPY`-based despite
the name and does not move; `default.sql` stays 31/48. The object census stays
`TABLE DATA: 5` in every case — the entry was always counted, just against the
wrong span.

**`public.empty_table` is why five, not six.** Its entry has zero rows, so its
comment block runs straight into the next entry's without an intervening
statement, and `Mode::Comment` overwrites `*toc` — only `escapes` survives from
that pair. Unchanged by M7 and unrelated to it; it is the same absorption
`inserts_dump_with_an_embedded_newline_value_still_tiles` already documents.

**Pinned two ways**, because neither alone says enough: a `map.rs` unit test
(`an_insert_run_absorbs_its_data_entry_and_owns_it`) fixes the mechanism —
one span, opening at the comment, `toc_owned` — and a fixture test
(`tests/map.rs`, `every_insert_run_owns_its_data_entry`) fixes the property
across the real file, checking the runs rather than the entries precisely
because of `empty_table`.

## Grilling M7: both entries clear, and `--disable-triggers` breaks attribution outright

`STATUS.md`'s "Decisions worth another look" carried two M7 entries. Both are
closed; the grilling that closed them found two things neither entry was about.

**The corrected figures reproduce.** `pgdq parse` + `info` on today's tree:
`edge_cases/inserts.sql` 30/47, `column-inserts.sql` 30/47, `default.sql`
31/48, `data-only.sql` 6/21. Nothing to rule on — the entry existed only
because the queued prediction (35/52) was wrong, and the real number was
already recorded.

**Unconditional absorption stands, with a better reason.** The gated version
(`if toc.is_some()`) differs only for a comment block `parse_toc_header_line`
cannot parse that is immediately followed by `INSERT INTO`. `pg_dump` cannot
write that. What decides it is `pg-dump-compatibility.md`'s producers-other-than-`pg_dump`
row: a hand-written dump reaches the shape trivially (`-- a note` above an
`INSERT`), and there absorbing yields one `Data` span where gating yields a
`Framing` span plus a `Data` span. So the symmetry with `on_copy_start` is a
consequence of calling each path right, not the justification for either.

### `--disable-triggers` puts a statement between the entry and its data

`_printTocEntry(AH, te, true)` writes the `-- Data for Name:` block;
`_disableTriggersIfNecessary(AH, te)`, called immediately after it in
`restore_toc_entry()`, writes `SET SESSION AUTHORIZATION DEFAULT;` (first entry
only, via `_becomeUser`) and `ALTER TABLE … DISABLE TRIGGER ALL;`. The comment
is therefore not adjacent to the data — which is the one thing both
`on_copy_start`'s `Mode::Comment` arm and M7's `INSERT`-run arm depend on.
Recorded as **I31**.

Reproduced against 16.15 on a two-table scratch database, `COPY` and
`--inserts` form alike: **TOC coverage 2/24, and the two attributed spans are
the comment blocks themselves.** No data span in either file carries an entry.
Accepted as a known gap rather than fixed — see `STATUS.md`, which also carries
the three coordinated changes a fix needs and why that makes it a graded slice
rather than a drive-by.

### M6's asymmetry had a third wrong reason, and the test is why

The reason recorded on 2026-08-27 was that `on_copy_start` "reads the pending
`TocHeader` out of its `Mode::Comment` arm, and its `Mode::Statement` arm
pushes a separate span and passes `None`, so accepting `"Data for "` here would
make every `COPY` block in the file lose its TOC entry". That is false.
`on_copy_start`'s `Mode::Comment` arm never reads `saw_name`, and on a default
dump the close arm that `saw_name` governs never runs for a `COPY` block at
all: the blank line after the block's `--` is absorbed in place, and
`scan::CopyScanner` intercepts the header line as `Event::CopyStart` before
`feed_line` sees it.

The experiment: patch `looks_like_toc_name_line` to accept `"Data for "` and
run `cargo test --workspace`. **One** test fails —
`a_statistics_entry_parses_and_opens_a_span`, on its own
`assert!(!looks_like_toc_name_line("-- Data for Name: …"))`. All 169 others
pass. A tautological assertion is what let three successive wrong reasons stand
unchallenged, so replacing it is queued as **M8**.

The refusal is still right, and I31 is what makes it right. On a
`--disable-triggers` dump the patched build goes **2/24 → 1/22**: absorbing
routes the entry into `push_statement_span`'s `Framing` veto, and the leading
`SET SESSION AUTHORIZATION DEFAULT;` classifies `Framing`, so the entry is not
misplaced but destroyed. Refusing leaves it on a `Framing` span of its own —
worse than attributed, better than gone.

**The structural fact underneath both:** `on_copy_start`'s `Mode::Idle` arm
passes `None` rather than inheriting `governing_toc`, unlike `step`'s own
`Mode::Idle` arm, which seeds `toc: self.governing_toc.clone()`. That asymmetry
is why no rearrangement of the comment-close logic alone can recover the entry
across an intervening statement. Measured: **904 `COPY` spans across the whole
fixture tree, none unattributed** — so that arm is reached by nothing the tree
contains, and `--disable-triggers` is the only shape known to reach it. It
keeps no separate known-gaps entry of its own: it is one finding with the gap
above, and it is recorded beside the mechanism in `architecture.md`, where
anyone touching `on_copy_start` meets it.

## 4.4.4's refusal order: the argument for it was a hypothetical, and did not need to be

The array arm tests "element is opaque" before "element is an array", and the
order is dead: the opaque test matches a bare terminal (`box`, or a `TypeDef`
of kind `Base`/`Shell`) where the array test matches that same name with bounds
appended, so no input reaches both. `resolve_array` defended keeping it with a
counterfactual — I22's answer "must win if that ever stops being true".

**The counterfactual was the wrong argument, and the right one makes the
question small.** Both refusals answer `Utf8View`. The order can therefore only
ever select a *label* — `OpaqueElementType` against `NestedArrayElement` — and
never a type, so no caller's behaviour depends on it and keeping it costs
nothing. Both `resolve_array` and `architecture.md` now say that instead.

**What the order currently gets wrong, and why it is not scheduled.** An array
over a domain whose base is itself an array of an opaque type — `CREATE DOMAIN
d AS mybase[]`, a column of `d[]` — answers `NestedArrayElement`, which is true
and silent about the delimiter not being `,`. Making it answer
`OpaqueElementType` means testing opaqueness recursively through the element's
own array levels. That is a behaviour change, so it would need a slice, and
what it buys is a better *diagnostic* on a shape `pg_dump` cannot write (I21
writes only `elem[]`) — it reaches us only from hand-written DDL, and the
column is a string either way. Both docs name the alternative so the next
reader does not have to re-derive it.

## 4.6 owes three figures, not one

The spec named one — array decode throughput as a ratio against `text` columns.
Two more have a claim on the same run, and the run is the expensive part:

**The census cost on array-bearing rows was already promised to 4.6 in
writing.** `measurements.md`'s census section measures the census as free on
brace-free data — deliberately the koji shape, where every row is rejected by
the pre-filter — and says the array-bearing case, where the pre-filter passes
and every field is inspected, "is not measured here; it belongs with the array
stress data (slice 4.6)". It is a different code path from the decode ratio:
the census runs in the *scan*, the decode ratio in the *query*. Reassigning it
was considered and is not available — Phase 7 is the figure's consumer, not a
producer, so there is no other owner.

**Composites were the gap nobody had named.** Phase 4's deferral to Phase 7 is
that *nested* values always copy and Phase 7 "should measure before it widens".
That covers a composite's per-field copying exactly as much as an array's
per-element copying, and 4.6's stress data is the only data that will ever
carry a composite column — koji has none. Without it Phase 7 decides half its
question on evidence and half on inference.

**The shapes.** `v_int_array` (3-5 elements) and `v_int_array_long` (~50), same
element type, because Phase 7's question is the *per-element* cost and one
length cannot separate the slope from the per-value overhead; plus `v_comp`,
two fields. All non-`NULL` and uniform 1-D. Koji's own six array columns are
entirely `NULL`, which is the realistic shape and the wrong one to measure — it
would time the null check rather than the decode — so that observation is
recorded beside the figure instead of built into it.

**It is a section in `generate_perf_data.py`, behind `--arrays`.** The
one-script-per-benchmark precedent that made `generate_block_count_bench.py`
its own file is about whole-*file* shapes; `generate_perf_data.py` is already a
multi-column stress table (`v_long_text` and `v_escaped` sit beside `v_text`
for this reason), and `measurements.md`'s standing rule wants the ratio taken
on one file in one session — which a sibling column gives for free.

**The flag is load-bearing, and finding out why is what round 3 was for.**
`generate_perf_data.py`'s default output backs two existing figures that depend
on what it does *not* contain. `measurements.md`'s census figure states it
outright: the control "holds no `{` or `[` in any data row, so every row is
rejected by the census's own pre-filter after one pass over its bytes… That is
deliberately the koji shape." Verified against the generator — lorem words, hex
`bytea`, numerics, UUIDs, and a high-escape column using only `\`, `\t`,
`\n`, `\r`. Adding array columns unconditionally would leave that figure and
the scan-throughput table with no command that reproduces them, and
`measurements.md`'s own rule then calls for deleting them. Gated, the default
output is byte-for-byte unchanged.

*Rejected:* a second always-emitted table, `public.perf_nested`. It keeps a
brace-free table for the census pre-filter but not the *file-level* scan
figures, which would then cover both tables — half a fix.

**Which instrument takes which figure.** Three exist. `pgdq query` (with
`--schema-mode typed|strings`), `benches/decoders.rs` (per-type micro) and
`benches/whole_file.rs` (criterion, already reading this generator's output).
The decode ratio takes **two** of them: the micro, because Phase 7's question
is the per-element slope and that is where every other per-type decode cost
lives; and `pgdq query --schema-mode typed` against `strings` on the same file,
because `strings` resolves everything to `Utf8View` and is therefore the
control the end-to-end ratio needs without a second file. The census figure
comes from `parse`, since the census runs in the scan. `whole_file.rs` is
**rejected** despite already being wired to the generator: a whole-file scan
dilutes the array cost across the other sixteen columns and then duplicates the
end-to-end run more expensively.

This widens 4.6 beyond what the spec committed to, so it is a spec amendment
rather than a drive-by: `roadmap-phase4-composite-decoding.md`'s "The
performance deliverable is a ratio, not a gate" and its 4.6 slice row both now
say three figures.

## M8: the `Data for` refusal is pinned by behaviour, and three doc comments say why

The refusal was pinned by nothing but
`a_statistics_entry_parses_and_opens_a_span`'s
`assert!(!looks_like_toc_name_line("-- Data for Name: …"))` — an assertion that
restates the predicate, so it can only ever fail for the tautological reason.
That is how three successive wrong reasons stood unchallenged (above, "M6's
asymmetry had a third wrong reason, and the test is why").

It is replaced by `a_data_entry_keeps_its_own_span_when_disable_triggers_intervenes`,
a span-level test over I31's shape: the `-- Data for Name:` block, `SET SESSION
AUTHORIZATION DEFAULT;`, `ALTER TABLE … DISABLE TRIGGER ALL;`, then a `COPY`
header driven through `on_copy_start`/`on_copy_end` the way
`a_data_span_carries_the_toc_header_…` already drives one. It asserts the entry
survives on the comment block's own `Framing` span — `toc_owned` true, name
`t` — and, separately, that the data span carries no entry, so the test is not
read as a claim that attribution works on such a dump. That second half is the
accepted gap, not the property under test.

**It fails for the right reason.** Patching the predicate to accept `"Data for "`
leaves the whole workspace suite green except this one test, which panics on
`the entry survives on the comment block's own span`: the header is destroyed
by `push_statement_span`'s `Framing` veto rather than misplaced. Same experiment
that exposed the tautology, now with a test that answers it.

The doc comments on `looks_like_toc_name_line` and `parse_toc_header_line`
carried the superseded `on_copy_start` reason and now carry the I31 one. A
**third** copy of the same false claim — the inline comment in `Builder::step`'s
`Mode::Comment` close arm, not named when M8 was queued — is corrected with
them: leaving a reason we had just established is false, in the same module, is
the trap the other two were being fixed for. No behaviour change.

`architecture.md`'s "TOC enrichment" already held the durable half of the
reason, but one sentence of it — "Accepting `"Data for "` breaks no
behavioural test in the suite" — was true only while the tautology was the
only pin, so it is replaced by what pins it now.

**The type spellings.** It declares `time`, `timestamp` and `timestamptz`.
`pg_dump` writes `time without time zone` and the two long `timestamp` forms,
which is all `pgtype::resolve_declared_type` maps, so those three columns
resolve `Unknown` and stay `Utf8View`. Neither mode ever decodes them. This is
why `pgdq parse` reports "3 of 16 columns unmapped" on the control input.

**The fractional seconds.** It formats with `%H:%M:%S.%f` — always six
digits — over whole-second timestamps, so every value ends `.000000`.
`decode.rs`'s `format_hms_frac` trims trailing zeros and drops an all-zero
fraction, matching PostgreSQL.

**`v_real`.** It writes `repr()` of a Python float, a float64's 17 significant
digits, into a column declared `real`. `typed` decodes to `Float32` and
re-renders the shortest string that round-trips an `f32`, so
`-510216.29239304754` comes back `-510216.28`. `pg_dump` writes what
`float4out` produced, which round-trips by construction.

**The first two are coupled**, and that is the part worth not re-deriving:
correcting the spellings alone would send three columns that currently never
decode through a decoder that re-renders them differently from the file. One
silent problem becomes three loud ones. They move together.

`v_bytea` looks like a fourth and is not. The generator writes `\\x…` with a
doubled backslash and so does `pg_dump` — `fixtures/16/types/default.sql`,
`public.t_bytea`, holds `\\xdeadbeef00ff` — and both schema modes print `\x…`
for it. The `typed`/`strings` divergence on this input is `v_real` alone.

**What follows.** The consequence is a validity problem, not a fidelity
complaint: a benchmark whose purpose is the typed path measures 13 columns
while its table says 16. Fixing it changes the default output's bytes — rows
lose about 30 of 3,967 — which re-opens the scan-throughput table, the
brace-free census figure, `whole_file.rs`'s baseline and all three of 4.6's
figures. So the fix and the re-measurement are one change, and not 4.6's: it
reworks a tested benchmark input and re-takes five recorded figures, which is
the case `process.md`'s "Working unattended" says not to bundle with
high-confidence work.

**Admitted as out-of-band, `M10`.** It changes no decision any spec records —
nothing ever decided that the generator's declared types were right; nobody had
looked — and it fits one session. Phase 4's `--arrays` rationale ("the flag
exists precisely so the default output stays what this figure and the
scan-throughput table were taken on") is the near miss: the fix changes that
baseline, but re-takes its figures in the same change, which is the state the
rationale wants. `M3` is the precedent — a benchmark input plus the figures
taken on it. There is also no phase it could join without corrupting one:
appending it to Phase 4 as a `4.7` puts unrelated work in a phase's checklist.

**`M10` carries three things, not one.** The fix itself; a **drift guard**,
because nothing checks this script's fidelity today and the three infidelities
survived from whenever it was written until someone read its output beside a
real dump — a round-trip assertion that `typed` and `strings` agree byte for
byte over a small generated file would have caught all three, and it states
the script's charter rather than exceeding it; and the **`--arrays` /
`--composite` split** that 4.6.1 needs, taken here because `M10` is already
rewriting every recorded command that names this generator, so the churn is
paid once.

**Order from here: `M10` → 4.6.1 → the Phase 4 wrap.** The first link is
forced — 4.6.1 needs its own generated file and taking its figure on a
generator about to change means taking it twice. The second is a choice:
wrapping with 4.6.1 open would write the phase's consolidated notes before its
last slice exists and leave an open box under a heading saying the phase is
wrapped.

## 4.6.1 is earned, and the spec row's ambiguity is why

The tick stands, which is the one case `process.md` allows a ticked half.

The finding underneath it is the reusable part: **a slice row that names a

## M10: the generator writes what pg_dump writes, and re-measuring found a fourth thing

The three infidelities above are fixed, `scripts/generate_perf_data.py`'s
output is asserted from the Rust side, and every figure taken on that output
has been re-taken. Ledger line: `M10` in
[`../../design/roadmap.md`](../../design/roadmap.md).

**The fix, in the order the couplings force.** The three date/time columns
declare the long spellings, which is what `pgtype::resolve_declared_type`
maps; the same change gives them PostgreSQL's own rendering, trailing zeros
trimmed and an all-zero fraction dropped. `v_real` and `v_double` both route
through one `float_text` helper that emits `float4out`/`float8out` text: the
shortest decimal that round-trips, formatted fixed or scientific by the %g
rule at FLT_DIG/DBL_DIG. Two details are worth not re-deriving. Ties break
**away from zero**, not to even: Python's `%.Ne` rounds -390238.125 to
`-390238.12` and Rust's shortest formatter — which `decode::render_f32` goes
through — answers `-390238.13`, so the rounding runs over `Decimal(value)`,
the float's exact binary value, under `ROUND_HALF_UP`. And the fraction list
is fixed rather than a uniform random microsecond, because a uniform draw
essentially never ends in a zero and so would never exercise the trim.

**The guard needs two assertions, and the queued description of it named
only one.** `M10` was queued as a byte-for-byte `typed`-against-`strings`
round trip, on the grounds that it would have caught all three infidelities.
It would not have caught the spellings: an unmapped declaration leaves the
column `Utf8View`, which both schema modes render identically, which is
exactly how three of sixteen columns stayed untyped without anyone noticing.
So `pgdump_query-cli/tests/perf_generator_fidelity.rs` also asserts that
`pgdq parse` prints no "N of M columns unmapped" line — one assertion per
failure mode, and the second covers a census refusal on a nested column too.
Both assertions were checked against a deliberately re-broken generator before
the fix was restored.

**Re-measuring found that the census is not free on brace-free data.** The
recorded figure — "the array-shape census costs nothing on brace-free data",
−3% to +2.5%, differences on both sides of zero — was taken while the page
cache was still filling: its three "runs" fall 5.9 → 4.5 → 3.2 s, so an
0.8 s difference is inside the spread. Taken fully warm, in both pair orders,
the pre-filter costs **0.84 s per 3.00 GiB**, 1.03 µs per 16-column row,
**+39%** of a warm scan; cold it is +1.2%, hidden by the device. The
array-bearing figure reproduces almost exactly (+81% against the recorded
+87%, same absolute cost), which is the check that the two binaries and the
method are sound and only the brace-free reading was wrong. The consequence is
in [`../../design/architecture.md`](../../design/architecture.md), "The array
shape census" (the cost is two-tier, and neither tier is zero) and in
[`../../design/roadmap-phase7-inbox.md`](../../design/roadmap-phase7-inbox.md);
the decision it does *not* change — the census stays unconditional — is
flagged for review in `STATUS.md`.

**The scan-throughput table was re-taken whole, and cold.** Only its `COPY`
row sits on this generator, but its floor row turned out to have the same
page-cache contamination: a 3.00 GiB file on this SSD reads cold in 5.73 s,
not the 3.67–3.85 s recorded, and two of the three inputs were listed as
faster than a cold read of themselves. Re-taking one row against a floor known
to be wrong would have produced a table whose rows disagreed about what regime
they were in, so all three inputs were re-run with `drop_caches` before every
run. The story survives: `COPY` and large-object are within 20% of the floor,
`INSERT` is 2.7× it, and against the `COPY` path's own warm CPU (2.92 s) the
`INSERT` path is still ~5× the per-byte cost.

**What the fix cost the figures.** The end-to-end typed ratios moved because
three more columns are now actually typed: 2.26× (control, sixteen scalar
columns) and 3.45× (plus three nested), against 1.85× and 2.91× when thirteen
were. The nested attribution is unchanged in substance — 14.6 µs per row for
three nested columns, against the ~16 µs the earlier pair implied. One
secondary finding, since **corrected**: the two files' `strings` baselines read
8.80 s against 8.04 s here, and the gap was attributed to the untyped path
being partly per-row, the control holding 817,024 rows to the nested file's
701,287 at the same byte count. That is not what it was. `4.6.1`'s interleaved
sweep put the same three files' baselines within 2% of each other with the
row-count spread unchanged, so the 9% gap was apparatus: this session ran the
comparison a file at a time, which maps the session's own drift onto file
identity. What survives is only the negative half — equal baselines were never
the check that the untyped path is byte-driven. The rule that replaces the
mistake is in [`../../design/measurements.md`](../../design/measurements.md),
"Re-take a comparison table whole, in one interleaved sweep".

**Not re-taken:** `benches/decoders.rs`'s `nested` group. Its literals are
written in the bench, not read from the generator, and no library code moved.
`benches/whole_file.rs` regenerates its input only when
`runs/perf-whole-file.sql` is missing, so that file was deleted; its criterion
baseline is void either way.

## 4.6.1: what differencing two generated files can resolve, and what it cannot

`pgdq query` has no column projection, so 4.6.1's instrument — the one its
spec row names — is a third generated file (`--composite` without `--arrays`)
whose per-row `typed` − `strings` figure is subtracted from the control's.
Run, that subtraction returns **−0.10 µs/row** over five interleaved reps and
**−0.49 µs/row** over an eight-rep pair. A cost cannot be negative, so the
reading is apparatus.

**The floor was measured rather than assumed.** A second control
(`--size-mb 3072 --seed 43`, the same sixteen columns) differenced against the
first gives **+0.22 µs/row**, per-rep spread ±0.39, six interleaved reps —
where the true answer is exactly zero. So this instrument resolves nothing
under roughly ±0.5 µs/row, and the composite column's share (0.43 µs of decode
plus render in the micro, plus an Arrow build for two fields) is inside that.
The recorded result is the bound and the attribution it buys: the two array
columns carry essentially all of the 15.1 µs/row the three nested columns
cost.

Two contributors to the floor are identified and neither is removable within
the instrument. The three inputs hold the same bytes and therefore different
row counts (817,024 / 806,322 / 701,287), so a per-byte component of the typed
path does not normalize away per row. And the machine drifts upward over a
long run of containers: measured in blocks — control's ten runs, then
composite's ten — the drift landed entirely on the difference, which is what
first made the composite look 0.5 µs/row *cheaper* than the control. Every
recorded run interleaves the files for that reason.

The instrument that would resolve it is a byte-identical pair: the same rows,
one file declaring `v_comp` as `public.perf_comp` and the other as `text`, so
row count and bytes are equal and only the decode differs. It needs a
generator knob that writes a deliberately weaker declaration than the value's
real type. Named, not built — filed into
[`../../design/roadmap-phase7-inbox.md`](../../design/roadmap-phase7-inbox.md),
because Phase 7 is a whole campaign of one-thing-at-a-time cost questions
against this same generator.

**The whole table was re-taken in one sweep**, not extended with one row: the
recorded control and `--arrays --composite` rows were `M10`'s, an hour
earlier, and a cross-file attribution spanning two sessions is what
`measurements.md`'s regime rule forbids. The ratios moved (3.45× → 3.08×,
2.26× → 2.11×) because this session's `strings` leg is ~9.6 s on all three
files where `M10`'s was 8.0–8.8 s and varied by file; the derived per-row
figures moved by ~3% (14.6 → 15.1 µs/row for the three nested columns). That
also withdraws the explanation `M10` recorded for its unequal `strings`
baselines: here the three legs sit within 2% of each other across a 14% spread
in row count, so a per-row component of the untyped path does not account for
the 9% spread seen then, and nothing else does either. It is one more reason
to read the per-row difference rather than the ratio. What
the design consumes is the per-row difference, which is why the section now
leads with it and treats the ratio as the fragile statement of the same fact.

## The review of the six measurement decisions

Six entries stood open in `STATUS.md`, "Decisions worth another look", all of
them calls made without the maintainer while `M10`, `4.6` and `4.6.1` re-took
the figures this design consumes. Three are settled here.

**The ~10% session-to-session swing is common-mode, and the fix is the
headline, not a diagnosis.** Reconstructing both sessions' raw legs from
`M10`'s recorded baselines and `4.6.1`'s table gives:

| File | `strings` M10 | `strings` 4.6.1 | `typed` M10 | `typed` 4.6.1 |
|---|---|---|---|---|
| control | 8.80 s | 9.74 s (+10.7%) | 19.89 s | 20.55 s (+3.3%) |
| `--arrays --composite` | 8.04 s | 9.56 s (+18.9%) | 27.74 s | 29.45 s (+6.2%) |

Both legs of a file move together in absolute seconds, which is why the ratio
moved a lot (the drifting baseline is its denominator) and the per-row
difference barely moved. No investigation was opened: an unexplained ~10%
level shift on identical binaries and inputs is exactly what an instrument is
built to be immune to, so the instrument changed instead. `measurements.md`'s
nested section now leads with `typed − strings` per row and demotes the ratio
to a derived column, and two standing rules were added to that doc's preamble.
The first is the maintainer's, and is more general than the table that
prompted it: **a figure about parsing CPU is taken with its input on tmpfs**,
not page-cache warm off a filesystem — device time and background I/O swamp
the difference being measured, the HDD worst of all, and page-cache residency
is an assumption rather than a guarantee. Every warm figure in the doc
predates the rule and is marked to be re-taken when next touched. The second
is **re-take a comparison table whole, in one interleaved sweep**.

`M10`'s own explanation of its unequal `strings` baselines is **retracted**
rather than merely weakened: it read the 8.80/8.04 gap as the untyped path
being partly per-row, and `4.6.1` puts the same files 2% apart with the
row-count spread unchanged. `M10` ran the comparison a file at a time, which
maps a session's drift onto file identity — which is the second rule's
evidence. The paragraph in this file's `M10` section is rewritten in place.

**The composite share's tick stands; its promise is what was wrong.** Nothing
consumes a figure sharper than the recorded bound, and the bound already
answers the phase's question. The sharper instrument's cost is now named
concretely instead of as "a scope decision": a generator knob declaring
`v_comp` as `text` writes a declaration `pg_dump` would not, which is the
opposite of what `M10` corrected the generator to do, so it needs an explicit
exemption from `perf_generator_fidelity.rs`. 4.6.1's spec row is amended to
promise whatever the instrument resolves.

**The census pre-filter gets faster rather than skippable.** The 39% warm cost
is 0.84 s per 3.00 GiB out of a hand-rolled scalar two-comparison byte loop
(`map.rs:1269`) running at ~3.8 GB/s. `memchr` is already a direct dependency
of `pgdump_query`, so the loop is one SIMD call away. A knob would re-introduce
what 4.5.1 deleted and would have to be plumbed to a caller who cannot know
whether a later query will retype an array column — so the knob question is
deferred behind **M11**, and reopens only if the swap does not deliver. The
census stays unconditional either way; its justification never rested on the
pre-filter being free.

**Three more of the six settled the same day.** `M10`'s date/time `FRACTIONS`
list is chosen for rendered-shape coverage, which is a correctness goal the
fixtures already meet — `00:00:00`, `.000001`, `.123456`, `.85312` and
`.999999` all appear there — and it is unrepresentative as a benchmark input:
300,000 rows of koji's `task.create_time` hold **zero** values with no
fractional part and 9.9% ending in a zero digit, against the list's 37.5% and
50%. The stake is 0.2% of a row's bytes across three of sixteen columns, well
under the instrument's floor, so the correction rides the next re-take rather
than buying one. The census figures' source-edit recipe stands; what it lacked
was a pointer from `map::Builder::on_row` back to the two figures that patch
it, which `M11` adds. And the scan-throughput table's whole re-take needed no
ruling at all — correct re-measurement forced by a contaminated floor row is
not a decision to weigh in on, and the practice is now a standing rule.

**The seventh entry — the fidelity guard's `uv` skip — is reversed, and
generalized.** The skip defends an environment that does not exist:
`mise.toml` pins one tool, `uv = "latest"`, and there is no CI, so the suite
runs where `uv` is present. It also covers the file's only test, so firing it
means a green suite with no guard at all against the generator drifting from
what `pg_dump` writes — the condition under which `M10`'s three infidelities
survived. Its stated reason, "a failure it cannot act on", is false: the
remedy is `mise install`, which is what pinning tools with `mise` buys — a CI
run is one step from having every tool the suite needs. `roadmap.md` gains the
standing rule, since the hazard is general: a conditional skip is invisible in
a passing run, and the test carrying one is usually the test nothing else
covers. The rule names the one exception, a machine-local resource `mise`
cannot pin, which gates the opposite way per `CLAUDE.local.md`'s koji-replica
policy.

**The measurement standing rule gains its second clause.** 4.6 earned the rule
by naming a deliverable without an instrument; 4.6.1 is the same row-shape
failing the other way — the instrument was named and run, and answered below
its own floor. The clause added is that a named instrument is satisfied by
whatever it resolves, a bound or a null result included, with the floor stated
beside the figure and the sharper instrument named but not built. The failure
it forecloses is an unattended session treating a null reading as unfinished
work and building a second instrument for it, which is scope growth entering
through a measurement row and looks more like finishing than reporting a bound
does.

**The warm set is re-taken as a bundle, and the queued work splits into
three.** Every warm figure in `measurements.md` is a page-cache-warm SSD read
predating the tmpfs rule, and re-taking them lazily — each whenever someone
next touches it — would leave the doc's warm figures disagreeing about regime
for as long as that took, which is the failure both new standing rules were
written from. So `M13` re-takes the whole warm set in one session: both census
figures, the nested end-to-end table, the per-block quadratic table, and the
`COPY` path's warm CPU. The criterion micros are out of scope (they read
literals written in the bench), the scan-throughput rows are cold on purpose,
and koji cannot be staged in memory at all.

The staging hazard is worth recording because it is silent: the four 3.00 GiB
inputs must be **generated on tmpfs from the host, before any container
starts**. `/dev/shm` is 16 G against ~21 GB available here, so 12 GiB fits —
but tmpfs pages are charged to the cgroup that faults them in, so writing them
from inside the 512 MB-limited container would kill it. Generated first, the
pages are already resident and charged to the host when the container opens
the file read-only.

The queued work is three ledger rows rather than one, because four unrelated
edits under one row is unreadable later, and the order is forced by what each
lands on: **`M12`** (generator hygiene — `FRACTIONS` to a uniform draw, and
`have_uv()`'s skip to an assertion) changes the generated bytes, **`M11`**
(the `memchr2` pre-filter plus `on_row`'s doc comment) changes what is being
measured, and **`M13`** measures both.

## `M12`: the benchmark generator draws a uniform microsecond, and its guard asserts `uv`

`scripts/generate_perf_data.py` draws the microsecond component of its three
date/time columns uniformly over the whole range. The weighted `FRACTIONS`
list it replaces was chosen for the *rendered* shapes it produced — an absent
fraction, one digit, six digits, and both ends of PostgreSQL's trailing-zero
trim — which is shape coverage a benchmark input does not owe: `fixtures/`
already carries all five, produced by `pg_dump` itself. What the list cost was
an input 37.5% of whose timestamps rendered with no fractional part at all,
against zero such values in 300,000 rows of koji's `task.create_time`. The
comment at the draw now says where shape coverage lives, so the list is not
re-derived as an improvement.

This changes the default output's bytes, which is why it lands first: every
figure `M13` re-takes is taken on them. The control's brace-free contract is
unaffected — a fraction is digits — and was re-checked over a whole 3.00 GiB
file rather than assumed.

`pgdump_query-cli/tests/perf_generator_fidelity.rs` now asserts `uv` is
runnable instead of skipping itself, with `mise install` named in the failure.
The reasoning is `roadmap.md`'s standing rule "A test may assume the tools
`mise` pins"; the two doc paragraphs that recorded the skip's defence are
rewritten to record the assertion's.

## `M11`: the census pre-filter is `memchr2`, and `on_row` names the figures that patch it

`map::Builder::on_row`'s pre-filter is `memchr::memchr2(b'{', b'[', raw)`.
`memchr` was already a direct dependency, so the scalar
`raw.iter().any(…)` — measured at ~3.8 GB/s, 1.03 µs per 3,943-byte row, +39%
of a page-cache-warm scan — is a one-line swap for a SIMD search. Nothing else
about the census changes: it stays unconditional, type-blind and keyed by
column.

**The figure that justified the swap has not yet been re-taken against it.**
Both census sections in `measurements.md` were measured on the scalar loop and
are marked as pre-`M11`; `M13`'s sweep is what says whether the expected
+39% → ~+7% arrives. The deferred question behind it — whether the census
should be skippable at all — reopens only if the swap does not deliver, and
that is now decidable from a number rather than from an argument.

`on_row` also gained the doc comment the review asked for: it names the two
`measurements.md` sections whose census-off column is taken by putting a bare
`return;` at the top of that function, so renaming or splitting it cannot
silently break the recipe. The same pattern as `architecture.md`'s "`Event` is
the scanner's contract" — the constraint is recorded at the site that would
break it.

## `M13`'s sweep is launched; a later session reads the log

The warm-set re-take runs detached as `runs/m13-warm-set.sh`, logging to
`runs/m13-warm-set.log`. It is gitignored (one machine's paths, nothing in the
repo consumes it), so the file is the artifact and `measurements.md` is where
the numbers land once a session reads it. Expect roughly 25 minutes of
generation and a similar amount of measurement.

Three binaries were built before the launch, because a detached script must not
be patching and rebuilding the tree it measures: `runs/pgdq-m13-census` (the
working tree), `runs/pgdq-m13-nocensus` (the same tree with `return;` first in
`on_row`), and `runs/pgdq-m13-prethrottle` (a release build of `b726f6b`, the
commit before 9.5's `SaveThrottle`, from a throwaway worktree). All three are
static musl builds; the log records their hashes and the tree's `git status`.

**Stages, and what each figure needs from the log.** `S3`/`S4` are the two
census figures — six reps each, the pair run in both orders, on the 3.00 GiB
brace-free control and the `--arrays --composite` file. `S3`'s census-on column
is *also* the `COPY` path's warm CPU that the scan-throughput table cites: same
binary, same command, same input, so it is not measured twice. `S5` is the
nested end-to-end table, five interleaved reps over three files and two modes;
`S6` is its cross-file floor, six reps of the seed-42 control against a seed-43
one. `S7`, `S7b` and `S7c` are the per-block quadratic table's three columns —
timings with and without the throttle, the map alone with the cache disabled,
and `strace` save counts.

Two apparatus calls are recorded in `STATUS.md`, "Decisions worth another
look": `S7` runs on the host rather than in a container, and the quadratic
table's "before" column is re-taken from the pre-throttle build rather than
carried over.

The inputs live in `/dev/shm/pgdq-m13` and are deleted by the script's last
stage. **If the run is killed, delete that directory by hand** — up to 9 GiB of
tmpfs is otherwise held until reboot.
