# 2026-10-26

## 15.17's split, reviewed

With the maintainer, closing the "Decisions worth another look" entry on
15.17's split. The split stands: 15.17 is ticked for the frontier, its gate is
15.17.1's, and 15.18 follows 15.17.1. Two things changed, both now in the P15
spec's "Slice order" and 15.17.1's row.

- **The spec's reason for the gate was false.** It said a frontier waiting
  only for a decode holds the pass to serial "whatever a task costs". 15.17
  built that frontier and four jobs stayed slower: the tasks slow the frontier
  and the scan beside them. At two jobs they bought nothing at all, no decode
  ever handed out and many speculations landing behind the frontier
  (`runs/p15.17/diag/t-j2.log`).
- **The three directions were not three.** A guess reads only the window
  before its stop (`gz-seek`'s `speculate.rs`, where a `Guess`'s `end` is
  built), while the marked sink keeps the whole chunk as 16-bit values, grown a
  push at a time. So 15.17.1's rework is one change: the sink holds that window
  alone, as a ring copying in bulk wherever its source lies past the last
  marker, which removes a chunk-sized buffer, its growth and its page faults at
  every count. Handing speculations out in runs a chain can use stays unchosen
  until a reading after the rework.
- **The slowdown beside the tasks is separated first, inside 15.17.1.** This
  machine's logical count is twice its physical one, its L3 split four ways, so
  the 24-job leg shared every core with a worker. The slice opens by
  separating the clock, a core shared by SMT siblings, a shared L3 and memory
  bandwidth, by cycles and instructions per byte and by placement. Its gate is
  two and four jobs no slower than serial and the physical count falling
  toward the scan's floor, the logical count read against that account. The
  rework does not wait on it, removing memory traffic under every cause.
- **A local first pass recommends the logical count**
  (`first_pass.rs`'s `default_workers`), so a default run on this machine is
  the 24-job leg: no faster than serial, at many times its CPU
  (`runs/p15.17/jobs-probe/times.txt`). 15.17.1 settles that default from its
  reading, amending D2 for the gzip first pass alone; xz's has no reading
  against it. 15.7.1 times the default it leaves.
- **At the high counts the frontier is held by serving and the scan**, not by
  speculations (`runs/p15.17/diag/t-j24.log`). 15.17.1's gate owns both. A
  cause in serving's code earns its own increment, a core path apart from the
  sink; contention stays in 15.17.1.

## The release target state, reviewed

With the maintainer, closing the "Decisions worth another look" entry on the
release target state reused across images. The call is reversed: every cargo
target directory the release image builds into is keyed on what compiles
objects, read from inside the image — the base digest, rustc's version and
installed components, the C compiler's and libc-dev's versions — and not on
the image tag, which tools that compile nothing also move.

- **The shipped arm64 archive is built in that state.** `/release`'s rehearsal
  builds both targets in `target/release-image/target/` and attaches its arm64
  archive, so the state's contents are what the release ships; D104's claim
  that one pin names the build is a claim about the release, not only the
  figures. v0.2.0's arm64 binary was clean only because its target's objects
  were first built after `rust-src` arrived (`runs/d109-archive-diff/findings.md`).
- **The timed legs share the defect**: each instrument and allocator leg's own
  target directory is filled in the image and keyed to nothing.
- **Cargo's fingerprint misses exactly these inputs**: it keys on rustc's
  version and the flags, not sysroot components or the image's C toolchain.
- **A mismatch clears the directory** and logs it, in `release.py`, so every
  leg's `--target-dir` inherits the key. The directory is a cache of its key;
  nothing switches back between images.
- **Admitted as `M253`, blocking P15**: 15.17.1's gate readings and 15.7.1's
  figures time the gzip engine's C objects, built in these directories. It is
  accepted by a clean keyed build at v0.2.0's commit reproducing CI's x86-64
  binary, the findings' unverified step; one that does not reproduce names an
  input the key still misses.

## `M253`: the release target state keyed

- **Every target directory a `release.py` step builds into is keyed** (`image_key`, `key_target`), read inside the
  image; the Dockerfile copies itself to `/opt/toolchain/Dockerfile` for the base digest. One holding another key,
  or none, is cleared before the step, saying what moved. Every existing directory names no image, so the first step
  into each rebuilds it: the release state's, each leg's under `alloc-builds/image/`.
- **Accepted, the clock aside.** A clean build at v0.2.0's commit matched CI's x86-64 `pgdt` byte for byte once
  `SOURCE_DATE_EPOCH` was CI's build time. Unpinned, it differed only by the `__DATE__`/`__TIME__` gcc stamps into
  mimalloc (`runs/m253-v0.2.0-clean/findings.md`). D109 says so; the clock is pinned by `M254` (below).

## The release build's clock, reviewed

With the maintainer, closing the "Decisions worth another look" entry on the
unpinned build clock. The call is reversed: every in-image build is held to one
clock, and `attach` refuses CI's x86-64 archive differing from the rehearsal's.

- **The clock is a constant**, one `SOURCE_DATE_EPOCH` in `release.py` set on
  every in-image build, not `HEAD`'s commit time. Neither `libmimalloc-sys`
  0.1.49's `build.rs` nor `cc` 1.4.4 declares `SOURCE_DATE_EPOCH` to cargo, so
  `options.c` is compiled once per target-directory key and keeps the clock of
  that build; a per-commit clock on kept state would carry an earlier commit's
  date. The proof build matched only once mimalloc's objects were deleted.
  The archives' member mtimes stay `HEAD`'s commit time (`check_archived_from`).
  Rejected: the commit time with mimalloc forced to rebuild, or the clock in the
  key, a cold build per commit; `-D__DATE__=…`, a workaround inside a dependency.
- **Accepted by two builds before `attach` refuses**: a clean keyed build at
  v0.2.0's commit reproducing CI's x86-64 `pgdt` under the pinned clock, and one
  at v0.2.0 on target state kept from an earlier commit's build reproducing the
  same bytes. Kept against clean is the case a rehearsal meets and is unshown;
  a difference there is what is found before the refusal lands.
- **Admitted as `M254`, not blocking P15**: D109 changes with it, a register
  entry no spec records, as `M253` changed D104 and D109; no P15 slice runs
  `attach`.
