## `pgdump.inheritance` stays a dump's option

Reviewed with the maintainer: the mode is a `STORED AS PGDUMP` option and `:inheritance=`, read at registration, not
the `SET` the P38 spec first named. The provider builds every table's provider when the catalog is
(`datafusion-pgdump`'s `catalog.rs`, `PgDumpCatalog`), listing a table by whether its schema resolves under the dump's
modes and keeping its statistics, and the mode moves all three: under `only` a load-via-root root refuses, under
`descendants` its partitions do, and row counts differ. The `pgdump.` `SET` settings are scan-time knobs read when a
scan is planned (`settings.rs`). Filed in D132; the spec's sentence amended.

- **Both modes in one statement** is one dump registered twice, once in each mode; nothing in `pgdt sql`'s
  registration refuses two of one path, read from the code and not yet run. 38.7's row now carries the manual's
  account of it and a `pgdt sql` test joining the two against both oracles.
- **`SET pgdump.inheritance` fails naming only the four scan settings** (`PgDumpSettings::set`), as `SET
  pgdump.schema_mode` and `pgdump.unrepresentable` already did; `M266` makes it name the dump's option. It does not
  block P38.

## A partitioned table read alone answers empty: 38.3.1

Reviewed with the maintainer: 38.3 refuses a `--load-via-partition-root` root read alone (`PartitionRootAlone`) and
each partitioned table below it read alone (`PartitionThroughRoot`, `Refusals::of` in `dump/descendants.rs`), where
the server answers no row. A partitioned table has no storage, and the table a load-via-root header names is always
one: `getRootTableInfo` of an `ispartition` table, `pg_dump` skipping partitioned parents' data (I2's proof). So
the answer is certain, and the refusal was the wrong contract. The spec's load-via-root decision is amended and
**38.3.1** earned, next before 38.4 so 38.5's hypertable refusals meet the narrowed `Refusals`.

- **The columns** come from the blocks holding the table's descendants' rows — its own-named blocks for the root,
  the through-root blocks `table_read` already gathers for one below — by `TableColumns::settle`'s rule for a table
  with no block of its own (`stream/replay/plan.rs`): declared columns a block names, so a generated column drops
  out. D132's rejection of the declared columns alone stands.
- **The invariant** (a partitioned table holds no rows of its own) is a new `I<n>`, filed by 38.3.1, not a widening
  of I2.

## The hypertables' findings, said per read too: 38.5.3

Reviewed with the maintainer: 38.5.2's three findings stay `DiagnosticKind`s — each a property of the file under D19,
what `pgdt info` and an embedder's dump-level drain hear — and **each is also a `PlanNote` on a read it bears on**, so
`pgdt query`, which prints no file-level diagnostic, says them where the answer differs from the server's. A per-read
note is no fifth channel: `PlanNoteKind::ReadAsNull` is already a table's property raised per read
(`crates/pgdt-query/src/stream/note.rs`). Rejected: per read only, which leaves `pgdt info` without them until 38.6;
`pgdt query` printing the file's findings, every kind's and every hypertable's, and none on a cold partial map.

What 38.5.3 delivers, settled in the same review:

- **Which reads raise which note.** Root rows: a hypertable read through whose root holds rows, and read alone where
  the stated version is 2.28 or later, the server's `ONLY` answering the root's rows at 2.23–2.27 as pgdt does (TS8).
  Absent chunks: the hypertable read through. An unreadable catalog, under either mode: every read in its database
  that succeeds unchecked for compression — a table below a hypertable its rows name, any table with an ancestor
  where they name none, and a named hypertable read as a plain table, the file holding none of its chunks. A refused
  hypertable's refusal already names the catalog.
- **Each a `Warning`**, as its `DiagnosticKind` and `ReadAsNull` are: one fact, one severity on both channels.
- **Per mode beside `Refusals` in `TableRead`**, derived in `table_read` from `Verdict`, the plan raising them as it
  does `ReadAsNull`; the root rows and absent chunks counted by derivations `pgdt_model::timescaledb::findings`
  exposes, so the two channels count by one function. **Three `PlanNoteKind`s of their own**, each sentence the read's
  consequence rather than the file's.

## A named hypertable with no chunk held reads: 38.5.4

Reviewed with the maintainer: 38.5.3's call that an unreadable catalog's note goes on no read of a named hypertable.
The review that settled 38.5.3 listed "a named hypertable read as a plain table, the file holding none of its chunks",
a read the code never made: `Verdict::unreadable_refusal` (`crates/pgdt-query/src/dump/hypertables.rs`) refuses a
named hypertable read with its descendants whether or not the file holds a chunk of it (38.5.1's notes, "Negative
results"), while the spec's "reads as a plain table" sentence sat under the fallback, where no name reads. So knowing
the names refused a read the fallback made.

Settled, the spec's "TimescaleDB" amended to match:

- **The refusal narrows**: under an unreadable catalog a table refuses read with its descendants only where the file
  holds a descendant of it and it is named, or no name reads. The refusal guards compression, which a read reaching no
  chunk cannot meet; what is left unknown is chunks the file lacks, which a readable catalog reads as absent with a
  note rather than refusing.
- **That read raises a `Warning` note of its own kind**, not `CompressionUnchecked`: the catalog does not read, so
  which chunks of the hypertable the file lacks cannot be known, and the read holds its root's rows alone. One kind
  per consequence, as `HypertableChunksAbsent` beside `CompressionUnchecked`. The fallback's unnamed hypertable with
  no chunk held stays noteless, indistinguishable from a plain table.
- **No note on a named hypertable read alone**: its answer is its root's rows either way, and where the server's
  `ONLY` differs (2.28 on) the root-rows note says so. Filed as D135's `Rejected`.

The work is slice **38.5.4**, earned under 38.5 by 38.5.1 shipping the wrong contract, ahead of 38.6.

## What refuses a read is a finding `pgdt info` prints

Reviewed with the maintainer: 38.6's call that `pgdt info`'s `tables with descendants` says no refusal. Its premise,
that saying one means `info` building a `Dump` (D61), does not hold: `table_read`
(`crates/pgdt-query/src/dump/descendants.rs`) settles every refusal from the `DumpIndex` alone. What stood in the way

into.

Settled:

- **`info` owes them.** The spec's "What is shown, claimed and checked" — "what decides whether a query refuses is what
  an administrator reads first" — binds 38.6, and nothing `info` prints says KD158.
- **As file-level findings, D135's shape**, not a clause per parent's line: a partition root whose partitions' rows
  were written through it, and a hypertable whose chunks are compressed, are properties of the file (D19). Findings
  reach the leaf partitions a read refuses by name, which no parent's line names, and an embedder's dump-level drain;
  the query layer's refusals read the same model derivation that counts them.
- **One finding per partition root and one per hypertable, each a `Warning`**, the grain of `Refused::Through`'s root
  and of `TimescaleChunksAbsent`. **No per-read note**: the read they bear on refuses, its error saying why, where
  D135's notes exist for a read that succeeds unlike the server's.
- **A parent's line is unchanged**: it counts what the file holds, which stays true (38.6's notes, "Negative results").
- The spec's "with a finding naming the blocks written through the root" was met at 38.2 by `datafusion-pgdump`'s
  `RefusedTable`, a registration's report, which `pgdt info` never hears.

The spec's "What is shown, claimed and checked" is amended; the work is slice **38.6.1**, earned by 38.6 saying no
refusal, ahead of 38.7, which records it.
