### The floor's disqualification threshold is its own number

`measurements.md` had one number, ~8%, doing two jobs: the resolution floor for
warm *figures*, and the tolerance that disqualifies a sweep whose co-measured
warm `dd` floor comes in slow. The two jobs have different noise bands, and
both are already measured in that doc — pure drift moved a warm floor **13.6%**
(and the *same* floor, measured twice inside one sweep pair, disagreed with
itself 13.6% against 11.3%), while the one witnessed contention episode moved
the warm floors **+19–24%** with the cold floor at +0.1%. So ~8% sat inside the
band drift alone produces, and a sweep drifting 9–13% slow would have been
thrown out as contended.

The threshold is now **~15%, measured on floors**, and it takes a second
condition: the slow move must be **shared across the sweep's warm floors**.
That is the measured signature of the mechanism — contention is machine-wide
and moved every warm floor together, while tmpfs staging luck is per-file, and
in the stamped pair the `control` file's floor moved 13.6% while the `arrays`
file's moved −0.9%. The number is the backstop, the shared move is the
discriminator, and both must hold. Two costs are stated in the doc rather than
hidden: a contention episode milder than ~15% now passes the gate, and
"shared" is a weak test across only two or three warm files.

Decision: [`../../design/measurements.md`](../../design/measurements.md), "The
floor is read directionally". The check remains a human rule read off the
sweep's own tables; `measure.py`'s automated gate is the counters
(`contention_verdict`), which does not look at the floor.

### A `--filter` value is trimmed on both sides — settled, not yet landed

The maintainer chose trimming over the alternatives, on both sides of the
value: `--filter 'foo = the answer '` searches for `the answer`.

Three facts the grilling turned up, which is what changed the shape of the
question:

- **The column side already trims.** `parse_filter` does `column.trim_end()` on
  every form, so the asymmetry is trimming left of the operator and not right
  of it, rather than no trimming at all.
- **The variant `STATUS.md` proposed — trim only for the ordering operators,
  "where no value can begin with a space" — is refuted by the ordering
  register.** `Utf8View` reached by `text`/`varchar`/`char`/`name` is an
  orderable row, so an ordering literal that begins with a space is
  legitimate.
- **The hazard is narrower than the entry stated, and worse where it bites.**
  On a typed column the spaced spelling fails loudly, as
  `Error::PredicateValueDecode` before any row, naming the value. The silent
  case is a text column under `=`: `--filter 'name = alice'` looks for
  `" alice"`, matches nothing, and prints an empty result that reads as an
  answer.

**Trimming is the CLI parser's alone.** `Predicate` is a plain public struct an
embedder fills in field by field, with no library-side parse of `column=value`,
so there is no ambiguity there to repair — and trimming everywhere would make a
space-padded `char(n)` value unaskable through the API.

**Whitespace is Rust's `str::trim`**, matching the `trim_end()` the column side
already uses, so the parser holds one definition rather than two; a
non-breaking space pasted out of a web page is the case this exists for. An
all-whitespace value collapses to the empty string with no special handling.

Lands as **`P5.9`**, together with the quoting work below — not as out-of-band
work. The admission rule permitted an `M<k>`, since no spec recorded the
whitespace rule, but this changes a documented contract of the mechanism `P5.5`
and `P5.6` built, wants a notes doc that out-of-band work does not get, and P5
is open. It is a clarification of the P5 work that would have gone into the
spec had it been anticipated, and the spec now carries it: "A filter term is
parsed for two audiences". It touches `parse_filter` in
`pgdump_query-cli/src/main.rs`, the `--filter` help text, the whitespace
paragraph at the end of `architecture.md`'s "Ordering operators compare typed",
and `type-handling.md`'s filter-term line.

## Two kinds of user read the filter syntax differently

CLI feedback from real use, and the first thing pooled for the CLI-feedback
pass. **Sysadmin-shaped users find the bare `column=value` spelling natural.
SQL-fluent users assume a string literal must be quoted**, and write
`--filter 'foo = "the answer"'` — double quotes rather than SQL's single ones,
because the term is already inside shell single quotes. Today that searches for
the six-character value `"the answer"` including the quote marks, and on a text
column it silently matches nothing.

So `P5.9` supports both spellings rather than choosing between them: an
unquoted value is trimmed, and a quoted value is taken exactly as written. That
also replaces the escape the trim decision was leaning on — a value with real
leading or trailing spaces becomes expressible on the command line as
`--filter 'foo = " x"'`, so the CLI is no longer weaker than the library, and
the `char(n)` case is reachable from both.

### The quoting grammar

**Both `'` and `"` open a quoted value, matching pairs only.** Accepting one
would punish whichever half of the audience reached for the other, and from
inside the term both look equally like SQL. Which one a user picks is decided
by the shell, not by taste: the term is normally already inside shell single
quotes, which is why the feedback shows `"` even from users whose SQL instinct
is `'`.

**A quote inside a quoted value is doubled**, as SQL does it — `'it''s'`, and a
double-quoted value holding `"` doubles it the same way. Backslash escaping was
rejected because a backslash inside a shell double-quoted argument is itself
shell-processed, so the correct spelling is something nobody writes right
twice — and because doubling keeps the grammar closed, with no escape alphabet
and so no second decision about what a backslash-n or a doubled backslash mean.
Two quote characters give a lazier escape for free: a value holding `"` can be
written in single quotes, and the reverse.

**Quotes work on the column side too, and the operator split is quote-aware.**
PostgreSQL identifiers hold spaces, case and operator characters, and SQL
spells that `"my column"`; the quotes are stripped and nothing else happens,
since column names are matched verbatim and there is no case-folding to
reproduce. `split_filter_op` skips quoted regions rather than taking the
earliest operator byte anywhere, which is what makes a column named `a=b`
parse. The existing rule — earliest position, longest spelling — is unchanged
for every unquoted term, so `name=alpha>x` still parses as documented. The
`IS NULL` / `IS NOT NULL` forms get quoting for the same reason: they take a
column name and nothing else.

**A malformed quote is refused, never reinterpreted.** If what remains after
trimming outside the quotes opens with a quote, it must close with the matching
one at the very end, with every interior occurrence doubled; an unterminated
quote and trailing text after the closing one are the same error with the same
message. Falling back to the unquoted reading instead would hand a user who
mistyped one quote a value nobody meant and an empty result that reads as an
answer — the defect this whole grammar removes, in another hat. Whitespace
outside the quotes is tolerated on both sides.

**A value that opens and closes with a matching quote is quoted, always** —
there is no way to tell a SQL user quoting a string from someone searching a
`json` column for the six characters that spell a quoted `hello`, and a rule
that guessed from the column's type would make a term's meaning depend on a
schema resolved much later. The escape is the doubling rule. That case and the
`char(n)` one are the two the manual has to show, since they are where a user
needs to know the rule exists.

**Quoting stops at `--filter`; `--column` and `--table` take their names
verbatim.** Quoting earns its place in a filter term because one string has to
be split into three parts and the quotes say where the boundaries are.
`--column` has no boundary to find — the shell already delimited it — so quotes
there would be decoration that made a column genuinely named with quote marks
unaskable. The failure is loud either way, so what is added is the missing
sentence: a name that is not found and that opens and closes with a matching
quote says it was matched literally, quote marks included, and that the flag
takes the name as given. Same for `--table`.

**The `IS` forms are the fallback, not the first test.** `parse_filter` checks
for an operator outside quotes first and tries `IS NULL` / `IS NOT NULL` only
on a term that has none. That is a fix, not just a reordering: today the suffix
is stripped from the whole term before any operator is looked for, so
`--filter 'note=this is null'` parses as `IS NULL` on a column named
`note=this`. Under the new order it is an equality against the value
`this is null`, which is what it plainly says. Quote-awareness is needed on top
of the reordering rather than instead of it — that unquoted term goes wrong
with no quotes anywhere — and it is what lets `--filter '"is null" = x'` name a
column `is null`. The architecture paragraph has to say the `IS` forms are the
fallback, or the next reader restores the order that reads more naturally and
reintroduces the misparse.

## A sweep at every wrap buys a stamp the next phase invalidates

`scripts/measure.py` and the harness *is* its apparatus, so neither oracle
applies and only taking it settles it. One red figure with its reason written

**What is given up, knowingly.** The doc's numbers drift from the code between
performance phases, so someone may quote a figure that is a few percent
off — or 16% off, as the `INSERT`/`COPY` ratio was. The protection is not
freshness but the standing rules that already exist for exactly this: quote a
magnitude rather than three significant figures, and read a move against its
regime's resolution floor. That is the lesson the last sweep actually taught,
and it points away from sweeping more often.

## The schedule is reordered to P11 → P7 → P10 → P6 → P8

Decided by the maintainer after a review of what each recorded placement
actually rested on. The decision is `roadmap.md`'s index table and its per-phase
placement paragraphs; this is why.

**Two reasons were withdrawn, and both are recorded in the roadmap so they are
not re-derived.** Typed predicates sat behind the engine story because
DataFusion hands a `TableProvider` an `Expr` tree with a per-filter
exact/inexact/unsupported answer, and designing a boolean expression language
before seeing that looked like inventing a second one. But that shape is
documented and stable, readable from the DataFusion source without building
anything, and the measured v55 semantics for `List` and `Struct` comparison
were already filed in P11's inbox by an earlier phase — so it is a research
input to the grilling, not a dependency on a phase. Scan performance sat behind
the engine story because `object_store` would settle the I/O layer any
readahead or parallelism scheme lives behind; that question turned out to be
settled in P7's own design doc instead, which rejects mmap *because* it bypasses
`ByteRangeSource` and so could never be an `object_store` path. What genuinely
does not transfer is tuning — readahead depth and chunk sizes measured on local
devices say nothing about a ranged high-latency backend — and that is a second
set of measured defaults, not a rework.

**One reason held, and it is why P10 did not move ahead of P7.** The maintainer's
first draft had statistics second. Statistics attach to row groups, a row group
is the sparse row index's checkpoint interval, and the index is P7's — but the
decisive part is not the addressing scheme. This phase's best outcome is
sortedness plus the sparse index turning a range predicate into a binary search
for a byte range, and that is *unreachable* without the index. Run first, the
phase would ship row-group pruning and leave the payoff that motivated it
unbuilt. The roadmap's bullet now says so rather than resting on the addressing
argument alone.

**What the new order buys that the old one did not.** A `TableProvider` presents
whatever the predicate can express, so building it before typed predicates means
committing to today's conjunction and changing it underneath the provider
afterwards; widening what a provider pushes down is additive, rebuilding one is
not. The engine story is also the least-specified phase, so it gains most from
being handed two settled inputs rather than settling them itself.

The numbers do not move: `P<k>` is identity, the table is the schedule.

## P11 is grilled and specified, and equality turned out to be in scope

[`roadmap-P11-typed-predicates.md`](../../design/roadmap-P11-typed-predicates.md)
is the spec; its inbox is drained and deleted. Three findings changed what the
phase covers relative to the roadmap's sketch.

**Equality was silently wrong and nothing recorded it.** The register covers
ordering only, and the justification for an untyped `=` — every value in a dump
is already canonical `*_out` form — is true of the *field* and says nothing
about the *literal the user typed*. So `--filter 'v=1.5'` matches no row of a
`numeric(10,2)` column written `1.50`; `--filter 'v=a'` matches no row of a
`char(5)` column, since `bpchareq` compares after `bcTruelen` strips the
padding; `--filter 'v=2020-01-01'` matches no row of a `timestamp` written
`2020-01-01 00:00:00`. A plausible command line, no error, an empty result that
reads as an answer. Typed `=`/`!=` is now slice 11.6, and the fast path costs
nothing on the common case: the field is always canonical, so the *literal* is
rendered into canonical form once at block resolve and the per-row compare stays
bytewise. Two types are exceptions and decode per row — bare `numeric`, which
preserves scale, and `interval`, whose `interval_cmp_value` collapses months to
30 days so `'1 mon'` and `'30 days'` are equal and written differently.

**The union rule needed a check, not a sentence.** Version-varying semantics are
implemented as the newest semantics unconditionally, because an older server
cannot have produced the value — safe exactly while no two majors disagree about
what the same text *means*. That condition is now machine-checked rather than
asserted: the oracle records whether the server *accepted* each input as well as
its answer, tables are generated and committed per major, and a cross-major diff
classifies every changed cell as additive (older major rejected the literal) or
non-additive (both accept, answers differ — the check fails). The differences
that already exist are committed and asserted by the ordinary suite, so a stale
file cannot land. A prose "what to check when a new major arrives" document was
rejected: nothing fails when nobody follows a checklist, and this project has
twice chosen a script instead (`measure.py --stale`, `deficiencies.py`). The
ritual keeps its existing home in
[`postgres-invariants.md`](../../design/postgres-invariants.md)'s header and
gains the mechanical half.

**`KD7` is narrowed to one statement, and two of its rows close by
statement.** (The plan on this day was full retirement; 11.6 found the one
statement that survives — see
[`2026-09-01.md`](2026-09-01.md), "`KD7` survives at one statement rather than
being struck".) Closing the enum and bare-`numeric` rows forces the register off
its `DataType` key — both need the declared type, and the enum needs
`TypeKind::Enum { labels }` — which moves it into L2 beside `pgtype.rs`'s
mapping table. Once re-keyed, each remaining text-held type is one comparison
and one register row, so leaving them would be an unowned queue behind an owned
phase. The two statement-closed rows are `text` under a collation the file does
not record (I32) and `json`/`xml`, which have **no comparison operator at all**
in PostgreSQL — no `=`, no default operator class — so "agrees with PostgreSQL"
is not a question they can be asked. Both become properties beside the
mechanism, with no identifier.

**Three source facts the spec rests on**, all v16.15 unless noted. `array_eq`
memcmps dimensions *and lower bounds* before comparing an element, so the
`[lb:ub]=` decoration is semantically load-bearing. `array_cmp` and `record_cmp`
carry the identical comment — *"We consider two NULLs equal; NULL > not-NULL"* —
so nested comparison is two-valued throughout and sorts NULL high, and both
raise when the element type has no comparison proc, which is why comparability
is inherited. `daterange_canonical` skips any bound that is `DATE_NOT_FINITE`,
so `[2020-01-01,infinity]` keeps its inclusive upper: canonicalization is not
total, and the exception is exactly I34's values. `interval` gained infinities
in v17, which makes I34's scope limit — excusing them because interval never
reaches a typed comparison — false as of slice 11.5.

**Two facts were filed forward rather than used here.** P7's inbox gains the
sharpened per-row cost: every term walks the row itself, and a disjunction
short-circuits on the first term that *succeeds*, so the shape costing *n* walks
is now the ordinary one rather than the pathological one — the fix is a rework
of a tested core path and must not share a review cycle with a change whose
worst bug is a wrong row set. P6's inbox gains the mapping constraint: a
divergent comparison must be reported `Unsupported`, never `Inexact`, because
v55's `Inexact` promises a *superset* and a divergent order can omit rows that
pass. `{Agrees, Diverges, Refused}` and `{Exact, Inexact, Unsupported}` are not
the same trichotomy, despite the shapes matching.

## 11.2 was mis-sized: the reconciliation is `11.2.1`, after 11.3

The slice row asked for the differ, the committed differences file, a
**three-way reconciliation** and the suite assertion. Two of the
reconciliation's three directions — every arm of the comparison register
resolves to at least one oracle case, and every case back to an arm — join
against the **L2** comparison register, which `11.3` builds. They are therefore
not buildable in `11.2` at any effort. The third direction, every major in
`fixtures/` having an answer file, is a precondition the differ has to check
before it may zip two files at all, and it does.

So the spec's row is rewritten to what landed and the remainder becomes an
earned `11.2.1`, placed after `11.3`. Its second direction also stops being a
moving target there: an arm added by `11.4` or `11.5` with no case is exactly
the coverage decay the check exists to catch, so a check written before those
slices would have to be re-run against a register that keeps growing.

**The fact was already on the page.** `11.1`'s notes and
`test_comparison_oracle.py`'s docstring both say the reconciliation needs the
register first; the slice table was not changed to match. The durable lesson is
that a slice's row is what to re-read when the *previous* slice files a
prerequisite — the prerequisite was recorded correctly and the plan that
depended on it was not.

Alternative considered and not taken: folding the reconciliation into `11.3`.
`11.3`'s review property is "did anything change?", and a diff that also adds a
coverage check is a diff where that question is harder to ask. Filed under
`STATUS.md`'s "Decisions worth another look" as a call the maintainer may
prefer to reverse, which costs a merge of two small slices and nothing else.

## The union rule is checked, and it holds across 13–18

`fixtures/oracle-differences.tsv` holds **509 differences between adjacent
majors, every one of them additive**: `numeric`'s infinities and the two
multirange types arriving in v14, `interval`'s infinities in v17. Nowhere do two
majors that both accept an input disagree about it, and no accepted literal's
canonical output spelling moves. That is the evidence P11's "implement the
newest semantics unconditionally" rests on, and it is now `I35` with a one-line
re-verification rather than a sentence in a spec.

Two shapes the differ classifies that the spec's table did not name, both
deliberately **non-additive**. An accepted literal whose `output` spelling
moves: 11.6 renders a literal into the form the *file* holds, so a spelling that
differs between majors is a rendering no single implementation can get right —
the spec had put that out of scope on the grounds that a fixture regeneration
shows it as a file diff, and it costs nothing to catch here. And a cell moving
between two rejections with different SQLSTATEs, which moves nothing a dump can
hold: that is the one strictness with no consequence, kept because the
conservative direction is a false alarm rather than a false silence, and it has
never fired.


## The collation witness: what the fixture images can and cannot show

Probed while grilling the oracle's musl limitation. The facts, all measured on
this machine against the images in use.

**The Alpine fixture images already carry ICU.** `pg_config --configure` on
`postgres:16.15-alpine` shows `--with-icu`, and the server links `libicui18n`;
`pg_collation` holds 870 ICU collations on `13.23-alpine` and 908 on
`18.6-alpine`. `('a' COLLATE "und-x-icu") < 'B'` is **true** where the bytewise
answer is **false** — so a collation divergence is observable on the images
already in use, with no second image family.

**A glibc image shows it at the database default instead.** On `postgres:16`
(Debian trixie, glibc 2.41) `datcollate` reads `en_US.utf8` and `'a' < 'B'` is
**true**, while `COLLATE "C"` gives **false**. Debian variants exist at every
pinned minor — `13.23`, `13.23-bookworm`, `13.23-trixie`, and the same for
14.24 / 15.19 / 16.15 / 17.11 / 18.6 — so switching families would not force a
minor to move.

**This sharpens I32 rather than merely illustrating it.** The same collation
*name* answers differently on musl and glibc, so a dump that recorded its
collation still would not determine the order: the reader would need the
server's libc and its version too. `pg_collation.collversion` for the glibc
default reads `2.41`, which is that version.

**The image pins float their base.** `postgres:13.23-alpine` resolves to Alpine
3.22 while the later majors' `-alpine` tags resolve to 3.23/3.24, and the ICU
identity moves with it: `und-x-icu`'s `collversion` is `153.128` on
`13.23-alpine` against `153.136` on `18.6-alpine`. The Postgres minor is pinned
exactly; the libc and ICU behind it are not. Harmless today, because nothing in
the oracle's cases depends on either — musl's `strcoll` is `strcmp` and no case
names an ICU collation — and load-bearing the moment one does.

## The reconciliation split is affirmed

The maintainer agreed with `11.2.1` sitting after `11.3` rather than folding
into it. The reasoning is now a rejected-alternative paragraph in the phase
spec beside the slice table, and the `STATUS.md` review entry is deleted.

### What the witness is, and what it is not

Settled: the closure of the register's text row gets a **witness** rather than
a change of apparatus. The two collations are `C` and the database's UTF-8
locale, chosen for prevalence — between them they are what nearly every
deployment runs — which means musl cannot produce it and the witness runs on a
Debian-based image while the six fixture images stay Alpine. One major, outside
the per-major oracle, with a test that fails if no case diverges.

An ICU collation was the free alternative and was not taken: it needs no new
image, but it is not what deployments run, and its identity floats with the
base image where libc's does not. Switching the whole fixture family to glibc
was rejected for a sharper reason — today's text cells are `C`-collation
answers, the case where pgdq **agrees**, so a family switch trades away the
half the file currently checks to buy the half it does not.

The decision, with both rejected alternatives, is in
[`../../design/roadmap-P11-typed-predicates.md`](../../design/roadmap-P11-typed-predicates.md),
"The text row's closure is witnessed, not asserted".

### The differ's apparatus guard excludes the one key that names the libc

`oracle_differences.py`'s `APPARATUS_KEYS` requires nine `meta.tsv` keys to
match across majors and excludes `version` because it must differ — but
`version` is the only key carrying the platform triple
(`on x86_64-pc-linux-musl`). A major swapped to a glibc base passes the guard
in silence while `datcollate` still reads `en_US.utf8` and means something
else. The triple becomes a guarded key parsed out of `version`, so the version
number may still differ. Settled independently of the witness; the witness is
what makes it load-bearing, by putting a second image family in the repo.

### The spec said one input grammar where there are three

11.1 recorded that `record_in` does not skip whitespace where `array_in` does,
and the spec was not amended to match — the same failure the 11.2 mis-sizing
taught. Amended now, in the spec's "The literal side gets a bounded input
grammar" and in 11.9's slice row.

### The witness's apparatus, measured before it was specified

`postgres:16.15-trixie`, glibc 2.41. The case set was run against a live server
under both collations before being written down, which is how the agreeing
pairs came to be in it:

| left | right | `C` | `en_US.utf8` | why |
|---|---|---|---|---|
| `A` | `a` | t | f | case ordering |
| `a` | `B` | f | t | letter before case |
| `é` | `f` | f | t | accent sorts with `e`, not after `z` |
| `_x` | `ax` | t | f | punctuation ignored at the primary level |
| `de luge` | `deluge` | t | t | agree |
| `e` | `é` | t | t | agree |
| `1` | `a` | t | t | agree |
| `co-op` | `coop` | t | t | agree |

Equality needs nothing added: a case is already asked for all six of
`OPERATORS`, so a collation-qualified case carries `=` and `<>` too. Every libc
collation is deterministic, so `texteq` stays bytewise and equality **agrees**
under both collations where ordering diverges under one — the split 11.6
inherits, now visible in the file rather than argued from the source.

Lands as **`11.2.2`**, before `11.3`: apparatus with no library code, and the
phase's rule is evidence before the code that leans on it.

### The family switch, and why the witness stopped being a separate thing

The maintainer reversed the earlier call once the question was put the right
way round: not "how do we observe a glibc collation" but "what should this
project's evidence be taken under". Answer: **glibc**. PostgreSQL promises to
apply what the platform's libc provides, not that a collation name means the
same order everywhere, so pgdq need promise no more than that either — and
"only glibc collation" is a stated limitation of the evidence rather than a
claim about servers.

So the whole fixture family moves from Alpine to Debian, with every generator
edited, every fixture regenerated and every correctness test re-run, and the
one-major witness folds into the oracle it was going to sit beside. The
agreement half — bytewise equals PostgreSQL under `C` — survives as a case-table
dimension: each text pair is asked under `COLLATE "C"` and under the database
collation, so both halves are in one file and neither is an accident of the
base image.

**Verified at both ends of the range before deciding**: `postgres:13.23-trixie`
and `postgres:18.6-trixie` are both glibc 2.41 with `collversion` `2.41`,
`datcollate` `en_US.utf8`, `datlocprovider` `c` (PG15+, where the column
exists), and both answer `'A' < 'a'` false and `'a' < 'B'` true. A single suite
pin therefore gives a uniform apparatus across all six majors, which is what
keeps libc drift out of the cross-major differences.

**No performance figure is affected.** No figure declares `fixtures/` or
`scripts/generate_fixtures.py` — every measured input comes from
`generate_perf_data.py` or `generate_block_count_bench.py` — so this touches
`--stale` not at all.

### The apparatus, and how the regeneration is checked

`-trixie` at every pinned minor, one suite for all six, never the unsuffixed
tag. The collation becomes a fourth field on an oracle case rather than extra
columns on a row, so a text pair is two cases and the existing row-for-row
check against the case table extends unchanged. And the regeneration is
diffed: into a scratch tree, compared against the committed one, with the
byte-identity of the dump corpus recorded either way — the prediction is that
`pg_dump` output does not move, since its TOC sort is `strcmp` and the minors
are unchanged, but the fixture tree is what every snapshot test reads and that
is not a thing to discover during `cargo insta review`.

## The register's text row was wrong, not merely weak

Found by probing the glibc image the family switch was being decided on.
`'A'::name < 'a'::name` is **true** where `'A'::text < 'a'::text` is **false**:
`pg_type.typcollation` is `C` for `name` and `default` for `text`. So pgdq's
bytewise comparison agrees with PostgreSQL exactly for a `name` column, on
every server — and the register told that column's user to distrust an exact
answer.

**The file states more than `I32` claimed.** `pg_dump`'s own attribute query
carries the rule: *"Since we only want to dump COLLATE clauses for attributes
whose collation is different from their type's default, we use a CASE here to
suppress uninteresting attcollations cheaply."* The type's default, not the
database's — which `I32` had wrong, in the direction that makes the file look
less informative than it is. Three cases the dump distinguishes: an explicit
`COLLATE "C"`/`"POSIX"` clause or a bare `name` (**agrees exactly**), an
explicit non-`C` clause (**known to diverge**), and no clause on a
`default`-collation type (**unknown**, so registered as diverging). Only the
database default is withheld.

`I32` is corrected — claim, proof, consequence and re-verify — and the phase
gains **11.11**, "the declared collation is read", after 11.3: `COLLATE` is
already located by `preamble.rs`'s `STOP_WORDS` and then discarded, so the
change is to keep it and consult it. It changes no comparison, only which
columns are told they diverge. Discovered scope rather than a split, so it
takes the next free number and the table carries the schedule.

### Two loose ends from the round the reversal landed in

The manual's first sentence about collation lands in **11.2.2**, with the
evidence rather than with 11.6's equality work — `docs/manual/` mentions
collation nowhere today, though text ordering shipped in P5.

And the question of where a separate witness module would live, and whether a
default regeneration would run it, is **moot**: the witness folded into the
oracle, so its cases are oracle cases and `--skip-oracle` already covers them.
No new pass, no new flag. The principle that settled it survives — a default
run produces everything committed.

## `char(n)` is not a collation row, and `COLLATE "C"` does not close it

Found while building 11.11. The phase spec had `char` with `text`, `varchar`
and `name` in one row, all four closing under an explicit `COLLATE "C"`. Three
of them do; `char` does not, and the reason has nothing to do with collation.

A dump writes every non-NULL `character(n)` value blank-padded to `n` — visible
in `fixtures/16/types/default.sql`, where `v_char char(10)` holds `hi` followed
by eight spaces. PostgreSQL's `bpcharcmp` calls `bcTruelen` on **both** sides
before `varstr_cmp` is reached, so the collation is consulted on trimmed
strings:

```c
len1 = bcTruelen(arg1);
len2 = bcTruelen(arg2);
cmp = varstr_cmp(VARDATA_ANY(arg1), len1, VARDATA_ANY(arg2), len2,
                 PG_GET_COLLATION());
```

The filter's literal is not padded. So `--filter 'code>ab'` on a `char(10)`
column selects the row whose `code` is exactly `ab` — bytewise, `ab` plus eight
spaces is greater than `ab` — where the server trims both to `ab` and answers
false. It is a real divergence, it exists under `C` as much as under any other
collation, and promoting `char` on the strength of a `COLLATE "C"` clause would
have been a claim of agreement the file does not support.

That is the same error the text row was corrected for, pointing the other way,
so it is recorded the same way: **I38** in `postgres-invariants.md`, the spec's
disposition table gains a `char(n)` row of its own, and the register answers
`OrderingDivergence::BlankPadded` for `character` without consulting the clause
at all. **11.6 inherits the fix** — trimming both sides is the same
canonicalization its "canonicalize the literal once" fast path already opens for
`=`, and closing it there closes both operators together.

**I37 was added beside it**, for the mechanical half 11.11 depends on and I32
only gestured at: `pg_dump` emits `COLLATE` at three sites the DDL grammar
reads (a table column, a `CREATE DOMAIN`'s base type, a composite attribute)
plus a fourth in a dummy view clause, always as `fmtQualifiedDumpable`'s
schema-qualified quoted reference, and in a table column it appends the clause
*after* `DEFAULT`/`GENERATED` and `NOT NULL` — verified identical in all six
majors. That placement is why the parser scans the fragment instead of looking
at the token after the type.

## 11.11 ships without a collated fixture: `11.11.1` is earned

No file under `fixtures/` carries a `COLLATE` clause, and none has a `name`
column. So the two cases where 11.11's answer changes *to agreement* — the half
that matters, since a wrong "agrees" is the error the register must not make —
cannot be exercised end to end on the tree as it stands.

Adding them means editing `fixture_schema_types.sql` and regenerating all six
majors. That rewrites **every** file under `fixtures/`, not only the `types`
ones: the `\restrict` token is freshly generated per dump, so a regeneration is
never a no-op diff. A diff of that size cannot share a review cycle with a
library change whose whole question is "did exactly the right columns change
verdict" — which is `process.md`'s "size a slice by its review" in the shape it
usually arrives in.

So the fixture work is **`11.11.1`**, apparatus-only with no library code,
exactly like 11.1, 11.2 and 11.2.2 before it, and it is written into the spec's
slice table with that reasoning. 11.11 itself lands with the emitted shapes
pinned by unit test against the strings a real `pg_dump` writes — taken from a
throwaway `postgres:16.15-trixie` container and recorded as I37 — and with the
*divergent* verdicts exercised end to end on the existing `public.t_text`.

## The `11.11.1` split is affirmed, and grilling it changed five things

The maintainer affirmed shipping 11.11 ahead of its fixture evidence. The
reasoning is now a *Rejected:* paragraph beside 11.11.1's row in the spec —
the two halves ask different review questions, a regeneration rewrites all 109
files under `fixtures/` whatever the schema does, and I37 is the stronger of
the two kinds of evidence anyway — and the register entry is deleted, which is
the only record that the review happened.

Grilling the slice turned up five things the spec did not have.

### Padding a `char(n)` literal is sound for `=` and unsound for `<`

The spec's canonicalize-once section prescribed padding the literal to `n`.
That is a bijection on the trailing-blank equivalence classes, so equality
survives it — and ordering does not, because a byte below `0x20` sorts *under*
the pad space while the server, having stripped the pad, ranks the longer
string above. Probed on 16.15:

```
select ('ab'||chr(9))::char(3) > 'ab'::char(3);                     -- t
select rpad('ab'||chr(9),3,' ') > rpad('ab',3,' ') COLLATE "C";     -- f
```

Trimming both sides holds for both operators, and it is admissible on the
per-row path because it is a reverse scan and a shorter length rather than a
decode. The spec now names three canonicalizations instead of two exceptions,
and 11.6's row says it retires `OrderingDivergence::BlankPadded`. Filed as
I38's corollary.

### The oracle cannot currently see that

`character(10)`'s case values are `("a", "a" + nine blanks, "hello", None)`,
all printable, so nothing in the file distinguishes pad-and-compare from
trim-and-compare. 11.11.1 adds `"a\t"` — `escape_copy_text` already maps the
tab, so the TSV needs no format work — and asks `character(10)` under both
collations, since 11.6 will split its arm three ways and a regeneration is
cheaper now than then.

### What the fixture images actually offer

`datcollate` is `en_US.utf8` at all six majors, so a no-clause `text` column
carries the real divergence and `COLLATE "C"` really does emit a clause. The
libc collations present are `C`, `C.utf8`, `POSIX`, `en_US`, `en_US.utf8`,
`ucs_basic`, plus ICU. Two of them are **bytewise in fact and divergent by the
register's name-based rule**: `ucs_basic` is defined with `collcollate = C`,
and `C.utf8` sorts by code point — both answer `'B' < 'a'` exactly as `C`
does. That is the asymmetry costing what it is designed to cost, and it is
recorded as a property beside the mechanism. `ucs_basic` earns a fixture column
for it. ICU stays out: its `collversion` moves with the ICU release.

### `TypeCases.collation = None` meant two different things

For the plain `text` and `character varying(10)` groups it means the database's
collation — the divergent population — and for `name` it means `C`, that type's
own default. A reconciliation that resolved `None` per type would be a second
copy of the register's type-default rule living in Python, which is the fork
11.2.1 exists to prevent, arriving from inside the check. So those groups state
`collation="default"` and `None` is left to mean "the register does not branch
on the clause here".

### I37 is observed at one of its three emission sites

Its **Observed** paragraph covers a `CREATE TABLE` column; the `CREATE DOMAIN`
and `dumpCompositeType` emissions rest on source greps, and the container that
produced the one observation is gone — while 11.11 has already widened
`TypeKind::Composite`'s field list on the strength of the composite claim.
11.11.1's domain covers the second site and a composite with a collated
attribute covers the third.

## `eca96be` is acknowledged for seven figures; three are left out

11.11's touches to declared paths carry no work — `map.rs` is a type change
with no new call, `batch.rs` is one line under `#[cfg(test)]`, `cache.rs` is a
`FORMAT_VERSION` bump. Its one executable addition on a scan path is
`extract_collation`, once per column of DDL, and `generate_perf_data.py` writes
exactly one `CREATE TABLE` per file — so every figure taken on its inputs is
excused, and the entry's `verified` is that grep.

`map-only`, `per-block-quadratic` and `preamble-prepass` are deliberately not
in the entry: their input is `blocks4000`, 4000 tables of four columns, so the
same addition runs 16000 times, and `preamble-prepass` *is* the measurement of
the prepass. Unlike `M28`, reachability argues nothing here — `blocks4000`
carries no type DDL, but every one of its tables has columns. Seven of the
thirteen figures now read stale, down from twelve.

## 11.11.1: a regeneration moves four things, and the plain `text` case had to go

**The reproducibility probe found a fourth mover.** 11.11.1's split rests on
"the `\restrict` token is the only nondeterminism in a plain dump", which
nothing had tested. Regenerating with `fixture_schema_types.sql` unchanged and
diffing against the committed tree: 109 files moved, and with the token lines
excluded the residue was not empty. Everything left was a wall-clock timestamp
— `logs.events.logged_at` and its `pgdq_tenant` counterpart, plus `--verbose`'s
`-- Started on` / `-- Completed on` pair, which is the one nothing had written
down. No DDL moved and no `--binary-upgrade` OID drifted on that run. The
premise holds with a wider ignore list; `architecture.md`'s "Fixtures" now says
four rather than three and carries the check that produced it.

The spec's own command under-matches, which is worth not re-deriving:
`-I'^\\(un\\)?restrict '` is a literal backslash then an optional `un\`, so it
matches `\restrict` and `\un\restrict` but not `\unrestrict`. The working
form is `-I'^\\(un)?restrict '`.

**Labelling the plain `text` case `"default"` produced nine duplicate rows.**
The spec has the plain `text` and `character varying(10)` groups stating their
collation explicitly, so that `TypeCases.collation = None` means one thing. For
`character varying` that is all it takes; for `text` it left two `default`
cases of one type sharing `A`, `a` and NULL — nine identical
`(type, left, right, collation)` rows in a file that carries no case
identifiers and is aligned positionally by the differ, which is precisely what
`test_no_duplicate_comparison_case` exists to catch. The plain case was folded
into the alphabet instead — `""` and `hello` joined its values — so `text` now
has exactly one case per collation, structurally identical to `character(10)`.
The rule the spec states is intact; the group it names is gone. Comparisons per
major go 1616 → **1745**, literals 279 → **291**, and
`fixtures/oracle-differences.tsv` is unchanged at 509, all additive.

**`literal_cases()` dedupes globally rather than skipping a collated case.**
The old rule was written when the text alphabet was the only collated thing in
the table; with `character varying(10)` and `character(10)` labelled it would
have dropped `12345678901`'s length rejection and the `char` tab's padded
`output`, both of which exist in no other case.

## Grilling 11.11.1's leftover: I37's placement, and two gaps beside it

11.11.1 closed by asking, under "Decisions worth another look", whether I37's
*placement* consequence deserved a fixture column. Re-running the probe
answered it and changed the plan: slice **11.11.2** is earned. The decision
sits in [`../../design/roadmap-P11-typed-predicates.md`](../../design/roadmap-P11-typed-predicates.md);
the evidence is here.

**Both of the entry's premises were false.** It priced the column at a
`NOT NULL` exception to `t_collate`'s one-alphabet property, and it said the
16.15 observation could not be re-run. Every `-trixie` image is still cached
locally; a twenty-second probe on `postgres:16.15-trixie` confirmed the string
the unit test hard-codes and showed the exception to be self-imposed:

```
v_def  text DEFAULT 'x'::text COLLATE pg_catalog."C",
v_nn   text NOT NULL COLLATE pg_catalog."C",
v_both character(10) DEFAULT 'x'::bpchar NOT NULL COLLATE pg_catalog."C",
v_gen  text GENERATED ALWAYS AS (upper(v_nn)) STORED COLLATE pg_catalog."C",
```

`DEFAULT` alone displaces the clause and `NOT NULL` alone displaces it. A
nullable column with a default observes the placement and keeps `NULL` in the
ninth row, so the alphabet survives intact. What is missing is therefore not
the observation but its form: I37's strongest claim rests on a string
transcribed by hand into a unit test, where every other claim in that entry
rests on committed bytes at six majors.

**I37 is wrong by omission about v18.** `dumpTableSchema`'s append order
between the type and `COLLATE` is, in v13–v17, `[GENERATED ALWAYS AS (expr)
STORED | DEFAULT expr] → [NOT NULL]`. v18 adds two shapes to it —
`CONSTRAINT <name> NOT NULL` and a following `NO INHERIT`, and a *virtual*
`GENERATED ALWAYS AS (expr)` with no `STORED`. A reader building a parser from
I37 as written meets a v18 dump it does not describe. Neither can be fixtured
without version-conditional schema SQL: `generate_fixtures.py` carries
`min_version` for dump flags only, and one schema `.sql` runs against all six
majors, so an 18-only shape fails on 13–17. That capability is a
fixture-family concern and wants its own slice.

**`objects.c_collation` is created and referenced by nothing.** So the
user-collation reference form — schema-qualified, unquoted, outside
`pg_catalog` — has never been observed, and neither has `collated_text`'s
answer for it: `NonBytewiseCollation`, even for a collation declared
`FROM "C"` and therefore provably bytewise. That answer is deliberate, since a
user collation named `"C"` in another schema is the one error the register must
not make, which is exactly why it is the cell most likely to be "fixed" by a
later session with no test in the way.

**Two smaller findings, neither actionable.** An inline column `CHECK` is
lifted to a table-level `CONSTRAINT` line, so a table column fragment never
carries one in real output. And a `STORED` generated column is absent from the
`COPY` column list — DDL but no data; `resolve_columns` walks `COPY` order and
looks each name up in the DDL, so a declared column with no data column is
simply never asked about.

**The full displacer stack is free, on the column that carries no data.**
`v_gen_nn text GENERATED ALWAYS AS (upper(v_src)) STORED NOT NULL COLLATE
pg_catalog."C"` is what 16.15 wrote for a `NOT NULL` stored generated column —
all three displacers in one fragment. Because a `STORED` generated column is
excluded from `COPY`, no row has to hold a value for it, so the `NOT NULL` the
original entry was willing to break `t_collate`'s one-alphabet property for
costs nothing at all. What it costs instead is reachability: a column absent
from `COPY` never enters a `TableStream`, so it cannot be filtered or
projected, and its assertion goes in `tests/preamble.rs` — which already walks
`DatabaseMetadata` across all six majors — rather than in `tests/ordering.rs`
beside the others. 11.11.2 is therefore the first slice where `t_collate`'s
columns are asserted in two files, split by reachability rather than subject.

The user collation dumps as `CREATE COLLATION public.c_collation (provider =
libc, locale = 'C')`, and a column of it as `v_user text COLLATE
public.c_collation` — schema-qualified and unquoted, the `public.mycoll` shape
the preamble unit test had only guessed at. The two lines together are what
makes the register's cell vivid: the dump states `locale = 'C'` and the
register still answers `NonBytewiseCollation`, because the collation is not in
`pg_catalog` and nothing stops a user defining a non-bytewise `"C"` elsewhere.

A generated column is not itself a new fixture shape — `edge_cases`'s
`total integer GENERATED ALWAYS AS ((a + b)) STORED` has been in the tree all
along. What is new is a *collatable* one, so that a clause follows the
parenthesised expression.

**Two registers deliberately gain nothing.** The comparison oracle is not
asked about `public.c_collation`: it is `FROM "C"`, so a third collation column
would reproduce the `C` column cell for cell, and it would be the first row in
that file put there to document a decision of ours rather than an answer of
PostgreSQL's — which is the discipline that makes the oracle worth trusting.
The deficiency register gains nothing either. `collated_text` answering
`NonBytewiseCollation` for a provably bytewise user collation yields *correct
rows* with a spurious advisory note; there is nothing for a user to remedy, so
it is a property filed beside the mechanism, not a `KD<k>`. `KD7` is the list
of places pgdq's order genuinely differs from the server's, and this is the
opposite shape.

**The probe recipe survives the fixture that supersedes it.** Committed bytes
re-verify placement at the six majors we generate, via the `grep` already in
I37's `Re-verify`. The recipe answers the same question for a *seventh* — a
newly released major, before any fixture for it exists — which is when the
walk-the-register ritual actually fires. It goes inline in the entry rather
than into `scripts/`, where nothing would consume it.

**The two v18 shapes get a coverage row and no owner.** I37 naming them is not
the same as exercising them, and the difference is exactly what
`pg-dump-compatibility.md` exists to record — so a session walking the
invariants at the next release can see that `CONSTRAINT <name> NOT NULL`,
`NO INHERIT` and virtual `GENERATED` rest on source reading alone. The row
names the blocker: `generate_fixtures.py` conditions flag *sets* on version
(which is how `fixtures/18/objects/stats.sql` exists) but runs one schema
`.sql` against every major, so an 18-only DDL shape fails on 13-17. The gap
itself is filed nowhere else — it is no deficiency, nothing being wrong and no
user affected, and a roadmap "Future" row would assert intent nobody holds.
The matrix row sits where the next session wanting a version-specific DDL
fixture will hit it, which is the only trigger worth having.

## The ADBC driver's type mapping is a floor worth declaring: `P12`

The Arrow ADBC PostgreSQL driver maps a PostgreSQL type to an Arrow type in one
C++ `switch` (`postgres_type.h`, `PostgresType::SetSchema`). Adopting it as a
**floor** — wherever it yields a real Arrow type, ours is never a widening of it
— turns the open-ended goal "every built-in type, eventually" into a bounded
target somebody else already ships, checkable rather than judged. That is `P12`, since
grilled and specified in
[`../../design/roadmap-P12-adbc-type-floor.md`](../../design/roadmap-P12-adbc-type-floor.md),
which the survey behind it was drained into.
It absorbs the Future item "Exhaustive built-in type coverage, with tests to
match", which is the same work without a bound.

**We are already at or above the floor almost everywhere, and the survey's
value was in why.** ADBC reads the *binary* wire format with the catalog in
hand; we read text under "the dump alone determines the value". So its bottom is
raw bytes plus a type name, ours is the file's own text, and on the forty-odd
types it declines to model — `inet`, `bit`, `xml`, the geometric family, **every
range and multirange** — our answer is the more useful one. Where it does map a
type we are equal or narrower everywhere but five: `numeric(p,s)` is a decimal
against their string, an enum a dictionary against their string, a range a
struct against their opaque bytes.

**The cheap bucket collapsed from four types to one under inspection**, which is
the finding that decided the scheduling:

- `oid` is a plain unsigned integer in text and stays cheap.
- `regproc` is not a gap at all: `regprocout` emits the function *name*, where
  the binary encoding ADBC reads is the OID. The two encodings carry different
  data, so "narrower" is not a question the text can be asked.
- `int2vector` needs a space-delimited nested codec — no brace-delimited literal
  to reuse — for a catalog type nobody's schema has.
- The `arrow.json` / `arrow.uuid` extension metadata turned on a rule question
  — does the floor cover metadata as well as type — which the maintainer
  answered **yes** the same day. That makes those two cheap and takes them with
  `oid`; see below for what else the answer obliges.

**Two rows sit below the floor by decision rather than by omission**, and they
are why the rule needs a stance field rather than a verdict. `money`'s text is
written through the monetary locale (`cash_out` reads `frac_digits`,
`mon_decimal_point`, `mon_thousands_sep`) and `pg_dump` sets neither
`lc_monetary` nor `IntervalStyle` — verified empty at v16.15 — so the file does
not determine the value. `interval` is reachable but needs an invariant first:
I4 records that `IntervalStyle` is never set, and the claim that the four
styles' outputs are mutually distinguishable is an observation until somebody
proves it.

## `M29`: `oid`, and the two canonical extension names

Out-of-band work, pulled into `P11`'s run — the three rows of the ADBC floor
survey that need no decision `P12` has not made. No spec and no notes doc: this
entry is the notes ([`../../process.md`](../../process.md), "Out-of-band work").

**What landed.**

- `builtin_scalar` gains an `"oid"` arm mapping to `UInt32` — **not** ADBC's
  `Int32`, which misreads an OID at or above 2^31 — with `ColumnBuilder::UInt32`
  behind it, a `public.t_oid` fixture column, an `oid` oracle case, and all six
  majors regenerated.
- `arrow.uuid` on a `uuid` column's field, and `arrow.json` on `json` and
  `jsonb`, through any chain of domains. `pgtype.rs`'s `extension_for` is the
  walk and arrow-rs's own extension types do the writing.

**Why it was admissible as out-of-band work.** It changes no decision any spec
records. The existing bar already licenses `oid` — the text is an unsigned
integer with no session state behind it, and the value is what it says. The two
extension names change no Arrow type, and the cache stores no Arrow types at
all — it holds declared type strings and the schema is derived at query time —
so `FORMAT_VERSION` did not move.

### `oid` needed a `CompareKind` of its own, and the reason is the literal

`CompareKind::Int` would have ordered every *value* correctly: an OID's range
fits `i64` and unsigned order agrees with signed order over it. It is a filter
**literal** that separates them. `oidin` accepts a leading minus and wraps it —
`-1` is 4294967295, at every major from 13 through 18, and the oracle's
`literals.tsv` now holds that answer identically at both ends — so sharing the
`Int` arm would have read `-1` as −1 and quietly returned the wrong rows. All
three facts `oid`'s mapping and its register row rest on are now **I39**.
`CompareKind::UnsignedInt` parses `u32`, which turns the same literal into
`Error::PredicateValueDecode`: a refusal the user can see instead of a
comparison that means something else. The register row is therefore **agrees**
with no `KD7` entry, and the weakness is stated in the row's own cell.

The wrap survives v16's rewrite of `oidin` onto `numutils.c`'s
`uint32in_subr`, which kept the backwards-compatibility branch verbatim
(I39). What that rewrite *did* change is the `strtoul` base, 10 to 0 — so a
hexadecimal OID literal is accepted from v16 and rejected below it. No case
asks for one; adding one would file an additive difference and nothing else.

### The extension names cost a direct `arrow-schema` dependency

`arrow::datatypes` re-exports arrow-schema's type list and **not** its
`extension` module, so the canonical `Uuid`/`Json` types and the `ExtensionType`
trait are reachable only by naming `arrow-schema` directly — pinned to 59.2.0,
the same version `arrow` itself resolves, with `canonical_extension_types` on.

That is worth more than the four lines of hand-written metadata it replaces.
`arrow.json`'s metadata key must be *present and empty*, and arrow-rs's own
`try_canonical_extension_type` refuses a field where it is absent — so a
hand-rolled version would most likely have produced a name that arrow-rs itself
could not read back. `supports_data_type` doing the storage-type check is the
same argument: the rule is upstream's rather than a restatement of it, and
`the_extension_names_fit_their_storage_type` is the test that fails if
`builtin_scalar` ever moves `uuid` or `json` off the type the extension permits.

**Top-level columns only, deliberately.** A `uuid` inside a composite or an
array element carries no name: the nested `Field`s come from this module's
shared type constructors, and a `uuid[]` column's own field is a `List`, which
is not a UUID. Whether the floor reaches nested positions is filed in `P12`'s
inbox, since it is a rule question rather than an omission.

### What the regeneration moved

83 s for the full six-major run. Outside `fixtures/*/types/` and
`fixtures/*/oracle/` the only movement is `\restrict` tokens and wall-clock
timestamps — `edge_cases`, `objects` and `partitions` are otherwise
byte-identical, checked with 11.11.1's own command. Inside `types/` the
non-`--binary-upgrade` diff is `t_oid` and nothing else; the
`--binary-upgrade` files also carry OID and `relfrozenxid` drift, which two more
relations in the database necessarily produce and which the previous
no-change regeneration had no occasion to show.

`fixtures/oracle-differences.tsv` is **byte-identical**: `oid` answers the same
at all six majors, wrap included, so the new case group introduced no
cross-major movement at all. The counts moved 1745 → 1776 comparisons and
291 → 299 literals, and the reconciliation from 36 arms/52 cases to 37/53.

`regproc` deliberately did not come with it — see the entry above. Neither did
the `POSTGRESQL:type` key ADBC writes on *every* field, nor `arrow.opaque` on
the columns we do not map: those are the rest of what "the floor covers
metadata" obliges, and both need a decision `P12` has not made — including
whether a column of readable text may honestly claim an extension whose meaning
is *cannot interpret*.
