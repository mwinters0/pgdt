# 2026-09-07

## Decode scaling bends well before 24 workers, and the thesis table's worker counts are floors

`P16`'s thesis table
([`roadmap-P16-parallel-scan.md`](../../design/roadmap-P16-parallel-scan.md),
"The thesis") extrapolates a probe linearly: one core decodes ~446 MB/s of
plaintext, four reach ~1.48 GB/s, therefore *~12 fused workers reach the HDD's
4,656 MB/s offer* and *~17 reach it for a typed query*. `16.1` built the
instrument that turns the probe into a measurement, and both probes reproduce —
~435 MB/s at one worker on real koji bytes, ~1.50 GB/s at four. The
extrapolation past them does not: on koji's bytes the curve flattens to 7.78×
one worker at twenty-four, with the twenty-fourth worker buying essentially
nothing over the sixteenth. Twelve decode workers reach 3,116 MB/s, against the
4,656 MB/s the table's arithmetic put them at.

**What that changes is the arithmetic, not the conclusions.** Decode is still
far below every device's offer, still the stage worth parallelizing, and the
fused worker is still self-balancing for the reason the spec gives — the ratio a
split pool would need is a property of the command. What it changes is that the
worker counts the table names are **floors on what will be needed** rather than
estimates of what will suffice, so the slices that price parallelism read the
figure and not the table.

The reasoning and the mechanism are beside the slice:
[`roadmap-P16.1-xz-decode-scaling-notes.md`](../../design/roadmap-P16.1-xz-decode-scaling-notes.md).

## An instrument slice lands in two commits, because the reading must name a commit the apparatus is already in

`xz-decode-scaling` is published at
[`measurements.md`](../../design/measurements.md), "What a second decode worker
buys", taken at `7d21c6e` and naming that commit inside its own marker;
`measure.UNTAKEN` is empty again.

Getting there took two commits, and the constraint generalises to any slice that
both builds a measuring apparatus and publishes a reading from it. A figure
published outside a stamped sweep declares the commit it was taken at inside its
own marker, and `--stale`, acknowledgement spentness and `--verify-additive`
each argue from that commit. A sitting run from a working tree carrying the
instrument, its generator and its register entry uncommitted has no such commit
to name: the parent names a tree where the instrument does not exist, and a
marker pointing there would report the figure stale against the very commit that
lands it — red with no explanation, which is the state
[`measurements.md`](../../design/measurements.md)'s staleness rules exist to
prevent, and which no acknowledgement can excuse, since an acknowledgement
asserts that a commit moved no reading and this one *created* the reading.

So the apparatus commits first and the sitting is taken from that commit. Here
that was the density gate at `7d21c6e`, whose landing also regenerated both
`.xz` legs — `generate_xz_input.py` being one of the figure's `depends` — which
is why the gate had to precede the publishing sitting rather than follow it. The
fold-in moved the register entry into `FIGURES` and replaced the session stamp's
accounting sentence with the one `--check` prints, the register having gone from
18 figures to 19.

## koji has no compression ratio, it has a range — so a decode rate is quoted with its density

The koji leg's offset was raised under "Decisions worth another look" as a call
worth review, and the review found the offset defensible and its *justification*
wrong. Sampling eight streams at twelve depths — a seek and ~10 MB each —
profiles the download as anything but homogeneous:

| offset | ratio | | offset | ratio |
|---|---|---|---|---|
| 0 G | 33.05× | | 20 G | 15.89× |
| 2 G | 25.56× | | 24 G | 15.23× |
| 4 G | 27.15× | | 28 G | 11.50× |
| 8 G | 28.15× | | 32 G | 16.83× |
| 12 G | 31.74× | | 36 G | 22.88× |
| 16 G | **5.02×** | | 39 G | 24.10× |

The whole file is 19.41× and the chosen slice 15.70×, which the slice notes had
called "the file's own neighbourhood". It is not one: koji's regions differ from
each other by 6.6×, so no offset is representative and the sentence was deleted
rather than softened.

**What settles it is that the figure's own two legs measure the effect.** The
control at 5.45× decodes ~205 MB/s on one core where koji's 15.70× decodes ~435,
so density drives the absolute rate hard — and the control therefore sits on top
of koji's *densest* sampled region (5.02× at 16 G) rather than being merely
"the synthetic leg". The two legs bracket the corpus. Three consequences, all
folded in: the scaling curve is what the figure publishes and an absolute rate
is always quoted with the density it was taken at; a third koji column is
refused, because leg one already spans the spread; and the slice's ratio is
gated to 14–18× rather than remembered, since a moved offset or a refreshed koji
could republish a rate for 31× bytes under the same heading — the plausible-table
failure the instrument already refuses twice.

The offset itself did not move. The decision is beside the mechanism
([`architecture.md`](../../design/architecture.md), "The compressed source") and
the profile is beside the slice
([`roadmap-P16.1-xz-decode-scaling-notes.md`](../../design/roadmap-P16.1-xz-decode-scaling-notes.md)).

## `KD14`'s growth is live structure per table, not churn — and none of the three mechanisms the entry named

The entry said peak RSS grows ~9.9 KB a `COPY` block and that three mechanisms
could produce it: the span list, `map::Builder::snapshot`'s whole-list clone,
and glibc returning little of what a churn of clones frees. Nine legs at two
block counts say it is mostly a fourth thing, and that the third is backwards:

- **+6,002 B a block is paid by `parse --preamble-only`**, which stops at the
  end of the schema section before a data block is read — three fifths of the
  full `parse`'s +10,390. An `info` over the finished cache costs +5,722 by an
  entirely different route, so the number is the *structures* and not the route.
  It is therefore per **table**, not per `COPY` block; `blocks4000` gives each
  table exactly one block, and only the preamble leg separates them, by paying
  it before the data section exists.
- **The whole-list clone is one to two kilobytes a block**, measured as `query
  --dqcache none` against a cached twin one flag apart. Real, a fifth of the
  growth, and the noisiest leg — two sittings an hour apart read +1,303 and
  +2,278 where every other leg moved by under 3%.
- **The allocator is not it.** Under the shipped shape glibc has the lowest
  slope of three: +10,390 against mimalloc's +11,415 and jemalloc's +13,703.
  Only with the throttle off does retention appear, and there mimalloc recovers
  ~4 KB a block.

What this changes for `P16`: the dominant term is parsed once, by the leader,
before any worker exists, so a parallel bound is `preamble + N × slot` rather
than `N × (what one scan holds)`. The finding is beside the mechanism
([`architecture.md`](../../design/architecture.md), "`parse` resumes, and saves
as it goes") and the readings are in
[`measurements.md`](../../design/measurements.md), "What the per-block resident
growth is made of" — a section outside the register, taken by
`scripts/rss_attribution.py`. Why it is a diagnostic rather than a figure is under
`STATUS.md`'s "Decisions worth another look", where a person can weigh it.

## The RSS attribution is a figure, and what decides that

Reviewed the call `16.2` flagged — that the attribution be published as a
diagnostic rather than registered — and reversed it. Three of the four reasons
it gave do not survive the tree:

- *"A resident set is not a timing, so none of a figure's apparatus control is
  doing anything for it."* `peak-rss` is a registered figure whose reading is a
  resident set, and its section publishes an apparatus line over every run. The
  argument deregisters `peak-rss` too.
- *"Legs no sweep would take — a second and a third allocator."* The `allocator`
  figure already builds and times jemalloc and mimalloc, and the attribution
  borrows those binaries rather than building them precisely because that is
  the `allocator` figure's apparatus rule. What is genuinely new is two command
  shapes, `--preamble-only` and `info --dqcache`.
- *"An unattended session that does not commit cannot publish a figure taken at
  a named commit."* `16.1` did exactly that hours earlier, across `2622eb7`,
  `7d21c6e` and `d24168a`. The subagent does not commit; the loop does.

What survives is that a ranking drifts less than an absolute — which bears on
how often a figure needs re-taking, not on whether anything should be told when
it goes stale. The precedent decides it: `peak-rss` was registered *because* the
same claim sat outside the register in the koji section, where no `depends` edge
could go red, and it stayed a megabyte wrong for a whole slice. The attribution
now publishes nine medians and three derived slopes the phase reasons from, one
section below the paragraph recording that failure.

The criterion this settles is filed beside the mechanism
([`../../design/measurements.md`](../../design/measurements.md), "The register's
boundary is declared, not inferred"): a section is a figure when this document
publishes falsifiable numbers from it *and* the harness can re-take them, and it
stays outside only when the run is not the harness's to make (`koji`) or it
publishes no number the design quotes (`benches`). The kind of reading does not
enter into it. The work is `M65`.

**A live claim is licensed by the wrong figure meanwhile.**
[`../../manual/dump-inspection.md`](../../manual/dump-inspection.md) says
resident memory grows with the number of tables "by roughly 10 KB each" — a
per-*table* claim, written by `M58` — and it sits in `peak-rss`'s `quoted_by`.
`peak-rss` cannot tell per-table from per-block: `blocks4000` gives every table
exactly one `COPY` block, so the two coincide in its inputs, and only the
attribution separates them. `M65` moves the citation.

**`koji` has the same hole and always has.** `Outside` carries `id`, `section`
and `why`, and `--stale` never reads `NOT_OURS` — so no outside-register section
can go red however far its inputs move. Registering the attribution does not
close that; `M66` does, by giving `Outside` an invalidation edge, which
separates registration-for-staleness from registration-for-sweeping.

## 16.4 split: backpressure has no test without a second holder

`16.4` committed to two things — the pool sized in a currency a block fits in,
and **backpressure**, a `take` that waits for a free slot instead of
allocating. The first landed; the second earned `16.4.1`, and the reason is a
property of the pool rather than of the schedule.

**The pool cannot tell its two kinds of holder apart.** A serial reader holds
`(max_source_span / chunk) + 1` buffers at once — 65 at the defaults, and
**unbounded** under `max_source_span: None`, which is a supported setting —
because a batch pins every read chunk it has taken a `Utf8View` into until it
flushes, and the deque's own eviction at the scanner position cannot release
one the builder holds. A worker given an LF-split range inside one block holds
exactly one slot. A wait is backpressure for the second and a **deadlock** for
the first: the only thing that could free a slot is the task that is waiting.
Nothing in a `take(len)` call says which is calling, and length does not
separate them any more than it separated a chunk read from a span read.

**A caller-set budget does not rescue it, and knowing which half is
load-bearing is what shapes `16.4.1`.** The obvious softening — wait only above
a budget the caller set — fails on the arithmetic: at the defaults the serial
reader legitimately reaches 65 MiB against a 64 MiB budget, so any budget below
the holder's reach deadlocks, and under `max_source_span: None` no finite budget
is above it. What makes a wait safe is therefore the **exemption**, a holder
that never waits because it cannot be the one to free a slot; the budget is a
knob on the waiting holders and never the thing that keeps the serial path
alive.

**The ground for deferring is testability, not the absence of a consumer.**
"It needs its consumer" proves too much — `16.6` lands
`ByteRangeSource::partitions` with no consumer at all, so this phase plainly
accepts mechanism ahead of use. The distinction is what a test can assert.
`partitions` is a pure function whose whole contract is its return value, and a
fixture pins it. A blocking acquire has no behaviour except its interaction with
holders: with only the exempt holder in the tree, the strongest assertion
available is "it did not block", which is exactly what the non-waiting `take`
already guarantees. Landing it early would buy a passing test of nothing and
defer the real review to the slice that supplies the contention.

**The seam is not one the spec's slice list could have predicted, and it is
worth naming.** `../process.md`'s recurring seam is a mechanism paired with the
evidence that mechanism needs. This one is a **sizing paired with a bound**:
sizing is reviewable against the read path in front of it, and a bound is only
reviewable against the holders it bounds. That is visible once the holders are
being enumerated and not before.

**`max_source_span: None` and a waiting pool are formally incompatible, so
`16.4.1` refuses the pair.** An unbounded holder against any finite budget is a
deadlock waiting for a filter sparse enough to reach it — not a configuration
error anyone meets in testing, and one whose symptom is a hang rather than an
error. The serial exemption hides it today, but `16.8` partitions *replay*,
which is the path that carries `RowBatcher` and its span cap, so the parallel
path would inherit a setting that can make its own bound unsatisfiable. `16.4.1`
raises an option-validation error naming both settings when `max_source_span` is
`None` and `Parallelism` is not `Serial`. Clamping `None` to the pool budget was
the alternative and is refused: it turns a memory promise into a silent
reinterpretation of what the caller asked for, and `None` is a caller saying
explicitly that they do not want this cut.

**The re-derivation came out as no change, which is the finding.** The 64 MiB
`max_source_span` was 64 default read chunks, so the cap and the pinning bound
were one number. Against a decoded block the rounding is to 24 or 128 MiB
units, and a batch confined to one worker's range inside one block pins exactly
that block whatever the cap says — so on a block-shaped source the cap is not
the bound at all, and the pool's slot budget becomes one when `16.4.1` makes it
bound what is outstanding rather than only what is idle. Neither the default nor
the trigger moved; what moved is which mechanism the memory claim is read off
([`architecture.md`](../../design/architecture.md), "Three flush triggers, and
only one of them bounds memory").

## 16.5 takes a second pool, because a pool describes one unit

`BufferPool::hinted` is a single atomic, written by `hint_read_size` and read by
two rules at once: `keeps()`, the only clause that lets a buffer over the 8 MiB
ceiling be pooled at all, and `slot_bytes()`, which `slots()` divides the budget
by. **One pool can therefore be right about one read unit, and `16.5` puts two
on the same `XzSource`** — block decodes into pooled buffers, underneath a read
loop still announcing `chunk_size`.

Either setting is wrong for the other unit. At the chunk length a decoded 24 MiB
block fails `keeps()` and is dropped on release, so every block decode is a
fresh `calloc` of 24 or 128 MiB while `slots()` reports 4 against a unit nothing
is holding — block-sized on paper, chunk-sized in fact. At the block length
`keeps()` is satisfied and the chunk reads above it get block-sized slots
instead, collapsing `slots()` to 1 or 2 and taking the pooling away from the
path the **1.83×** miss is measured against
([`measurements.md`](../../design/measurements.md), "What the read chunk size is
worth") — on exactly the source class the phase exists for.

**So the block decoder gets its own pool.** Each keeps the existing derivation
unchanged, and the one new question — how the two budgets add up — is one
`Parallelism`'s byte half (`16.7`) has to answer regardless. The alternatives
are both compromises: teaching `hinted` to hold a *set* of units complicates
`keeps()` and `slots()` to buy what two pools give structurally, and letting the
single hint name the block accepts the chunk path's regression as the price.

## `16.5`'s holder keeps the pool's discipline by releasing before it acquires

`16.4` deferred backpressure until a second holder existed and named the
discipline that would make a wait safe: **one slot per holder**. `16.5` landed
the holder, and it does not have that shape. `XzSource`'s retained blocks can
occupy every slot of the block pool — which is what a chunked read loop over a
24 MiB block unit requires, since the alternative is decoding the block again
per 1 MiB call — so counted by slots held it looks like the serial reader the
exemption exists for.

What makes it safe instead is the **order**: the retention evicts down to one
below the slot count and *then* takes, so the buffer a decode is about to want
is one the cache has already given up. A holder that frees a slot before asking
for one cannot be the task a wait is waiting on. That is a second sufficient
discipline beside the per-holder count, and `16.4.1` is to hold the block pool
to it rather than to a number of slots.

The order is worth 24 MiB on its own. Bounding the retained set and the free
list independently — each at the pool's slot count — reads 89.2 MiB resident on
the 3.00 GiB `.xz` control where releasing first reads 64.7, because the two
bounds are then two numbers for one budget. The mechanism is beside itself
([`architecture.md`](../../design/architecture.md), "The compressed source") and
the readings are in
[`roadmap-P16.5-xz-concurrency-notes.md`](../../design/roadmap-P16.5-xz-concurrency-notes.md).

## The block-decode cap declines memory, not seekability

Both of `16.5`'s "Decisions worth another look" entries were reviewed and both
calls stand. What the review changed is the account of *why*, which was wrong in
four places, and one spec row.

**The single-block fallback is the ordinary path for a large archive.** `xz`
writes one block per stream unless it is threading, so plain `xz bigfile` — no
`-T`, the default — produces a file whose one block is the entire plaintext:
`xz -0 -T1` over 240 MB gives 1 stream and 1 block, against 8 for `xz -0 -T4
--block-size=32MiB`. Refusing that shape, which is what the entry asked about,
would retire the fallback path and `BLOCK_DECODE_MAX_BYTES` together and make
the most ordinary `.xz` there is unreadable. So the fallback stays, and it is
not a concession to an edge case.

**The reason written beside it was false.** Four documents said the cap declines
only a file with no parallelism to lose, one block being one decode unit. The
cap is keyed on the file's largest block, not on its block count, so a
multi-block file written with large blocks — `xz -T8 --block-size=512MiB` —
is declined by it and genuinely does have parallelism to lose. **Any file with
more than one block is seekable, and decodable block-wise, for a client willing
to allocate a block**; what the cap declines is memory. The sentence is
corrected in `io.rs`, [`architecture.md`](../../design/architecture.md), the
slice notes and `STATUS.md`, with the two alternatives refused with it — keying
on block count, and deciding per read rather than per file.

**That makes the cap `16.7`'s, and its spec row now says so** — `16.7.1`'s once
that row split, which is below, "16.7 split: a value, then what reads it". The
256 MiB line
and `POOL_BUDGET_BYTES`' 64 MiB are unrelated numbers, and the smaller is not a
bound above its own slot size: `BufferPool::slots` clamps to at least one, so a
128 MiB block is 128 MiB resident against a 64 MiB budget. Once a caller states
a parallelism budget, "a slot must fit what the caller allowed" is the line and
the constant retires into it. Deriving it now would derive it from another
constant, so nothing changed in the code but the doc comment that overstated the
budget's reach.

**The retention cap stands, and the entry that questioned it was aimed at the
path that holds least.** Retention is capped at the block pool's `slots` — two
against a 24 MiB block — where one serial reader walking forward needs one. But
`pgdq parse`, which the 64.7 MiB probe timed, builds no batches, so
`RetainedChunks` never runs; on the query path a retained chunk is a zero-copy
view into a whole block, so retaining 1 MiB of a 24 MiB block holds all 24 and a
batch bounded by `max_source_span`'s 64 MiB pins several blocks — more than the
cap holds. Cutting the cap to one also makes eviction keep zero and drain before
every decode, so an outstanding view forces a fresh allocation of the block unit
instead of a reuse. The cap stays one number off the pool's own budget; the
first measurement of a compressed scan's resident cost belongs on a query, which
`16.13`'s `parallel-peak-rss` row already covers.

**A streaming-fallback source advises one partition, and `16.6`'s row now says
so.** The spec stated `XzSource`'s partitioning answer unconditionally — "at
these block boundaries" — which is right for the block path and silent about
the fallback, that having become a distinct read path only when `16.5` split
it. Such a source still has a seek table and still has block boundaries, but
reaching an offset inside a block has one route: restart at the block's start
and decode forward, discarding. So two workers on different partitions each
force the other's restart, and parallel mode over that file is **worse than
serial** rather than merely unaccelerated. Advising one partition gives up
nothing — LZMA2's dictionary runs the length of a block, so a block is the
parallel unit entire, and the shape this reaches in practice is a single-block
file, which has no second worker to give at any budget.

## 16.4.1 waits on 16.7

`16.4.1` was the next unticked box and was not taken, because two of its three
commitments name something that does not exist yet and the third is unsafe
without it. The phase's order after the evidence slices is **allocation order,
not a schedule** (this document's "Slices"), so `16.6` was taken instead and the
binding-orderings line now carries the dependency.

**The row validates a condition it cannot spell.** It commits to "an
option-validation error naming both settings when `max_source_span` is `None`
and `Parallelism` is not `Serial`", and `Parallelism` is `16.7`'s enum. Nothing
in the tree has a non-serial state to compare against, so the check is vacuous
until that row lands. Introducing the enum here would land half of `16.7` — the
rest of that row is the `ScanOptions`/`QueryOptions` wiring, the CLI flags and a
manual page — which is a slice boundary crossed to satisfy a sentence.

**And the wait has no number.** `POOL_BUDGET_BYTES` is a constant; the budget a
pool serving N workers waits against is `Parallelism`'s byte half. A wait wired
to today's constant is a wait on the serial path's number.

**The block pool is a holder the `16.4` analysis did not enumerate, and it is
not exempt on the query path.** `16.5`'s notes say the block cache keeps the
discipline by *releasing before it acquires* — eviction runs down to one below
the slot count and then takes — which is sufficient only while the source's own
retention is the sole holder of a decoded block. It is not, on a query: a
retained chunk is a zero-copy view into a whole block
([`architecture.md`](../../design/architecture.md), "The compressed source"),
and `batch::RetainedChunks` holds every chunk a batch has taken a view into
until it flushes. At the defaults that is a 64 MiB `max_source_span` of chunk
views spanning roughly four 24 MiB blocks against a block pool of **two** slots:
eviction drops the cache's own references and the views keep the slots
outstanding, so a waiting acquire blocks on the very read loop that would free
them. `parse` never reaches it — it builds no batches — which is why the 64.7 MiB
probe saw nothing.

So the constraint the wait actually has to satisfy is not the
`None`-versus-parallel pair the row names. What replaces it is below, "The wait
is exempted by holder class, not validated by an option pair"; the ordering was
settled either way, since every answer needs a caller-stated budget to be
written against.

**The half of `16.7` that binding names is `16.7.1`.** `16.7` was itself split
later the same day (below, "16.7 split: a value, then what reads it"), and the
value it landed is not what a wait waits on: the budget has to be a number the
*pool* reads, and the pool still reads a constant. So `16.4.1` waits on
`16.7.1`, and the spec's binding-orderings line says that.

## The wait is exempted by holder class, not validated by an option pair

`16.4.1`'s option-validation commitment — an error when `max_source_span` is
`None` and `Parallelism` is not `Serial` — is **withdrawn**, and nothing
replaces it. The exemption that makes a waiting acquire safe is stated by
**holder class** instead: a read that will be retained into a batch never
waits, whatever the options say. The decision is beside the mechanism
([`architecture.md`](../../design/architecture.md), "Execution model and API
surface") and the row is amended
([`roadmap-P16-parallel-scan.md`](../../design/roadmap-P16-parallel-scan.md),
`16.4.1`).

**The pair it named is neither necessary nor sufficient.** Not necessary: the
verified hang is `Parallelism::Serial` at both defaults, one serial query over
a 24 MiB-block `.xz`, whose batch pins three or four block slots against the
two a 64 MiB budget affords. Not sufficient: `TableStream` yields its
`RecordBatch`es to the caller and a `Utf8View` batch carries the block views
its columns were built on, so a consumer dropping each batch before pulling the
next holds one batch's worth however the span is set, and one that collects
them holds every block the query touched. **How many slots are outstanding is a
property of consumer code**, which is the fact that kills the whole shape: no
pair of option values can predict it, so a check over them reads as proof of
safety it cannot give.

**The stated bound therefore has two terms, and only one is a ceiling.** The
waiting holders' slots are the library's; what in-flight batches pin —
`max_source_span` rounded out to the retained unit, times however many batches
the caller keeps — is the caller's. Folding the second into the first is what
the withdrawn check was doing implicitly.

**Two documents were asserting the wrong ground.** `architecture.md`'s
`Rejected: backpressure` analysis stated its holder arithmetic purely in chunk
units, so the block unit never entered it; and the paragraph beside it held
that the block pool's **release-before-acquire** — `BlockCache::slot` draining
`retained` to `slots - 1` before taking — let that holder wait safely. It does
not, on a query: the drain releases the cache's own `Arc` while the batch's
views keep the buffer outstanding, so the block cache and the batch builder are
the same slots counted twice. Release-before-acquire is a property of the
`parse` shape, which builds no batches, rather than of the pool. Both
paragraphs are rewritten, and the same correction is folded into `16.4`'s and
`16.5`'s notes, which handed the claim forward.

**No code changed.** `io::BufferPool::take` still allocates on a miss, so
nothing in the tree can hang on this; what changed is what `16.4.1` is to
build.

## 16.7 split: a value, then what reads it

`16.7` committed to four things — the `Parallelism` enum, its
`ScanOptions`/`QueryOptions` wiring, the CLI's `--jobs` / `--parallel-memory`
with a manual page, and `BLOCK_DECODE_MAX_BYTES` retiring into the stated
budget. The first two landed; the last two earned `16.7.1`, and the seam is a
property of the fourth rather than of the schedule.

**Retiring the cap is a rework of the two pools every timed path runs
through, and it turns on a choice with no free answer.** `io::BufferPool`'s
budget (64 MiB) and the block-decode cap (256 MiB) are unrelated numbers, and
making both the caller's forces a decision about where the *default* sits:

- **64 MiB.** The cap becomes the budget, every slot count in the tree is
  unchanged, and a file whose largest block is between 64 and 256 MiB falls back
  to the streaming reader instead of block-decoding. That is the budget being
  honoured — today a 128 MiB block is 128 MiB resident against a 64 MiB budget,
  which is what the spec row calls out — and `xz-seek` endorses exactly that
  fallback (`vendor/xz-seek/src/plan.rs`: a budget too small for one worker
  "clamps to one and reports", so a caller "can fall back to its own streaming
  decoder"). It costs a `query` over `koji-…blocks128.xz` under the default,
  with `--parallel-memory` as the remedy.
- **256 MiB.** No file changes read path, at the price that the block pool's
  slot count goes 2 → 4 on a 24 MiB-block file — the serial `parse` probe's
  64.7 MiB becoming roughly 112 — and the chunk pool's documented 64 MiB
  ceiling moving to 256.

Both are defensible, both move a number a document states, and neither is
visible from the spec row — which is why the split was earned rather than the
call being folded into `16.7`'s diff. `16.7.1` took the first, below.

**The CLI flags follow the rework rather than the value.** `--parallel-memory`
is only honest once the number it states changes something, and `--jobs` only
once a worker exists; a flag whose value changes nothing is surface that lies to
a user, which is a stronger objection than the one against an option field
documented as unread — `ByteRangeSource::size_is_exact` is carried and unread
today, and `ByteRangeSource::partitions` landed with no consumer at all.

**What this leaves is a value whose whole contract is its shape**, which is the
same ground `16.6` stood on: `Parallelism::workers(1, …)` is `Serial`, so no
`Workers` of one exists, and `--jobs 1` is the serial path without the CLI
arranging it. The reasoning is beside the mechanism
([`architecture.md`](../../design/architecture.md), "Execution model and API
surface") and the inherited decision is beside the slice
([`roadmap-P16.7-parallelism-surface-notes.md`](../../design/roadmap-P16.7-parallelism-surface-notes.md)).

## The stated budget goes to 64 MiB, and the block-decode line falls with it

`16.7.1`'s open choice — where the default budget sits once
`BLOCK_DECODE_MAX_BYTES` retires into it — is settled at **64 MiB**, which is
the smaller of the two candidates above and the one that keeps the number
honest rather than the one that keeps every file on the same read path.

**What decided it is which way the pool's one-slot floor points.**
`BufferPool::slots` clamps to at least one, so a unit above the budget is still
allocated at its own size — the budget cannot be honoured by shrinking a slot,
only by *refusing the unit*. That is what `BlockCache::affordable` now does, and
raising the default to 256 MiB would have kept the floor as the escape hatch it
was: a 128 MiB block resident against a stated 64 MiB. It also costs the serial
path — four retained blocks where two suffice on a 24 MiB-block `.xz`, and four
buffers of a raised `--chunk-size` where the budget afforded one — which is
memory every user pays to spare two file shapes a slower read.

**What it costs is `xz -9 -T0` as well as `koji-…blocks128.xz`.** The threaded
block size `xz` picks is three times the dictionary, so `-9 -T0` writes ~192 MiB
blocks and now falls back to the streaming reader under the default. `parse` is
unaffected in fact — it never reads backwards, and `16.5`'s probe had streaming
marginally faster — but `query` re-decodes forward from a block start on every
backward read. `--parallel-memory` is the recourse and it is the flag this same
slice adds; the entry under "Decisions worth another look" is what puts the
trade in front of a person.

**One number bounds a source, not each of its pools.** `XzSource` has two read
units, so the stated budget is divided rather than handed to both: the chunk
pool takes its own ceiling — 4 MiB at the 1 MiB default chunk — and the block
pool takes the remainder, which leaves a 24 MiB-block file the two slots it had.
Giving each pool the whole budget was the simpler shape and was refused: the
block term is the one that grows, so a source could hold twice what a caller
allowed, in a phase whose central promise is a number in bytes. The split is
recomputed from the source's own stored numbers on both announcements, so
`hint_read_size` and `hint_parallelism` may arrive in either order.

**`jobs` is the block pool's depth and not the chunk pool's**, which is the one
asymmetry worth carrying forward. A chunk buffer is taken and released inside
one `read_range`, so its free list wants the replay path's depth; raising that
ceiling with a worker count grows a query's resident set by
`(jobs − POOL_DEPTH)` chunks the moment `RetainedChunks` releases what a flushed
batch pinned — 20 MiB at the CLI's default on this machine — bought for
concurrency no scheduler produces yet. It is a number to re-derive against real
holders, not a rule.

## The budget fallback is announced, and the budget stays one number

Reviewing the "Decisions worth another look" entry `16.7.1` filed. Two halves,
settled separately, and the entry's own framing was too narrow in both.

**The default budget stays 64 MiB, and the alternative that had not been
considered is rejected beside the one that had.** The entry put the choice as
64 against 256 globally. But `ScanOptions::parallelism` and
`QueryOptions::parallelism` are separate values announced at three separate
points — deliberately, so a query's two passes are bounded separately — and the
cost of the low default is asymmetric: `parse` never reads backwards and 16.5's
probe had streaming marginally faster, while only a backward read pays. So a
third option existed: default the replay higher than the scan, sparing the
declined shapes exactly where it hurts and costing the serial path nothing. It
is refused because `--parallel-memory` states a bound, and a run holding
256 MiB after the user asked for 64 makes the stated number untrue in the
direction the derivation was written to fix. Both rejections are filed at
[`../../design/architecture.md`](../../design/architecture.md), "The compressed
source".

**The silence was defended on a cost that is not there.** The entry, and the
paragraph it produced, said a per-run diagnostic "would need the source's
budget to reach `index.rs`, which is a trait method for a sentence."
`ByteRangeSource::partitions` is already that trait method — synchronous and
pure since 16.6 — and `XzSource::partition_advice` returns
`Partitioning::single` on exactly the declined-on-budget arm and
`Partitioning::at` otherwise. A source advising one partition over a seek table
holding many blocks has declined for budget, and `index.rs` already holds the
source and already calls `seek_table()` at the two sites where it pushes
`NonSeekableCompressedSource`. Detection is a comparison between two values in
hand, so the reason for staying silent was gone and the call went the other way.

**The user also cannot discover the number the recourse needs.**
`--parallel-memory`'s help already says to raise it "on a file written with
large blocks", but `max_block_uncompressed()` reaches no reader outside
`io.rs` and `info` reports nothing about block sizing, so the answer today is
`xz --list` — an 85-second walk on the multistream koji file. The diagnostic is
where that number is wanted, because it is the moment the user learns they want
it.

**The warning is not pushed wherever an index is built, which makes it the
first diagnostic whose site is a caller's decision.** The condition holds
identically under both commands; the consequence does not. Only a backward read
pays for streaming, and `parse` never seeks backwards — 16.5's probe had it
marginally faster — so warning there is advice to spend 128 MiB to buy nothing.
Varying the severity by command instead was refused: it would make severity mean
"which verb did you type", which nothing else in the register does.

**A budget decline cannot be cached, and the offline view answers shape
instead.** `NonSeekableCompressedSource` is a property of the file, which is
why `cache::status_from_file` replays it from the persisted table; a decline is
a property of the file *and* the run's budget, so `info --dqcache` will not
report it. Persisting the budget in force at save time was refused for the same
reason the per-pass default was — it would report a decision made under a number
the current run never stated. What the cache can answer is the whole shape:
`SeekTable::stream_count`, `block_count` and `max_block_uncompressed` are public
and serialized with the envelope, so `info --verbose` reports the largest block
a user would have to budget for and the stream count that explains the
multistream footer walk, with no dump file present. A per-block listing was
refused as an `xz --list` reimplementation whose worst case is the 31,150-block
file it would flood.

Both are admitted as `M67`. It changes no decision any spec records — the
`16.7.1` spec row commits to the flags and the manual page and says nothing
about silence — and it fits one session, so it is out-of-band rather than a
slice. It does not block P16's remaining slices: no figure and no later slice
reads a diagnostic.

## The holder class is a permission, and the shipped loops take the exempt one

`16.4.1` landed with `scan` and `map_forward` announcing the waiting class, and
that is reversed: both take the exempt class, and the pair is renamed to say
what it selects rather than what the holder is (`M68`). Three things decided
it, and the first two are facts the landing session did not have.

**The wait's test does not run through a read loop.**
`io::tests::a_transient_read_waits_for_a_slot_rather_than_allocating` builds a
bare `BufferPool` and calls `set_class` on it directly — two threads, a
one-slot pool, a negative assertion before the release. It never constructs a
source and never calls `hint_holder_class`. So the wait is exercised against
real contention whatever the shipped loops announce, and the argument that
moving them to the exempt class would leave the mechanism untested was
answering a question the test suite had already closed. What announcing the
waiting class on a production loop buys is not coverage but exposure.

**A half-built contract is this phase's normal shape, not a cost.** `16.6`
landed the partitioning advisory with "No consumer yet" in its own spec row,
and `16.7` landed the `Parallelism` value with "No consumer" in its. The two
slices either side of this one shipped one half of a contract deliberately and
said so, so "nothing in the shipped build exercises it" is not an argument this
phase recognises against doing the same again.

**The two failure directions are not comparable.** The exempt class where the
waiting one was right means the bound silently fails to bind: more memory,
degraded, and visible in `peak-rss`. The waiting class where it was wrong means
a hang on the hottest read path, with no output and nothing to measure. The
code already encodes that judgement — `Retaining` is the `Default`, so a source
nobody announces to cannot hang — and the two discard loops were the one place
the build departed from its own safe default with no consumer requiring it.
`16.10`'s fused worker is the first holder that genuinely needs the wait, and it
arms it then.

**Rejected: gating the wait on `Parallelism::Serial` instead of on the class.**
Under `Serial` there is one reader, so a bound on what is outstanding buys
nothing, and a gate there would arm the wait exactly when `--jobs` is stated. It
is refused because it puts a second axis back on a mechanism this phase reduced
to one — "The wait is exempted by holder class, not validated by an option pair"
above — and the distinction from the option validation rejected there (this
infers *pointlessness* from the worker count, that inferred *safety* from an
option pair) is too fine to survive being read by a later session.

**What the rename is for.** `scan` genuinely does not retain, so putting it in a
class called `Retaining` states something false about the loop in order to
select a behaviour. The class is a permission — *may this holder be made to
wait* — not a description of what the holder does with its buffer, and the name
is what should carry that. The spelling is `M68`'s to settle; what is decided
is that the pair reads as policy rather than as description, and that
`tests/holder_class.rs` goes on recording which loop announces which.
