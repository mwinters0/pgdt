## The ICU `collversion` is guarded (`M42`)

`fixtures/<13-18>/types/binary-upgrade.sql` carries `CREATE COLLATION
public.nd_collation (…, version = '153.128');` — the tree's only ICU release

the exact fault an across-majors identity check exists to report. Naming

`153.136` fails it by name.

written: the option is present under `--binary-upgrade`, absent from `default`,
absent from `data-only` (which emits no `CREATE COLLATION` at all), and absent
from `public.c_collation` under every flag set, a `C` libc collation having no

**Where the guard is written down.** `architecture.md`'s "Fixtures" section

## The two filter flags disagree about a string both accept

`--filter` and `--where` read one term grammar, and the phase spec claimed that
made the widening hazard tractable: `--where 'note=a or b'` is refused because
`b` alone is not a term, so a user who typed a `--filter` string into `--where`
would be told. That covers only the half where the right-hand fragment fails to
parse. Against `fixtures/16/types/default.sql`:

```
--filter 'v_text=hello and v_char=hi'   → no rows   (equality against the literal)
--where  'v_text=hello and v_char=hi'   → 1 row     (a conjunction)
```

Both exit 0. Two flags do not avoid a hazard by having it between them instead
of inside one, and between them is worse: the user cannot see which reading
they got.

**`--where` is a capability superset and not a spelling superset.** Every
`Predicate` reachable through `--filter` is reachable through `--where` —
quoting is always available, the tokenizer skips a quoted region whole, and
`dequote` round-trips any string by doubling interior quotes, so a keyword
column (`--where '"and" is null'`) and a paren-bearing value both work. What
`--filter` has that `--where` cannot give back is the unquoted spelling:
`--filter 'note=a b'` needs no internal quotes, and one shell array element is
one term. That is why dropping `--filter` was rejected in favour of refusing the
overlap — the refusal buys the same single-meaning property and keeps the cheap
spelling for the audience the two-audience grammar exists for. It is `KD11`, and
slice 11.13 closes it.

The `IS DISTINCT FROM` spelling that slice 11.8 added to `parse_filter` stands.
It reaches both flags because it is in the term grammar rather than in the
expression grammar, which is what keeps one term grammar rather than two, and
`PredicateOp::symbol` the only spelling table. Its one reinterpretation —
`a is distinct from b=c` names the column `a` where it named
`a is distinct from b` — is loud wherever `a` is not a column, and silent only
against a schema carrying both names; the grammar is not distorted for that, and
the reasoning now sits in `architecture.md`, "A filter term is parsed for two
audiences". The spec's operator-surface section obliged a CLI spelling before
the wrap without any slice row naming one, because the row table splits by
mechanism while the operator surface cuts across all four; that hole is the
spec's, not 11.8's, and the section now says which slice carries it.

The refusal is defined by `where_expr`'s tokenizer rather than by a second scan
beside it: a `--filter` term is tokenized and refused unless the result is a
single `Leaf`. A separate scan for the reserved spellings would over-refuse
today — `keyword_at` needs whitespace or a paren before a keyword, so
`--filter 'v_text=not a'` is already one leaf under both flags — and would be
free to drift from the grammar it copies tomorrow. The one string the rule
reaches that was never returning wrong rows is a term with no operator, such as
`--filter 'and is null'`; it is refused anyway, since a string one flag accepts
and the other rejects also cannot be moved between them, and the exception
would cost the property that makes the tokenizer definition worth having.

## The array comparison the spec described is `array_eq`'s, not `array_cmp`'s

P11's spec had a nested array comparing "dimension count, dimensions and
**lower bounds** first, then element-wise", citing `array_eq`'s `memcmp` of
`dims` and `lbs`. That is right about equality and wrong about the *order*:
`array_cmp` walks the elements first, up to the shorter array's length, and
reaches the shape only when those agree — element count, dimension count,
dimensions, lower bounds, in that order. The two agree on equality, and only
`array_cmp` defines an order, so the ordering rule is `array_cmp`'s.

The committed oracle already said so and nobody had read it that way:
`integer[]`'s `{1,2}` is **above** `[0:1]={1,2}` and **below**
`{{1,2},{3,4}}`, and a shape-first order answers the first of those backwards.
Shipping the spec's rule would have passed every hand-written test and failed
the oracle walk the moment arrays stopped being refused.

The fact is now I45, with a probe run against 16.15 and 18.6; the spec's bullet
is corrected in place, per "Spec vs. notes" — the *decision* (compare nested
values structurally) is unchanged and what moved is what the server does.

## 11.10 splits by container kind

The spec's 11.10 row named four container kinds as one increment. Two of them
share nothing but the word "nested": an array and a composite are a structural
walk over parts whose comparisons the register already has, while a range and a
multirange need the subtype's successor function for the three discrete
built-in ranges (`pg_range.dat` gives `rngcanonical` to `int4range`,
`int8range` and `daterange` and `-` to the other three), `daterange_canonical`'s
`DATE_NOT_FINITE` exception, the out-of-order-bounds refusal that is `22000`
rather than a grammar fault, and a multirange's sort-coalesce-drop.

**The seam is by container kind rather than by layer**, and that is the part
worth keeping. The obvious split — land the L2 tree, leave the L4 comparison —
produces dead code, since `resolve_term` refuses a nested column before it
consults the plan. The obvious *other* split — compare all four structurally
and canonicalize later — ships wrong rows: a range column would answer
`[1,10] ≠ [1,11)` where the server calls them one value, under a register that
claims to agree. Each kind shipped is therefore shipped whole.

11.10 landed the array and composite half; 11.10.1 is the earned remainder, and
`roadmap-P11.10-nested-comparison-notes.md` is written for it — it carries what
the canonicalization has to key off (the *range type*, not its subtype) and the
two refusals `tests/nested.rs` holds as exact sets today.

## The register's answer stopped being readable off the variant

`ComparisonPlan` gained a third variant, and a nested plan is **not by itself an
order**: a tree holding an `Uncomparable` position is the register saying the
column has none. Every site that asked `matches!(plan, Compared { .. })` now
asks `ComparisonPlan::orders()`. That is not a compile error anywhere it was
missed, and the failure mode is a column being ordered that `resolve_columns`
has already declined — so `comparison_for` mirrors `resolve_array`'s two
refusals (I22, I26) rather than leaving the disagreement to be masked by the
resolver zeroing the plan.

## The leaf grammar and the refusal's shape are both affirmed

The two calls 11.10 filed under "Decisions worth another look" were reviewed
and stand. Both entries understated their own case, and the corrected facts are
the part worth keeping.

**The leaf grammar.** A nested literal's leaf is read in that type's `*_out`
form and no wider, so `--filter 'p=( 1 , a )'` is refused. The entry justified
this as "a blanket trim over-accepts for `uuid`, `bytea` and an enum label",
which is incomplete in both directions. `network_in` is a fourth non-skipper —
`pg_inet_net_pton` wants a digit at offset 0 — and `macaddr_in`, which the
entry never considered, *does* skip: it is a chain of
`sscanf("%x:%x:…%1s")`, where `%x` eats leading blanks and the `%1s` guard
matches only non-whitespace (`mac.c`). Which input functions skip has to be
read, not guessed.

For two of the four the trim is not lenient but wrong: `byteain`'s escape
format takes a leading blank as a data byte, and an enum label may legitimately
be `' a '`, so trimming compares against a *different value* rather than a
wider spelling of the same one.

The decisive fact is that this is not a nested rule at all. `order_key` is
`str::parse` for a number, so `--filter 'v_integer=" 42 "'` is refused today at
top level — invisible only because the term grammar trims outside quotes —
while `fixtures/<13–18>/oracle/literals.tsv` records the server accepting
`integer ' 42 '` at all six majors. 11.10 made an existing scalar property
visible one level down; it did not introduce one.

And a per-type rule is cheap in code (one predicate over `CompareKind`) and
expensive in evidence, which is what stops it: the register-to-oracle test puts
every value through the server's `*_out` form by construction, so no oracle
cell can check an input-grammar arm.

**11.10.1 inherits this settled rather than open.** A range bound reads the
same way, so `[ 1 , 10 )` is refused, and 11.9's `CANONICALIZED` entry for
`("public.point2d", "( 1 , a )")` stays declined.

**The refusal's shape.** An ordering refusal on a nested column names the
position and its type in `UnorderedPredicateColumn::reason`, a `String`. The
entry justified this by the cost of putting a payload on
`ComparisonPlan::Refused`, and priced two consequences that do not exist: the
plan *is* the structured channel. `ComparisonPlan` and `NestedCompare` are
public, `ResolvedSchema::comparisons` is public, and
`NestedCompare::uncomparable()` answers `(path, declared type)` — so an
embedder never parses a sentence, and `pgdq info --verbose` already reads that
same plan for an enum's labels. The one real gap is that `uncomparable()`
answers the *first* uncomparable position and nothing public enumerates the
rest; that is left unbuilt deliberately, having no consumer.

## A user range's `canonical` parameter: the review of `KD12`

11.10.1 reproduces PostgreSQL's canonicalization for the three discrete
built-in range types, keyed off the range type's *name*. A user-defined range
declares its own canonical function in DDL `pg_dump` writes and
`TypeKind::Range` does not keep, so a column of such a type is compared as
though the function did not exist. That was filed as `KD12` and as a decision
worth another look; the maintainer's review settled it and the entry is closed.

**The decision: capture the parameter and refuse the column** — but the
refusal has to be a stronger one than the register can currently express.

### What the review established

Six facts, four of which the filing session did not have.

**`pg_dump` writes the parameter.** `pg_dump.c:10866` appends
`,\n    canonical = %s` whenever `rngcanonical` is set. Confirmed against a
real 16.15 dump.

**The grammar already parses it.** `parse_create_type`'s `AS RANGE` arm
(`preamble.rs`) splits every `key = value` in the body and keeps `subtype` and
`multirange_type_name`, discarding the rest — `canonical` included. Capturing
it is one `else if` and one field, not the grammar change the filing described.

**The cache bump is free.** `cache.rs`'s `FORMAT_VERSION` doc states it: pre-1.0
a bump is one character and nothing migrates. It was cited as a cost and is not
one.

**The blast radius is the literal, never two stored values.** `range_key`'s own
comment says canonicalization is idempotent on a `range_out` field because the
server already applied it — the file side is canonical by construction. There
is no `--order-by`, and `ResolvedSchema::comparisons` is consumed only by the
predicate path. So `KD12` can only produce a wrong answer through a
user-supplied `--filter`/`--where` literal.

**The shell type does not save it.** `pg_dump` emits `CREATE TYPE x;` ahead of a
range whose canonical function it dumps (`pg_dump.c:5619`), so the dump names
the type twice. `record_type`'s I11 rule makes a shell lose deliberately, and a
dump built for this review resolves the column as `Range<Int32>` — the wrong
comparison is reached, exactly as filed.

**Such a type is rare, and rarity argues *for* refusing.** A canonical function
must be declared against the shell type, and a SQL function cannot take one
(`ERROR: SQL function cannot accept shell type`) — the review's fixture needed
`LANGUAGE internal`. So it takes a C or internal-language function, in practice
an extension or a hand-loaded module. That makes the refusal nearly free: almost
nobody loses a working filter, and the one person who has such a column stops
getting wrong rows.

### Why the filed remedy would not have closed it

`ComparisonPlan::Refused` on a *mapped* column refuses the four ordering
operators and lets `=`/`!=` fall through to `Comparison::Canonical` — bytewise
text — with no divergence announced, since that arm reports one only for
`UnknownType` and `OpaqueBaseType`. So under the remedy the entry proposed,
`--where "r = '[1,10]'"` against a stored `[1,11)` is still false and still
silent: the ordering half is fixed and the half the entry's own example is made
of is not.

**The register has no outcome meaning "refuse every operator, equality
included."** That is what closing `KD12` actually needs, and it is why the
closure is admitted work rather than a two-line edit.

### The adjacent hole, which is not the same defect

The same fall-through catches any nested column with an uncomparable position:
a `json[]` refused ordering and then answered `=` bytewise, saying nothing.
11.15 closed that; it is recorded here because the two defects share one code
site and the review had to separate them.

It was **not** a wrong answer the way `KD12` is. `array_cmp` raises for a
`json` element, so the server has no `=` to disagree with — bytewise offers more
than the server does, which is the same posture top-level `json` already takes
deliberately. The defect was that top-level `json` **announces** it
(`ComparisonDivergence::AsText`) and the nested case did not. So the two share
one code site — the `_ =>` arm's divergence list — and wanted different
remedies: `KD12` a refusal, the nested case an announcement.

### What was decided

**Capture the parameter and refuse the column, in P11, before the wrap.** The
out-of-band rule admits an item only where it changes no decision a spec
records; adding an outcome to the comparison register is a decision
`roadmap-P11-typed-predicates.md` records, so this is a slice. P11's row is
still `Current`, and the phase exists to close wrong-rows-in-silence — wrapping
it around a known instance of exactly that is what the review rejected.

**Two slices, split by review confidence.** `11.14` is additive and disturbs
nothing that works today: capture `canonical`, add the register outcome, bump
the cache format, refuse. `11.15` changes an already-tested path — every nested
column's `=` reports no divergence today, and the oracle asserts it. Bundling
them would force one review to accept both at one confidence.

**The outcome is a fourth `ComparisonPlan` variant**, not a reason field on
`Refused`. `Refused` means "no ordering, equality as text" at every site that
returns it — the empty enum, `Base`/`Shell`, an undeclared column — and that
fallback is correct there, announced as `UnmodelledType` where the type is
opaque. A fourth variant leaves those alone and makes `resolve_term`'s match
force each site to choose, which is the property that surfaced this gap.

**`11.15` announces rather than refuses.** `ComparisonDivergence::AsText`
already means "the server defines no comparison here" and already reports on
equality (`affects_equality` is `true` for it), which is how top-level `json`
is handled. The nested case differs only in being silent, so the remedy is to
reach the same divergence from the `_ =>` arm, naming the position the way the
ordering refusal already does.

## Three phases on the roadmap: compressed input, remote input, the rest of the codecs

`P13` (compressed input, xz), `P14` (remote input) and `P15` (gzip and zstd)
are allocated and sketched. The decisions live in
[`../../design/roadmap.md`](../../design/roadmap.md); the evidence behind them
is here and in
[`../../design/roadmap-P13-compressed-input-inbox.md`](../../design/roadmap-P13-compressed-input-inbox.md),
which holds the probes themselves.

**The trait was already the right shape; the cost model was not.** The question
that opened this was how much of it `object_store` covers. Remote reading:
nearly all of it — `read_range`/`size` were shaped against `get_range`/`head`
deliberately, and with a complete cache a query already reads only the cache,
the source identity, and the target block's byte range, which is the minimal
ranged-GET pattern without anything being added. Compressed reading: none of
it. `object_store` is a byte store; DataFusion's compression lives a layer up
in `file_compression_type.rs` and is a forward-only `Stream`/`Read` adapter,
so adopting it buys `pgdq parse` and gives up `pgdq query`. What makes
compression a phase is that a decompressing `ByteRangeSource` satisfies the
trait and breaks the unstated assumption behind it — that a read at an
arbitrary offset costs what a read at the next offset costs. Exactly two
callers read backwards (replay, and `attach_text`), `size()` is taken before
every scan, and a seek table has to be persisted somewhere the cache format
does not currently allow. That last one is why this is a phase rather than an
out-of-band item.

**Compressed input is plausibly a performance feature, not a convenience.** The
koji sample's own `.xz` is 40.4 GB against 730.2 GiB uncompressed and — the
part that was assumed wrong — **31,150 self-contained streams**, so it is
randomly accessible at ~24 MiB granularity with no index of ours. One core
decodes it at ~446 MB/s of plaintext against the published ~240 MB/s HDD scan
of the plain file, four concurrent per-stream decodes reach ~1.48 GB/s, and
`xz`'s own `-T8` gains nothing on it because its threaded decoder parallelises
blocks *within* a stream. So the compressed path reads 19× fewer bytes and can
decode them faster than the disk delivers the plain ones. That reframes the
schedule: `P13` goes ahead of `P7`, because a source shape that is CPU-bound at
~450 MB/s a core rather than device-bound at ~240 changes what `P7` is setting
its readahead and parallelism defaults against. Parallel decode itself is
`P7`'s — it is that phase's "Parallelism" section with the hard half,
discovery, already solved by the stream index — and is filed in its inbox.

The probes are probes: no harness, no `drop_caches`, no `measure.py`
registration, so nothing may quote them as figures.

**`P14` is carved out of `P6` and placed ahead of it.** An `object_store`
byte source is an L1 addition, not a surface `P6` presents, and it is the only
part of that phase with a user-facing CLI feature attached. It sits ahead of
`P6` for the reason `P6`'s own scheduling note gives: a `TableProvider` commits
to the I/O layer beneath it, and built while that layer is in motion it is
built twice. Backburnered relative to `P13` and `P7`, which is the maintainer's
call.

**The compatibility matrix was wrong about `-Z` on plain format.** It read
`N/A for plain`, on the grounds that compression applies only to the archive
formats. `pg_dump`'s documentation says the opposite — for plain text output a
nonzero compression level compresses the entire output file, as gzip, lz4 or
zstd (`doc/src/sgml/ref/pg_dump.sgml`, the `--compress` entry, 18.6; gzip long
predates the method selector, lz4 and zstd arrive with PG 16). So
`pg_dump -Fp -Z9` output is ordinary plain-format output this build cannot
read, which is what gives `P15` a compatibility gap to close rather than a
convenience to add, and what puts it ahead of `P8` — whose Track B needs the
same two decoders per archive entry.

## The loop can run a phase without the maintainer (`M43`)

`/gosub` stops the moment a round files an entry under "Decisions worth another
look", and `/dwal` spends the maintainer's presence closing it. That cycle has
been the project's most productive mechanism and it is bounded by one person's
availability. `/gosolo` removes the bound: it runs `gosub` unchanged, and where
`gosub` would stop for review, invokes `/gm` to settle the frontier and
resumes.

**What the maintainer was actually contributing had to be separated from what
they were being asked for.** The observation that opened this is that the
answers had become agreement — most `/dwal` sessions end with every
recommendation accepted. The value was still real, and the reasoning is worth
keeping because it decides the design: it comes from *writing the entries down
under the expectation of review*, and from a **cold** session grilling them,
neither of which needs a person. What does need one is the rare veto, and its
cost is not its rate — it is that deferring it grows superlinearly, since each
further slice cements the call into docs, code and an eventual keystone.

So the design trades **timeliness** of review for **auditability** of it, which
is acceptable here only because the blast radius is bounded: pre-1.0, no
compatibility guarantees, and docs rewritten freely, so a reversed call costs
wasted work rather than a shipped mistake.

**The stand-in adjudicates rather than agrees, and that is the whole design.**
An agent that says yes is the weakest possible substitute and would make the
grilling self-approving — `/dwal`'s round format is calibrated to a reader with
a veto. The better substitute costs the same, because the reason the maintainer
agrees is that the recommendation is usually **derivable from the written
record**: a standing rule, a rejected-alternative paragraph, an invariant,
`process.md`, or an earlier slice's precedent. That is checkable. `/gm`
therefore returns one of four verdicts per question — `record` with a citation,
`judgement` where the record is silent, `misfiled` where the entry was not a
decision at all, and `escalate`, which stops the loop.

That buys a self-measuring loop, which is the part that matters most: the
verdict counts say whether the premise this design rests on still holds. A
phase answered almost entirely on `record` ran on precedent; a rising share of
`judgement` means the loop has started improvising, and `misfiled` rising means
it has started manufacturing entries because entries are what it rewards. The
maintainer reads those counts instead of trusting the assumption that their
input rate stays low.

**The escalation line is not how far the process moves — it is whose future the
call binds.** Re-slicing, admitting out-of-band rows, and striking or rewriting
a `KD<k>` inside the open phase are all discovery doing its job, and were
rejected as stop conditions: `/go` already licenses a split unattended, and
`deficiencies.py` mechanically catches a register entry that goes missing, so
guarding either a second time with a person buys nothing. `gosub` stops on a
split for a different reason — a re-plan may invalidate the next slice — and
that reason is *consumed* by `/gosolo`, where a grilling round follows and
reviews exactly that. What escalates is a standing rule, an invariant, a
`KD<k>` re-targeted onto a phase nobody has grilled, or a spec rationale
reversed; inside the phase, work sits under a spec the maintainer approved and
will read at its keystone, and outside it there is no such approval.

Amending the open phase's spec was considered as a fifth escalation and
rejected as a separate rule: an amendment filling a gap the spec never
addressed is discovery, and one reversing a rationale the spec argued for is by
construction a case the record does not settle — so the existing escalation
criterion already catches it, and a rule would only be a second copy.

**The transcript is verbatim and lives outside the repo**, at
`/mnt/ssd/fedora/scratch/pgdump_query/grilling/P<N>.md` (`CLAUDE.local.md`).
Verbatim because the context a grilling round establishes before its questions
is the most-read part of the exchange and the first thing a summary would take.
Outside the repo because a record of how a session unfolded is precisely what
the writing-style rule, the history rules and the keystone exist to keep out —
those rules are right whenever the maintainer was present, and keeping the file
out of the tree means the exception costs no carve-out and weakens nothing.

It is safe to lose, which is why ungitted and machine-local is acceptable:
every closure still files its reasoning beside its mechanism before the entry
is deleted, so the transcript carries only the account of who settled it. That
is also a review criterion — **a rationale that exists only in a transcript is
an incomplete closure.**

**The ledger became a work queue, which is a change `/gosub` wanted anyway.**
Grilling a decision routinely turns up a defect or clarification that changes no
decision, so it lands out-of-band — and it can still be in the way of the
phase's remaining slices. `/go` read only the STATUS checklist, so those rows
were invisible to it. The row now carries a `Blocks` column set by the admitting
session, because that session has just grilled the thing and a session picking
the row up later has only the description. `/go` takes a blocking row ahead of
the next unticked slice and re-tests the admission rule before building it: an
item that turns out to change a decision was misfiled, and that is a stop rather
than a slice invented on the spot.

**Every agent in the stack is disposable, including the stand-in.** A long
grilling degrades as it lengthens — shallower questions, the record read less
carefully — and that is precisely the judgement `/gm` exists to supply. A
supervising layer above it was rejected: it would only move the accumulation up
one level. What bounds context here is the rule the rest of the project already
runs on, that **state lives in files and agents are cold-started**, and `/gm`
was the one place it had not been applied.

That makes the grillmaster something `/gosolo` **dispatches** rather than
invokes. Invoking `gm` as a skill would make `/gosolo` the grillmaster and land
every round of every grilling in the one context that has to survive the whole
phase, which is the accumulation the rotation exists to bound; dispatching
spends an agent per grilling exactly as `gosub` spends one per implementation
round.

`/gm` retires itself and its griller together at a round boundary — the
first of twelve questions or five rounds, earlier where a segment took heavy
reading, never mid-entry, since `dwal`'s step 4 owes a closure for every entry
grilled. It returns saying the frontier is not empty; `/gosolo` starts a fresh
`/gm`, which starts a fresh `/dwal`, and both contexts reset in one move.
Rotating only the griller was rejected as fixing the half that matters less.

**The repo is the hand-over, not the transcript.** A fresh pair reads the
frontier — shorter, because a closed entry is a deleted one — and the docs the
closures have already updated, and is given nothing from the previous segment.
Feeding the transcript forward would undo the rotation. What it re-derives is
the griller's design tree, which is the price and is partly a benefit: step 2's
cold re-reading of the mechanism is where an entry that has gone stale gets
caught. The same rule is written into `dwal` unconditionally, because it is the
practice an attended session was already following by hand.

**One rule had to have its scope stated, because rotation collides with it.**
`/dwal` commits nothing while the frontier is non-empty, so a rotation hands
over written, uncommitted closures; `gosub`'s baseline reads a dirty tree as a
round that did not finish. Both stand — `gosub`'s check is about an
*implementation* round — and `/gosolo` keeps them apart by never dispatching one
while a grilling is unfinished.

`/gosolo` is disposable on the same terms, by a file rather than by an agent
above it: a resume log beside the transcripts, one line per round, carrying the
work, the commit, the transcript segments and the verdict counts. Everything
else it would need to continue mid-phase is already committed; the narrative
for the final report was the only thing it was carrying that was not.

**`/gosub` is unchanged as a loop and stays the tool for work worth staying
close to.** Both loops run the same rounds, the same independent verification
and the same commits; `/gosolo` overrides two of its stop conditions and nothing
else, and the overrides are stated in `gosolo` alone so there is one copy of the
round mechanics.

## P13 is grilled, partly specified, and blocked on a crate that does not exist

`pgdq --source koji.dump.xz` needs a positioned read over an `.xz` file —
give it an uncompressed offset, get the bytes, without decoding from zero.
**No crate on crates.io does that**, and the survey establishing it is in
[`../../design/roadmap-P13-compressed-input.md`](../../design/roadmap-P13-compressed-input.md),
"Blocked". The near misses are instructive: `lzma-rust2` has every container
primitive — `Index`, `BlockHeader::parse`, `StreamFooter`, multi-stream block
scanning, a parallel block decoder — all of them private, and implements `Seek`
nowhere; `liblzma`'s safe API exposes neither an index parser nor a block
decoder, only raw FFI; `gibblox-xz` has the right shape but is GPL-3, pre-alpha,
and caps an uncompressed block at 64 MiB, which the koji corpus exceeds.

So the addressing layer is being carved out into its own crate and repository,
on the collation spike's pattern: requirements written from here, kept there, at
`/mnt/wd12t/fedora/experiments/xz-seek/docs/design/historical/initial.md`
(`CLAUDE.local.md`). Nothing in this repo builds against it, and P13's roadmap
row says `blocked` until it can answer a positioned read.

**D1–D6 in the spec stand.** They are decisions about `pgdump_query` — what
`size()` promises, which shapes are read, the trait becoming dyn-compatible,
`stored_size()`, where the seek table lives, the decoder's read policy — and
none of them depends on who supplies the decoder. What is *not* settled is
everything downstream of the crate: how a source is recognised as xz and where
it is constructed, the diagnostic that announces a non-seekable file, the
fixture family, the figures owed, and the slice list. Those get their own
grilling when the phase unblocks.

**The evidence that changed the shape of the phase.** `xz` 5.6+ defaults to
`-T0`, so its default output is one stream of many blocks — seekable for a
single footer read — and the non-seekable one-stream-one-block file now takes a
deliberate `-T1`. That inverts the sketch's assumption that non-seekable was the
common case. Meanwhile the file that actually has to be read, the upstream koji
download, is 31,150 concatenated streams, whose footer walk is 85 s of HDD
seeks — which is what makes the seek table a persisted artifact rather than
something re-derived per run.

**The koji `.xz` corpus was renamed** as a result: the upstream download is
`koji-2026-07-23.dump.multistream.xz`, and a locally recompressed
`xz -T15 --block-size=128MiB` copy becomes `koji-2026-07-23.dump.multiblock.xz`.
Both live in `/mnt/wd12t/fedora/koji/`.

## The ADBC floor is a release, not a branch

P12's grilling opened by discharging the contingency its inbox flagged as
deciding the whole shape: `adbc_driver_postgresql` installs cleanly under `uv`
here, and answers a live schema query. It does, at 1.12.0 — so the apparatus the
phase wants is available. What the same probe showed is that **the driver the
inbox surveyed and the driver a user can install are two different floors.**

The survey read upstream main at `be5f50f08` (2026-08-30). The current release is
`apache-arrow-adbc-24`, tagged 2026-07-24 and published as Python
`adbc_driver_postgresql` 1.12.0. Three commits sit in the gap, and two of them
carry the metadata behaviour the phase's largest obligation rested on:
`6e0d7a135` maps `uuid` to `FixedSizeBinary(16)` + `arrow.uuid`, and `223664fee`
writes `POSTGRESQL:type` on every non-root field. Neither is released.
`64f555f56`, which returns `json`/`jsonb` as `arrow.json`, is.

Taken against the release by querying one column per type through the driver
(the koji replica, PG 16): `uuid` comes back
`arrow.opaque[storage_type=binary, type_name=uuid]`, and **no modeled field
carries any metadata at all** — `integer`, `text`, `date` and the rest have an
empty metadata map. The only key present anywhere is the deprecated
`ADBC:postgresql:typname`, on the opaque fields alone.

So the inbox's "every column we emit is below the floor on that key" is true of
main and false of every shipped driver. The phase takes the **release** as its
floor (D1), which makes the metadata obligation shrink to nothing: against
release 24 we already meet or beat it everywhere, stamping `arrow.uuid` on a
real `FixedSizeBinary(16)` where the release hands back opaque bytes.

**One row changed kind rather than value.** `numeric` is `string` at both
revisions — but tagged `arrow.opaque`, at both. Under the phase's own scoping
rule, which defines the floor only where ADBC yields a non-opaque type, that
makes `numeric` not a floor row at all rather than a row we beat. The four-row
delta the survey found (`regproc`, `money`, `interval`, `int2vector`) is
otherwise confirmed against the release exactly as recorded.

## The floor sweep's array exclusion

P12's D7 spelled the ADBC floor sweep's array exclusion as a shape test,
`typelem <> 0 AND typlen = -1`. It is the back-reference `NOT EXISTS (SELECT 1
FROM pg_type e WHERE e.typarray = t.oid)`, which is what `scripts/adbc_floor.py`
implements and what the committed `fixtures/<13–18>/adbc/floor.tsv` were taken
under.

**The two predicates' symmetric difference was measured**, against the koji
replica at PG 16, over the sweep's own row set (`pg_catalog`, `typisdefined`,
`typtype IN ('b','e','r','m','d')`). It is exactly `int2vector` and
`oidvector`: both varlena with a non-zero `typelem`, neither named as any
type's `typarray`, and both declarable — `CREATE TABLE t (a oidvector, b
int2vector)` succeeds. Every array type proper is varlena, so the
back-reference set is a strict subset of the shape set and that pair is the
whole difference. `pg_catalog` carries no domains at all, so `typtype = 'd'`
contributes to neither side.

That makes the shape test inconsistent with the spec rather than merely
awkward: D5 commits the phase to closing `int2vector` as a floor row, and D6's
reconciliation fails in both directions — so under the shape test 12.6's new
arm would be a mapped arm with no floor row, needing an exemption in the very
check D5's closure is meant to satisfy. Where a spec contradicts itself the
clause carrying the reasoning wins, and D7's parenthetical was a spelling with
no argument behind it while D5 is a full paragraph with its own *Rejected:*
note. D7's reason sentence survives the amendment intact.

**A third predicate was measured and rejected.** D7's stated reason — our
resolution reaches array types by recursing from the element type — names a
*spelling* test, since that recursion strips a trailing `[]`, a bound or the
`ARRAY` keyword off the declared name (I28) and never consults a catalog. So
`format_type(oid, NULL) LIKE '%[]'` is what the reason literally says, and over
this row set it is coextensive with the back-reference:
`EXISTS(typarray back-reference) <> (format_type(oid, NULL) LIKE '%[]')`
returns zero rows at PG 16. It buys no behaviour change, and both the committed
TSVs and `architecture.md`'s filed paragraph are already correct under the
back-reference and would not be under it.

**No invariant was added.** `CLAUDE.md`'s trigger is a *decision* depending on
external behaviour, and the dependant here is fixture apparatus rather than
library code; and D7 already elected the committed sweep as this fact's
evidence — "the sweep proposes and the reviewed file disposes, so a
regeneration diff *is* the 'a new major added a type' signal" — which
re-verifies on every regeneration instead of on a walk-the-file ritual. If a
later slice makes library code depend on the array-spelling equivalence, that
is when it earns an `I<n>`.

**`oidvector` costs 12.2 nothing.** D2's rule holds only where ADBC yields a
non-opaque type, and `extension` is a committed column, so the opaque tail —
`oidvector` with it — is placed by the file's own columns rather than by a
per-type line. D2 already writes that bullet collectively ("the geometric
family", "every range and multirange") and its *Rejected:* paragraph turns down
enumeration outright. The two `E42883` refusals are a second column-placed
class. What stays a hand-written exemption is only what the columns cannot say:
`money`, the `reg*` family, and D10's two waiting rows.

## A falsified manual claim is corrected by the change that falsifies it

The review of the "Decisions worth another look" entry asking whether 12.3 was
entitled to correct `docs/manual/type-handling.md` a slice early. Both the
entry and 12.3's notes framed it as a session overrunning its slice row; the
premise is false, and the ruling is filed in
[`../../process.md`](../../process.md) beside the manual's existing re-read
rule.

**The spec said both things.** D9 closes with "prose asserting that `interval`
or `int2vector` comes back as a string goes false when D4 and D5 land, and
correcting it is an obligation of *those slices*", which assigns the correction
to the landing slice. D11's table assigns it to 12.4. Neither the 12.3 notes
nor the STATUS entry cites D9 — both reasoned against D11 alone — so what
looked like a session departing from the spec was a session obeying the clause
that states the decision rather than the one that schedules it. D4 spans 12.3
and 12.4, so "those slices" is loose; the sentence's own mechanism settles it,
since the correction is tied to the claim *going false* and that is the
resolution arm, in 12.3. Even on the loosest reading D9 permits 12.3 where D11
alone forbids it, so the contradiction is real either way and D9 is the clause
carrying an argument.

**The rule, and the asymmetry that decides it.** A slice boundary orders
review; it is not licence to publish a sentence known to be false. The two
errors are not comparable: a doc corrected one slice early costs a slightly
larger diff in a slice whose review is about a decoder, while a doc corrected
one slice late publishes something known false in the one document written for
a reader who cannot check it against the source. That last clause is why the
rule binds the manual absolutely and the rest of the doc set only as ordinary
discipline — every other document's reader can see the code.
`process.md`'s existing sentence already pointed this way independently: "a
change to what a command prints re-reads the manual for its **claims**" makes
the re-read an obligation of the change, and 12.3 changed what `pgdq info
--verbose` prints for an `interval` column.

**D11's row yielded, narrowly.** The four words "and `type-handling.md`
corrected" are struck from 12.4's row and from its STATUS checklist line, with
one paragraph under D11 recording that D9 owns it. That is a decision edit, not
progress-tracking: the row is not rewritten to describe what 12.3 did, and the
phase's commitment — correct the manual within P12 — is unchanged under either
reading. Leaving it would have made 12.4's row undeliverable as written, so
whoever landed 12.4 would have had to re-litigate this or tick a box against an
earlier commit's work. D11's "Two splits are deliberate" paragraph argues the
*code* split and says nothing about the manual, so nothing recorded is
reversed.

**No check, and the obvious one was costed.** A mechanical check would
reconcile the Arrow type names the manual states in prose against the register
`floor_mapping.py` already parses out of `pgtype.rs`. Against the worked
instance it fails: 12.3 falsified five sentences and exactly one of them names
an Arrow type. The other four said *comes back as a string*, *arrives as the
text the dump holds*, listed `interval` among the types `info --verbose` says
nothing about, and counted how many string-shaped types there were. A claim
about a type is usually spelled in words, not in the type's name, so the check
would have caught one fifth of the only instance the rule has and none of the
sentences a user meets first. No ledger row was admitted: a queued row enters
the unattended loop's work queue, and this one would have queued a check that
does not catch the defect motivating it. The rule is discipline, `process.md`
says so, and it records what a second attempt would have to key on.

**`int2vector` inherits nothing from this.** D9's other half is vacuous —
neither `int2vector` nor `oidvector` appears anywhere under `docs/manual/` — so
12.5 and 12.6 carry no manual obligation and P12 has exactly one instance of
the contradiction, already resolved by the code.

## An arm's oracle case belongs to the slice that writes the arm

The review of the "Decisions worth another look" entry asking whether
`int2vector`'s comparison-oracle case is evidence — and so 12.5's — or
mechanism, and so 12.6's, where it was left. The call stands, and it stands on
a ground the entry did not cite.

**The record already answers it.**
[`../../design/architecture.md`](../../design/architecture.md), "The
register-to-oracle reconciliation", draws the consequence of the join being
existence rather than branch coverage: *an arm's cases are owed by whoever
writes the arm, and "the reconciliation passes" is not the question to ask of a
new row.* That assigns the case to 12.6 directly. The precedent supplies the
schedule: P11's three type-closing slices — 11.5 (`4082d53`), 11.6 (`2bea261`)
and 11.6.1 (`7430325`) — each touch `pgtype.rs` and
`scripts/comparison_oracle.py` in one commit, and the reading that would move
this case a slice earlier makes all three mis-sliced in retrospect, which is a
large claim to make in order to move one case. `interval` never posed the
question at all: its case landed with the oracle itself at 11.1 (`b315aba`), a
phase before its arm, so for `interval` "evidence first" and "cases owed by the
arm's author" never came apart. `int2vector` is the first type where they do.

**The entry's first ground is defective and is retired.** It argued that a
comparison oracle is generated by a PostgreSQL server and so cannot be tainted
by the arm it checks. That is true of the oracle's *answers* and false of its
*cases*: which literals get asked is a choice the slice makes, and a case
chosen after the codec exists can be chosen to agree with a wrong codec. The
seam rule in [`../../process.md`](../../process.md) says the evidence half must
land first "so that the mechanism is checked against something it did not
produce", and the server producing the answers satisfies that on its own terms
— but only for the answers.

**So the residue is the case's content, and it is filed as a requirement on
12.6.** `architecture.md` already refuses a mechanical branch-coverage check
over a `match` written in another language, and the same refusal covers a check
that a case discriminates. 12.5's notes therefore carry the property 12.6's
case must have — a pair on which element-wise and lexical order disagree, with
`'2'` against `'10'` as an example rather than as the requirement — because a
plan that fell back to text agrees with the server on most `int2vector` pairs
and a case built only of those passes while the plan is wrong. 12.5 had already
found that pair by hand; what it had not done was state it as something 12.6 is
held to.

**The entry's second ground survives as an observation.**
`predicate.rs`'s `the_register_answers_every_committed_oracle_cell` asserts the
set of declared types the register refuses an ordering operator on as an exact
set (`REFUSED`, six entries), so a case landed before the arm forces a seventh
entry that 12.6 removes again. True, and checked — but it is a churn argument,
not the reason the case is 12.6's. Nor is cost: `architecture.md` prices the
late re-take at `generate_fixtures.py --skip-dumps`, which rewrites the
`oracle/` TSVs and touches no `.sql` file, so the ordering was a free choice
rather than a trade. That is the asymmetry `11.6` relied on when it labelled
`character(10)`'s collation cases a slice early — "labelling later costs a
six-major run of its own" — and it does not hold here.

**D11's 12.6 row gained one clause**, naming the oracle case alongside the
codec and the resolution arm, with the STATUS checklist line following it. No
decision changed — the record already assigned the case to 12.6 — so the spec
got the clause and no explanatory prose, and the reasoning is here and in 12.5's
notes. No ledger row was admitted: everything the answer implied landed in the
closure itself.

## The sibling project's two loop rules come back (`M44`)

`schemadetection` bootstrapped from an early copy of this process and has been
running it since; importing this repo's `/dwal`, `/gm` and `/gosolo` into it
surfaced two rules it had grown that this repo lacks, and one that does not
travel.

**A handback reads out the whole "Decisions worth another look" section, not
just what the loop added.** The closing rule fires when the maintainer *answers*
an entry, so an entry nobody surfaces is never answered and never closed, and
`STATUS.md` cannot tell it apart from one that was read and kept. The handback
is the only moment that reliably fires, so it is where the section gets read
out. `gosub`'s final report carries it.

**A review does not re-arm the loop.** When `/gosub` stopped on an entry and the
maintainer then reviews it, the loop is over: a review is a re-plan — it
reverses deferrals, admits ledger rows and adds slices — so the next unticked
box is no longer necessarily the next piece of work, and a blocking row may now
sit ahead of it. `/gosolo` is the exception by construction, since its Override
1 resumes at a fresh baseline precisely because it knows the plan may have
moved.

**And `grilling` gained two of that project's rules.** A fact-finding
exploration is dispatched to a sub-agent and *not* blocked on — a running
exploration is an unsettled prerequisite, so only the questions downstream of it
wait — and every specific the user hands over, not only the answers to numbered
questions, is written into the docs in that same turn. This repo keeps its three
questions per round rather than that project's one; the questions here are
denser.

**One rule deliberately did not travel, in the other direction.** This repo's
"the process governs iteration on the product, not on itself" exempts
`process.md` from earning a ledger row. `schemadetection` files those rows and
has four standing (`M1`–`M3`, `M7`), so importing the exemption would have
invalidated them — a decision change rather than an import, and not something to
land out-of-band in someone else's repo.
