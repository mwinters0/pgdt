## The ICU `collversion` is guarded (`M42`)

`fixtures/<13-18>/types/binary-upgrade.sql` carries `CREATE COLLATION
public.nd_collation (…, version = '153.128');` — the tree's only ICU release
number, and the one committed fixture byte that moves with a base-image pin
while nothing demanded anything of it. The prose that said so lived in a doc
comment on `tests/preamble.rs`'s
`the_types_schema_declares_one_deterministic_and_one_non_deterministic_collation`,
which asserted which flag set carries the version and could not be wrong
loudly. That is the shape `M41` had just repaired one file over, in
`oracle_register.py`'s exemption, where a free-text claim about bytes went
false in two places on its first use.

`the_icu_collversion_reaches_binary_upgrade_alone_and_agrees_across_majors`
replaces the claim with the check it describes. It reads the fixture text
rather than `DatabaseMetadata`, because the parser drops the field on purpose:
`CollationDef` keeps a name and a determinism answer, nothing resolving a
collation's order from a version this build does not implement.

**The assertion is agreement, never the literal**, which is what
`oracle_differences.py` already demands of `meta.tsv`'s
`default_collversion`. All six majors read one version because all six pins are
`-trixie` and resolve to one libicu; the documented drift is *across* base
images (`und-x-icu` is `153.128` on `13.23-alpine` against `153.136` on
`18.6-alpine`), so a split between majors means the pins have drifted apart —
the exact fault an across-majors identity check exists to report. Naming
`153.128` was rejected: it fires on every routine image bump, which is a
deliberate regeneration whose diff already shows the change, and a check that
fires on the expected event is a signal that is always on. Verified in both
directions — the test passes as committed, and rewriting one major's fixture to
`153.136` fails it by name.

The shape claim is the guard's other half and is asserted exactly as it was
written: the option is present under `--binary-upgrade`, absent from `default`,
absent from `data-only` (which emits no `CREATE COLLATION` at all), and absent
from `public.c_collation` under every flag set, a `C` libc collation having no
`collversion` to record.

**Where the guard is written down.** `architecture.md`'s "Fixtures" section
holds the mechanism and its two rejected alternatives; I42's Observed paragraph
names the test, and its `Re-verify` block runs it; `pg-dump-compatibility.md`'s
`CREATE COLLATION` row, `fixture_schema_types.sql`'s `nd_collation` comment and
11.12's slice notes cite it in place of the literal. I42's citation of the
determinism test resolves again — it had named
`the_types_schema_declares_a_deterministic_and_a_non_deterministic_collation_at_every_major`,
a function that has never existed.
